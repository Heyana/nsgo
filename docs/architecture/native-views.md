# Hosted views

`WebView`, `Video` and `Native` host a platform view inside a view: the platform's web view and player, or one the app registered. Each follows NSH's design and behavior on every target; NSGo changes only the API's shape to Go's. Read this before changing these elements or a backend's host for them.

## Shared design

- The control fills a `KindWeb`, `KindVideo` or `KindNative` view, which keeps the decoration, frame and accessibility.
- One config item carries the whole state: `ItemWeb` with `WebConfig`, `ItemVideo` with `VideoConfig`; `ItemNative` carries a component's changed props.
- Commands ride their own items: `ItemWebCommand` for `Ref`'s history, scripts and messages, `ItemVideoSeek` for `Ref.Seek`, `ItemNativeCommand` for `Ref.Command`.
- Core resolves defaults before sending, so platforms see final values: a video's volume, rate, progress interval and resize mode (Contain).
- Platforms report an event only when the view's `EventMask` has it.
- NSGo keeps Go's zero values as defaults: `NoScroll` and `NoJavaScript` invert NSH's `scrollable` and `javaScriptEnabled`, and `window.nsgo` replaces `window.nsh`.
- A restricted web view's top-level navigations are decided on the native backends by `driver.WebConfig`, from `WebHosts`, `AccessWebSchemes` and the schemes the app serves (`core/access.go`): `Navigable` for the page's own and `SourceNavigable` for the app's loads and history commands (see below). Apple, Windows and Android refuse them as they start (Android's `WebNode.navigable` mirrors `Navigable`); Linux refuses them before they commit, a page-made `data:` or `blob:` page at its main-frame response, but an `about:` page as it commits (see below). The web's iframe hides its page's navigations, so nothing holds them there.

On macOS and iOS, a rounded `Overflow: Hidden` with an outer shadow or outline clips hosted native content in a separate holder, keeping the decoration visible. Adding it preserves the loaded web page and player; input focus and selection stay with the editor. Images and scroll views have the remaining limits described in [styles](styles.md#drawing).

## Web views

tvOS reports `Env.HasWebView` false and answers each configuration with a `WebError` for its source URL, without loading WebKit. The simulator may expose private WebKit classes; their presence does not make the public API available. Commands on the uncreated native view are no-ops.

On Linux, initialization checks whether the system bubblewrap can start WebKitGTK's sandbox under AppArmor's user namespace restriction. A failed probe uses the same placeholder as a missing WebKitGTK library, and cookie requests return the diagnostic. The check runs once, on the first use of WebKitGTK.

- `WebView.UserAgentSuffix` appends a token after `UserAgent` or the engine's own user agent. macOS and iOS use `WKWebViewConfiguration.applicationNameForUserAgent` at creation for the default agent and `customUserAgent` for an override. Windows and Linux append to the WebView2 or WebKitGTK agent, and Android uses `WebSettings.getDefaultUserAgent` when the app supplies no override. These hosts send the result in HTTP requests and expose it as `navigator.userAgent`. HarmonyOS, the web and mini programs keep their host's user agent.
- `WebView.Muted` and `MutedFunc` apply to the hosted view across navigations. Windows calls `ICoreWebView2_8::put_IsMuted` and Linux calls `webkit_web_view_set_is_muted`, silencing all page output including Web Audio and frames. macOS 12 and iOS 15 or later suspend and resume media with `WKWebView.setAllMediaPlaybackSuspended`. Changing the setting applies to the existing view and page. Other hosts keep their usual playback. Android support is tracked in the [roadmap](../roadmap.md#from-nsgos-issues).

- An empty `WebSource` loads `about:blank`, both initially and when `SourceFunc` or `Ref.Load` clears a previous page, with the usual load start, load and navigation events. Core resolves that default before sending configurations and load commands to every backend. Its origin is `null`; the web's blank iframe keeps an opaque sandbox origin so it cannot reach the app's page.
- Linux reports a page-made load's start from its main resource request, so `OnLoadStart` and the loading navigation state name the destination before its response arrives, even while WebKitGTK's view URI names the page still shown. Frame and subresource requests never consume that start; loads with no resource, such as a cached history entry, use the committed URI, and a provisional failure uses its failing URI. A restricted view's page-made data: or blob: page that its config refuses at the main-frame response reports no start, as other platforms refuse it before it starts. App-owned loads keep reporting at `WEBKIT_LOAD_STARTED`. NSH reads the view URI there; NSGo uses the request to avoid reporting the previous page.
- On Linux, WebKitGTK coalesces URI and title notifications and back-forward list changes into `OnNavigationStateChange` snapshots when the page is idle. The load signals still report the start and finish of a full load.
- A refused page-made `about:` navigation on Linux reports no load start, load or navigation state; its refusal and the previous page's restoration still report normally. WebKitGTK's URI at load start may still name the previous page, and its policy check does not say whose frame an action is, so a page-made start that names a refused `about:` page, or follows a refused `about:` action with no other navigation action between, waits for its top-level commit to accept or refuse it, and is reported before an error if the load fails first. Each navigation action replaces that hint, so a frame's `about:` action followed by the page's own navigation, a link or `location.href`, does not hold that navigation's start, which is reported as it starts; the app's own HTML loads report their start as usual.
- Every page starts with `WebBridge`, defining `window.nsgo.postMessage(data)`, which reaches `OnMessage` as a string and `OnMessageFrom` with the page's origin. `PostMessage` dispatches a `MessageEvent` on the page's window.
- `OnOpenWindow` gives the app a page's requested URL in `WebWindowRequest` on Apple, Windows and Linux. The platform suppresses the new window whether the app handles the request or ignores it. Restricted views check the URL through `Navigable` and report a refusal through `OnError`. WebView2 sets `Handled` in `NewWindowRequested`, and WebKitGTK's `create` returns no view. Both give the app their user-gesture flag. Apple's `WKUIDelegate` returns nil. WebKit identifies links and forms by navigation type. macOS also enables WebKit's pop-up blocker, so it can treat a script's delivered request as user-initiated. iOS uses its default pop-up policy and reports a gesture for links and forms.
- A message reaches the app only from the page's top frame and only from an origin `MessageOrigins` allows, by default the source's: `driver.WebSource.Origin`, Src's, BaseURL's for HTML, `"null"` for HTML without one, which a page the view navigates to on another origin, a redirect included, does not share. Core checks this in one place (`webNode.allows`) on `EventMessage`'s `Origin`, `URL` and `MainFrame`, which every backend fills, and logs a view's first refusal. Frames never reach the app, so that every platform takes the same messages: Android and Linux tell no caller for a frame's post, and Windows only through `CoreWebView2Frame`, which the host does not follow, so a frame relays through the page with `window.parent.postMessage`, whose event the browser gives the frame's origin. Origins are written as `driver.WebOrigin` does: scheme://host, the port only when not the scheme's own, `file://` for every file, `"null"` for an opaque one (about:blank, data:, blob:null). As every page without an origin of its own has `"null"`, a `"null"` message, allowed by default or listed, reaches the app only from the source's page (`driver.WebSource.Shows`): about:blank for HTML without a base URL, which every backend loads it at (the web's srcdoc, about:srcdoc), and the source's URL otherwise. So a data: or blob: page a frame sends the view to after a user's tap, which Android's WebView loads and WebKit loads for a user's action, does not post as HTML without a base URL; Chromium refuses a page's own top-frame navigations to data: URLs on Windows (`BlockedSchemeNavigationThrottle`), so there a data: page of such HTML is the one `NavigateToString` loaded, reported at about:blank. `"*"` takes every page. A frame can still send the view to an empty about:blank, which posts nothing of its own.
- Each backend tells the top frame and its origin its own way. Apple reads `WKScriptMessage.frameInfo`: `isMainFrame`, and the security origin, or the frame's URL for a document whose security origin is opaque, such as a sandboxed one. Windows hears only the top document through `CoreWebView2.WebMessageReceived` and reads its `Source`. Linux's WebKitGTK reports neither, and gives every frame the message handler, so its bridge, a top-frame user script, prefixes a token of the view's own, which it keeps in a closure with the handler's `postMessage` bound before page scripts run; the page is the view's URI as its load commits (`WEBKIT_LOAD_COMMITTED`), so a page the view only started to load does not take the messages of the one still shown, though a message still in flight as the next page commits takes the new page's. Android gives every frame its JavaScript interface and tells no caller, and `WebViewCompat.addWebMessageListener`, which would, is androidx's, which the runtime does without: `WebNode` makes a token for each page as it starts, runs the bridge holding it with `evaluateJavascript`, which reaches only the top frame, and takes only messages carrying the current page's token, reporting the URL the view showed as it handed it out, so a frame or a later page posting to the interface itself is dropped. android.webkit reports a page's start once it commits, and `evaluateJavascript` reaches the page committed last, so the view gives the bridge only while it shows the committed URL (for HTML, whose commit is a data: URL, its history URL); showing another, it has committed a later page, whose own start follows, or is loading one the app asked for, whose URL the page still shown would otherwise report. A page that starts again, such as one restored from the back-forward cache, gets a bridge with the new token in place of its old one. HTML with a BaseURL takes it as its history URL there, so the view shows the page at the base URL, as other platforms do, rather than about:blank. The web hands the srcdoc page's port to the app only from the frame's own window and with the page's token, and drops it as that page leaves, for a link or a script setting `location`, which its bridge says on `pagehide`, reporting a load start; a page it went to has no bridge, so `InjectJavaScript` and history steps there are dropped with a warning until the source shows again, and those sent while the source's page loads wait for its port.
- `Ref.Evaluate` answers with a script's result as JSON, or its error, through that bridge rather than each platform's evaluation callback, so every backend with web views answers alike, Android's with no runtime rebuilt: `WebEvaluateScript` runs the script as an expression, awaits a promise, and posts the answer after a marker with a random key, which the core takes, ahead of the origin check, for the `Evaluate` waiting on it and never hands to `OnMessage`. A page leaving (`EventLoadStart`, reported while one waits) ends those waiting with an error. On the web, which bridges only an HTML source's page, an `Evaluate` with no such page to come, a URL's or one the page went to, ends with an error at once; elsewhere a page whose bridge is gone never answers.
- A page loads again when the source, an injected script or its request headers change. `Ref.Load` loads a `WebSource` as a new source would, even one equal to the source, through the same access check, which sends nothing for a refused one, and with the view's `Headers` (`driver.WebLoad`, carrying the source in `Data`). It navigates the view as a link does: each backend loads it with the load the source uses, keeping the configured source, which the next change of the source, the scripts or the headers loads again and whose origin messages come from by default. Other settings apply to the live view.
- `Ref.Reload`, `GoBack` and `GoForward` keep an app-owned page's exemption from `AccessWebSchemes`. Apple and Linux retain native history objects for app-created entries, releasing those the browser drops; Windows records CDP's native entry IDs and selects the checked ID for history commands, with `NavigationStarting` also checking its native reload/history kind. Matching a source URL alone never grants a page-created navigation, and a history command's grant holds only for the native back-forward navigation to the entry it chose: a step within one document, such as back to the entry before a `pushState`, starts no navigation, so the page's next navigation of another kind or to another URL drops the grant rather than taking it (WebKit's navigation type on Apple and Linux, `NavigationKind` on Windows). WebKit reloads string HTML as a blank page, so the host replays its bytes; initial HTML that WebKit omitted from history is kept before the first native entry, with `CanGoBack` and `CanGoForward` reflecting it. Apple also exempts a page's own reload of an app-created entry, which can only load the current entry again; a page's own back-forward step, whose target entry WebKit does not report, is held to the schemes on every backend but Android, and Linux, whose WebKitGTK does not say which frame an action is, grants nothing from a navigation action beyond the host command's own. Android already leaves reload/history out of `shouldOverrideUrlLoading`; the web keeps its iframe's behavior and cannot enforce page scheme restrictions. The `internal/testhost/testdata/webhistory` fixture passed on a physical iPhone XR (iOS 18.7.11) and Pixel 3 XL (Android 12, WebView 157), including forward history after reloading an earlier entry, an iframe reload and a same-document back step that grants no subsequent navigation (#1364). Chromium skips entries that navigate without user activation, so the fixture touches the page before creating its history.
- `WebView.PinchZoom` lets a pinch magnify the page, off by default: macOS sets `WKWebView`'s `allowsMagnification`; Windows sets WebView2's `IsPinchZoomEnabled` for touch screens and `IsZoomControlEnabled`, as a precision touchpad's pinch reaches a window as Ctrl with the wheel, which also takes Ctrl with + and - away; Android sets `WebSettings`' built-in zoom, its buttons hidden. iOS zooms as the page's viewport says, and WebKitGTK and the browser have no switch, keeping their own handling.
- `WebView.Mobile` presents a phone to the page on the desktops; the others ignore it. Windows calls the DevTools protocol on the view's page session (`Emulation.setUserAgentOverride` with Android client hints, `setTouchEmulationEnabled` with five points, `setEmitTouchEventsForMouse` in its mobile configuration and `setDeviceMetricsOverride` with `mobile` and the view's own size), which the session keeps across navigations, and the navigation waits for the calls as it does for the document scripts. macOS and Linux have no such emulation, so the user agent is a phone's, iPhone Safari's in WKWebView and Android Chrome's in WebKitGTK, where x.com showed its error page to iPhone Safari's, and `driver.WebMobileScript` (`webmobile.js`) runs at the start of every frame: it reports touch support (`maxTouchPoints`, the `ontouch*` handlers, matchMedia's pointer and hover, `Touch` and `TouchEvent`, which macOS's WebKit lacks, built from `UIEvent`), dispatches touch events for the primary button's presses and drags, hides the mouse's moves meanwhile and the click after a drag, and pans the nearest element a finger would scroll when the page prevents no touch, gliding on as it is let go. On every desktop the script also makes a wheel or trackpad scroll that nothing under it would scroll a finger's swipe, which Chrome's emulation leaves a wheel, lifting the finger after 150 ms of rest or a quarter of the view, and dropping the rest of the scroll, such as its momentum. Changing `Mobile` loads the source again.
- A new page on Windows drops the presses, taps and drags it gets before its first contentful paint, as Chrome does: Blink holds the previous page's paint for a navigation (paint holding) until the new one paints text or an image, or for 500 ms when none comes (`kCommitDelayDefaultInMs`, `LocalFrameView`), and while it holds, the renderer's `WidgetInputHandlerManager::DispatchEvent` drops every input but mouse and pointer moves (`kDeferCommits` with `PaintHoldingReason::kFirstContentfulPaint`), though `SendMouseInput` and `SendPointerInput` succeed and the page's `requestAnimationFrame` callbacks run. A page with nothing to paint, such as an empty body, takes nothing for its first 500 ms. The backend forwards such input as it comes, without holding or replaying it, as the page has not shown what the user aimed at; a test that drags across a page right after it loads waits for its `first-contentful-paint` entry (`PerformanceObserver` of type `paint`), as `TestWebMobilePresentsAPhone` does (#851).
- `WebView.Headers` adds fields to the initial URL request on Apple, Windows, Linux and Android; HTML sources and the web backend do not apply them yet.
- On Apple, a `file:` source uses `WKWebView`'s file loader and grants the page read access to its containing directory; links to files outside that directory are refused, as they are for HTML whose base URL is a `file:` one, outside the base's directory. A page from any other source leaves `file:` links to WebKit unless the view is restricted, which refuses them.
- `WebView.Incognito` uses WebKit's non-persistent data store on Apple, an ephemeral WebKitGTK network session of the view's own on Linux, released with the view and WebView2's in-private controller profile on Windows. `android.webkit` keeps one cookie store and one set of website data per app with no per-view switch, so an incognito view on Android loads with `LOAD_NO_CACHE`, DOM storage (`localStorage`, `sessionStorage`) off and `setSaveFormData(false)`, which Android 8 and later ignore for autofill, while its cookies, IndexedDB and HTTP authentication stay shared with the app's other web views; the web backend has no per-frame storage switch.
- The persistent store every web view of the app shares is `Scope.SetWebCookies`, `WebCookies` and `ClearWebsiteData`: one `ItemWebCookies` carrying a `WebCookiesRequest` whose `Op` sets, lists or clears, answered by `EventWebCookies`, a list's cookies in its `Data`. They work with no web view shown, and Incognito views keep their data apart, in memory, but on Android. Core refuses a cookie no platform takes (a missing name or domain, SameSite None without Secure, a `__Secure-` or `__Host-` name without its prefix's attributes) and a filter with both a URL and a domain or a URL other than http or https before any reaches the platform, and holds code an Access holds to `AccessWebView` with `AccessCookies`, which no TSX capability grants, for each cookie's URL, the filter's URL or `https://` and its domain, or `""` for the whole store and for clearing. A list filters in Go (`driver.FilterWebCookies`) on the targets that list the store whole, by RFC 6265's domain and path match, Secure going only to https, and drops expired cookies. WebView2 reaches a profile's cookies and browsing data only through a web view (`ICoreWebView2_2::get_CookieManager`, `ICoreWebView2_13::get_Profile`), so Windows uses a web view of the window showing pages of the app's profile, and while there is none a hidden one it makes in the profile's environment, starting it with the schemes `ServeScheme` serves to the calling scope, as a first web view would; the hidden one closes once a web view of the profile shows pages, since WebView2's processes, and the session cookies, end with the profile's last web view. `AddOrUpdateCookie` applies after it returns, so a set on Windows answers once `GetCookies` lists the cookies, failing after five seconds. Android reaches `CookieManager` through the runtime's `msgCookies` and `msgCookiesSet` rather than the batch.
- Apple and Windows exchange cookie expiry dates as Unix seconds and a separate fractional part, covering the cookie date range without `UnixNano` overflow. Windows removes expired cookies with WebView2’s `DeleteCookiesWithDomainAndPath`, since its expiry setter rejects negative dates, and waits for their keys to disappear before completing the write. Linux already uses GLib’s Unix seconds, keeps a sub-second future expiry from truncating to expired before `soup_cookie_set_expires` runs, and checks `!g_hostname_is_ip_address` with `soup_tld_domain_is_public_suffix` before adding any cookie, since libsoup’s `SoupCookieJar` otherwise silently drops public-suffix cookies while `webkit_cookie_manager_add_cookie_finish` reports success; Apple, Windows and Linux prepare every native cookie object in a batch before mutating their store. Android writes the RFC date in `Set-Cookie`.
- `Env.HasWebView` reports whether the target provides a web view host; it is false on tvOS, whose UIKit target has no WebKit host, and true on the other targets that expose `WebView`.
- `Scope.ServeScheme` registers app-owned URL schemes for web views under that scope, the nearest scope's handler answering, while other subtrees and windows neither load nor serve them; it refuses those web views handle themselves, such as `ws` or `javascript`, which would end the app on Apple. `ServeScheme`'s handler returns bytes and answers every request 200 whatever its method; `ServeSchemeRequest`'s sees the request's method and headers where the platform reports them (Apple, Linux and Windows name the method, Apple's and Linux's request headers included) and answers the response's status, headers and body, a nil one 404, the Content-Type the response's headers name, else what the native host infers. Apple uses `WKURLSchemeHandler`, which marks its schemes CORS-enabled, Windows answers WebView2 resource requests, and Linux registers a WebKitGTK URI scheme once on the shared web context, marks it CORS-enabled on the context's security manager as WKWebView does, and answers each request as HTTP (`webkit_uri_scheme_request_finish_with_response`) from the handlers of the view whose page made it, failing it when that view serves no such scheme. Schemes are read when a native view is first made. WebView2 takes its schemes only as its environment starts, with the batch that makes a profile's first web view: a scheme served after that does not load on Windows, which the log says once. Android and the web backend do not provide this bridge yet.
- Load start and load each come with a navigation state change, carrying `WebNavigation`. Errors arrive as `*WebError` with the failing URL and, on Apple, Linux, Windows and Android, the platform's `Domain` and `Code` (`driver.WebFailure` in the event's `Data`; on Android, `android.webkit.WebViewClient` and `WebResourceError.getErrorCode()`, carried in the event's data and index); access refusals leave both empty. A load cut short, stopped or replaced by another (`NSURLErrorCancelled` and `WebKitErrorFrameLoadInterruptedByPolicyChange` on Apple, their WebKitGTK equivalents, WebView2's `OPERATION_CANCELED`, and on Windows the `CONNECTION_ABORTED` WebView2 ends a navigation with when it is stopped, replaced or turned into a download), is no error: Windows drops the failure of a navigation that is not the last one started (`NavigationId`) or that the app stopped or replaced, and holds a `CONNECTION_ABORTED` for half a second, dropping it when a download or another navigation starts, as WebView2 reports those only after the failure; Windows reports the URL that failed, which never committed, rather than the page still shown.
- On macOS and iOS, `WKWebView` observes `URL`, `title` and both history flags and reports their updated `WebNavigation` together through `OnNavigationStateChange`. The navigation delegate reports the start and finish of a full load. WebKit may supply the title after that finish, which reports a new state.
- A web view with `OnDownload` saves what its pages download, as NSH's macOS one does: core sends `WebConfig.DownloadDir`, the app's data directory's `downloads`, and Apple's host turns a main frame's response WebKit cannot show or marked an attachment, and a link asking for a download, into a `WKDownload`; Linux's WebKitGTK host handles its `download-started` signal; Windows' WebView2 host handles `DownloadStarting`, cancelling without `DownloadDir` or when closed and reporting setup failures as `WebDownloadFailed`; and Android's WebView host handles `DownloadListener`, fetching an http(s) download again with the page's cookies, user agent and Referer and, on the source's origin, its `Headers` (following http(s) redirects while stripping app `Headers` and recomputing cookies and Referer on each hop), decoding a `data:` URL itself and having the page read a `blob:` URL, which needs the page's JavaScript and holds the whole file in memory, with the `Blob` kept from the link's click so a URL the page revokes right after clicking it still saves (an object URL made before the host's script runs as the page starts, or in a frame, is fetched instead and fails once revoked), with the name a link's `download` attribute gives. These hosts save to `<id>/<file name>` under that directory and report their start, end and bytes or failure; a view that closes cancels the downloads it was saving on Linux, Windows and Android.
- `WebView.Media` lets the pages capture the microphone, the camera or both through `getUserMedia`, as NSH's `webview.media` capability does; TSX's `media` prop sets it, held to a package's `webview` capability's `media` (`AccessMedia`). Each host answers its web view's request from it without the engine's own prompt, so only the system asks the user for each device, and refuses what it leaves out, a request for both needing both: Apple's handler is also the `WKUIDelegate` (`requestMediaCapturePermissionForOrigin:`, macOS 12 and iOS 15), refusing too where the Info.plist lacks the device's usage description, as the system would end the app; Windows handles WebView2's `PermissionRequested` for its microphone and camera kinds, keeping each answer out of the profile every view of the app shares (`SavesInProfile`), and leaves other kinds to WebView2; Linux turns WebKitGTK's `enable-media-stream` on only with a device and answers `permission-request`'s user media requests, refusing screens; Android's `WebChromeClient.onPermissionRequest` asks for `RECORD_AUDIO` and `CAMERA` through the activity first where the app holds neither, as `NsgoView.permissionResult` hears; and the web sets the frame's `allow`, which takes effect from its next page. An app declares the devices in its package: `apple.info`'s usage descriptions, which also claim them under the hardened runtime, and `android.permissions`.
- Android adds request retirement to NSH’s system permission flow so delayed answers cannot outlive a page’s capture policy. Removing a requested device from `Media`, loading another page or destroying the view denies its pending requests; WebView’s cancellation retires a request without answering it again. A delayed system permission result never grants a retired request, and a grant rechecks all requested system permissions. Apple, Windows and Linux answer their host’s media policy requests synchronously and have no corresponding host-held system permission callback.
- `Ref.SendInput` gives the page a click, typed text or a key as the user's own, so the page's events are trusted (`isTrusted`) and carry user activation, which `InjectJavaScript` cannot do, taking the keyboard focus first: macOS hands the `WKWebView` AppKit events with each character's US key; Windows delivers clicks through `ICoreWebView2CompositionController::SendMouseInput` and keys/text through WebView2's `Input.dispatchKeyEvent`; Linux delivers clicks and mapped keys through X11's XTest extension into the `WebKitWebView` (with WebKit's `InsertText` editing command for unmapped Unicode characters, reporting `Env.CanSendInput` where X11 and XTest are available); and iOS delivers taps through `UITouch`/`UIEvent` on `WKWebView`'s content view and its tap/touch gesture recognizers, US-layout keys and text through `UIKey`/`UIPress`/`UIPressesEvent` on `pressesBegan:withEvent:`/`pressesEnded:withEvent:`, and non-US characters through `UIKeyInput`'s `insertText:`. `Env.CanSendInput` reports this capability; other targets drop it. TSX apps need the `webview` capability's `input` for it.

| Android | `CookieManager.setCookie` of each cookie's `Set-Cookie` value on a URL it goes to, then `flush` | `CookieManager.getCookie` of the filter's URL: names and values, `Domain` the URL's host; a domain or the zero filter answers unavailable (`driver.NoWebCookieDomains`) | `CookieManager.removeAllCookies`, `flush` and `WebStorage.deleteAllData`, which leave the web views' HTTP cache |
| HarmonyOS, web, tvOS, watchOS, mini programs | Unavailable (`driver.NoWebCookieStore`) | Unavailable | Unavailable |

## Videos

- A source is a URL, a file path or an `asset:` path resolved against the app's resources.
- `Video.Headers` copies the HTTP request headers when the video mounts. Android passes them to `MediaPlayer.setDataSource(Context, Uri, Map)` for HTTP and HTTPS sources, including a new URL from `SourceFunc`. Apple uses an `AVAssetResourceLoaderDelegate` for finite HTTP files, streaming the ranges AVFoundation asks for and canceling them when the asset closes. It forwards the configured headers through same-origin redirects. The same loader sends the configured headers with direct HTTP `AudioSource` files. Playlist URLs ending in `.m3u` or `.m3u8` keep the native loader.
- Linux sets the primary HTTP source's `souphttpsrc` headers on GstPlay's `source-setup` signal. GStreamer retains control of byte ranges and content encoding. Protected sources disable redirects when the plug-in lacks `location-trusted` or the app sets `User-Agent`. Otherwise the plug-in strips app headers on cross-origin redirects. NSGo keeps the source's HTTP header event out of adaptive demuxers so segment downloads do not inherit app headers.
- `EventLoad` carries the duration, the picture's size in points and whether the backend can change the rate. `EventProgress` comes every `ProgressInterval` while playing.
- `EventEnd` follows the platform: AVFoundation and Android report every end, then a repeating video starts over; a looping Media Foundation engine, `<video>` or GTK stream never ends.
- A non-repeating video stays at its end through unrelated configuration changes. Changing `Paused` to true and then false replays it from the beginning unless the native scrubber moved it before the end, in which case it resumes there; seeking before the end resumes there when `Paused` is false, and leaves it paused otherwise. Opening another source starts from that source's beginning.
- iOS, tvOS, macOS and Android videos, and web videos in supporting browsers, opt into [Picture in Picture](picture-in-picture.md) with `PictureInPicture`; `Ref` starts and stops it, and `OnPictureInPicture` reports readiness and state. The PiP window plays and pauses the player, which `OnPlay` and `OnPause` report as they do the controls'.
- `Controls` shows the platform's controls. Windows has none, so it draws NSH's bar.
- `Paused` applies when it changes and when a source opens. Between changes the platform may pause or play the video itself, and the player keeps that state until `Paused` changes; each is reported once, `OnPause` with a `VideoPauseReason` and `OnPlay`, sharing the driver's answer kinds `EventImageInfo` and `EventMenuClosed`, as an `EventMask` has no room left. The built-in controls (`VideoPauseControls`) report on Apple, Android, Windows, GTK and the web, Control Center and the PiP window on iOS; an interruption (`VideoPauseInterruption`: a call, Siri, another app taking the audio session, the app going to the background) on iOS and, for a video with an `AudioSession`, which holds the audio focus, on Android; and a lost output such as unplugged headphones (`VideoPauseRouteLost`) on both, for a video that is not `Muted`, which has nothing to stop. When an audio-session interruption ends and the system lets it, iOS's `AVAudioSessionInterruptionOptionShouldResume` or Android's focus coming back, a video still paused by it plays on and reports `OnPlay`; a background pause, a permanent loss of the focus and a lost output leave it paused. A background pause clears any earlier interruption's pending resume even when its rate notification arrives later. As the app backgrounds on iOS, an active or starting Picture in Picture session keeps its video playing, including video in a custom content tree. The backend pauses other videos before iOS reports an audio-session interruption. A play the app does not make keeps its `Rate`: Android sets it on the player, Apple makes it the player's `defaultRate` (macOS 13, iOS 16), at which the controls and the PiP window play. An app that shows its own play state follows them in `Paused`, which takes the video back. `internal/platform/videoplay.State` keeps this policy for Apple, Windows, GTK and the web; Android’s `VideoNode.java` keeps the same policy across its runtime boundary. App commands are recorded before native playback calls, so their notifications produce no control callbacks. GTK observes `notify::playing`, Windows observes Media Foundation’s playback notifications, and the web reads the current element state for queued `play` and `pause` events. Natural completion remains `OnEnd` alone.
- `AudioSession` is NSH's `audioSession`. On iOS, while a video with one plays, the shared `AVAudioSession` is the playback category in the spoken-audio mode (mixing with others for `AudioSessionMixWithOthers`), and goes back to what it was, deactivated a second later to let other apps play, once none plays (`apple/audiosession_ios.go`, `internal/audiosession`); a video with the default `AudioSession` keeps the session active in the app's own category while it plays, so switching to or from it moves the session across instead of deactivating it under the video; `AudioSessionFunc` (TSX's `audioSession`) changes it as the video plays, and iOS holds the new session before letting the old go, so playback goes on without a gap. On Android the sound is speech, and a playback video holds `AUDIOFOCUS_GAIN_TRANSIENT` while it plays, pausing for another app's focus as above; a change opens the source again. The desktops and the web ignore it.
- With `AudioSource`, Apple loads the video and audio assets' first matching tracks away from the main thread and gives one `AVPlayer` their composition. The tracks start at zero, longer audio is cut to the picture's duration, and a pending seek is applied when the composite item is installed. Replacing or closing the video cancels the loads and discards late results.
- A video's alpha channel shows what is behind it where the platform's decoder outputs it: Apple sets `AVPlayerLayer` non-opaque with no background (`clearPlayerLayer`) so HEVC with alpha composites over views behind it, and clears `AVPlayerViewController.view` on iOS; GTK composites the textures GStreamer's `vp8alphadecodebin` and `vp9alphadecodebin` (the codecalpha plug-in of gst-plugins-bad) give it, and with `Controls` gives `GtkVideo` the `nsgo-video` CSS class (`video.nsgo-video { background: none; }`) to clear GTK 4's default black background; Android's `VideoNode` calls `setOpaque(false)` on its `TextureView` so transparent frames composite when a decoder keeps alpha; and the web gives `<video>` `background: transparent` so VP9 alpha WebM (and HEVC with alpha in supporting browsers) shows views behind it. AVFoundation opens no WebM and GStreamer decodes no HEVC alpha. Windows draws a video's frames with their alpha ignored, as NSH's backend does, and what Media Foundation's media engine outputs for VP8's and VP9's alpha (a second stream in Matroska's block additions) and HEVC's alpha layer has not been checked on a Windows machine; until it has, Windows refuses every clip that declares alpha rather than draw it opaque or draw it premultiplied in Direct2D on an unchecked assumption, as #569 proposed. A player does not say it dropped the alpha before it draws, so `internal/platform/videoalpha` reads what a local file declares from its container headers (Matroska's `AlphaMode`, the alpha channel information SEI in an `hvcC`), and a backend that cannot keep it reports `EventError` with `VideoErrorAlphaUnsupported` in `Index`, which core gives the app as `MediaError.Reason`'s `MediaErrorAlphaUnsupported`, instead of opening the source: WebM with alpha on Apple, any on Windows, and on Linux HEVC, or VP8 and VP9 when GStreamer's registry lacks the decoder. Android's and the web's backends do not read it and play such clips as their decoders output them, as do all backends for remote sources. With `Controls`, AVKit's player chrome may still draw black behind the picture. Clips no platform here decodes with alpha go through the app's own decoder ([#107](https://github.com/nsgo-dev/nsgo/issues/107)).
- A painted macOS window samples a video's alpha when `HitTestAlpha` is positive, the video has an identity track transform and its controls are off. The window's timer reads each new BGRA frame from an `AVPlayerItemVideoOutput` and keeps the latest alpha mask. Hit tests map the pointer through `AVPlayerLayer.videoRect` into that mask. The view's background and borders still count as painted, and a video without a sampled frame uses its view bounds.

On 2026-11-22, the controls regression failed before the fixes and passed in Chromium with trusted pointer clicks on its own media controls, and in GTK under Xvfb through the native play/pause button’s clicked signal. Both checked exactly one callback per controls change, held state across volume and rate changes, controls playing while `Paused` remains true, and no callbacks for app commands. GTK’s completion/replay regression and macOS’s existing real AVPlayer controls regression passed; the shared policy tests also cover interruption reasons, resume, background suppression and completion. Windows has a corresponding control-bar click and replay regression, but native Windows controls still need a usable session; iPhone calls, unplugged headphones and Control Center, and physical Android headphone removal still need acceptance ([roadmap](../roadmap.md#from-nsgos-issues)).

| Target | Player |
| --- | --- |
| Apple | `AVPlayer` in an `AVPlayerLayer`, or `AVPlayerView` and `AVPlayerViewController` with controls; AVFoundation and AVKit load on the first video |
| Windows | Media Foundation's media engine in frame-server mode, drawing each frame as a Direct2D bitmap |
| Linux | A `GtkMediaStream` backed by GstPlay in a `GtkPicture` or a `GtkVideo` with controls. Rate changes seek from the current position and `scaletempo` preserves pitch. The stream paints through `gtk4paintablesink` when installed and through RGBA textures from `appsink` otherwise. If the libraries or pitch filter are absent, `GtkMediaFile` plays at 1× and reports `RateChangeable: false`. |
| Android | `MediaPlayer` on a `TextureView`, with a `MediaController` for controls |
| Web | A `<video>` element |

## Native components

An app registers its own platform views by name, as NSH's embedding apps do (`nsh/docs/dev/embedding.md`): `nsgo.Component(name, factory)` hands `nsgo.Run`'s or `nsgo.NewView`'s backend a `core.NativeComponents` table, so a registry belongs to one surface, never to the process. An iOS or Android app embedding NSGo registers its own Swift or Java components with each view, which take the names Go's table lacks ([embedding](embedding.md)).

- `Native` names the component; its `Props` cross only when they change, a removed one as nil, and `Ref.Command` reaches the component's `Command`.
- The first `ItemNative` makes the component with a `NativeContext`, whose `Emit` reaches `OnEvent` and whose `SetSize` gives the element a natural size, as an image's; a width of 0 asks for its height alone, as a bar as wide as it is placed.
- A prop whose value is an `AnimatedNode` is bound rather than sent, as NSH 0.3.0's are: `NativeConfig.Bindings` names each bound prop's node and whether it outputs a color, and the backend's `Animator` (`BindNative`, `ChangedNatives`) hands the component each value that changed on the frame clock, through `driver.AnimatedPropSetter` or else `SetProp` with a `float64` or a `Color`. A plain value replacing a node is sent; a removed prop is sent as nil. Android binds them in Java as a canvas's arguments are and calls the view's setters, or a registered `NsgoComponent`'s `setAnimatedNumber` and `setAnimatedColor`, never an `AndroidPropMapper`; iOS hosts' components take the optional `setAnimatedNumber:value:` and `setAnimatedColor:argb:`.
- macOS and iOS register `driver.SwitchComponent` themselves, for `core.SystemSwitch`: NSSwitch and UISwitch; Android registers its framework Material 3 `Switch`, showing the user's choice at once and measuring itself. Its parent centers it rather than stretching it, as a native view with a natural size keeps its aspect when stretched.
- iOS and Android register `driver.TabBarComponent` themselves, for `mobile.TabBar`. iOS's `UITabBar` subclass (`NsgoTabBar`) reports its detached `sizeThatFits:` height at creation without adding the key window's bottom safe area, then re-measures at its laid-out width when attached to a window or when its safe area, layout, traits or items change, reporting only changed heights. UIKit's answer is the natural height as it is: a classic bar's grows by the bottom safe area it overlaps, while iOS 26's floating bar keeps one height at every placement. On a leading or trailing edge it reports the vertical bar's width instead. An explicit height still takes precedence. Android's reports a natural height of 80 points plus the part of its frame overlapping the system navigation bar, updating when it or an ancestor moves. Only that overlap becomes bottom padding, so a bar elsewhere keeps all 80 points for its tabs; an explicit height still takes precedence. Android takes `tabBarBackground`, `tabBarIdle`, `tabBarSelected` and `tabBarIndicator` from the palette as native props. Their custom-palette defaults are `Surface`, `TextMuted`, `Accent` and `accentContainer` or a 12% accent fill. The default palette keeps Material's background and idle colors and tints the selected tab with the accent.
- Native tab bars receive badges separately from their items. Updating a badge keeps the tab views and selection. UIKit sets `badgeValue` and `accessibilityValue` on its existing items. Android updates an icon-corner mark and the item's spoken description, using the danger color. `mobile/locales` supplies the spoken dot label for both backends and `ui.TabShell`'s drawn tabs.
- Factories run on the main thread and may return nil; an unknown name leaves an empty box and is logged once.
- Registering differs per platform only in what `View` returns, so an app registers a target's components in files built for it, as the gallery's `components_*.go` do.

| Target | `View` returns | Hosted as |
| --- | --- | --- |
| Apple | An `NSView` or `UIView` | A subview resizing with the view; on iOS placed at each frame, as views such as `UITabBar` size themselves |
| Windows | A window handle | A child window following its view after every frame, clipped with a window region to what its clipping ancestors leave visible, above what NSGo draws, as NSH's `NativeComponent::window` |
| Linux | A `GtkWidget` pointer | A widget hosted in the view's widget, as web views and videos are |
| Web | A DOM element (`js.Value`) | A child element filling the view |
| Android | The name of a `View` class | Built by reflection in the Java runtime, props set through its one-argument `set` methods and commands through its methods; the Go process cannot make views |

On Android the runtime also installs a listener on each `setOn…Listener` method the view's own class declares and reports its callbacks as events named after them, their arguments as a JSON array. A component may implement `android.PropMapper` to turn a prop into ordered setter calls, and `android.EventMapper` to receive those callbacks itself, as the gallery's `SeekBar` does.

### Custom Android classes

A library can ship an Android `View` subclass in a precompiled `.dex` or a DEX JAR. Its Go factory returns the fully qualified class name from `NativeComponent.View`, and the app lists the library file under `android.classes` in `nsgo.yaml`. Paths are relative to that file unless absolute. The class needs a public constructor that takes `android.content.Context`. The [Android native example](../../examples/android-native) registers such a class and passes a Go prop to its Java setter.

The Android toolchain is needed to prepare the library's DEX, for example with D8's `--min-api 28` and a `.jar` output. NSGo's Go packager puts the runtime in `classes.dex` and adds the supplied shards as `classes2.dex`, `classes3.dex` and so on in APKs and App Bundles. Android loads them through the activity's class loader. An embedding app supplies its Java libraries through its own Android build.
