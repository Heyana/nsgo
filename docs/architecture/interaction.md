# Interaction

Accessibility, pointer events, keyboard focus, touch areas, touches and the responder, gestures and file drops: what the core sends so platforms decide on the main thread. Read this before changing accessibility props, pointer events, focus, touches, gestures or drops.

## Accessibility

`MultiSelectable` marks a grid, listbox or tree whose collection permits more than one selected item. The web maps it to `aria-multiselectable`, Windows exposes UI Automation's Selection provider, and GTK reports the multiselectable state; `base.DataTable` sets it for multi-row selection.

Elements carry NSH's accessibility props: `Role` (a menu item's checked kinds, `RoleListbox`, `RoleOption`, `RoleGroup`, `RoleRegion`, `RoleNavigation`, `RoleTree`, `RoleTreeItem` and `RoleToolbar` among them, each on a backend's nearest role, as WebKit maps ARIA's; Android reads those as plain views for now, [roadmap](../roadmap.md#finish-the-existing-platforms)), `Pressed`, `Busy` and `Invalid` (ARIA's `aria-invalid`, which `aria-invalid:` styles), `Label` (`LabelFunc` when it changes), `AccessibilityDescription` (`AccessibilityDescriptionFunc` when it changes, read after the label) and `Hint`, `AccessibilityValue` (a range when `Max` is above `Min`, and `Text`), `Expanded`, `SelectionItem` (an item in a selectable collection, independent of `Selected`), `AccessibilityActions` with `OnAccessibilityAction`, `Accessible`, `ImportantForAccessibility`, `AccessibilityElementsHidden` and `LiveRegion`. `Ref.SetAccessibilityFocus` moves the screen reader, as an `ItemAccessibilityFocus` command.

- The props go in `ViewProps`, except a label changing alone on mounted props, which goes as `ItemAccessibilityLabel`.
- NSGo adds reference-based labels, which NSH does not provide: `Text.LabelFor` and `View.LabelFor` focus and activate a live control, name it from current visible text, and project its disabled/invalid state onto the label without changing its own props. `LabelledBy` on views, texts and inputs names from ordered refs ahead of `Label`; otherwise `Label` precedes implicit labels in tree order. `labels.go` resolves only registered relations after text preparation, retaining immutable native IDs and clearing removed links. Hidden, detached, repeated and cyclic references are ignored; relations cannot cross surfaces or confinement, and activation respects modal layers. Label-only presses infer no button role or Tab stop. Web uses `aria-labelledby`, GTK `labelled-by`, AppKit the title element and its reverse relation, UIA `LabeledBy`, and Android native label refs (several from API 36); AppKit and UIA expose the first relation with the full resolved name. UIKit consumes the resolved name; watchOS, mini programs and HarmonyOS retain their existing accessibility limitations ([roadmap](../roadmap.md#finish-the-existing-platforms)).
- Where a platform has one place for what is read after the name, it reads `ViewProps.HelpText`: the description, then the hint, each a sentence: macOS's `accessibilityHelp`, iOS's `accessibilityHint`, the web's `aria-description`, GTK's description and Android's hint. Windows keeps them apart, the description as UIA's `FullDescription` and the hint as `HelpText`. `Invalid` is `aria-invalid` on the web, also on an input's own element, UIA's `IsDataValidForForm` false, GTK's invalid state, and "invalid data" in iOS's spoken value; Android sets `setContentInvalid`; macOS's `AXInvalid` waits for the attribute override ([roadmap](../roadmap.md#finish-the-existing-platforms)).
- `base.Dialog` is a `RoleDialog`, or the `RoleAlertDialog` it gives (ARIA's `alertdialog`: WebKit's `AXApplicationAlertDialog` subrole on macOS, UIA's dialog pane on Windows, GTK's alert dialog, a dialog on Android), named by its `Label`, with its `AccessibilityDescription` read after it, as `ui.Dialog`'s `Title` and `Description` are.
- A scroll view on macOS is an `AXScrollArea` with an `AXScrollBar` on its axis (`axscroll.go`), as AppKit's scroll views are, since it draws its own indicator: the bar is made when a client first asks, its value where the view is scrolled to from 0 to 1, posted with each scroll report. A list's spare cells are `Display: none`, out of what screen readers read, until it binds a row to them.
- An input on macOS is its editor, a field's cell or the text view, which answers through `accessibilityAttributeValue:` with the input's label, help and test ID, as AppKit's text classes read no attributes set on them, and its value text, such as a multiple combobox's chosen items, as `AXValueDescription` where it is not the editor's text. The editor also exposes `Placeholder` through `accessibilityPlaceholderValue` and `AXPlaceholderValue`, following updates and clearing; a multiline input's drawn placeholder, a label of its own, is no element. With `RoleSearchField` it is an `AXTextField` with the `AXSearchField` subrole, with `RoleCombobox` an editable `AXComboBox` with the popup's `AXExpanded`, and with `RoleSpinButton`, a `NumberInput`, an editable `AXIncrementor` whose `AXIncrement` and `AXDecrement` are the input's actions, its view no element in either; a view with `RoleCombobox`, a select's trigger, is an `AXPopUpButton`, and one with `RoleSpinButton` an `AXIncrementor` of its own.
- `RoleStatus` is a polite live region unless its `LiveRegion` says otherwise, and reads its whole text when any of it changes, as ARIA's atomic `status`: WebKit's `AXApplicationStatus` subrole on macOS, a container on iOS, `role=status` with `aria-atomic` on the web, UIA's status bar on Windows, GTK's status and a role description on Android. `RoleSearchField` keeps an input its platform's editable field and adds the search semantics: macOS's `AXSearchField` subrole, iOS's search field trait on the editor, `role=searchbox` on the web, GTK's search box, and an edit control described as a search box on Windows and Android. Android's role descriptions, its mixed, expanded and collapsed states and Windows' search box are in the language the app shows, from `desktop/locales`, which `ItemDirection` carries; the roles Android's classes name, as a button's or a checkbox's, TalkBack says in the system's.
- An `Accessible` view is one element. Without a label of its own, the core labels it with the text inside it, so every platform reads the same words, and the label follows the text.
- Tooltips keep their content mounted under a synthetic root while their overlay is hidden, so `tooltip.go` resolves their current text into the trigger's description before focus. Decorative wrappers pass it to their controls; explicit descriptions win, and text matching the resolved name is omitted. `sentProps` hides every tooltip descendant and clears its role and live region, including hoisted overlays, while the synthetic root excludes the hint from the trigger's name. Hidden content and nested tooltips contribute no text. This extends NSH's visual hints with descriptions shared by all backends (#533).
- Standard actions (`activate`, `increment`, `decrement`, `longpress`, `expand`, `collapse`, `escape`, `magicTap`) take the screen reader's own gestures; others are listed as custom actions. A disabled view's actions are dropped.
- macOS sets NSAccessibility attributes: AXIncrement, AXDecrement and AXCancel are the standard actions, the others `NSAccessibilityCustomAction`s. iOS sets UIAccessibility properties: the adjustable trait's swipes, `accessibilityPerformEscape` and `accessibilityPerformMagicTap`, and `UIAccessibilityCustomAction`s; an escape no element takes goes back, closing the newest popup or screen. Both read an unlabelled element's texts, and announce live regions themselves when a label or a text inside one changes.
- The web maps the props to ARIA. A group hides its children with `aria-hidden`, and a focused view's arrow keys, Escape, Enter and Space perform its standard actions; ARIA has no custom actions, so those are not offered. Selectable `DataTable` rows and cells, and `base.Tree` rows, keep `aria-selected="false"` when unselected; a table without selection leaves the attribute off.
- Android sets `importantForAccessibility`, live regions and screen-reader focus on the view, and range info, hint, state description and actions in its `AccessibilityNodeInfo`. It has no escape or magic tap.
- Windows answers `WM_GETOBJECT` with a UI Automation provider per element, made on demand: a control type, the hint as help text and the Invoke, Toggle, ExpandCollapse, SelectionItem, RangeValue and Value patterns the role and state call for. Views that are no elements are flattened, and controls group the texts inside them as on iOS and Android. An element a client was given raises a property-changed event when its name, description, toggle state, range value, expanded state, selection or field text changes, so Narrator hears a changed label or a toggled switch on the element it is on; a masked field's text is not sent. Live regions raise `LiveRegionChanged`, and announcements are notifications.
- Linux gives each view's widget a role from its construction (GTK keeps it), its label, hint, value and states through `GtkAccessible`, which AT-SPI exposes, and ranges through `GtkAccessibleRange`. Live regions and announcements go through `gtk_accessible_announce`; GTK has no custom actions.
- A canvas's nodes are elements of their own, children of the canvas ([canvas](canvas.md#nodes)).

## Pointer events

Presses, the mouse and secondary clicks carry where they happened, as NSH's `PressEvent`, `MouseEvent` and `ContextMenuEvent` do: `Position` in the view, `PagePosition` in its root view (the surface, or the modal around it) and the `Modifiers` held (`Platform` is Command on Apple platforms, the Windows or Super key elsewhere). A `PressEvent` also counts its `Clicks`.

- `OnPress`, `OnLongPress`, `OnPressDown` and `OnPressUp` take a `PressEvent` with where the press went down and the keys held then. A press from a screen reader or the keyboard is at the view's origin with one click. Keyboard activation on desktops and the web preserves modifiers through every press phase, after the keymap has had the key, except that Windows sends Space and Return held with Alt to the window menu as system keys; screen-reader activation has no modifiers. Physical-keyboard activation on mobile platforms remains a [gap](../roadmap.md#keyboard-popups-and-screen-readers).
- A view takes presses only for its own press handlers, or as a label of a control: an `Active` style, a group or a peer marker adds none, since the event mask also makes the view a keyboard stop and, on the web, a press target that takes text selection from its contents. Such a view is pressed while it takes a press or holds a responder's touch, so a press on a button's face is the button's and a plain view's `Active` style shows nothing.
- `OnMouseEnter`, `OnMouseMove` and `OnMouseLeave` are the DOM's events and take a `MouseEvent`, which adds the `PressedButton` a drag holds; any of the three makes the view follow the mouse, and `OnMouseLeave` says where it was last. `OnMouseMove` hears every move over the view, with or without a button down; what only follows a resting mouse checks `PressedButton`, as the editor's hovers do. Each listening view under the pointer hears a move, innermost first, and the engine merges a view's queued moves. A modifier key pressed or released under a still mouse is a move with the new modifiers: macOS hears it in its event monitor's `flagsChanged`, Windows in the modifiers' `WM_KEYDOWN` and `WM_KEYUP`, Linux in the key controller's `modifiers` signal and the web in `keydown` and `keyup` of the modifier keys.
- Desktop hover and mouse events follow the pointer in unfocused windows too, on macOS, Windows, Linux and the web; leaving a view while its app is in the background removes its hover. macOS reads the `NSEvent`: `clickCount`, `modifierFlags`, and moves from a tracking area with `NSTrackingMouseMoved` and `NSTrackingActiveAlways`. The surface's own moves pick the hovers in the background too, but set the cursor only while the app is active, since macOS shows a background app's window with the active app's cursor; its separate `NSTrackingCursorUpdate` area, active in the active app only as AppKit requires, sets the cursor as the app becomes active under a resting mouse. A tracking area holds the mouse even under an overlay, so a view is hovered only while the surface's hit test at the pointer lands in it, checked on each move and each batch, and after a scroll once it settles ([macOS scroll views](scrolling.md#macos-scroll-views)). A drag goes only to the view it began in, so the surface reports drag moves to the views under the pointer itself.
- Windows counts clicks against the system's double-click time and distance, and reads the keys with `GetKeyState`; Linux takes GTK's press count and the controller's modifier state. Both route moves through the views they hit-test.
- The web counts clicks itself, since pointer events carry none: 500 ms and 4 points apart at most. Moves are mouse `pointermove`s.
- iOS reads the touch's `tapCount` and the event's `modifierFlags`, and hovers with a `UIHoverGestureRecognizer` (a pointer or a hovering Pencil). Android reports a mouse's moves from `setOnHoverListener` and its coming and going with no position, and no button with either ([roadmap](../roadmap.md#finish-the-existing-platforms)). It reads `MotionEvent`'s meta state, counts every press as one click, and sends the page position and keys after the rest of an event.

## Keyboard focus

Desktop web views report focus and blur for the page and its descendants: macOS observes its host window's `firstResponder`, Windows follows WebView2's focus events, and Linux uses a GTK focus controller. Core tracks these events beside inputs, so confined bindings and bindings yielding to text-sensitive menu shortcuts follow page focus too.

A `base.DataTable` exposes its named grid as the keyboard and accessibility focus stop; its pointer hit layer is not an unnamed control.

On desktops, the web and an Apple TV, views that take presses are Tab stops beside the text inputs, unless disabled, hidden, `NoFocus` (a backdrop that closes a popover) or under a newer modal. `View.Focusable`, when set, decides over both, following what it reads: it makes a stop of a view that takes no presses, whose keys come through the keymap and its `OnKeyDown`, and a group's roving focus turns stops on and off with it; Return and Space press the focused one once unless a binding that does not leave them to it takes them (`KeyAlways` or `KeyNotEditing`; a `KeyAuto` binding leaves a focused control the keys it uses, [keys](services.md#keys-and-the-status-bar)), and a click presses without focusing. `Style.Focus` (`focus:`) follows any focus, `Style.FocusVisible` (`focus-visible:`) the focus that shows, and `View.OnFocus` and `OnBlur` hear it come and go. The platform's blur for a view that left the tree finds no view, so when the focused view goes the next commit, or the platform's report of the next focus if it comes first (before that view's `OnFocus`), runs its `OnBlur` once, under the nearest owner still there, as its own usually went with it. On touch-only phones, focus stays on text fields. `Ref.Focus` reaches the same stops as Tab or the TV focus engine; invalid requests leave the current focus alone, and `Ref.Blur` clears only its own view. NSGo extends this contract to Windows as well as NSH's desktop backends so deliberate focus and roving controls agree across desktops.

- macOS puts the views in AppKit's key view loop (`acceptsFirstResponder`, `canBecomeKeyView`, the window recalculating it); the surface, which holds selections, hands Tab to the window's first key view. A modal remembers what had the focus as it came and gives it back as it goes, if the focus fell to the window; a field comes back with the caret at the end.
- Windows keeps the focused field or view on its native surface and routes Tab and activation keys to it; UI Automation reports and moves that same focus. Linux grabs the stop's GTK widget, reports its native focus changes and routes Tab through the same tree order; a press blurs only a focused field or page, so a focused stop keeps the focus, and Return, after a click elsewhere, as on Windows and macOS. Both take the focus off a field or view a modal covers and give it back as the modal goes, unless it went, hid or stopped being a stop meanwhile, or something else has the focus by then. Linux keeps what each modal covered, before the modal's own focus requests and whatever moves the focus inside it, so modals closing one after another each give back theirs.
- The web makes them `tabindex=0`, reports their focus, prevents a pressable's `mousedown` from moving the focus, and makes what a modal covers `inert` until it goes, then gives the focus back.
- Android's `NsgoView` holds native focus while no app control does, as NSH's host does: it is focusable in touch mode with `FOCUS_BEFORE_DESCENDANTS`, takes focus on attach only when the window has none, and takes it back when a field blurs, the keyboard is dismissed or the focused view leaves the tree, so shortcuts work without a field focused. The host draws no focus highlight and exposes only its descendants to accessibility; `AutoFocus` and explicit focus still reach the app's controls. Focusable overlay windows use the same host, while their window flags decide whether they take keys (#413).
- An Apple TV (`focus.go`, the iOS backend where the idiom is TV) makes them the focus engine's items (`canBecomeFocused`) and reports `didUpdateFocusInContext:`; the remote moves the focus, its select button presses the focused view and holding it long-presses. Its Menu button goes back while `ItemHistory` counts somewhere to go back from or a modal shows, else leaves the app, as tvOS's apps do. A modal takes the focus as it comes, through the controller's `preferredFocusEnvironments`, and gives it back as it goes; the focus system moves none while the app is inactive, and focuses the views itself as it becomes active. `ui` lays out a TV as a desktop: `ui.Touch` is false there.

`View.OnKeyDown` hears the keys that go down while its view itself has the focus, a modifier pressed alone included, before the keymap and the view's own Return and Space; returning true consumes the key, as a shortcut recorder takes Command+S from the app's Save. `View.OnKeyUp` hears each of those keys come up at the same view, whether its down was consumed or not and wherever the focus has gone since, with the modifiers still held, a modifier released alone not among them. Their `KeyEvent` names the key as `OnKey` does, with the modifiers held and whether it repeats, and `Shortcut` writes it in `OnKey`'s and `RegisterHotKey`'s form with each modifier by name. The platform asks the engine and waits for the answer on its main thread (`Engine.DispatchKeyDown`, `EventKeyDown`), before it matches the keymap: macOS in its event monitor's `keyDown`, and `flagsChanged` for a modifier, Windows in the message loop's `WM_KEYDOWN` and `WM_SYSKEYDOWN`, Linux in the key controller's `key-pressed`, the web in the document's captured `keydown`, where a consumed key is prevented and goes no further, an Apple TV in `pressesBegan`, and `nsgotest`'s `Key` and `KeyDown`. A modifier alone is reported and never consumed, as no binding takes one and the window follows the modifiers through it. Android, iPhone and iPad report none to a view ([roadmap](../roadmap.md#keyboard-popups-and-screen-readers)).

`core.KeysDown` and `KeyHeld` read the keys held on a window, a frame loop's input: the tree counts each name from the downs that are not repeats and their ups, in one signal, so both Shifts read as one "shift" until both are up, a repeat changes nothing, and an up whose down came only as a repeat, as a key held before the window took the focus, never takes a count below none. The first read sets `MountItem.HeldKeys` on the next `ItemKeymap` for the life of the window, and the platform then reports the downs no focused view hears too, asynchronously with ID 0 and no Count (`Engine.Dispatch`), so a frame loop's engine never holds the main thread; a key already held then stays unknown until pressed again.

The event protocol keeps its masks: `EventKeyDown`'s bit means the view hears keys, going down or up, a view with only `OnKeyUp` answering every synchronous down false. `EventKeyDown` shares `EventKey`'s kind, a binding's press, which always has a Count, where a key down has an ID, or neither. `EventKeyUp` is appended after the other kinds and never goes in a mask, as a kind of 64 or more could not: a mask is 64 bits on the wire and Android's runtime shifts `1L<<kind` into it, so the mask was not widened, and later kinds such as a mouse up follow the same way. A key up is asynchronous (`Engine.Dispatch`), as nothing consumes one, and reaches the engine after its down, as the engine keeps the order of what the platform reports.

Each platform records, per surface, the view and name of each physical key it reported going down (a macOS key code, a Windows scan code and its extended bit, a GDK key code, the web's `KeyboardEvent.code` or else its `key`, an iOS HID usage), a key flagged as a repeat included when it is not recorded yet, and reports an up only for a recorded key, to the recorded view with the recorded name, never gated by where the focus is now. It records nothing while a text input or a web view has the focus or an input method composes, so those keys never reach `OnKeyUp` or the held keys. The ups come from the macOS monitor's `keyUp` and the release side of `flagsChanged`, Windows' `WM_KEYUP` and `WM_SYSKEYUP` before the menu bar takes Alt's, GTK's `key-released`, the web's captured `keyup`, which `owns()` does not gate as the focus may have left the surface, and `pressesEnded` on iOS, which has no auto-repeat. When the window loses the focus the platform reports an up for every recorded key, with no modifiers, and clears its record: macOS on `NSWindowDidResignKeyNotification`, Windows on `WM_KILLFOCUS`, which focus moving into a WebView2 child also sends, and on `WM_ENTERMENULOOP`, as the menu's modal loop takes the ups, Linux when the window stops being active or an embedded surface's focus controller leaves, the web on `blur`, a hidden `visibilitychange` and `pagehide`, and iOS on `UIApplicationWillResignActiveNotification`. The web on a Mac also releases every key as Meta comes up, as browsers there send no `keyup` for keys pressed while Command is held, macOS and the web report a lost up first when a recorded key goes down again without repeating, and Windows releases a held Shift whose side `GetKeyState` shows up, as it sends no `WM_KEYUP` for the first of two Shifts released.

Whether the focus shows is the core's, as NSH 0.5.0 decides CSS's `:focus-visible` (`focusShows`): every backend reports what the user last gave the surface input with, `EventInputModality` with a key other than a modifier or a pointer, pen or finger going down, before the focus moves it causes, through `Engine.InputModality`, which sends only changes. An input that edits always shows its focus; any other view shows it unless the last input was a pointer, so Tab, arrows and shortcuts show it, a press does not, a move the app makes shows it after a key and not after a press, and a key typed while it does not show makes it show. `updateFocusVisible` puts `stateFocusVisible` on the focus and takes it off the view it left, and a part shown focused (`PartStates.Focused`: a list's or a tree's cursor) shows it too while the focus shows. `ui`'s rings are `FocusVisible` styles. Whether the keyboard moved the focus is kept as it moves (`focusByKeyboard`): such a focus shows the tooltip of the view it is on or in (`updateFocusHint`), and the stop it reaches scrolls into view in the scroll views around it (`Ref.Reveal`, nearest on both axes), where a press's scrolls nothing. A `List` keeps the row holding the focus and the rows beside it, and those holding an open overlay, whatever its window, so Tab walks every row and a row's menu stays.

The core keeps one focus per surface for `focus-within:` and `FocusWithin`: inputs and views that take presses report their focus whether or not they style it, and `focusReported` takes the view that gained it as the focus, whatever order a move arrives in; a blur of another view changes nothing, and the root is no focus. The next commit puts `stateFocusWithin` on the focus and the views around it and takes it off those it left (`updateFocusWithin`), walking the two chains and nothing else. The views around are parents in the core's tree, where an overlay is the child of the view the app put it in, so a popup's focus is within the view holding its trigger, as in a React portal.

The app's own requests to move the focus, `Ref.Focus`, an input's `AutoFocus`, `DismissKeyboard` and `Ref.SetAccessibilityFocus` (which moves the keyboard focus too on the web and desktops), pass one gate (`mayMoveFocus`). Those of an owner `Scope.Confine` confined, such as a TSX sandbox, move it only while the focus is already on a view the owner owns, or until the commit after the user's own input landed on one (`Tree.activated`): a press going down or up, completing or held, a secondary click, an accessibility action, a finger going down or lifting, or a menu it showed being chosen from or closed. Otherwise the request is dropped, and the owner's first refusal logs. As a browser lets a cross-origin frame take the focus only on the user's activation, this keeps what a host shows from taking the focus, and with it the keys its confined bindings hear, whenever it likes.

On Linux, `Ref.Focus` and `AutoFocus` place a newly focused single-line field's caret at the end by default. A `Ref.SetSelection` in the same update supplies the range. Tab follows GTK's select-on-focus setting.

- The window ends with the commit rather than after a time, so it is the input's own handling: what that renders may take the focus, a dialog's `AutoFocus` field opened by a press included, on macOS and Android where a press focuses nothing; a request after a timer, or after an `await` of what settles later such as a fetch, is refused. Keys need no window, as they land where the focus already is.
- With the focus nowhere a confined owner is refused too: the keys then reach the host's bindings, and taking the focus would hand them over. So the `AutoFocus` of its first render is refused, even when a press on the host's view showed it: where the focus starts is the host's to decide.
- The same window (`confinedMay`) holds what a confined owner would show over the window, where its frame cannot clip it, and what it would have the screen reader say: a `Modal` mounts nothing, `ShowAlert` answers -1, `PopupMenu` runs its closed callback, `LookUp` answers false and `Announce` is dropped, each kind's first refusal logging. A modal so shown stays until closed or a back takes it away ([layers](core.md#layers-and-navigation)).
- What the user focuses, a tap or click on a field, is the platform's and never gated, nor a modal giving the focus back as it goes. `Ref.Blur` is not gated, as it takes the focus only off its own view, nor `Ref.SendInput`, which takes it on macOS as a click would and which the `webview` capability's `input` holds instead.

## Touch areas

`View.PointerEvents` (`Auto`, `None`, `BoxNone`: only the children, `BoxOnly`: only the view), `HitSlop` and `DelayLongPress` go in `ViewProps`. Hit tests undo each view's transform before checking its bounds and hit slop, following scrolling and the backend's current animation values; pointer and touch positions are in the view's untransformed coordinates. Children transformed outside an unclipped parent remain reachable, including under `BoxNone`; clipping, scroll viewports and confined owners stop the search ([layers](core.md#layers-and-navigation)). `ItemOverflow` gives the area the children's layout frames cover outside the view and says whether a child, or one of theirs, has been drawn transformed: only then is the search not bounded by the area, so hit tests skip untransformed subtrees the point cannot reach. The flag stays once set, as a transition back to no transform still draws the child elsewhere.

- `driver.IntoView` undoes a view's transform by unprojecting its drawn plane; a collapsed plane takes no pointer. `ReachView` checks its local bounds, slop and pointer events, and the children by the area or, once flagged, anywhere.
- macOS overrides `hitTest:` and undoes the layer's presentation transform itself, since AppKit's view conversion leaves it out; a layer never transformed is taken as it is laid out without asking Core Animation. iOS uses UIKit's transformed coordinate conversion and searches the children outside the bounds by the area and flag too. A press ends as a press in the slop too. A macOS scroll view's container asks only the children a point may reach. The raw hit test for window drags, drops, selections and scroll bars returns the deepest view rather than its pressable ancestor, with the same pointer events.
- Android's `Group` hands a touch outside every child's bounds, each child's transform undone, to the topmost child whose slop or area holds it or that is a group not clipping its children, for the rest of the gesture; `None` declines the touch, `BoxNone` leaves it to the children and `BoxOnly` intercepts theirs. A child that declines the probe keeps no `childrenOnly` flag and no gesture views from it, and a finished routed gesture clears the flag too.
- The web needs no area, since the browser finds children outside their parent itself. `pointer-events` classes carry `PointerEvents`, and a slop is a pseudo-element around the view.
- A slop works where the parent's bounds or area hold it, as in UIKit and React Native.
- Long presses wait 500 ms, or the view's `DelayLongPress`: a timer on macOS, iOS, the web and Linux, which no longer uses GTK's long press gesture, and on Android when the delay is the view's own, the system's long click then only taking the press. Windows reports press down, up and long presses from the left button itself and finds the press's view by its own hit test at the release, as Linux does.

## Touches and the responder

`View.OnTouch` hears the fingers and `View.Responder` takes part in React Native's touch responder, as NSH's core runs them for Rust components (`core/touch.go`). Platforms send `EventTouch` with each finger's surface position while a view's mask has it. macOS, iOS, Android, Windows, Linux and the web also snapshot the native hit target and each listening view's local positions when the report arrives, following bound transforms and running animations. The snapshot travels with its event so an engine delay cannot read a later frame's geometry. Capture, bubbling, responder claims and responder callbacks all read it, including a responder on a lifted finger's path while another finger remains. Headless tests snapshot the model's bound transforms; reports without geometry use the core's committed layout and static transforms ([remaining targets](../roadmap.md#finish-the-existing-platforms)).

- The responder is negotiated as in React Native: captures from the outermost in, then from the finger outwards; with a responder, only the views around it are asked, and `Keep` refuses to hand the touches over, or `OnTerminationRequest`, asked each time another view claims them. A claim's `Ask` decides with the `PanGesture`; the responder stays pressed for its `Active` style until the touches end.
- `OnTouchCapture` hears the touches from the outermost view in before `OnTouch` hears them from the finger out, as the DOM's events capture and bubble; `TouchEvent.StopPropagation` ends the round.
- A responder whose claim does not `LetNative`, or whose `BlockNative` says so at the grant (TSX's `onResponderGrant` returning true, as React Native's), sends `ItemBlockNative`: iOS disables the pans of the scroll views around it, Android disallows their interception, the web cancels `touchmove`, and Windows and Linux keep their scroll views from taking a touchscreen's drag. Mouse drags scroll nothing.
- A scroll view that starts dragging first cancels the touches: iOS from `scrollViewWillBeginDragging:`, Android when a scroll view takes the touch, the web through `pointercancel`, and Windows and Linux when a scroll view takes a touchscreen's drag, cancelling all its touches.
- The desktops report the primary mouse button as finger 0, and Windows and Linux each touchscreen touch as a finger from 1, the lowest ID free while it is down (`internal/platform/finger`). Windows reads touches from `WM_POINTER` messages and still hands them to `DefWindowProc`, unless a page or a scroll view takes the touch, so `WM_GESTURE` pinches and rotations and the primary touch's mouse messages go on; those mouse messages, marked as a touch's by `GetMessageExtraInfo`, report no finger 0, and a pen stays the mouse. `RegisterTouchWindow` would end `WM_GESTURE` and `EnableMouseInPointer` would turn every mouse message into a pointer's. Linux reads GDK's touch sequences, on X11 and Wayland, with a capture-phase legacy controller that leaves them to GTK's gestures, and a touchscreen's press reports no finger 0. iOS tracks every touch with a gesture recognizer that never recognizes, Android in its root view's `dispatchTouchEvent` and the web with capturing pointer listeners.
- A `TouchClaim` with `OnPan` claims as the platform activates the view's `PanActivation`, so scroll views share the touch until then: the view becomes the responder exactly when its pan begins (`EventPan`'s first report), and its other claims are not asked.

## Cursors

`Style.Cursor` sets the pointer's look over a view. `Auto` leaves it to the nearest ancestor that names one, and the platform's arrow shows where none does, over pressable views, links and the web's alert buttons too. The diagonal resizes are `CursorNwseResize` and `CursorNeswResize`, which CSS's corner names read as; macOS draws them with AppKit's frame cursors from version 15 and the open hand before it. macOS sets the cursor of the view under the pointer by the same hit test, inputs' I-beam too, since AppKit's cursor rects and text views' tracking areas would show through overlays: NSGo's fields and text views give them up, and a secure field's AppKit-made editor takes a subclass that does as it comes; Windows answers `WM_SETCURSOR` with that view, Linux sets GTK's named cursor, and the web sets CSS `cursor`. A span's `Cursor` goes ahead of its text's over the span's glyphs, not the blank past a line's end: macOS, Windows and Linux find the glyph under the pointer, Linux setting the cursor on the text's widget while the pointer is over the span, and the web sets it on the span's element; a batch that changes a text's span cursors sets the cursor under a still pointer again. Touch platforms ignore it; resizable handles ask for the column or row resize cursor. `ui` names a cursor only for text fields and resize or scrub drags, so its pressables keep the platform's arrow. macOS gives a view its tracking areas only within what its parents show, so a handle's band lies inside its group.

## Gestures

`View.OnPan`, `OnPinch` and `OnRotation` follow gestures the platform recognizes; they report to the engine, which merges each gesture's moves per turn and never its first or last report.

- The platform decides on the main thread when a drag becomes a pan, from the view's `PanActivation`. Until it does, a scroll view around may still take the touch.
- An active pan takes the touch from presses and scroll views.
- A drag or wheel turn scrolls the innermost scroll view under it that can move its content that way, so an inner one passes on only at its edge. A touch or trackpad gesture keeps the scroll view it began with. Android still uses its scroll views' own handling.
- Desktop scroll bars show while their scroll view moves and while the pointer is over it, and can be dragged: the view's own indicator on macOS, `internal/platform/scrollbar`'s on Windows and Linux (Windows fades it as macOS does), and the browser's on the web.
- `View.PanValues` binds a drag to animated values: the platform moves them before it reports each move, so the view follows on the main thread, as NSH's bound values do. A drag through `OnPan` and a signal costs a commit per turn.
- A pinch reports its `Position` in the view: the fingers' middle, or the pointer over a trackpad, so a canvas zooms around it.

`core.PanEvent` reports the current `Position` in the view and `PagePosition` in its page on every phase, alongside its translation and velocity.

Windows shows the overlay scroll indicator for user scrolling and its momentum, not app-owned offset changes.

`View.OnWheel`, which NSH lacks, takes the wheel and touchpad scrolls over a view before the scroll views around it, for what pans and zooms itself, such as a flow diagram; a scroll view inside the view takes its own first. `WheelEvent.Delta` is how far the content moves, a notch about 100 points as browsers scroll, and `Touchpad` tells a touch surface's scroll from a wheel's turns. The engine adds queued turns of one view up rather than replacing them.

| Target | Takes | Touchpad | Glide after the fingers |
| --- | --- | --- | --- |
| macOS | `scrollWheel:` before the surface routes it to scroll views; a gesture and its momentum keep their view | A phase, which only touch surfaces report | The system's momentum, as more changes and an end |
| iOS | Two scroll-only `UIPanGestureRecognizer`s: continuous for a trackpad, discrete for a wheel | The continuous one | The view's own, from the end's `Velocity` |

## File drops

Files dragged from other apps follow NSH's `file-drop.md`. `View.OnFileDrop` receives `file:` URLs, which `core.FileFromURL` opens as a `File`; `OnFileDragEnter` and `OnFileDragLeave` follow the drag.

- The destination is the innermost view under the pointer whose mask has `EventFileDrop`, unless it is disabled; the topmost modal bounds the search. The platform decides on the main thread from the mounted views and answers Copy or nothing.
- Leaving one destination for another reports a leave, then an enter. A deleted destination hears nothing more, since its ID may be reused.
- macOS takes `NSPasteboardTypeFileURL` on the surface, Windows registers an OLE `IDropTarget` written in Go while a view listens, and Linux adds a `GtkDropTarget` for `GdkFileList`. Browsers hide paths, so the web delivers each file as a `blob:` URL, its name as the fragment; the backend keeps the dropped `File` by URL, so `FileFromURL` gives its size, type and time and reads its `Blob` a slice at a time, and fetches a `blob:` URL the page made otherwise.
