# The nsgo tool

`cmd/nsgo` builds, runs, tests and packages apps from their `nsgo.yaml`, shelling out to `go` and, for Apple targets, Xcode's tools. It follows NSH's `nsh-cli` (`nsh/docs/dev/tooling.md` and `embedding.md`). Read this before changing `cmd/nsgo`.

## Output

Command flags go before the directory or file. `parseCommand` rejects misplaced flags with an example and extra paths before loading or changing a project; commands that take no path reject positional arguments too. `nsgo test` lets through the flags `go test` shares with it (`-run`, `-timeout`, `-bench`, `-trace`), which are go test's after the path. Unlike NSH's clap parser, NSGo keeps Go's flags-before-path convention and diagnoses the mistake rather than changing how existing arguments parse.

Every command prints one line per step and the details only when a step fails, as NSH's CLI does (`nsh/crates/nsh-cli/src/ui.rs`, `nsh/docs/dev/tooling.md` "Output"): `✓` a step that finished, `→` where to find something, `•` what a device or server did, `warn` and `error` for problems. The tool's lines are indented two spaces, so the app's own lines stand apart. On a terminal a step that takes a while shows a spinner in its line with what it does at the moment (`stage`: compiling TSX, compiling Go, signing…), and colors are used unless `NO_COLOR` is set; redirected, a step prints its label as it begins (`vetting for android_arm64…`) and its result line when it ends, without a spinner or redraws, so a CI or agent log names the step a slow, failed or interrupted run was on. All of it is stderr.

`nsgo build` and `nsgo dev` start with the NSGo version the tool was built from, the app's name and version and the targets, then what they do. `nsgo build` times each package and measures its directory, so each target's line reads `✓ built macos_arm64 (1.4s, 23.4 MB)`, numbered as `[2/5]` in a build of several targets, which ends with their number, time and total size. Targets building at once show a spinner line each, in the targets' order, and what one says while it builds (`detailIn`, `warnIn`) waits for its `✓` line, so their lines never interleave. `nsgo dev` reports each build's time, the app's start and whether it watches for changes, which it does unless `dev.hot_reload` is false. A tool's output, Go's or Xcode's, appears indented under `error` only when it fails.

`run`, `output` and `goTool` use the process runner in `cmd/nsgo/process.go`. It takes the executable, arguments, directory, environment and output handling. Tests can provide a runner through their context to check signing order, release repository discovery and target-test commands without starting external tools. Callers such as the device test log readers own their pipes and child process lifetimes directly.

Apple package minima follow NSH's native plist keys in `apple.info`: `LSMinimumSystemVersion` and `MinimumOSVersion` (`appleminimum.go`). Packaging emits each once, rejects malformed or below-runtime values, and carries the chosen version into icon compilation and signing projects. iOS-family app links and embedded framework slices take the deployment target; macOS app links use Go 1.27's `-macos`, whose runtime floor is 13.0. iOS stays at least 15.0, tvOS 17.0 and watchOS 26.0; Mac Catalyst's iOS-equivalent framework floor is 16.0 for the Darwin runtime. App Clips retain their independent `app_clip.minimum`.

`icon.windows`, `icon.linux` and `icon.android.png` keep target artwork independent across executables, installers and store assets. Unlike NSH's per-platform map with no fallback, `icon.png` remains the fallback for existing projects; Android keeps its mapping so bitmap and adaptive layers can coexist. `android.uses_cleartext_traffic`, NSH's setting in YAML spelling, adds both the typed Android manifest flag and an all-host network security policy to APKs and App Bundles. It takes precedence over the existing loopback-only policy; embedded AARs leave policy to their host.

## Dev loop

`nsgo dev` (`dev.go`) starts a dev server on `-port` (8080), or the next free port on the same address. It listens on every interface unless `-host` names a local IP address or hostname.

Dev builds take the `nsgodev` tag, which links the dev client `nsgo.Run` starts (`internal/dev`, `client.go`): it follows the server's `/_nsgo/events` and shows a failed build's output in an overlay over the running app, as it shows the app's own render failures. Its Reload button posts `/_nsgo/reload`. Its Command/Control+R binding belongs to the app scope for an app function, so it remains available in other windows after the main view closes; a root-view app keeps the binding on its wrapped root. The overlay's title and buttons come from the dev client's catalog (`internal/dev/locales`), in the language the app shows (`i18n.Language`), so `-lang zh-Hans` shows them in Chinese for an app whose catalog has it, and follow it as it changes. `-fps` and `-lang` start the app with the engine's flags `--nsgo-fps` and `--nsgo-lang` (`nsgo`'s `flags.go`), which `nsgo.Run` takes out of `os.Args` before `main`: as arguments on desktops and through `simctl` or `devicectl`, as an intent's `nsgo-` extras that `NsgoActivity` turns back into arguments on Android, and in the page's query, which `nsgo.js` puts in `go.argv`, on the web. `-limits`, alone or with limits as `tsx.ParseLimits` reads them, runs a TSX app sandboxed as `tsx.View` runs a package, with every module, its bundles replacing it rather than updating it in place: `compiler.devLimits` and `compiler.devCapabilities`, `nsgo.yaml`'s capabilities as base64url JSON, are set through `-X`.

On macOS, Windows and Linux, the native dev tool gives each session a private temporary frame file. AppKit and Windows apply the main view’s last regular window frame before layout and record subsequent changes on a worker. Windows also restores its borderless full-screen mode and keeps the regular frame for when the window leaves it. Both use their normal screen placement checks. GTK applies the last regular default size before layout and requests the last confirmed full-screen mode before showing; the X11 window manager or Wayland compositor places the window. Frame writers are absent from release builds. Windows stages each new build in its own directory so the running executable stays available while its replacement builds. [#658](https://github.com/nsgo-dev/nsgo/issues/658) tracks additional windows, Linux X11 position, macOS full screen, continuous handoff and navigation.

`-target android -android-host` builds the Go app for the development machine with `nsgoandroidhost`, which selects the Android renderer. The debug-only APK hosts a local socket in the Activity and checks the adb daemon's peer credentials and a per-session token. The tool forwards a loopback port to it and launches each successful Go build with that port and the development server in its environment. A Go rebuild stops the previous process and attaches a fresh view inside the same Activity. The tool reinstalls the APK when its resources, precompiled classes, icons or YAML change. Go data and cache use `.nsgo/dev/android-host` on the development machine, and the tool removes the forward when the session ends.

The app gets the server's address through `NSGO_DEV_SERVER`, which the simulator gets as `SIMCTL_CHILD_`; Android, physical Apple devices and mini programs get it with `-ldflags -X`. Android connects to `127.0.0.1` on the device through `adb reverse`, which dials the server's bound address (loopback for a wildcard bind); the rule is removed when the run ends. Physical Apple devices reach the server over the LAN, so a loopback-only listener is not reachable. Mini programs reach it at `127.0.0.1` from the local developer tool. The automation bridge still requires a listener reachable over loopback.

Each run makes a token, 32 random bytes, which every endpoint that reads the app's state, the build's or the project's, or changes them takes, compared in constant time, and refuses without with 401 (`devServer.handle`): `/_nsgo/events`, `/_nsgo/bundle`, `/_nsgo/reload`, `/_nsgo/trace`, `/_nsgo/profile` and DevTools' `out`, `stream`, `project` and `command`. Only the pages' own files, the web target's and DevTools', and `/_nsgo/automation`, which takes the tools' token ([automation](#automation)), go without it. No command line carries it, as every user of the machine can read them. The app gets it as `NSGO_DEV_TOKEN`: in its environment beside the server's address or, on Android, iPhones and mini programs, from a file the build adds to its main package through `-overlay`, which sets the variable as `main` initializes; `-X` would put it on `go build`'s and the linker's command lines, `GOFLAGS` included, and the module cache's files cannot be overlaid. The app takes it out of its environment as it starts or, set by `main`, when its dev client first needs it (`devtools.Token`), so the programs it runs never inherit it, and sends it in `X-NSGo-Token` (`devtools.Fetch`). The pages get it in the fragment of the addresses the tool prints and opens, `#nsgo-token=`, which no request carries; the tool opens them through `osascript`'s input on macOS and elsewhere through a page only its user reads, which sends the browser on and goes when the run ends. Each page moves it at once to the tab's `sessionStorage`, out of the address bar, the tab's history and whatever copies the address, where its reloads and the web target's Go find it, and sends it in the header or, from an `EventSource`, which sends none, as the query's `nsgo-token`. No response allows another origin to read it. The server also answers only requests whose `Host` is an IP address, `localhost` or this machine's name, with `.local` or without, refusing any other with 403, so a site whose name is pointed at this machine reaches nothing from its pages.

The web target is served from the same server; its page shows the overlay itself and loads each build, in the words the page's Go gives it as `nsgoDevMessages`, the same catalog's in the language the app shows, and in English before the app has started. A run ends with the app, and without hot reload a failed first build ends it. `-release` builds as `nsgo build` does, for measuring with `-fps`. `-trace` builds with `-X internal/dev.devTrace=1`: the dev client sets `engine.Trace` for every engine of the process and posts each commit to `/_nsgo/trace`, printed as `nsgo test -trace` prints a batch (`driver.WriteTrace`), labeled by its number, with the app's output. With it `driver.TraceCauses` is set, also by `nsgo test -trace` (`nsgotest`): each signal write records its callers and each computation run its kind, and a tree's commit takes them into `MountBatch.Causes`, which `driver.WriteTrace` prints above the items. A write's site is its first caller outside `core` and NSGo's internal packages, or NSGo's outermost function for writes NSGo made itself, as an animation's; writes that changed no tree count toward the next tree that commits. `-highlight` builds with `-X internal/dev.devHighlight=1`: the dev client mounts `core.UpdateHighlights`, DevTools' overlay, over the app, as it does under `-layout` and `-devtools` with `NoUpdates` set; it outlines the views each commit's items created, moved, restyled or filled anew, other than its own, posting them once the commit is done, so its own commits outline nothing. Dev builds' files take the `nsgodev` tag, so `nsgo check` in NSGo's repository vets the root package with it too, and vets the root package, `internal/dev`, `nsgotest` and the backend with `nsgoautomation` on macOS, Windows, Android, Linux and the web. `-devtools` builds with `-X internal/dev.devDevtools=1` and serves DevTools, plain HTML and JavaScript embedded in the tool (`devtools/`), at `/_nsgo/devtools/`. The dev client sets `devtools.Enabled` before any graph starts, as `Run` starts tracing and DevTools once (`startDevClient`) before it starts the engine, for an app's function as for a root view, so `core` records what DevTools read: the component each scope renders, the signals each owner makes and every computation with how often it ran, each with its site, the first caller outside the packages that run apps, as a whole path for the editor's link; a binding takes its component's. It registers each tree in `internal/devtools`, whose `Surface` the client drives on the graph's goroutine through `Post`: DevTools pages list every one but the first of an app that opens windows, which shows no view, and `-automation`'s agent gets every one ([automation](#automation)). The page's commands reach the app as `devtools` events on `/_nsgo/events`, and the app posts its answers and each commit, a quarter of a second's at a time, to `/_nsgo/devtools/out`, which the server passes to pages following `/_nsgo/devtools/stream`. Both take the run's token, only their JSON content types, which another site's page cannot send without a preflight the server never allows, and no `Origin` but the server's own. Pick and the inspected outline draw in `UpdateHighlights`' overlay, a Topmost overlay ([core](core.md#layers-and-navigation)) over the app's modals too, which takes the pointer while picking and hit-tests past its own views; the recorder hears presses and edits in `Tree.Dispatch` and names views by test ID, then role and label, then text. Unset, `devtools.Enabled` costs a nil check where a signal, a computation or a component is made, a computation runs and a scope goes. With it, and under `-trace` and `nsgo test -trace`, which set it too, each commit's causes name the computations it ran by kind and site with their own time, not counting what their writes ran next, and the app's time before it and its layout's. `driver.Apply` times each batch on the platform's main thread for `driver.Applied`, which the client joins to its commit; every backend applies through it but Android's, whose Java runtime applies batches. A write's site is read as the write is made, and one in tsx's Go asks `devtools.ScriptSite`, which tsx sets for the JS its runtimes run now, mapped by goja or the page through the bundles' source maps, so a TSX app's sites are its TSX lines, relative to the app, which the page joins to the directory `/_nsgo/devtools/project` names. Recorded scrolls are kept per scroll view and become one `ScrollTo` once the user does something else, the view rests or recording ends. A phone is told the address the machine sends from first (`outboundIP`), as virtual networks' interfaces may come before the Wi-Fi's. The web page's Go finds the server at the page's origin and leaves build failures to the page. `-automation` lets tools drive the running app ([automation](#automation)). `-device` picks a simulator by name or UDID, booting it, or an adb serial or an emulator's AVD name.

`-layout`, alone or as `-layout=bounds,grid=4`, which `layoutFlag` checks and writes without spaces, builds with `-X internal/dev.devLayout`, which the dev client reads into `UpdateHighlights.Layout` (`parseDevLayout`). The layout audit (`core/audit.go`, after knothhe's mygo-layout-audit) draws on that overlay, under the update outlines: a canvas that takes no pointer outlines the boxes DevTools read, walking the views as `Elements` lists them and taking each one's presented box (`devChildren`, `devBox`, `devGeometryFrame`) with upstream's colors—following transforms (static, bound/animated and keyframe), layout animations, style transitions and sticky offsets, each box clipped where its scroll views and clipping views cut it, where upstream draws them whole, and a grid. It leaves out hidden subtrees, scroll bars' hosts, what the platform shows apart from the surface and DevTools' own views, while platform-presented iOS sheets mount their own audit layer scoped to the sheet, mapping the surface's presented geometry into the sheet's space (`devSpace`). `driver.GeometrySource` sends native-thread presentation matrices, viewport sizes and unclipped bounds to the graph after complete mounts and animation/scroll frames; versioned snapshots and an initial idle barrier protect reused IDs. macOS/iOS/tvOS read presentation layers, Linux/Windows/watchOS reuse their drawing geometry, the web reads the DOM and Android samples pre-draw matrices. The core caches these for bounds, quad outlines and Pick, with no mirrored animation on those backends. `devDrawn` remains the fallback for backends without feedback, including HarmonyOS and mini programs; observation starts on the first diagnostic read and ends with the tree. While it reads the boxes, a round that moved, resized, hid, restyled, transformed or removed a view, or followed a scroll, draws them again after the `OnLayout` handlers (`bumpAudit`), within the commit's batch, and active animations or transitions request display frames (`tickAudit`) until they settle; otherwise a commit pays a check. The overlay sets those hooks as it mounts (`keepAudit`), so a release build keeps of them only a flag its frames set and nil checks. A readout in the bottom start corner, of numbers and icons only and hidden from assistive technology, stays out of the Tab order where a pointer is present and takes focus where there is none (such as Apple TV), even over an open modal; it shows the surface's size and the measurement, and its buttons toggle the boxes, the grid and the ruler, a second Topmost overlay that takes every press to pick two points and leaves on Escape, which it binds while it measures, on back (including the Apple TV remote's Menu button), which reaches it before the app's modals, and on its button. While measuring, directional keys (and the Apple TV remote's D-pad or touchpad swipe) move a crosshair by the active grid step (8 points by default, or 1 point with Shift), Enter, Space or the remote's Select button picks its point with a live span until the second point locks it, and leaving the ruler in remote mode returns focus to its readout button. Mod+Alt+Shift+L (`auditKey`), which the overlay binds only when `-layout` configures bounds or a grid, so `-highlight` and `-devtools` alone bind no key, shows and hides the audit across every surface via the shared controller; the app's newest binding of the key wins, so the chord is one apps seldom bind, where Mod+Shift+L is the editor's and the gallery's. The page's Layout checkbox shows and hides it across every surface too (`Surface.Layout`) and follows it (`Surface.WatchLayout`). Release builds link none of the overlay (`TestReleaseBuildsLinkNoDevClient`), and `TestDevBuildsLink` builds the dev client for each target, which only this machine's build did before.

`nsgo dev -profile cpu|heap|trace` uses the app's dev client to record the Go process with `runtime/pprof` or `runtime/trace`. The `nsgodev` file `internal/dev/profile.go` starts the request when `nsgo.Run` starts the client and the tool has set the profiling linker flag. The authenticated `/_nsgo/profile` endpoint returns the mode and duration and takes the completed capture. The client posts CPU and heap profiles after collecting them, so a device holds no idle upload open during sampling. It streams execution traces through the authenticated dev connection, buffered by the browser's HTTP adapter on WebAssembly. The server renames a temporary file only after it receives the full body and accepts one completed capture per run. NSH focuses its tool's trace on commit output. NSGo keeps that output on `-trace` and uses `-profile trace` for Go scheduler and goroutine events.
### Component previews

`dev -preview` lists the selected package with and without `nsgopreview` in the target's build environment. `preview.go` generates a small command importing the `PreviewXxx` fixtures found in files that only the preview tag enabled. Its temporary directory is inside the component's module and is excluded from ordinary Go package searches. The existing development loop builds the command, watches the component and its dependencies and regenerates the command on saves. The host reads the app's catalogs and theme, copies its resources from their original directory and stores its controls under a separate app ID so relaunching keeps the selected fixtures and their display settings.

On iOS simulators, the dev session watches package resources and icons and builds the next bundle before it stops the running app. When the build's inputs, Info.plist and resource seal match the installation, it copies the signed executable to a new inode in the installed bundle and relaunches. A changed bundle or a failed replacement uses a full install.

`dev -debug` retains DWARF, disables Go optimization and starts the native desktop executable through the `dlv` on `PATH`. Delve's multi-client server binds to an available IPv4 loopback port and keeps that port across successful reloads. Each build uses a new directory so the earlier executable can remain open while its replacement builds on Windows. The normal app flags and dev environment reach the debuggee. The tool monitors Delve's state for app exit and detaches with the debuggee marked for termination when a run is replaced or stopped.
## Automation

`nsgo dev -automation` (`automation.go`) builds with the `nsgoautomation` tag beside `nsgodev`, which links `nsgotest`'s agent into the app (`internal/dev/automation.go`), and relays tools' requests to it; it refuses `-release` and, so far, every target but `web`, `android`, the mini programs (`miniprogram_wechat`, `miniprogram_qq`, `miniprogram_alipay` and `miniprogram_douyin`), `native` on Windows, macOS and Linux, and `ios`, `tvos`, `watchos`, `ios_simulator`, `tvos_simulator` and `watchos_simulator` on macOS ([roadmap](../roadmap.md#automation)). On Android, `-automation` marks the APK `android:debuggable="true"`, launches `NsgoActivity` with `--ez nsgo.automation true` so the runtime creates `TestAgent` (release and non-debuggable builds never instantiate it), and reaches the server at `127.0.0.1` over `adb reverse`. For simulators, `simulatorEnv` passes the dev server URL and token through `SIMCTL_CHILD_` variables. For physical Apple devices (`ios`, `tvos`, `watchos`), `configureAppleDeviceDev` stamps the Mac's LAN dev server URL into the binary with `-ldflags -X` (as `devServer`), gives the app the run's token through `devTokenFile`'s main-package `-overlay` (so no command line carries it), signs with Xcode and launches through `xcrun devicectl`. The agent is DevTools' (`devtools.Automation`): the dev client sets `devtools.Enabled` for it as for `-devtools` (on `nsgo.Run` and `nsgo.NewView`), and DevTools' registry hands it each surface `core` registers, the app's own first one too, which pages leave out. It follows every graph of the process (`Surface.Follow`), telling their surfaces apart by `(graph, surface ID)` and assigning each listed window, scene or embedded view a unique positive automation window ID (reporting `Window.Graph`), hearing each batch they commit and each event they dispatch until they unregister, modeling each as a test's app on a target and acting through the backend's live surfaces with native input ([testing](testing.md#driving-a-running-app)). Dev builds without the flag link none of it, and `-fps` readings with it count the models' work and what DevTools record.

- On `-target web`, `webAutomationSession` opens a headless Chromium browser over the Chrome DevTools Protocol (`cdp.go`, `openWebAutomation` in `testweb.go`), installs the `nsgoTest` binding at 1280×800 CSS pixels (scale 2), navigates to `devServer.pageURL` with the run's token in `#nsgo-token=` (which the page moves to `sessionStorage` so reloads keep it and `location.href` drops it), forwards `Runtime.consoleAPICalled` and `Runtime.exceptionThrown` to `appConsole` (feeding `logs`), keeps the browser across rebuilds and closes it when `dev` exits.
- The app connects out once `dev.Start` runs, over DevTools' channel (`internal/dev/devtools.go`): it follows `/_nsgo/events?devtools`, its DevTools stream, which is the one the tools' requests reach, as `automation` events, and posts each answer as an `automation` message to `/_nsgo/devtools/out`, at once rather than with a quarter of a second's commits, both with the run's token. The server passes answers to no DevTools page, and a page's commands, sent as `devtools` events, never make a request; without `-devtools` the app takes none. A second app's DevTools stream is refused while one is connected, and tries again each second.
- Tools post requests to `/_nsgo/automation` from this machine's loopback, with no `Origin` header, which keeps web pages out, and the tools' token as a bearer; `status`, `logs` (the app's last 2000 lines) and `reload` the tool answers itself. The protocol, `internal/automation`, is internal and unversioned, as the tool and the app come from one module version; MCP, `automation` and `nsgotest` are the public interfaces.
- The session file `.nsgo/automation.yaml`, readable by its user alone, holds the server's address, the tools' token, the process and the target. It goes as `dev` ends, and a second `dev -automation` for the app is refused while the first runs and its server answers `status` with the file's token, so the file a crashed one left is replaced even when another process took its ID.
- The app runs with its real data directories, as `dev` runs it, not a test's temporary ones.

`nsgo mcp` (`mcp.go`, on `github.com/modelcontextprotocol/go-sdk`) serves MCP on standard input and output, the tool's other output going to standard error. It uses the session the file names, or starts `nsgo dev -automation` with its own flags as a child, which it stops as the client leaves. Each tool is a request with that request's params as its input, so one definition gives both their schemas: `status`, `windows`, `snapshot`, `find`, `press`, `type`, `key`, `scroll`, `drag`, `hover`, `menu`, `alert`, `wait`, `screenshot` (an `image/png`), `logs` and `reload`. A rebuild restarts the app, so `status`'s run count grows and the `view:` refs of an earlier run are stale. What tools list, find and press is the app's alone: under `-devtools`, `-highlight` or `-layout` the agent leaves DevTools' overlay (`devtools.OverlayTestID`) out, as the page's `Elements` does.

Go apps and libraries call `automation.Register` on the graph goroutine with a scope, a unique name, a description, an object input schema and a handler. The graph keeps the registration until that scope's cleanup. The MCP server reads the catalog through the same authenticated bridge on `tools/list` and checks for changes while connected, so registrations, scope cleanup and app rebuilds update the list. Discovery gives way to an in-flight request. The agent uses `Surface.Post` to read the catalog or call a handler on the graph goroutine, under its registering scope. A handler receives raw JSON arguments, validates its inputs and returns a JSON-encodable value or an error; an automation call gives it up to one minute, including time in the engine's queue. The registry also builds for headless and target tests, where `automation.Call` runs the same handler inside `nsgotest.App.Post`. In other builds registration is a no-op and the protocol and registry are absent from the app.

`TestAutomationEndToEnd` builds `testdata/automation` with the tags and drives it through a hub with posted events, the menu bar, the Dock or Jump List menu and alerts. It also lists and calls a fixture tool over a separate `go tool nsgo mcp` process. It opens a window, so it runs only with `NSGO_AUTOMATION_E2E=1` on macOS or Windows. `TestSimulatorAutomationEndToEnd` builds and launches `testdata/automation` in an iOS simulator with `SIMCTL_CHILD_` and drives it through the hub when `NSGO_SIMULATOR_E2E=1`. `TestWebAutomationEndToEnd` builds the same app for the web and drives it end to end in a headless browser through both the hub and `nsgo mcp`, skipping when no Chromium browser is installed. On Linux, `TestLinuxAutomationEndToEnd` starts `nsgo mcp` as a client would and drives the GTK app it starts with `nsgo dev -automation`. Run it with `NSGO_AUTOMATION_E2E=1 xvfb-run -a go tool nsgo test -run TestLinuxAutomationEndToEnd ./cmd/nsgo`.

## TSX apps

The tool finds a package's TSX entries in its `compiler.App(src, "App.tsx")` calls (`bundle.go`), compiles each with `tsx/bundler` from the app's directory and adds the bundles to the package with a file calling `compiler.Bundled`, through `go -overlay`, built with the `nsgo_bundled` tag, which leaves the compiler out. The overlay names the package's directory as `$PWD` spells it and by its real path, since `go` names the files by either.

`nsgo dev` compiles hot bundles ([TSX](tsx.md#developing)). With a detected entry, it watches the bundle source files separately from the Go build inputs: a change to those sources alone compiles the TSX again and sends `bundle <entry>` over `/_nsgo/events`, which `/_nsgo/bundle?entry=` serves, with no Go build; a failed compile shows as a failed build does. Without an entry, embedded files stay in the Go rebuild set regardless of extension.

A web release's bundles are split ([TSX](tsx.md#split-bundles)): `buildWeb` writes each chunk as `chunks/<module>.<10 hex>.js` before the Go build, and the file the overlay adds gives `compiler.BundledChunks` their URLs.

## New apps

`nsgo init` (`init.go`) writes an app of `-template` `go` (the default), `tsx` or `mixed`, NSH's `ts` and `mixed` templates: `nsgo.yaml` and tests each, and for TSX a main package embedding the sources, `App.tsx`, `app.test.tsx`, `tsconfig.json` and `.gitignore`; `mixed`'s `App.tsx` imports a Go component, function and class `native.go` registers under `<slug>/native`. It refuses a directory holding any of its files. `TestInitTemplates` writes each and runs its tests against the checkout.

`-template <module>[@version][#<name>]` adds a template from a Go module's `template/` directory, or `template/<name>/` when `#<name>` is given, and `-list` prints the templates a module offers. `init_module.go` runs `go mod download` outside the caller's workspace, preserving Go's cache, proxy and checksum settings and disabling direct repository downloads. It renders `main.go`, `nsgo.yaml` and `*.tmpl` with the built-in templates' fields, then copies the other files as-is. It checks output paths before writing and removes files it creates if a write fails. NSH has no module templates.

## Catalogs

`i18n.go`, `i18n_message.go`, `i18n_gen.go` and `i18n_build.go` check packages' catalogs and write their Go code ([languages](languages.md#the-tool)): `dev`, `build` and `test` before they compile, `check` without writing, and `nsgo i18n` for one directory. `dev` watches the YAML files of the directories it watches, and the app's catalogs before it imports them.

## Modules

The first step of `dev`, each rebuild's included, and of `build`, `check` and `test` lists the app's packages and their dependencies (`appPackages` in `i18n_build.go`). When go list says the module's `go.mod` or `go.sum` lacks what one of them comes from, as after pasting an app that imports `ui` into a module made with `go get github.com/nsgo-dev/nsgo`, the tool runs `go mod tidy` and lists them again, so the build after it finds them. It then requires `tsx` at the NSGo version the app requires, since the types `check` and `dev` write import it through an overlay `go mod tidy` cannot see; writing them after a tidy the user ran does the same.

Every go command the tool runs for an app, this listing included, takes the same tags (`goTags` in `tags.go`): those of `-tags` in `GOFLAGS`, from the environment or `go env -w`, then `build.tags`, then the tool's own for the command (`nsgodev` and `nsgoautomation` for `dev`, `nsgo_bundled` for a TSX app's bundle, `nsgotest` for target tests, `nsgocheck` for headless ones, `nsgowatch`, the mini programs' and `nsgoembed`). The go command lets a `-tags` on the command line replace the one in `GOFLAGS`, so the tool passes them all as one, and only when there are any; it never sets `GOFLAGS` itself, so the rest of the app's applies.

Every go command that links the app takes `build.ldflags`, with the values of `build`'s and `test`'s `-ldflags` after them, at the head of the tool's own `-ldflags` (`project.ldflags`); headless tests pass them alone. The linker keeps a variable's last `-X`, so the app stamps its own variables but cannot replace the identity, update or dev values the tool sets.

### License notices

Standalone builds list the target's Go packages with the release tags, build environment and TSX overlay. The universal macOS build takes the union of both architectures. `licenses.go` reads license and notice files from the selected module roots and package directories, including local replacements, vendored packages and the Go toolchain. Main modules — the app's own module and sibling modules in a Go workspace (`Module.Main`) — are treated as first-party: their license files are included when present, and they are exempt from `licenses.unknown` and `licenses.copyleft`. For third-party modules, it keeps the original text and uses Google's license classifier to apply `licenses.unknown`, `licenses.copyleft` and exact module exceptions. The shared resource walk puts `THIRD_PARTY_NOTICES.txt` in the package. The main package's generated overlay supplies the same string to `core.ThirdPartyNotices`.

### Native libraries

`package_natives.go` reads `nsgo-natives.yaml` only from the Go packages selected by the executable's target, tags and overlay, through the same dependency listing as license notices. Version 1 declares individual desktop targets with names, URL or package-local path, SHA-256 and license paths ([author contract](../public/en/native-libraries.md)). Explicit native license groups use the owning module's license policy; their texts join the compiled and packaged notices without local checkout paths. Vendored package notices follow the selected vendor directory even when Go reports an original replacement's module directory.

The tool checks binary format and architecture, confines local files and licenses to the package, rejects filename conflicts and streams copies with checksum verification. URL files are content-addressed under the user cache, verified on reuse, written atomically and guarded by a process-independent file lock. Libraries enter `Contents/Frameworks` on macOS or the executable directory on Windows and Linux before existing signing and installer steps. Universal macOS builds require identical library-name sets, thin publisher fat assets per target and join the two slices before signing. Windows signs the executable and DLLs even when installers are disabled. Development and desktop target tests share discovery and copying; other targets are an explicit packaging gap in the roadmap.

NSH's packager supplies the packaging order; package YAML is NSGo's extension so Go dependencies need no app-specific post-build step. NSGo's built-in libghostty and updater packaging remain in their owning helpers.

## Checking

`nsgo check` (`check.go`) checks the catalogs, runs `go vet ./...` and, for an app with a `tsconfig.json`, as only a TSX app has, writes the declarations of the modules its TSX imports to `.nsgo/types`, with `.nsgo/tsconfig.json`, and runs TypeScript 7's checker (`tsgo`, a pinned version of `github.com/microsoft/typescript-go` that `go run` builds and caches) on the app's `tsconfig.json`, which extends it. In NSGo's own repository it vets the root again with the `nsgodev` tag, and macOS, Windows, Linux and web dev builds with `nsgoautomation` too, tags only `nsgo dev` sets, so the dev client and the automation's agent are checked as well. A directory without `nsgo.yaml`, such as the repository's root, is checked as a tree of packages: catalogs and `go vet` alone.

`-target` vets the expanded target names instead of the host and the dev client, in the environment each build sets (`GOOS`, `GOARCH`, cgo with Xcode's clang for iOS). The primary `go vet ./...` skips a target only on Go's complete unmatched-pattern diagnostic; host vet and the repository's additional vets still treat it as a failure. In NSGo's repository each target also vets `internal/platform/...` with `nsgotest`, checking its test hosts against `testhost.Surface`; HarmonyOS adds `nsgoharmony`, as its app builds do. `all` is `build`'s list of what a Mac with Go and Xcode builds, but `check` skips its Apple mobile targets off macOS, or on a Mac whose SDK or clang lookup for one fails, such as an Xcode without the watchOS platform. An explicitly named Apple target, even beside `all`, still requires its SDK, and `build -target all` still needs Xcode.

The tool reports empty-package and unavailable-SDK skips separately in target order, retaining the first lookup error in an SDK group. If every target is skipped, the command fails because nothing was vetted. `-jobs n` vets up to n targets at once and passes `-p n` to each `go vet`, so one check bounds the compilers it runs, n² at most; without it targets go one at a time with go's own `-p`. A target whose vet fails does not stop the others: their errors are returned together in the targets' order, and cancellation starts no more. A check holds the operating system's lock on `.nsgo/check.lock` at its module's root (`lockCheck`; `flock`, or `LockFileEx` on Windows), so a second check in the module names the first's pid and waits, and a killed check's lock goes with its process.

The declarations come from the app's own program: the tool builds its main package with a file, added through the overlay, whose `init` runs after the package's others, so after every `tsx.Register`, writes them and exits before `main`. It checks with `go list` that the file is in the package before it builds, so the app itself never runs. A directory with `nsgo.yaml` but no Go, such as the TSX app a package holds, has nothing to vet, and its declarations are those of every module NSGo gives, from a main package the tool writes in `.nsgo/typesmain` importing them all, since the host decides which its packages may import. `nsgo dev` writes them too, for editors, after each Go build of an app with a `tsconfig.json` once the app has started; a failure only warns.

Go vet and tests, headless or on a target, follow the build's JSON policy (`smallJSON` in `build.go`). The tool adds `nojsonv2` to the experiments reported by `go env GOEXPERIMENT` unless that setting, from the environment or `go env -w`, already names `jsonv2` or `nojsonv2`, or the command's packages or dependencies import `encoding/json/v2` or `encoding/json/jsontext`. Test imports count when vetting or building tests. The first `encoding/json` implementation is already the default in Go 1.26; on Go 1.27 it links about 1 MB less on the web, 450 KB less on Android and 100 to 450 KB less on desktop targets. Mini program builds and target checks always use the first implementation to fit the package limit.

## Doctor

`nsgo doctor` (`doctor.go`) looks at the machine, starting nothing, and lists the tools it found, then each target with whether it builds and runs there: `✓`, `✗` with what to install or connect, or `–` for what no tool could change, such as another system's apps or Apple's on a Mac-less machine. It reuses the lookups the commands make, `findAdb`, `findNDK`, `findBrowser`, `simulators`, `iosDevices` and `canOpenMiniProgram`, so it and they agree, and reads Linux's libraries from the library directories, as the backend's `dlopen` would find them, with GTK's version from its file's name. It fails only when Go is missing, or older than go.mod's and unable to switch to it: GOTOOLCHAIN `auto` or `+auto` downloads it, `path` or `+path` needs its toolchain (`go1.27.3`) on PATH, and `local` or a Go before 1.21 never switches.

## Tests

`nsgo test` (`test.go`) runs `go test -json` and prints a line per test, with a test running the package's `*.test.tsx` files (`tsxtest.Run`) added through the overlay when it has any, a failure's output under it (a subtest's under its own line), a tally, and with `-junit` a JUnit report, a suite per package; skipped cases keep their diagnostic messages so CI can explain why they did not run.

If the process exits without ending its running tests, as a panic on another goroutine or the timeout ends it, those tests fail with their captured output, including the panic and stack, in both the console and the JUnit report; a crash outside any test, in an `init` function or a benchmark, shows under its package and, unlike a package that did not build (`FailedBuild`), is not called a build failure. Compiler `build-fail` events that no package failure claims, as in headless `-- -c` runs, become build failures when that command's event stream ends, keeping their diagnostics and run label in the console and JUnit without duplicating ordinary package failures.

Given a TSX entry rather than a directory, it runs `TestSteps` instead, which opens the entry on the network, lets it run 1.2 s and takes the steps standard input holds, none from a terminal (`tsxtest.RunSteps`, NSH's `nsh test <entry>`). A directory without `nsgo.yaml` runs every package under it, and one ending in `/...` names its tree, so the tool alone tests libraries and this repository, on a simulator or phone too, where the app the tests run in takes the ID `generatedID` makes of the directory's name, `dev.nsgo.` and its ASCII letters and digits, since Android's packages refuse hyphens and Apple's bundle IDs underscores; the TSX tests it adds skip `testdata` and directories holding an `nsgo.yaml` or `go.mod` of their own. `-bench` passes `-bench` and, unless `-run` is given, `-run '^$'`; `go test -json` ends benchmarks with no event, so each result line it prints counts as a passed test. `-run` filters; `-trace` sets `NSGO_TEST_TRACE`, under which `nsgotest` prints each batch under its step with its items and the commit's time.

An active headless `-fuzz` (or `-test.fuzz`) selects `.` instead of `./...` for catalog preparation, the `go list` probe for the JSON policy, and `go test`, because Go can fuzz only one package. Flags passed to the test binary after `-args` do not select fuzzing.

In NSGo's own repository, a headless run of the root, `internal` or `internal/dev` then tests `internal/dev` again with `nsgodev`, as `nsgo check` vets it, unless the run fuzzes or already has that tag. This covers the dev client's tests in CI with the same filters, flags and environment, a later `-tags` taking the earlier's place as in Go, and with ` [nsgodev]` after package names in the shared tally and JUnit report. It runs after the first fails, as go test goes on past a failing package, but not after an interruption, and its `-coverprofile` is appended to the first run's.

After the path and optional `--`, headless runs forward Go test arguments. Target runs forward `-short`, `-count`, `-cpu`, `-parallel`, `-failfast` and `-fullpath` as test-binary flags, accepting their `-test.` aliases too; unsupported arguments fail before listing, building or finding a device (`parseTargetTestFlags`). On a target `-run` and `-timeout` belong before the path so discovery and the process deadline agree. Discovery uses the top-level part of a subtest filter and receives the supported runtime flags too. A group whose children all skipped is reported and counted as skipped, recursively, unless the group itself failed; a group with a passing child stays passed. This applies to headless and target runs, and its JUnit skip message includes the children's reasons. Each target process yields one result that counts in the tally whatever its name (`parseTestOutput`): a run whose `-run` reached exactly one subtest at the depth it selects, as `Test/sub` or `Test/sub/leaf` does, reports that subtest unless the test failed outside it, and otherwise the top-level test reports its own result, never its first subtest's. Libraries keep Go's in-process `-count` and `-cpu` repetitions, whose results combine elapsed time and preserve a failure over a pass or skip. A package that links the native host launches a fresh process for each count and CPU combination, because phone and web hosts can open only one app per process; repeated results carry `[run N]`, screenshots go into `run-N` subdirectories, and each invocation has its own timeout. A nonpositive count reports zero tests, and `-failfast` stops launching further tests and repetitions after the first failure.

`-target` runs the tests on a platform, a process per test ([testing](testing.md#on-a-platform)), the TSX ones among them; a package whose tests link no platform, as a library's, runs headless in the target's runtime, so `tsx`'s run on the page's engine with `-target web`: the test binary carries the app's TSX, data and assets, since it runs where its sources are not, and starts the app from the bundles compiled ahead, as packages do. `-fps` has the test hosts of macOS, Windows, Linux, the iOS simulator and the web log their performance monitor's readings each second, and Android's the engine's alone, with no frames, which the tool prints as they come (`NSGO_TEST_FPS`, `testhost.Options.FPS`), as it prints a test's marks of what they measure (`nsgotest`'s `Mark`, logged as `nsgo: perf mark`) with or without it. `-env KEY=VALUE` adds to the tests' environment on every target, the only variables a phone's tests see. macOS, Windows and Linux on this machine, the web in a headless Chrome, Chromium or Edge it finds (or `NSGO_BROWSER`) over the DevTools protocol (`cdp.go`, on `x/net/websocket`), the iOS, tvOS and watchOS simulators through `simctl launch`, or `simctl spawn` for a package whose tests do not start the native test host from `TestMain` (a watch's test host enters touches where the SwiftUI host's do, at Go's hit testing, and scrolls a scroll view as `ScrollTo` does, since watchOS posts no touches for an app), and Android through `am start` with the test in an intent extra and its output read back from the device's log.

Web tests use a temporary browser profile. On macOS they prefer Chrome for Testing and disable code-signature bundle cloning. The tool asks the connected browser to close over CDP at completion or cancellation. When the connection is unavailable, macOS and Linux send SIGTERM. The browser gets ten seconds before a forced stop.

The Apple simulator and physical-device launchers do not return the app's exit status. Native test hosts mark each run's start and exit code with the token the tool passes in `NSGO_TEST_RUN`; the simulator runner merges stdout and stderr, keeps panic output and accepts a completed result even when `simctl` fails to attach after the app exits. It ends the console bridge once a result arrives, so a stalled bridge cannot replace that result with a timeout; terminating the app during cleanup takes at most five seconds. As NSH does, simulator setup waits for `simctl bootstatus -b` before installing or launching, since `Booted` can precede SpringBoard's readiness. A missing exit mark fails the run instead of reporting a successful launcher's exit code as the test's, and an app that ends before the start mark fails with simctl's error or, when simctl succeeded, a hint that `TestMain` must call `nsgotest.Main`. A package whose tests link no native host, or link it without a `TestMain`, runs through `simctl spawn`, which returns its process status. `TestSimulatorProcessResults` exercises fast passes and panics in a hosted package, a library and a package that links the host without starting it on an iPhone simulator when `NSGO_SIMULATOR_E2E=1`; `NSGO_SIMULATOR_DEVICE` selects one.

Android target tests check `dumpsys power`, `dumpsys window policy` and `dumpsys trust` before building and before each process starts (`testscreen.go`); whether a credential guards the keyguard is the trust manager's `deviceLocked`, since the keyguard delegate's `secure` can stay `true` with only a swipe lock (Android 9 and 15 after a cold boot). They wake a sleeping display and dismiss a keyguard without a credential, waiting up to 15 seconds for it to be ready. A secure lock or unreadable state fails with the device serial before the test starts. A failed `adb` read is retried three times, 100 ms apart and after `adb wait-for-device` when adb lost the transport (exit status 255); one that keeps failing is a device-lost error (`targetDeviceLostError`), which ends the run once, after the summary of the tests that ran, rather than failing every remaining test. No persistent device settings change.

Android's runtime keeps the test's log listener until stderr drains, even when the protocol pipe ends first. After the child exits, a missing exit or error mark produces `nsgo-test-error` with its process status, so a panic or `os.Exit`, including one before the Go host starts, fails immediately with its output instead of waiting out the test's timeout while the device's log stays open. Target tests install under a `.nsgotest` bundle identity and uninstall that identity after the run, leaving the app's installed build in place. `TestAndroidProcessExitResults` checks those results and JUnit output on a device when `NSGO_ANDROID_E2E=1`; `NSGO_ANDROID_DEVICE` selects one.

`web.base` fixes a packaged web app's relative assets to its deployed directory (an absolute same-origin path), so opening a deep application address loads the same bootstrap. The dev server strips that deployment prefix and serves the entry for missing HTML navigation routes while keeping missing asset requests as errors; [application addresses](../public/en/addresses.md) covers the URL/history contract.

## Packages

`nsgo build` strips symbols, paths and VCS stamps (`nsgo dev` keeps symbols unless `-release`) and writes a directory per target under `build.output`, building `build.jobs` targets at once (`-jobs`; half the CPUs by default, and never more than the CPUs), each `go build` with `-p` of the CPUs divided among them (`compileWorkers`), so the compilers of a build stay within the CPU count and a lone target keeps them all. Each builds from a copy of the project, which holds what one target's build sets, and the caches they share are written whole by content or under a lock, as the Android debug key is; the first target to fail stops the others and leaves no directory:

- macOS: `<name>.app`, signed with `sign.identity`, else ad hoc. iOS and tvOS: `<name>.app` and `<name>.ipa`, signed with `sign.profile`, else unsigned; tvOS's are iOS's (`appleOS` in `ios.go`) with its SDK, `GOOS=ios` still, its device family and an icon the Apple TV layers. watchOS: `<name>.app` alone, the Go executable built with the `nsgowatch` tag and the SwiftUI host (`watch/Host.swift`, `watchos.go`) compiled by swiftc into an object its external linker takes, ad hoc signed for the simulator and unsigned for devices; a watch-only app, arm64 alone, so watchOS 26 on Series 9, Ultra 2 and later. Android: `<name>.apk`, signed with `sign.keystore`, else the project's debug key.
- Windows and Linux: the executable with the resources beside it. The Windows executable links one resource object the tool writes into the main package's directory for the build (`writeWindowsResources` in `icon.go`, `winres.go`), as the linker takes `.rsrc` from one object alone: the icon, when the app has one, and a version resource, always, which Explorer's Details, Task Manager and the startup list read. Its fixed version is `version`'s four numbers, with `build_number` the fourth where it fits; `FileVersion` and `ProductVersion` are `version`; `InternalName` and `OriginalFilename` are `<name>.exe`; `CompanyName` is `windows.publisher`, else `windows.store.publisher_name`; `LegalCopyright` is `copyright`; and `ProductName` and `FileDescription` are the catalogs' `appName`, else `name`. Each language Windows has an ID for gets a version resource of its own, which the loader picks by the user's language; the source's is filed as the user's default language (`0x0400`), which it falls back to, as plain language neutral would win over the user's language and the lowest ID would win otherwise. The `.com` companion links the same object. An app's own `.syso` holding resources for the build's architecture replaces the tool's, with a warning.
- With `-embed`, for apps of their own to embed ([embedding](embedding.md)): iOS's `<module>.xcframework` (of dynamic frameworks with `-dynamic`) with `<name>Resources`, Android's `<name>.aar`, and no package for other targets.
- Web: `index.html`, `manifest.webmanifest`, `nsgo.json`, which names the rest for the loader, and every other file named by its content (`app.<10 hex>.wasm`, `nsgo.<10 hex>.js`, `page.<10 hex>.css`, `mount.<10 hex>.js`, `web.host`'s module as `host.<10 hex>.js`, a TSX app's bundle and chunks, the scripts its realm runs as `nsgo-runtime.<10 hex>.js` and each resource), so hosts cache them for good. The build writes smaller Brotli and gzip representations beside the original module, and the preview server serves them at its URL according to `Accept-Encoding` with `Vary: Accept-Encoding`. The page runs the app with the loader, from files of its own and none inline, so a Content-Security-Policy needs no `'unsafe-eval'` ([embedding](embedding.md#on-the-web)). It never zooms, as a window does not: its viewport is not user-scalable, its elements pan but leave pinches and double taps to the views that zoom, and Safari's `gesturestart` is cancelled, as Safari ignores the viewport.
- Mini programs (`miniprogram_wechat`, `_qq`, `_alipay`, `_douyin`): a project for the platform's developer tool, its runtime from `miniprogram/common` and the platform's render layer, and the module brotli compressed in the subpackage `nsgo-app`, with `miniprogram.appid`'s entry for the platform (else the AppID the tool wrote, else WeChat's tourist one) and `miniprogram.custom_navigation`. It is always stripped (`-s -w`) and left out of `all`, which says so, while `miniprogram` names the four; past 2 MB it is built again without inlining, then refused ([mini programs](miniprogram.md#the-package)). Release builds (`nsgo build` and `nsgo dev -release`) omit the dev client; `nsgo dev` builds mini programs with `nsgodev` and the dev client reaching the dev server through `nsgoMP.api.request` without linking `net/http` or `runtime/pprof`, so `-devtools`, `-highlight`, `-layout` and `-trace` reach them. `-run` and `nsgo dev` open WeChat's with DevTools' command line, whose service port must be on, closing and auto-opening the project after each build so DevTools compiles the fresh files, and the others with their apps on macOS, once a session.

NSGo adds optional offline web delivery to NSH's content-addressed site layout. A release with `web.offline` registers `nsgo-sw.js` after mounting the app. Its installation verifies and caches the page and its packaged files under a release digest scoped to the site's directory. Online navigations revalidate the page, whose manifest and dependencies have content-addressed names. The active worker serves cached files by exact URL and falls back to its cached page when the network is unreachable. Activation waits for the previous worker's pages to close before deleting that worker's cache. A TSX release's realm frame shows `realm.<10 hex>.html`, an empty page of the release, rather than about:blank, which Chrome leaves outside the worker, so its scripts and lazy chunks load offline; a host that refuses framing gets the about:blank frame back.

`resources/` ships at each package's resource root: beside the executable on Windows and Linux, beside the page on the web, in the bundle's `Contents/Resources` on macOS, at the bundle's root on iOS and in the APK's assets on Android, which with iOS leave out the paths `mobile.exclude_resources` lists. `imageload.ResourceRoot`, the web backend and Android's APK reader resolve `asset:` and font paths against it. App icons are drawn in Go; an Apple TV's is `icon.tvos`, Xcode's brand assets collection or a wide image, else the PNG over its own edges' color, as a two-layer image stack with top shelf images, since `actool` compiles no `.icon` for tvOS; an Apple Watch's is `icon.watchos`, its own `.icon` or square image, else `icon.apple`, which actool draws in circles; `actool` compiles Apple's `.icon` files, its output kept in the user cache by its version and the icon's content, and a Windows icon links from a `.syso` in the app's package directory, the only place Go links one from.

Native libraries come with the packages that hold them (`natives.go`): when the app's build links `base/terminal`'s library package, as `go list -deps` tells, libghostty-vt goes into a macOS app's `Contents/Frameworks` and an iOS app's `Frameworks/GhosttyVT.framework`, signed before the app so its signature seals them: ad hoc for macOS and the simulator, with the store's identity, or in Xcode's signing script for a device. Windows and Linux put it beside the executable before installer assembly. iOS `-embed` writes `GhosttyVT.xcframework` beside the app framework for hosts to embed and sign, with device, dual-architecture simulator and dual-architecture Catalyst slices; this applies to static and dynamic app frameworks. The arm64 AAR puts the Android prebuild beside `libnsgo.so` in its JNI ABI directory; #1452 supplies that prebuild and its loader. Android x86_64 and tvOS terminal libraries remain unavailable ([roadmap](../roadmap.md#terminal)).

An app's command-line programs, `commands`, go into its desktop packages (`commands.go`): each is a Go main package `go build` builds for the target with `CGO_ENABLED=0` and `build.tags`, linking `build.ldflags`, its own `ldflags` and the app's identity in `core.App` (`commandLdflags`), stripped and with `-trimpath` for a release. A macOS app holds them in `Contents/MacOS`, which `macos_universal` joins as it joins the app; they are signed before the bundle as `<id>.<name>`, in place of the linker's identifier, ad hoc as it is, or with `sign.identity`, the hardened runtime and a timestamp, without the app's entitlements, which are a bundle's. Windows and Linux packages hold them beside the executable, so the installers, their checksums and the appcasts carry them as the app's other files, and Windows signs them as it signs the executable. Homebrew's cask links each with a `binary` stanza. Store packages leave them out, as each store runs only the app's own executable.

`build_number` sets `CFBundleVersion` and `versionCode`, else they follow `version`. `android.permissions` adds `uses-permission`s to the APK's manifest beyond the runtime's, a name without a dot under `android.permission.`, and a direct channel's APK asks for `REQUEST_INSTALL_PACKAGES` as well, for `updater`'s installs; `android.recording` declares the runtime's `RecordingService`, a foreground service of the microphone type, with `RECORD_AUDIO`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE` and `POST_NOTIFICATIONS`, without which its notification does not show from Android 13, in the APK's and the bundle's manifest, which an app recording with `microphone.RecordWAV` needs and Google Play asks an app to justify, so no other app declares it ([Android recording](android-recording.md)); `-embed` libraries leave both to the host's manifest. An app that reads `core.Env.Geometry`, as its executable and its sources both tell, declares the device's `androidx.window.extensions` library without requiring it, in its APK, bundle or AAR, and no other app does ([foldable displays](foldable.md#platforms)). Listing `SYSTEM_ALERT_WINDOW` declares the overlay's `specialUse` foreground service with `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_SPECIAL_USE`, in the APK's manifest and the `-embed` library's, and no other app declares them ([Android floating windows](android-floating-windows.md)). Listing `FOREGROUND_SERVICE_LOCATION` declares the runtime's `LocationService`, a foreground service of the location type that background location streams run in, in the APK's and the bundle's manifest, and no other app declares it; `-embed` libraries leave it to the host's manifest ([location and motion](location-motion.md#permissions-and-packaging)). `apple.info` adds scalar, array and dictionary entries to the Info.plist of macOS and iOS packages, such as the `NSMicrophoneUsageDescription` recording needs; a string entry whose key is a message of the app's catalogs is localized in each language's `InfoPlist.strings` ([languages](languages.md)). Device bundles for iOS, tvOS and watchOS add Xcode's SDK metadata and `UIRequiredDeviceCapabilities` for `arm64` to the app and extensions; simulator bundles omit these device-only entries, and an `apple.info` value wins over generated metadata. `apple.requires_full_screen` sets the iOS package's `UIRequiresFullScreen`, true unless it is false, which lets an iPad run the app in Split View, Slide Over and Stage Manager and declares all four orientations in `UISupportedInterfaceOrientations~ipad`, as App Store Connect requires of an iPad app that multitasks; `apple.orientations` lists them for a full-screen app instead, and must list all four for one that multitasks. `apple.info` may set neither key. `file_types` registers documents in macOS's and iOS's `CFBundleDocumentTypes`, Windows's NSIS and MSIX packages, and Linux desktop entries with `MimeType` and `%F` (`filetypes.go`, `linuxfiletypes.go`): macOS and iOS export app-owned IDs and import others, with custom document icons currently on macOS alone; App Clips and tvOS leave the declarations out. NSIS records app-specific ProgIDs and extensions for guarded upgrade/uninstall cleanup; Linux uses the fixed `internal/mimeinfo` extension table or explicit `mime` references to system types, generating `application/x-<id>` and MIME-info XML for unknown owned extensions. Debian/Arch refresh caches after installation and removal; Flatpak installs the definition for export; AppImage bundles it for integration. Other targets leave the declarations out ([roadmap](../roadmap.md#application-and-windows)). `windows.command_line` adds a console-subsystem `<name>.com` beside the GUI `<name>.exe` (`windows_command.go`), forwarding arguments, standard streams and the exit code to it, so command lookup can run the app without changing its Explorer and Start menu behavior; the console's Ctrl+C and close reach the companion alone, which ends the app, as does the job it puts the app in when the companion is killed. Win+R, Task Manager's "Run new task" and Explorer's address bar look a bare name up through `Path` too and find the `.com` first, giving it a console of its own; with no other process on that console and its output not redirected, the companion starts the app untied to it and exits, so the console closes instead of staying open beside the app as a window whose close would end it. Store builds leave it out, since an MSIX installs where no command lookup finds it. Every MSIX declares a disabled `NSGoStartup` task (`msix.go`), which `desktop.SetLaunchAtLogin` enables through WinRT instead of a package's virtualized Run key. `appearance` starts the app light or dark through `-X`, and sets `UIUserInterfaceStyle`, macOS's Aqua appearance, Android's activity theme and the page's `color-scheme`. `-run` starts the package of the first target this machine runs: the app, the iPhone's or Apple TV's, the simulator's, the Android device's, or the site served with a CDN's cache headers. `-device` picks the device as `nsgo dev`'s does; Xcode signs the iPhone's package again for `-team`, as in the dev loop, since devices install only development builds.

`launch_screen` writes named color and image assets into the iOS app's catalog alongside its icon, with luminosity variants referenced by `UILaunchScreen`. Android's standalone APK and App Bundle add a launcher activity theme based on the existing system theme, with API 31 and night variants for the splash background and drawable. API 33 variants ask the system to show the configured image on every splash. The Go packager encodes the style and drawable configurations in both resource table formats. The artwork fits inside 128 points or dp, with transparent padding on Android to keep the whole image inside the system's circular mask. A fixed `appearance` selects the launch appearance on both platforms.

`android.loopback_cleartext` adds `android:networkSecurityConfig` to the APK's and App Bundle's application manifest. The `apk` package compiles the policy as binary XML for APKs and protobuf XML for bundles, with a resource table entry in each. The policy permits cleartext to the exact loopback host names `localhost`, `127.0.0.1` and `::1` and denies cleartext elsewhere. An AAR takes its host app's policy.

`game` writes Android's game classification and a `game_mode_config` XML resource to both the APK and base bundle. The table assigns XML resources after any icon and name resources so both encodings resolve the manifest references. The config keeps Android's system interventions available because opting into an app-managed mode requires the app to implement its own optimization. On macOS and iOS the flag writes the current and legacy Game Mode keys. It also defaults macOS's category to games and adds the freedesktop `Game` category to Linux's desktop entries. `gamepad` makes the gamepad and touchscreen optional on Android and declares the Extended Gamepad profile on macOS, iOS and tvOS, plus the Siri Remote's Micro Gamepad on tvOS, which package `gamepad` reads there. Explicit Apple settings take precedence.

### Installers

`project.installers` gates desktop installers and store packages: off for Steam or `build.installers: false`, and omitted for systems in `build.skip_installers` (`-skip-installers` replaces the list). `installer.go`, `dmg.go`, `windows_installer.go`, `linuxpkg.go` and `appimage.go` add what users install the desktop packages from, named `<slug>-<version>-<system>-<arch>` (`releaseName`) by the app's slug (`packageSlug`: its name in lowercase ASCII words, else its ID's last part), so a release page tells its files apart by system; MyGo's CLI makes them so (`mygo/cmd/mygo`) without the system's name. The Linux packages take it too, since dpkg and pacman read the name and version from inside. `release.go` moves each into `build.output`'s `releases` directory with a `<file>.sha256`. That directory holds everything to hand out, the one place to look: the installers, IPAs and APKs copied from their packages, the site zipped as `<slug>-<version>-web.zip` and the mini programs' projects in `miniprogram/<platform>/`, but no simulator's or watchOS's bundle. Machines building different targets add to it, so `.version` records its version, and a build of another empties it:

- macOS: `<slug>-<version>-macos-<arch>.dmg`. hdiutil images a folder holding the bundle, copied by `ditto --noclone`, a link to `/Applications`, the background picture in a hidden `.background` (`dmgbackground.go`: `macos.dmg_background`, joined with its `@2x` twin by `tiffutil`, else an arrow drawn in Go at both scales), a `.DS_Store` the tool writes (`dsstore.go`, MyGo's) placing the icons a quarter in from each side, each with its name centered from top to bottom (`dmgLabelDrop`, measured in Finder), and the hidden files stacked below the window at its left, so it scrolls no wider, which it sizes to the picture plus macOS 26's 32-point title bar, and `macos.dmg_icon` or the app's icon as `.VolumeIcon.icns`. Finder finds the picture through a Mac alias (`macalias.go`, as Python's `mac_alias` writes it for dmgbuild, checked against it byte for byte), whose node IDs and dates only the mounted image tells, so the layout is written again there over a placeholder of its size, and the volume's icon flagged; LZMA compresses it, through `diskutil image create from` where macOS 27 fails `hdiutil convert`. `sign.identity` signs it, and `notarize.go` notarizes it ([signing](#signing)).
- Windows: Go builds a native setup and a separate uninstaller (`windows_installer.go`, `windowsinstaller/`) for the target with the app's Go toolchain, from the runtime package's source the tool embeds, which imports the standard library alone, so no makensis or Windows SDK is needed. The setup carries the payload as a ZIP overlay and a fixed footer after its PE image and reads it in place, past an Authenticode signature too. Each program has `windows.installer_icon` or `windows.uninstaller_icon`, else the app's icon, version resources in the catalogs' languages with the executable's publisher and copyright, and an `asInvoker` manifest. Native TaskDialog pages choose the folder and an optional desktop shortcut, show progress and offer to launch the app; COM writes the Start menu and desktop shortcuts, and the app stamps the Start menu one with its toast activator (`--nsgo-register-toast`, `--nsgo-unregister-toast` on uninstall). It installs for the user in `%LOCALAPPDATA%\Programs\<name>`, and again where the uninstall entry under `HKCU`, keyed by the bundle ID, says it is (`InstallLocation`), unless a final `/D=<folder>` overrides it; `/S` is silent, `/RELAUNCH` opens the updated app, and `/LANG=<LCID>` picks one run's language among the app's catalogs. It quits the app running from that folder first, asking unless silent. When `windows.command_line` is true, the package also holds the console `<name>.com` companion, and with it or `windows.path` the installer puts its folder on the user's `Path` under `HKCU\Environment`, unexpanded and whole, announcing the change with `WM_SETTINGCHANGE`. When the folder was not there, it records it as `NsgoPathAddedDir` in the uninstall entry, as the NSIS installers did, which an upgrade to the same folder keeps; the uninstaller, an upgrade to another folder and one without either option take off that recorded folder alone, so an entry the user had stays. File types and URL schemes are recorded under the uninstall entry as the NSIS installers recorded them, so an upgrade, of an NSIS installation too, removes those a version dropped, while a registration another app has taken since stays. Extraction validates the whole ZIP, writes through `os.Root` and stages each file before replacing it. The uninstaller runs from a temporary copy, deletes the files the build listed and their folders once empty, never recursively, so a folder the user picked keeps what else it holds, and a bounded `cmd` loop then deletes the two locked images. An uninstaller left in a folder an upgrade moved from, which `InstallLocation` no longer names, removes its own files alone. An `arm64` setup, an arm64 program, runs on ARM64 Windows alone.
- Linux: a `.deb` and an Arch `.pkg.tar.gz`, archived in Go as no Mac has dpkg or makepkg, installing the directory in `/opt/<slug>`, `/usr/bin/<slug>` and a `/usr/bin/<name>` link for each of the app's commands, which the package owns, so removing it removes them, a desktop entry whose `StartupWMClass` is the app ID, which the Linux backend gives the process as its program name before GTK opens the display, so X11's `WM_CLASS` and Wayland's app ID match it, and whose `Categories` are `linux.categories`, checked as `desktop-file-validate` checks them and required to hold a main category, the icon in hicolor at 256 and 512 pixels, AppStream metadata (`metainfo`) in `/usr/share/metainfo`, naming a license only from `linux.license`, no content rating and `Utility` as its category without `linux.categories`, where a store build's Flatpak keeps its proprietary-license and rating defaults, and `linux.share`'s tree under `/usr/share`, its `metainfo/<id>.metainfo.xml` in place of NSGo's and a file at another path the package writes refused (`addLinuxShare`). Their tar archives use GNU headers, since dpkg rejects PAX headers, which Go would otherwise emit for Unicode paths. The Arch package includes a gzip-compressed [ALPM-MTREEv2](https://man.archlinux.org/man/ALPM-MTREEv2.5.en) manifest of its payload and metadata, with SHA-256 hashes, escaped paths and link targets, modes and the same timestamps as its tar headers, so `pacman -Qkk` checks installed files. They depend on GTK 4 and recommend WebKitGTK 6, and append the app's `linux.depends` and `linux.recommends` entries to the Debian and Arch metadata, naming `linux.maintainer`, else the app's name. Beside them, an AppImage: AppImage's type 2 runtime, a static executable `fetch` downloads once by its pinned SHA-256 (`appImageRuntimes`), followed by a SquashFS 4.0 image `squashfs.go` writes, as no Mac has mksquashfs: zlib-compressed 128 KB data blocks with no fragments, 8 KB metadata blocks, inodes numbered children first, so a directory's listing knows its entries' inodes, and extended directory inodes for listings past 64 KB. Its AppDir is the Linux package with `AppRun`, a link to the executable, `.DirIcon`, and in `usr/share`, as the packages' `/usr/share`, a link to the desktop entry at its top in `applications`, which the metadata's launchable names, the metadata and `linux.share`. `appimage_update.go` fills the pinned runtime’s reserved `.upd_info` ELF section without changing its layout or cached bytes: `linux.appimage_update` names a stable zsync URL or GitHub release locator, an explicit empty value disables it, and otherwise `release.github` or the origin remote supplies a latest-stable locator per app and architecture. `zsync.go` writes the compatible delta control in Go, with padded 2 KB blocks, full rolling and MD4 checksums and the whole-file SHA-1. The `.AppImage.zsync` is released with its SHA-256 separately from the signed appcast, and excluded from subsequent package payloads. NSH packages Linux as a tarball; portable AppImages and their metadata are NSGo’s own.

Linux package acceptance (2026-11-23) installed and removed Hello installers built on macOS in disposable x86_64 Debian 13, Ubuntu 26.04 and Arch Linux containers, using their real package databases. Debian and Ubuntu passed `dpkg --verify`; Arch passed `pacman -Qk` and `-Qkk` with 18 files and none missing or altered. The opt-in `TestLinuxPackagesNative` also covers registration scripts, Unicode assets and symlinks, and checks that Arch reports an altered file. These checks do not launch the GUI or modify the host's package database.

When a build includes a desktop installer and the app has a GitHub repository (`release.github`, else the Git remote `origin`), the releases directory also holds `install.sh` and `install.ps1` (`install/`, NSH's install scripts made the app's). They download from that repository's `releases/download/<tag_prefix><version>/` with the tag prefix escaped as one URL path segment and the version theirs unless `<SLUG>_VERSION` gives one, and check each file against its `.sha256`. The shell one copies a macOS app from the disk image, Apple silicon's even under Rosetta, or installs the Arch package with pacman, else the Debian one with apt-get or dpkg; the PowerShell one runs the installer with `/S` alone, and keeps to ASCII (`psQuote`), as `irm` decodes GitHub's untyped files as Latin-1. `<SLUG>_DOWNLOAD_URL` replaces the release's address, for mirrors and tests.

### Store packages

A `store` build (`-channel store`) writes store packages for desktop and Android targets. When both architectures of macOS or Android are selected, that platform's pair shares one `universal` package. Store builds skip install scripts.

- macOS (`macstore.go`): `<slug>-<version>-macos-<arch>.pkg`, the app in the App Sandbox with the network, the files the user picks, the microphone, camera, calendars and Bluetooth `apple.info` explains and `macos.entitlements`, `sign.macos_profile` embedded as `embedded.provisionprofile` with its application and team identifiers, signed with the profile's identity, and packaged by productbuild, signed with `sign.installer`, else the keychain's installer identity of the profile's team. Without a profile it is signed ad hoc and unsigned, which runs sandboxed but uploads nowhere. It is never notarized. With widgets, both the app and `<id>.widgets` need macOS profiles from the same team granting the shared `apple.app_group`; `macwidgets.go` validates and embeds the extension's profile before signing it, without a home-directory exception. App-only builds also apply sandbox/profile signatures, without an installer identity. `internal/platform/macos` loads CoreFoundation with the executable (`sandbox.go`): its initializer has libsecinit enter the sandbox, which a Go executable loading AppKit alone never does, so AppKit's Launch Services check aborts it. The universal app joins both builds with `lipo`, as NSH does for its macOS runner, and signs and packages the result once.
- Windows (`msix.go`): `<slug>-<version>-windows-<arch>.msix`, with stored files, `AppxManifest.xml` carrying `windows.store`'s identity, a full-trust app, its languages, `file_types` and `windows.device_capabilities`, `AppxBlockMap.xml` hashing every file in 64 KB blocks past its local header, then `[Content_Types].xml`. `cmd/nsgo/pri` writes a deterministic MRT v2 `resources.pri` in Go: catalog `appName` language candidates with source fallback, and three logos' file candidates at 100%, 125%, 150%, 200% and 400%. The manifest uses `ms-resource:AppDisplayName`; no Windows SDK runs during a build. NSH v0.6.1 has no MSIX resource index; the format and checksums follow Microsoft's MRT Core (`NOTICE`). Without signing settings it is unsigned for the Store to sign. `sign.certificate` writes `AppxSignature.p7x` for distribution outside the Store; Windows requires its certificate to be trusted on the receiving machine and its subject to match `windows.store.publisher`. Trusted installation remains to be checked ([roadmap](../roadmap.md#installers)).
- Linux (`flatpak.go`): `<slug>-<version>-linux-<arch>.tar.gz`, the package with its AppStream metadata, and once the targets are built `flatpak/<id>.yml`, a manifest on GNOME's runtime (`linux.flatpak_runtime`, 51 by default) that installs each architecture's archive from the release, or from beside it without a GitHub repository or feed, for Flathub or flatpak-builder to build. `flatpak_bundle.go` and `cmd/nsgo/flatpak` also write an installable `.flatpak` in Go: an OSTree commit with checked file/directory checksums and one inline static-delta part, Flatpak reference bindings, matching permissions metadata and exported desktop/icon/metainfo files. The format follows [OSTree's data layouts](https://ostreedev.github.io/ostree/formats/) and Flatpak's bundle reader; NSH v0.6.1 has no Flatpak writer. No Linux tools run during packaging. An app without artwork gets a transparent icon, and an omitted category falls back to Utility for the store payload so AppStream composition can finish.

- Android (`apk/bundle.go`): `<slug>-<version>-android-<arch>.aab`, the base module's manifest and resource table as aapt2's protocol buffers, from the same manifest and table the APK's binary XML encodes, `BundleConfig.pb` keeping native libraries compressed, which the runtime needs extracted, `native.pb` naming the ABI directories for split APKs, and a JAR signature with `sign.keystore` (`apk/jar.go`), Play's upload key. The manifest targets the API level Play requires, 36, which `android.target_sdk` replaces; Builds reject a lower value for the App Bundle and warn for standalone APKs. A dual-ABI bundle shares one DEX, manifest and resource table. Its x86_64 slice uses the same NDK as `android_x64`.

`compliance.go` runs after target expansion. It reads the app author's optional questionnaire statuses from `compliance` and prints a reminder for an outstanding item on the corresponding channel and target. Apple store builds check the types of the export compliance keys in `apple.info` and validate the app's privacy manifest before and after merging, so an invalid field cannot disappear in the merge. Embedded packages take the host app's store requirements.

### Google Play publishing

`nsgo publish -target android -track TRACK` opens the store AAB from the project's release directory, or an explicit `.aab` file. `apk.ReadBundleIdentity` reads the package name and version code from the bundle's protobuf base manifest before any API request. The publisher authenticates with the Android Publisher scope using the service account key in `NSGO_PLAY_SERVICE_ACCOUNT`, through the same client as store listings. It opens a Play edit, compares the bundle against all version codes on the selected track, streams the bundle, updates the track and commits. If any step fails after the edit opens, the tool attempts to delete the edit and reports the original failure.

### Steam depots

`steam.go` limits the Steam channel to desktop targets, including `macos_universal`. The tool writes the ordinary signed bundle or executable directory and skips installers, store archives and the releases directory. Native `dev` with `steam.app_id` writes `steam_appid.txt` into its build directory and launches the app there, which is where Steamworks reads the file. Steam release and development packages filter copies of that file out of app resources.

`steam_linux_runtime.go` unpacks the embedded x64 GTK bundle into `nsgo-gtk/` and writes `steam-launch.sh`. Where `ldconfig` lists no GTK 4.14 or newer, as in the Steam runtimes, the launcher prepends the depot's library and data paths before executing the app; a system GTK is left in place, because the bundle needs the runtime's other libraries and its GLib would replace a newer one in the app and in what it starts. `build -run` uses the same entry point. `steam-linux-runtime/build.sh` rebuilds the archive with Valve's pinned sniper SDK and includes the licenses and source versions; the tool adds `NOTICE` and `build.sh` beside them, so each depot names the LGPL libraries' corresponding source.

### Updates

`updates.go` builds each package for the channel `updates.channel` or `-channel` names, as [updates](updates.md#channels) describes; development builds never update. Only the direct channel adds anything to a package beyond `-X` flags giving `nsgo.Run` `updates.automatic`; every build, development ones too, gets the app's identity, version and build number in `core` (`core.App`).

- Each direct macOS, Windows, Linux and Android release writes `appcast-<target>.xml`: Sparkle's RSS format, with this version's installer (or on Linux, signed items for `.deb`, `.pkg.tar.gz` and `.AppImage`), signed with EdDSA by `NSGO_UPDATES_KEY`'s key, which must be `updates.key`'s secret one. `-release-notes`' Markdown becomes the item's `<description>`, HTML rendered by goldmark without raw HTML, which Sparkle and WinSparkle show and `internal/platform/updates` turns back into text for the updater's prompt.
- There is one feed per target, since machines build targets apart, so nothing filters by `sparkle:os` or architecture. The direct `macos_universal` target writes one universal DMG and `appcast-macos_universal.xml`; macOS and Windows get none without the secret key, as Sparkle and WinSparkle refuse unsigned updates; Linux and Android still get theirs, unsigned, which the app answers with the release's page rather than an install.
- The feed is `updates.feed`, else `release.github`'s `releases/latest/download/`. The keys are `nsgo keygen`'s, which is Sparkle's format too: `updates.key` holds the public key itself, and the secret one lives only where releases build.
- macOS packages carry Sparkle 2.10.1, unpacked by macOS's tar to keep its links and signatures, and signed inside out as Sparkle documents. Info.plist names the feed, key and schedule.
- Windows packages carry WinSparkle 0.9.4 beside the executable. The appcast runs the installer with `/S /RELAUNCH`, which starts the new version once installed.
- `pkgmanifests.go` writes package manager manifests for a direct release's built desktop installers, scanning the releases directory so separate architecture builds join into one manifest: `homebrew/<slug>.rb` (declaring `auto_updates true`, `depends_on :macos`, per-architecture `arch`/`sha256` or universal/single-arch DMG URL and SHA-256, `app` and `zap` trash paths) and `winget/<id>.yaml`, `<id>.installer.yaml` and `<id>.locale.en-US.yaml` (winget-pkgs schema 1.9.0 with `exe` user-scope `/S` and `/D=<INSTALLPATH>` switches, `AppsAndFeaturesEntries` and `x64`/`arm64` entries).

Sparkle and WinSparkle are downloaded once into the user cache and checked against pinned SHA-256s, not committed as `classes.dex` is: they are other projects' builds, 16 and 27 MB of archives, that only a direct app needs, and WinSparkle builds with Visual C++ alone. Targets build at once, so one at a time downloads and unpacks them.

### Widgets

On Android, `android_widgets.go` and `apk/widgets.go` package each YAML kind as a stable manifest component named from the kind's hash, with localized name/description strings, provider metadata and generic RemoteViews layouts in both APK and AAB resources. `NsgoComponents`, an API 28 `AppComponentFactory`, instantiates those component names as one prebuilt `AppWidgets` provider; no app-specific Java or DEX generation is needed, and reordering kinds preserves installed widgets. This has no NSH counterpart.

Before it starts Go, the Java runtime sets `NSGO_WIDGETS_DIR` and `NSGO_WIDGET_KINDS` and watches the application-private `NSGoWidgets/<kind>/timeline.json` files. `widget.Update` uses the same atomic timeline/image encoder as Apple. The provider renders the last passed entry (or the first before all dates), refreshes on publication, resizing, boot, clock/zone/locale and package changes, and schedules the next date with an inexact alarm. A main-loop callback advances it while Java remains alive; after process death the system can start only the provider, without Go or an Activity. Android may defer background alarms; no exact-alarm permission is requested.

`WidgetRenderer` lays out the shared nodes and paints at no more than 1024 pixels per side. `AppWidgets` wraps that bitmap in RemoteViews, adds transparent per-view link regions and native chronometers for timers, and uses immutable explicit Activity PendingIntents for taps. The system launcher owns addition/removal; ordinary taps open the app and a declared URL scheme reaches its link handler. App Widgets select small/medium/large/extra-large families from the user-resized bounds, within the YAML families; other families use their declared fallback. Arbitrary SF Symbol names beyond the implemented portable glyphs, and native chronometer font weight/design/italic styling, remain roadmap goals; images provide portable artwork. Embedded Android hosts do not receive generated widget providers/resources.

`widgets.go` adds a widget extension to the macOS and iOS packages of an app whose `nsgo.yaml` lists `widgets`, as package `widget` describes ([layers](layers.md#dependency-graph)). WidgetKit declares widgets in Swift alone, and its views are SwiftUI's, so neither purego nor the Go runtime can make one, and the extension runs none of the app's code: the app writes timelines, and a generic extension draws them.

- `widgets/Widgets.swift` decodes a kind's `timeline.json` and builds SwiftUI views of its nodes, with a policy of `.never`, as the app reloads it; it reads images with ImageIO at no more than 1024 pixels across, as the system bounds a widget's memory. `Kinds.swift`, written from `nsgo.yaml`, declares a `Widget` per kind in one `WidgetBundle`, which holds ten. The extension links with `-e _NSExtensionMain`, as Xcode links app extensions.
- `WidgetCenter`'s methods take `self` in a register purego does not set, so `widgets/Reload.swift` exports `nsgo_widgets_reload` with `@_cdecl`, in `libNSGoWidgetKit.dylib` on macOS and `NSGoWidgetKit.framework` on iOS, which the package loads from the bundle's frameworks with the first `Update`.
- Both compile with `xcrun swiftc` for the target, kept in the user cache by their sources, the target and the toolchain, as actool's icons are. The extension is `PlugIns/Widgets.appex`, `<id>.widgets`.
- Where timelines live, the Info.plists of the app and the extension say. On iOS, an app group's container (`NSGoAppGroup`, `apple.app_group` else `group.<id>`), which the simulator grants from ad hoc signatures' entitlements and devices from `sign.profile` and `sign.widgets_profile`. Mac App Store builds use the same `NSGoAppGroup` container, authorized by `sign.macos_profile` and a macOS `sign.widgets_profile` from the same team, both granting the group. [Apple requires a profile for `group.` identifiers](https://developer.apple.com/documentation/xcode/accessing-app-group-containers). Direct and development macOS builds have no such profile, so the app writes `~/Library/Application Support/<id>/Widgets` (`NSGoWidgetsPath`), which the extension, in the App Sandbox as macOS runs widgets, reads through a read-only temporary exception, from the user's home rather than its container's (`getpwuid`).
- The extension is signed before the app, which is signed without `--deep`, so its entitlements stay its own. `nsgo dev` registers it with `pluginkit -a`, as it starts the app's binary rather than the bundle. For Xcode's device signing, the generated project gives it a target of its own, `<id>.widgets`, which copies the build's extension, is signed automatically and embedded in the app, both claiming the app group, which automatic signing registers; `-embed` packages carry none.
- `live_activities` gives the iOS app the extension too, `NSSupportsLiveActivities` and the app group. ActivityKit's `Activity` is generic over Swift types, so one `NSGoActivityAttributes` (`widgets/Activity.swift`, in both the extension and the library) holds a kind and an ID, and its content-state is the JSON package `widget` writes: the fields, which `widgets/ActivityViews.swift` lays out, and the views the app gave, drawn as timelines' are. Defaults drawn in Swift keep a state within ActivityKit's and APNs' 4 KB, and let a server push one without NSGo's views. `widgets/Activities.swift` exports the library's functions to start, update, end and list them and a callback for presses and push tokens; the library is weakly linked to ActivityKit and App Intents, younger than iOS 15.
- Widget buttons from iOS 17 and macOS 14 share `NSGoActionIntent` (`widgets/Actions.swift`) with Live Activities. iOS uses `LiveActivityIntent`; macOS adds `ForegroundContinuableIntent` only to the app library, routing actions to the app process without opening its windows. A widget sends an empty activity ID, which Go reports as `ActivityPress.Activity == nil`. The library's copy, built with `NSGO_APP`, waits for the callback `OnAction` sets before `nsgo.Run`, and for updates it starts. Widget-only apps also compile and package both bundles' `Metadata.appintents`, extracted with the toolchain's constant-value protocol list; intent names match across modules. macOS metadata lives in `Contents/Resources`.
- Android action presses use immutable broadcast pending intents to `LiveUpdateReceiver`, declared unexported in standalone and embedded manifests. Their URI includes an engine lifetime token and the full activity/action IDs, so hash collisions and another embedded engine cannot redirect a press. `NsgoEngine` registers the token only while its process runs and sends `LIVE_REPORT` through its synchronized pipe; ended engines drop stale actions. Permission replies refresh Live Update availability before invoking the app callback, which may immediately start an activity. Content taps retain Activity pending intents. Unlike iOS, this does not start Go in the background: [Android forbids a receiver from launching an Activity as a notification trampoline](https://developer.android.com/about/versions/12/behavior-changes-12#notification-trampolines), and viewless Go launch remains a separate lifecycle goal. NSH has no widget service to port.

An iOS app with `apple.share_types` also embeds `NSGoShare.appex` (`iosshare.go`). Its support package under `cmd/nsgo/shareextension` stays in vendored tool dependencies through a blank import whose host form contains no runtime code. The tool builds a temporary Go entry point with the app's selected module graph and Xcode's linker; it generates no C or Swift. The activation predicate admits only the declared UTIs. Xcode device runs sign each extension as a separate target; IPA builds require `sign.share_profile` for `<id>.share`, granting the same `apple.app_group` as the containing app. App Clips and non-iOS targets leave it out.

### App Clips

`appclip.go` nests an App Clip in the iOS package of an app whose `nsgo.yaml` has `app_clip`. The clip is an iOS app of its own, built by `buildIOSApp` from `clipProject`: the app's project under the clip's name, ID (`<id>.Clip`) and main package (`app_clip.main`, whose `resources/` it takes), without widgets or a clip. It goes to `AppClips/<name>.app`, its Info.plist holding `NSAppClip` and its `MinimumOSVersion` `app_clip.minimum` (16.0, as iOS 15 downloads clips of 10 MB alone).

- A device build larger than the system downloads, 15 MB or from iOS 17 100 MB, fails; the simulator's warns.
- `sign.clip_profile` signs a device build's clip before the app, as the widgets' profile does, its associated domains `appclips:` `app_clip.domains`; the app's profile must list the clip (`associated-appclip-app-identifiers`). The simulator refuses to launch an app whose ad hoc signature claims a `com.apple.developer` entitlement, so simulator builds claim none. Xcode's device signing gives the clip its own App Clip target and entitlements, makes the app depend on it and embeds its signed product. Parent and clip entitlements name each other through `$(AppIdentifierPrefix)`, and a separate clip product directory permits matching app and clip names. Widgets retain their own target beside the clip.
- Explicit `apple.app_group` opts both bundles into shared persistent data: `NSGoStorageAppGroup` in each Info.plist selects the group’s container, and both simulator signatures and Xcode’s entitlement files claim it. Profile signing checks that both `sign.profile` and `sign.clip_profile` grant the group before signing. Without an explicit group, each bundle keeps its sandbox storage; widgets alone do not opt in ([storage](core.md#storage-and-directories)).
- `nsgo dev -clip <url>` runs the clip alone, opened from the link: in the simulator it installs the build's clip and launches it with `_XCAppClipURL`, as Xcode does, and the iOS backend takes that as the opening link when no activity brings one, as `simctl` sends none. On an iPhone Xcode signs the clip as an App Clip product (`on-demand-install-capable`), with entitlements naming its parent through `$(AppIdentifierPrefix)` and its domains, and `devicectl` launches it with `_XCAppClipURL`; a personal team, which Apple lets sign no clip, is refused first, as Xcode's preferences mark it (`freeTeam`). It then prints the link as a QR code of half blocks, which the camera opens the clip from once the device's Local Experiences list the link.
- The backend reads universal links and clip invocations from `NSUserActivityTypeBrowsingWeb`, and full-app custom schemes from connection options and `scene:openURLContexts:`, into app-wide `Environment.OpenedURL`. Early arrivals also update the cached pre-engine environment; existing engines refresh before `OnOpenLinks` delivery, while file URLs stay separate. `NSAppClip` in the main bundle's Info.plist supplies `AppClip`. The explicit `app_links` host list claims full-app `applinks:` Associated Domains through Xcode or an authorizing IPA profile, with the server's AASA file still required; clips never inherit the parent's list and use their own `appclips:` domains.
- `mobile.ShowAppClipOverlay` sends a scoped request to iOS's `appclipoverlay.go`, which loads StoreKit through purego and uses `SKOverlayAppClipConfiguration`, with bottom or raised-bottom positioning. The owning scope's cleanup carries its request ID; per-scene ownership also protects a newer overlay from a different embedded engine. Surface close or scene disconnection dismisses and releases the overlay. Confined owners use the same user-activation presentation guard as review prompts. StoreKit decides whether to load the corresponding full app; the API promises no displayed offer or installation.

### In-app purchases

`storekit.go` puts a library of `storekit/StoreKit.swift` among the frameworks of the macOS, iOS and tvOS packages of an app whose `nsgo.yaml` sets `apple.purchases`: StoreKit 2's products and transactions are Swift's alone, so the library exports `nsgo_storekit_start` and `nsgo_storekit_call` with `@_cdecl`, which `internal/platform/apple` loads through purego and calls with JSON ([services](services.md#in-app-purchases)). It is `NSGoStoreKit.framework` on iOS and tvOS and `libNSGoStoreKit.dylib` on macOS, compiled with `xcrun swiftc` for the target, macOS 12 at least, and kept in the user cache by its source, the target and the toolchain, as the widgets' are; it is signed as the bundle's other frameworks and libraries are. It claims no entitlement, as In-App Purchase needs none. Apps without the setting link none of it, App Clips never do, and watchOS leaves it out with a note.

## Store asset packs

`mobile.asset_packs` lists named source directories and their delivery policies. The mobile resource walker excludes those directories before reading files into the base package. Android's AAB writer adds a protobuf manifest and namespaced files per asset module, signing and compressing the pack files from disk. Installed split APKs and fused APKs expose the same namespaced paths to `mobile.AssetPackReady` and `mobile.OpenAssetPackFile`. Google Play's fast-follow downloads require its Asset Delivery SDK to expose the downloaded directory, which remains pending.

iOS device builds map the two policies to essential and prefetch in `ba-package` manifests and emit separate `.aar` archives. Swift supplies the ExtensionKit entry point required by the Apple-hosted `StoreDownloaderExtension` template. The app uses Background Assets' Objective-C manager through purego. The app and downloader profiles share `apple.app_group`; the extension is signed with `sign.asset_packs_profile`. The NSH release has no equivalent store asset-pack build path.

## Signing

`sign.identity` signs macOS packages, libraries first: macOS keeps the permissions it grants an identity's app across builds, where each ad hoc signature counts as a new program. A non-ad-hoc `sign.identity` (such as a Developer ID) also claims `keychain-access-groups` from `macos.entitlements` (`macSignEntitlements`), as a store build does, so the app can use the data protection keychain. `nsgo dev` and `nsgo test` stay ad hoc, as macOS credits what a terminal starts to the terminal.

`sign.profile` signs the iOS package: `security cms` opens the profile, whose `application-identifier` must cover the bundle ID; a wildcard profile signs the app's own ID, which devices require. The profile goes in as `embedded.mobileprovision`, and `codesign` signs with `sign.identity`, else the keychain's identity for one of the profile's certificates. `-profile`, `-widgets-profile` and `-clip-profile` replace the app, widget extension and App Clip profiles from the command line.

`apple.sign_in_with_apple` claims `com.apple.developer.applesignin` with `Default` (`claimSignInWithApple`, `xcodeEntitlements`): in the entitlements Xcode's device signing registers, and in a device build's or a Mac App Store build's, whose profile must grant it, the build failing otherwise; a profile granting it claims it for no app that does not ask. macOS grants it only with a profile, so a direct macOS build leaves it out with a warning, and simulator builds, whose ad hoc signatures claim no developer entitlement, leave it out too ([services](services.md#sign-in-with-apple)).

`sign.notarize`, a notarytool keychain profile, or an API key in `NSGO_NOTARY_KEY`, `NSGO_NOTARY_KEY_ID` and `NSGO_NOTARY_ISSUER`, notarizes the macOS package of a release build (`notarize.go`), refused without a Developer ID `sign.identity` before anything builds. Every executable is then signed with the hardened runtime and a secure timestamp (`macSignArgs`), the app with the device entitlements `apple.info`'s usage descriptions ask for; the disk image, else the app zipped by `ditto`, goes to `notarytool submit --wait`, and the ticket is stapled to the image and the app. A rejection's error carries `notarytool log`.

`sign.keystore` signs release APKs (`apk/keystore.go`): PKCS#12, with PBES2 (PBKDF2 and AES or 3DES) as keytool and OpenSSL 3 write it or PKCS#12's SHA-1 schemes with 3DES and 40-bit RC2 as older tools do, or JKS, whose key protector is a SHA-1 stream of the password. `NSGO_KEYSTORE_PASSWORD` and `NSGO_KEY_PASSWORD` give the passwords, never `nsgo.yaml`; `sign.key_alias` picks a key. APKs sign with RSA keys only.

`sign.certificate`, a PKCS#12 that `apk.ReadKeystore` reads with `NSGO_CERTIFICATE_PASSWORD`, signs Windows packages with Authenticode in Go (`winsign.go`, `authenticode/`), so a Mac needs no Windows SDK: the executable, the command companion, the resources' PE images that carry no signature yet, and the installer, plus the MSIX on the Store channel. Its package signature carries the APPX SIP hashes of the payload records, central directory, content types and block map, and an existing code-integrity catalog when present. It preserves compressed payload bytes and block-map contents, replaces an old signature and registers its content type. ZIP entries use matching reader versions, creator version 45 and zero external attributes; both signing passes use ZIP64 end records, with the classic end record's disk numbers zeroed only for the digest, as Windows AppxSip requires. `authenticode/` appends a `WIN_CERTIFICATE` holding a PKCS #7 SignedData over the image's digest, as signtool and osslsigncode do: the digest covers the headers without the checksum and the certificate table's entry, every section's data in file order, and the bytes the sections leave out, whose last partial block pads to 8 bytes (NSIS's uninstallers need it), and it recomputes the PE checksum. An image signed before is signed again in place of that signature rather than twice. `sign.timestamp_url`, DigiCert's unless `none`, asks an RFC 3161 server for a token, which the signer carries as its unsigned attribute so the signature outlives the certificate. `sign.sign_command` signs each file with a tool of its own instead, `%1` standing for the path, for a certificate on a hardware token or in a cloud service. After a successful command, PE outputs must contain an embedded signature; `authenticode.Signed` checks the certificate-table entry, not its cryptographic validity, certificate trust or download reputation. Non-PE outputs such as MSIX remain the command's responsibility. The Windows uninstaller is signed with the same signer before it enters the setup's payload, and the setup once its payload is appended. `-certificate`, `-sign-command` and `-timestamp-url` replace the three from the command line.

## itch.io uploads

`publish itch` sends built web and desktop package directories to the game named by `itch.project` with Butler's `push`. It checks all packages and channels before uploading, forwards the build's version as `--userversion`, and takes `BUTLER_API_KEY` from the environment. The tool uses the installed Butler or fetches the pinned itch.io archive for the host using the updater downloads' cache and checksum check. The downloaded executable is unpacked into a temporary directory for the upload.

## Apple store uploads

`nsgo publish ios` and `nsgo publish macos` take a signed IPA or PKG. `publish_apple.go` reads the main app's `Info.plist` from the archive and expands macOS packages with `pkgutil` in a temporary directory. It uses the App Store Connect key and client that store listings use (`listings_appstore.go`), `NSGO_APP_STORE_KEY` or else the notarization key, and writes a key given as text to a private temporary `.p8` file for `altool`, removed when the command ends. `appstoreconnect.go` checks the bundle ID and build number before delivery, each query signed with a fresh ES256 JWT. On iOS, the version and platform scope the check. On macOS, the check spans all versions of the app. NSH delivers IPA bytes over App Store Connect's upload API. NSGo uses Xcode's `altool --upload-package --wait` for delivery and processing reports on both platforms.

## Signed packages

`publish.go` drives `tsx/pkg` ([signed packages](tsx.md#signed-packages)). Keys are base64 text, never files: `keygen` prints a pair, a 32-byte Ed25519 public key and the seed of its secret one, and writes nothing. Public keys are given as text, in flags, `nsgo.yaml` and apps' code; secret keys only in the environment, `NSGO_ROOT_KEY` for a root's and `NSGO_RELEASE_KEY` for a release key's, as `NSGO_UPDATES_KEY` gives updates' ([updates](#updates)), so none sits in a file beside the project, in shell history or in a process list. `certify` has the root certify the release key `-key` for `-apps` and `-days`, writing `-out`, `release.cert` by default, as JSON. `publish` compiles the app's TSX entry, the one its main package runs or `-entry`, else `App.tsx`, and signs it as the app of `nsgo.yaml`, its build `build_number` else Android's code of its version, with its `capabilities` (`capabilities.go`, read strictly and in snake case, as every command loading `nsgo.yaml` does), into `build.output`'s `<name>-<version>.nsgopkg`; given a package instead, it signs that again, to `-out`. It refuses to sign what devices would refuse. `verify` checks a package against the public keys `-root` lists and the revocation list files `-revocations` lists, or without roots against itself alone, and prints what it holds, its capabilities included, warning of a root whose list expired; `revoke` has a root sign list `-sequence` of release key IDs and packages, by SHA-256 or file, a root's lists counting up on their own and each holding all the root revokes, which expires in `-days` when given and otherwise never.

## Store listings

`listings.go`, `listings_appstore.go` and `listings_play.go` drive `nsgo publish -store appstore|play|all` (and `-dry-run`). Store metadata lives in `store/` (or `nsgo.yaml`'s `store.dir`, or `-listings`) as a strict, versioned (`version: 1`, unknown fields refused) top-level `listing.yaml` and per-locale `<locale>/listing.yaml` with optional `description.md`, `release_notes.md`, `promotional_text.md` and relative screenshot/preview files. Validation checks schema versions, locales (mapping canonical tags such as `zh-Hans` to `zh-Hans` on App Store Connect and `zh-CN` on Google Play), required fields, store character limits in Unicode runes, URL schemes and media files before reading credentials or making any HTTP request. App Store Connect uploads authenticate with ES256 JWTs signed from `NSGO_APP_STORE_KEY`/`KEY_ID`/`ISSUER` (falling back to `NSGO_NOTARY_*`); Google Play uploads exchange RS256 service-account JWTs from `NSGO_PLAY_SERVICE_ACCOUNT` for OAuth2 tokens and commit edits through Android Publisher API v3.
