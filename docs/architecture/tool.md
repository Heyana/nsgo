# The nsgo tool

`cmd/nsgo` builds, runs, tests and packages apps from their `nsgo.yaml`, shelling out to `go` and, for Apple targets, Xcode's tools. It follows NSH's `nsh-cli` (`nsh/docs/dev/tooling.md` and `embedding.md`). Read this before changing `cmd/nsgo`.

## Output

Command flags go before the directory or file. `parseCommand` rejects misplaced flags with an example and extra paths before loading or changing a project; commands that take no path reject positional arguments too. `nsgo test` lets through the flags `go test` shares with it (`-run`, `-timeout`, `-bench`, `-trace`), which are go test's after the path. Unlike NSH's clap parser, NSGo keeps Go's flags-before-path convention and diagnoses the mistake rather than changing how existing arguments parse.

Every command prints one line per step and the details only when a step fails, as NSH's CLI does (`nsh/crates/nsh-cli/src/ui.rs`, `nsh/docs/dev/tooling.md` "Output"): `✓` a step that finished, `→` where to find something, `•` what a device or server did, `warn` and `error` for problems. The tool's lines are indented two spaces, so the app's own lines stand apart. On a terminal a step that takes a while shows a spinner in its line with what it does at the moment (`stage`: compiling TSX, compiling Go, signing…), and colors are used unless `NO_COLOR` is set; redirected, a step prints its label as it begins (`vetting for android_arm64…`) and its result line when it ends, without a spinner or redraws, so a CI or agent log names the step a slow, failed or interrupted run was on. All of it is stderr.

`nsgo build` and `nsgo dev` start with the NSGo version the tool was built from, the app's name and version and the targets, then what they do. `nsgo build` times each package and measures its directory, so each target's line reads `✓ built macos_arm64 (1.4s, 23.4 MB)`, numbered as `[2/5]` in a build of several targets, which ends with their number, time and total size. Targets building at once show a spinner line each, in the targets' order, and what one says while it builds (`detailIn`, `warnIn`) waits for its `✓` line, so their lines never interleave. `nsgo dev` reports each build's time, the app's start and whether it watches for changes, which it does unless `dev.hot_reload` is false. A tool's output, Go's or Xcode's, appears indented under `error` only when it fails.

`run`, `output` and `goTool` use the process runner in `cmd/nsgo/process.go`. It takes the executable, arguments, directory, environment and output handling. Tests can provide a runner through their context to check signing order, release repository discovery and target-test commands without starting external tools. Callers such as the device test log readers own their pipes and child process lifetimes directly.

## Dev loop

`nsgo dev` (`dev.go`) starts a dev server on `-port` (8080), or the next free port, listening on every interface. Dev builds take the `nsgodev` tag, which links the dev client `nsgo.Run` starts (`internal/dev`, `client.go`): it follows the server's `/_nsgo/events` and shows a failed build's output in an overlay over the running app, as it shows the app's own render failures; its Reload button posts `/_nsgo/reload`. Its Command/Control+R binding belongs to the app scope for an app function, so it remains available in other windows after the main view closes; a root-view app keeps the binding on its wrapped root. The overlay's title and buttons come from the dev client's catalog (`internal/dev/locales`), in the language the app shows (`i18n.Language`), so `-lang zh-Hans` shows them in Chinese for an app whose catalog has it, and follow it as it changes. `-fps` and `-lang` start the app with the engine's flags `--nsgo-fps` and `--nsgo-lang` (`nsgo`'s `flags.go`), which `nsgo.Run` takes out of `os.Args` before `main`: as arguments on desktops and through `simctl` or `devicectl`, as an intent's `nsgo-` extras that `NsgoActivity` turns back into arguments on Android, and in the page's query, which `nsgo.js` puts in `go.argv`, on the web. `-limits`, alone or with limits as `tsx.ParseLimits` reads them, runs a TSX app sandboxed as `tsx.View` runs a package, with every module, its bundles replacing it rather than updating it in place: `compiler.devLimits` and `compiler.devCapabilities`, `nsgo.yaml`'s capabilities as base64url JSON, are set through `-X`.

On macOS, the native dev tool gives each session a private temporary frame file. The AppKit backend applies the main view’s last regular window frame before the app lays it out and records subsequent geometry changes on a worker. It uses the same screen check as `nsgo.WindowFrame`, and the frame writer is absent from release builds. [#658](https://github.com/nsgo-dev/nsgo/issues/658) tracks continuous handoff, other windows and platforms, full-screen state and navigation.

The server finds the app through `NSGO_DEV_SERVER`, which the simulator gets as `SIMCTL_CHILD_`; Android and iPhones, which pass no environment, get it with `-ldflags -X`, Android at `127.0.0.1` through `adb reverse`, removed when the run ends, an iPhone at the Mac's LAN address.

Each run makes a token, 32 random bytes, which every endpoint that reads the app's state, the build's or the project's, or changes them takes, compared in constant time, and refuses without with 401 (`devServer.handle`): `/_nsgo/events`, `/_nsgo/bundle`, `/_nsgo/reload`, `/_nsgo/trace` and DevTools' `out`, `stream`, `project` and `command`. Only the pages' own files, the web target's and DevTools', and `/_nsgo/automation`, which takes the tools' token ([automation](#automation)), go without it. No command line carries it, as every user of the machine can read them. The app gets it as `NSGO_DEV_TOKEN`: in its environment beside the server's address or, on Android and iPhones, from a file the build adds to its main package through `-overlay`, which sets the variable as `main` initializes; `-X` would put it on `go build`'s and the linker's command lines, `GOFLAGS` included, and the module cache's files cannot be overlaid. The app takes it out of its environment as it starts or, set by `main`, when its dev client first needs it (`devtools.Token`), so the programs it runs never inherit it, and sends it in `X-NSGo-Token` (`devtools.Fetch`). The pages get it in the fragment of the addresses the tool prints and opens, `#nsgo-token=`, which no request carries; the tool opens them through `osascript`'s input on macOS and elsewhere through a page only its user reads, which sends the browser on and goes when the run ends. Each page moves it at once to the tab's `sessionStorage`, out of the address bar, the tab's history and whatever copies the address, where its reloads and the web target's Go find it, and sends it in the header or, from an `EventSource`, which sends none, as the query's `nsgo-token`. No response allows another origin to read it. The server also answers only requests whose `Host` is an IP address, `localhost` or this machine's name, with `.local` or without, refusing any other with 403, so a site whose name is pointed at this machine reaches nothing from its pages.

The web target is served from the same server; its page shows the overlay itself and loads each build, in the words the page's Go gives it as `nsgoDevMessages`, the same catalog's in the language the app shows, and in English before the app has started. A run ends with the app, and without hot reload a failed first build ends it. `-release` builds as `nsgo build` does, for measuring with `-fps`. `-trace` builds with `-X internal/dev.devTrace=1`: the dev client sets `engine.Trace` for every engine of the process and posts each commit to `/_nsgo/trace`, printed as `nsgo test -trace` prints a batch (`driver.WriteTrace`), labeled by its number, with the app's output. With it `driver.TraceCauses` is set, also by `nsgo test -trace` (`nsgotest`): each signal write records its callers and each computation run its kind, and a tree's commit takes them into `MountBatch.Causes`, which `driver.WriteTrace` prints above the items. A write's site is its first caller outside `core` and NSGo's internal packages, or NSGo's outermost function for writes NSGo made itself, as an animation's; writes that changed no tree count toward the next tree that commits. `-highlight` builds with `-X internal/dev.devHighlight=1`: the dev client mounts `core.UpdateHighlights`, DevTools' overlay, over the app, as it does under `-layout` and `-devtools` with `NoUpdates` set; it outlines the views each commit's items created, moved, restyled or filled anew, other than its own, posting them once the commit is done, so its own commits outline nothing. Dev builds' files take the `nsgodev` tag, so `nsgo check` in NSGo's repository vets the root package with it too, and as macOS with `nsgoautomation` beside it the root package, `nsgotest` and the macOS backend. `-devtools` builds with `-X internal/dev.devDevtools=1` and serves DevTools, plain HTML and JavaScript embedded in the tool (`devtools/`), at `/_nsgo/devtools/`. The dev client sets `devtools.Enabled` before any graph starts, as `Run` starts tracing and DevTools once (`startDevClient`) before it starts the engine, for an app's function as for a root view, so `core` records what DevTools read: the component each scope renders, the signals each owner makes and every computation with how often it ran, each with its site, the first caller outside the packages that run apps, as a whole path for the editor's link; a binding takes its component's. It registers each tree in `internal/devtools`, whose `Surface` the client drives on the graph's goroutine through `Post`: DevTools pages list every one but the first of an app that opens windows, which shows no view, and `-automation`'s agent gets every one ([automation](#automation)). The page's commands reach the app as `devtools` events on `/_nsgo/events`, and the app posts its answers and each commit, a quarter of a second's at a time, to `/_nsgo/devtools/out`, which the server passes to pages following `/_nsgo/devtools/stream`. Both take the run's token, only their JSON content types, which another site's page cannot send without a preflight the server never allows, and no `Origin` but the server's own. Pick and the inspected outline draw in `UpdateHighlights`' overlay, a Topmost overlay ([core](core.md#layers-and-navigation)) over the app's modals too, which takes the pointer while picking and hit-tests past its own views; the recorder hears presses and edits in `Tree.Dispatch` and names views by test ID, then role and label, then text. Unset, `devtools.Enabled` costs a nil check where a signal, a computation or a component is made, a computation runs and a scope goes. With it, and under `-trace` and `nsgo test -trace`, which set it too, each commit's causes name the computations it ran by kind and site with their own time, not counting what their writes ran next, and the app's time before it and its layout's. `driver.Apply` times each batch on the platform's main thread for `driver.Applied`, which the client joins to its commit; every backend applies through it but Android's, whose Java runtime applies batches. A write's site is read as the write is made, and one in tsx's Go asks `devtools.ScriptSite`, which tsx sets for the JS its runtimes run now, mapped by goja or the page through the bundles' source maps, so a TSX app's sites are its TSX lines, relative to the app, which the page joins to the directory `/_nsgo/devtools/project` names. Recorded scrolls are kept per scroll view and become one `ScrollTo` once the user does something else, the view rests or recording ends. A phone is told the address the machine sends from first (`outboundIP`), as virtual networks' interfaces may come before the Wi-Fi's. The web page's Go finds the server at the page's origin and leaves build failures to the page. `-automation` lets tools drive the running app ([automation](#automation)). `-device` picks a simulator by name or UDID, booting it, or an adb serial or an emulator's AVD name.

`-layout`, alone or as `-layout=bounds,grid=4`, which `layoutFlag` checks and writes without spaces, builds with `-X internal/dev.devLayout`, which the dev client reads into `UpdateHighlights.Layout` (`parseDevLayout`). The layout audit (`core/audit.go`, after knothhe's mygo-layout-audit) draws on that overlay, under the update outlines: a canvas that takes no pointer outlines the boxes DevTools read, walking the views as `Elements` lists them and taking each one's box as it does (`devChildren`, `devBox`), with upstream's colors, each box clipped where its scroll views and clipping views cut it, where upstream draws them whole, and a grid. It leaves out hidden subtrees, scroll bars' hosts, what the platform shows apart from the surface and DevTools' own views. While it reads the boxes, a round that moved, resized, hid, restyled or removed a view, or followed a scroll, draws them again after the `OnLayout` handlers (`bumpAudit`), within the commit's batch; otherwise a commit pays a check. The overlay sets those hooks as it mounts (`keepAudit`), so a release build keeps of them only a flag its frames set and a nil check. A readout in the bottom start corner, of numbers and icons only and hidden from assistive technology and the Tab order, shows the surface's size and the measurement; its buttons toggle the boxes, the grid and the ruler, a second Topmost overlay that takes every press to pick two points and leaves on Escape, which it binds while it measures, on back, which reaches it before the app's modals, and on its button. Mod+Alt+Shift+L (`auditKey`), which the overlay binds only when the audit starts showing, as under `-layout`, so `-highlight` and `-devtools` alone bind no key, shows and hides it; the app's newest binding of the key wins, so the chord is one apps seldom bind, where Mod+Shift+L is the editor's and the gallery's. The page's Layout checkbox shows and hides it too (`Surface.Layout`) and follows it (`Surface.WatchLayout`), unchecked on a surface without the overlay. Release builds link none of the overlay (`TestReleaseBuildsLinkNoDevClient`), and `TestDevBuildsLink` builds the dev client for each target, which only this machine's build did before.

## Automation

`nsgo dev -automation` (`automation.go`) builds with the `nsgoautomation` tag beside `nsgodev`, which links `nsgotest`'s agent into the app (`internal/dev/automation.go`), and relays tools' requests to it; it refuses `-release` and, so far, every target but `native`, `ios`, `tvos`, `watchos`, `ios_simulator`, `tvos_simulator` and `watchos_simulator` on macOS ([roadmap](../roadmap.md#automation)). For simulators, `simulatorEnv` passes the dev server URL and token through `SIMCTL_CHILD_` variables. For physical Apple devices (`ios`, `tvos`, `watchos`), `configureAppleDeviceDev` stamps the Mac's LAN dev server URL into the binary with `-ldflags -X` (as `devServer`), gives the app the run's token through `devTokenFile`'s main-package `-overlay` (so no command line carries it), signs with Xcode and launches through `xcrun devicectl`. The agent is DevTools' (`devtools.Automation`): the dev client sets `devtools.Enabled` for it as for `-devtools`, and DevTools' registry hands it each surface `core` registers, the app's own first one too, which pages leave out. It follows those of the first graph that registers one (`Surface.Follow`), hearing each batch they commit and each event they dispatch until they unregister, models each as a test's app on a target and acts through the backend's live surfaces with native input ([testing](testing.md#driving-a-running-app)). Dev builds without the flag link none of it, and `-fps` readings with it count the models' work and what DevTools record.

- The app connects out once `dev.Start` runs, over DevTools' channel (`internal/dev/devtools.go`): it follows `/_nsgo/events?devtools`, its DevTools stream, which is the one the tools' requests reach, as `automation` events, and posts each answer as an `automation` message to `/_nsgo/devtools/out`, at once rather than with a quarter of a second's commits, both with the run's token. The server passes answers to no DevTools page, and a page's commands, sent as `devtools` events, never make a request; without `-devtools` the app takes none. A second app's DevTools stream is refused while one is connected, and tries again each second.
- Tools post requests to `/_nsgo/automation` from this machine's loopback, with no `Origin` header, which keeps web pages out, and the tools' token as a bearer; `status`, `logs` (the app's last 2000 lines) and `reload` the tool answers itself. The protocol, `internal/automation`, is internal and unversioned, as the tool and the app come from one module version; MCP and `nsgotest` are the public interfaces.
- The session file `.nsgo/automation.yaml`, readable by its user alone, holds the server's address, the tools' token, the process and the target. It goes as `dev` ends, and a second `dev -automation` for the app is refused while the first runs and its server answers `status` with the file's token, so the file a crashed one left is replaced even when another process took its ID.
- The app runs with its real data directories, as `dev` runs it, not a test's temporary ones.

`nsgo mcp` (`mcp.go`, on `github.com/modelcontextprotocol/go-sdk`) serves MCP on standard input and output, the tool's other output going to standard error. It uses the session the file names, or starts `nsgo dev -automation` with its own flags as a child, which it stops as the client leaves. Each tool is a request with that request's params as its input, so one definition gives both their schemas: `status`, `windows`, `snapshot`, `find`, `press`, `type`, `key`, `scroll`, `drag`, `hover`, `menu`, `alert`, `wait`, `screenshot` (an `image/png`), `logs` and `reload`. A rebuild restarts the app, so `status`'s run count grows and the `view:` refs of an earlier run are stale. What tools list, find and press is the app's alone: under `-devtools`, `-highlight` or `-layout` the agent leaves DevTools' overlay (`devtools.OverlayTestID`) out, as the page's `Elements` does.

`TestAutomationEndToEnd` builds `testdata/automation` with the tags and drives it through a hub with posted events, the menu bar, the Dock menu and alerts; it opens a window and makes it key, so it runs only with `NSGO_AUTOMATION_E2E=1`. `TestSimulatorAutomationEndToEnd` builds and launches `testdata/automation` in an iOS simulator with `SIMCTL_CHILD_` and drives it through the hub when `NSGO_SIMULATOR_E2E=1`.

## TSX apps

The tool finds a package's TSX entries in its `compiler.App(src, "App.tsx")` calls (`bundle.go`), compiles each with `tsx/bundler` from the app's directory and adds the bundles to the package with a file calling `compiler.Bundled`, through `go -overlay`, built with the `nsgo_bundled` tag, which leaves the compiler out. The overlay names the package's directory as `$PWD` spells it and by its real path, since `go` names the files by either. `nsgo dev` compiles hot bundles ([TSX](tsx.md#developing)) and watches the files they compile from apart from the Go ones: a change of them alone compiles the TSX again and sends `bundle <entry>` over `/_nsgo/events`, which `/_nsgo/bundle?entry=` serves, with no Go build; a failed compile shows as a failed build does.

A web release's bundles are split ([TSX](tsx.md#split-bundles)): `buildWeb` writes each chunk as `chunks/<module>.<10 hex>.js` before the Go build, and the file the overlay adds gives `compiler.BundledChunks` their URLs.

## New apps

`nsgo init` (`init.go`) writes an app of `-template` `go` (the default), `tsx` or `mixed`, NSH's `ts` and `mixed` templates: `nsgo.yaml` and tests each, and for TSX a main package embedding the sources, `App.tsx`, `app.test.tsx`, `tsconfig.json` and `.gitignore`; `mixed`'s `App.tsx` imports a Go component, function and class `native.go` registers under `<slug>/native`. It refuses a directory holding any of its files. `TestInitTemplates` writes each and runs its tests against the checkout.

`-template <module>[@version]` adds a template from a Go module's `template/` directory. `init_module.go` runs `go mod download` outside the caller's workspace, preserving Go's cache, proxy and checksum settings and disabling direct repository downloads. It renders `main.go`, `nsgo.yaml` and `*.tmpl` with the built-in templates' fields, then copies the other files as-is. It checks output paths before writing and removes files it creates if a write fails. NSH has no module templates.

## Catalogs

`i18n.go`, `i18n_message.go`, `i18n_gen.go` and `i18n_build.go` check packages' catalogs and write their Go code ([languages](languages.md#the-tool)): `dev`, `build` and `test` before they compile, `check` without writing, and `nsgo i18n` for one directory. `dev` watches the YAML files of the directories it watches, and the app's catalogs before it imports them.

## Modules

The first step of `dev`, each rebuild's included, and of `build`, `check` and `test` lists the app's packages and their dependencies (`appPackages` in `i18n_build.go`). When go list says the module's `go.mod` or `go.sum` lacks what one of them comes from, as after pasting an app that imports `ui` into a module made with `go get github.com/nsgo-dev/nsgo`, the tool runs `go mod tidy` and lists them again, so the build after it finds them. It then requires `tsx` at the NSGo version the app requires, since the types `check` and `dev` write import it through an overlay `go mod tidy` cannot see; writing them after a tidy the user ran does the same.

Every go command the tool runs for an app, this listing included, takes the same tags (`goTags` in `tags.go`): those of `-tags` in `GOFLAGS`, from the environment or `go env -w`, then `build.tags`, then the tool's own for the command (`nsgodev` and `nsgoautomation` for `dev`, `nsgo_bundled` for a TSX app's bundle, `nsgotest` for target tests, `nsgocheck` for headless ones, `nsgowatch`, the mini programs' and `nsgoembed`). The go command lets a `-tags` on the command line replace the one in `GOFLAGS`, so the tool passes them all as one, and only when there are any; it never sets `GOFLAGS` itself, so the rest of the app's applies.

Every go command that links the app takes `build.ldflags`, with the values of `build`'s and `test`'s `-ldflags` after them, at the head of the tool's own `-ldflags` (`project.ldflags`); headless tests pass them alone. The linker keeps a variable's last `-X`, so the app stamps its own variables but cannot replace the identity, update or dev values the tool sets.

## Checking

`nsgo check` (`check.go`) checks the catalogs, runs `go vet ./...` and, for an app with a `tsconfig.json`, as only a TSX app has, writes the declarations of the modules its TSX imports to `.nsgo/types`, with `.nsgo/tsconfig.json`, and runs TypeScript 7's checker (`tsgo`, a pinned version of `github.com/microsoft/typescript-go` that `go run` builds and caches) on the app's `tsconfig.json`, which extends it. In NSGo's own repository it vets the root again with the `nsgodev` tag, and macOS dev builds with `nsgoautomation` too, tags only `nsgo dev` sets, so the dev client and the automation's agent are checked as well. A directory without `nsgo.yaml`, such as the repository's root, is checked as a tree of packages: catalogs and `go vet` alone. `-target` vets for each target named instead of the host and the dev client, in the environment its build sets (`GOOS`, `GOARCH`, cgo with Xcode's clang for iOS), so code behind another platform's build tags is checked from a Mac too, and a run for some targets repeats no plain check's work. In NSGo's repository each target also vets `internal/platform/...` with `nsgotest`, checking its test hosts against `testhost.Surface`; HarmonyOS adds `nsgoharmony`, as its app builds do. `all` is `build`'s list of what a Mac with Go and Xcode builds, but `check` skips its Apple mobile targets off macOS, or on a Mac whose SDK or clang lookup for one fails, such as an Xcode without the watchOS platform, and names the skipped targets and the first reason in one warning; a target named on its own, even beside `all`, stays required, and `build -target all` still needs Xcode. `-jobs n` vets up to n targets at once and passes `-p n` to each `go vet`, so one check bounds the compilers it runs, n² at most; without it targets go one at a time with go's own `-p`. A target whose vet fails does not stop the others: their errors are returned together in the targets' order, and cancellation starts no more. A check holds the operating system's lock on `.nsgo/check.lock` at its module's root (`lockCheck`; `flock`, or `LockFileEx` on Windows), so a second check in the module names the first's pid and waits, and a killed check's lock goes with its process. The declarations come from the app's own program: the tool builds its main package with a file, added through the overlay, whose `init` runs after the package's others, so after every `tsx.Register`, writes them and exits before `main`. It checks with `go list` that the file is in the package before it builds, so the app itself never runs. A directory with `nsgo.yaml` but no Go, such as the TSX app a package holds, has nothing to vet, and its declarations are those of every module NSGo gives, from a main package the tool writes in `.nsgo/typesmain` importing them all, since the host decides which its packages may import. `nsgo dev` writes them too, for editors, after each Go build of an app with a `tsconfig.json` once the app has started; a failure only warns.

## Doctor

`nsgo doctor` (`doctor.go`) looks at the machine, starting nothing, and lists the tools it found, then each target with whether it builds and runs there: `✓`, `✗` with what to install or connect, or `–` for what no tool could change, such as another system's apps or Apple's on a Mac-less machine. It reuses the lookups the commands make, `findAdb`, `findNDK`, `findBrowser`, `simulators`, `iosDevices` and `canOpenMiniProgram`, so it and they agree, and reads Linux's libraries from the library directories, as the backend's `dlopen` would find them, with GTK's version from its file's name. It fails only when Go is missing, or older than go.mod's and unable to switch to it: GOTOOLCHAIN `auto` or `+auto` downloads it, `path` or `+path` needs its toolchain (`go1.27.3`) on PATH, and `local` or a Go before 1.21 never switches.

## Tests

`nsgo test` (`test.go`) runs `go test -json` and prints a line per test, with a test running the package's `*.test.tsx` files (`tsxtest.Run`) added through the overlay when it has any, a failure's output under it (a subtest's under its own line), a tally, and with `-junit` a JUnit report, a suite per package; skipped cases keep their diagnostic messages so CI can explain why they did not run. If the process exits without ending its running tests, as a panic on another goroutine or the timeout ends it, those tests fail with their captured output, including the panic and stack, in both the console and the JUnit report; a crash outside any test, in an `init` function or a benchmark, shows under its package and, unlike a package that did not build (`FailedBuild`), is not called a build failure. Given a TSX entry rather than a directory, it runs `TestSteps` instead, which opens the entry on the network, lets it run 1.2 s and takes the steps standard input holds, none from a terminal (`tsxtest.RunSteps`, NSH's `nsh test <entry>`). A directory without `nsgo.yaml` runs every package under it, and one ending in `/...` names its tree, so the tool alone tests libraries and this repository, on a simulator or phone too, where the app the tests run in takes the ID `generatedID` makes of the directory's name, `dev.nsgo.` and its ASCII letters and digits, since Android's packages refuse hyphens and Apple's bundle IDs underscores; the TSX tests it adds skip `testdata` and directories holding an `nsgo.yaml` or `go.mod` of their own. `-bench` passes `-bench` and, unless `-run` is given, `-run '^$'`; `go test -json` ends benchmarks with no event, so each result line it prints counts as a passed test. `-run` filters; `-trace` sets `NSGO_TEST_TRACE`, under which `nsgotest` prints each batch under its step with its items and the commit's time.

In NSGo's own repository, a headless run of the root, `internal` or `internal/dev` then tests `internal/dev` again with `nsgodev`, as `nsgo check` vets it, unless the run's tags already include it, so the dev client's tests run in CI: with the same filters, flags and environment, a later `-tags` taking the earlier's place as in Go, and its packages named with ` [nsgodev]` in the shared tally and JUnit report. It runs after the first fails, as go test goes on past a failing package, but not after an interruption, and its `-coverprofile` is appended to the first run's.

After the path and optional `--`, headless runs forward Go test arguments. Target runs forward `-short`, `-count`, `-cpu`, `-parallel`, `-failfast` and `-fullpath` as test-binary flags, accepting their `-test.` aliases too; unsupported arguments fail before listing, building or finding a device (`parseTargetTestFlags`). On a target `-run` and `-timeout` belong before the path so discovery and the process deadline agree. Discovery uses the top-level part of a subtest filter and receives the supported runtime flags too. A group whose children all skipped is reported and counted as skipped, recursively, unless the group itself failed; a group with a passing child stays passed. This applies to headless and target runs, and its JUnit skip message includes the children's reasons. Each target process yields one result that counts in the tally whatever its name (`parseTestOutput`): a run whose `-run` reached exactly one subtest at the depth it selects, as `Test/sub` or `Test/sub/leaf` does, reports that subtest unless the test failed outside it, and otherwise the top-level test reports its own result, never its first subtest's. Libraries keep Go's in-process `-count` and `-cpu` repetitions, whose results combine elapsed time and preserve a failure over a pass or skip. A package that links the native host launches a fresh process for each count and CPU combination, because phone and web hosts can open only one app per process; repeated results carry `[run N]`, screenshots go into `run-N` subdirectories, and each invocation has its own timeout. A nonpositive count reports zero tests, and `-failfast` stops launching further tests and repetitions after the first failure.

`-target` runs the tests on a platform, a process per test ([testing](testing.md#on-a-platform)), the TSX ones among them; a package whose tests link no platform, as a library's, runs headless in the target's runtime, so `tsx`'s run on the page's engine with `-target web`: the test binary carries the app's TSX, data and assets, since it runs where its sources are not, and starts the app from the bundles compiled ahead, as packages do. `-fps` has the test hosts of macOS, Windows, Linux and the iOS simulator log their performance monitor's readings each second, and those of the web and Android the engine's alone, with no frames, which the tool prints as they come (`NSGO_TEST_FPS`, `testhost.Options.FPS`), as it prints a test's marks of what they measure (`nsgotest`'s `Mark`, logged as `nsgo: perf mark`) with or without it. `-env KEY=VALUE` adds to the tests' environment on every target, the only variables a phone's tests see. macOS, Windows and Linux on this machine, the web in a headless Chrome, Chromium or Edge it finds (or `NSGO_BROWSER`) over the DevTools protocol (`cdp.go`, on `x/net/websocket`), the iOS, tvOS and watchOS simulators through `simctl launch`, or `simctl spawn` for a package whose tests do not start the native test host from `TestMain` (a watch's test host enters touches where the SwiftUI host's do, at Go's hit testing, and scrolls a scroll view as `ScrollTo` does, since watchOS posts no touches for an app), and Android through `am start` with the test in an intent extra and its output read back from the device's log.

The Apple simulator and physical-device launchers do not return the app's exit status. Native test hosts mark each run's start and exit code with the token the tool passes in `NSGO_TEST_RUN`; the simulator runner merges stdout and stderr, keeps panic output and accepts a completed result even when `simctl` fails to attach after the app exits. It ends the console bridge once a result arrives, so a stalled bridge cannot replace that result with a timeout; terminating the app during cleanup takes at most five seconds. As NSH does, simulator setup waits for `simctl bootstatus -b` before installing or launching, since `Booted` can precede SpringBoard's readiness. A missing exit mark fails the run instead of reporting a successful launcher's exit code as the test's, and an app that ends before the start mark fails with simctl's error or, when simctl succeeded, a hint that `TestMain` must call `nsgotest.Main`. A package whose tests link no native host, or link it without a `TestMain`, runs through `simctl spawn`, which returns its process status. `TestSimulatorProcessResults` exercises fast passes and panics in a hosted package, a library and a package that links the host without starting it on an iPhone simulator when `NSGO_SIMULATOR_E2E=1`; `NSGO_SIMULATOR_DEVICE` selects one.

Android target tests check `dumpsys power`, `dumpsys window policy` and `dumpsys trust` before building and before each process starts (`testscreen.go`); whether a credential guards the keyguard is the trust manager's `deviceLocked`, since the keyguard delegate's `secure` can stay `true` with only a swipe lock (Android 9 and 15 after a cold boot). They wake a sleeping display and dismiss a keyguard without a credential, waiting up to 15 seconds for it to be ready. A secure lock or unreadable state fails with the device serial before the test starts. A failed `adb` read is retried three times, 100 ms apart and after `adb wait-for-device` when adb lost the transport (exit status 255); one that keeps failing is a device-lost error (`targetDeviceLostError`), which ends the run once, after the summary of the tests that ran, rather than failing every remaining test. No persistent device settings change.

Android's runtime keeps the test's log listener until stderr drains, even when the protocol pipe ends first. After the child exits, a missing exit or error mark produces `nsgo-test-error` with its process status, so a panic or `os.Exit`, including one before the Go host starts, fails immediately with its output instead of waiting out the test's timeout while the device's log stays open. Target tests install under a `.nsgotest` bundle identity and uninstall that identity after the run, leaving the app's installed build in place. `TestAndroidProcessExitResults` checks those results and JUnit output on a device when `NSGO_ANDROID_E2E=1`; `NSGO_ANDROID_DEVICE` selects one.

## Packages

`nsgo build` strips symbols, paths and VCS stamps (`nsgo dev` keeps symbols unless `-release`) and writes a directory per target under `build.output`, building `build.jobs` targets at once (`-jobs`; half the CPUs by default, and never more than the CPUs), each `go build` with `-p` of the CPUs divided among them (`compileWorkers`), so the compilers of a build stay within the CPU count and a lone target keeps them all. Each builds from a copy of the project, which holds what one target's build sets, and the caches they share are written whole by content or under a lock, as the Android debug key is; the first target to fail stops the others and leaves no directory. Every build of an app, its tests' on a target too, takes `GOEXPERIMENT=nojsonv2`, encoding/json's first implementation, which from Go 1.27, where encoding/json is built on encoding/json/v2 by default, is about 1 MB smaller on the web, 450 KB on Android and 100 to 450 KB on desktops (Go 1.26 builds the first implementation already), unless its packages or dependencies import `encoding/json/v2` or `jsontext`, or `GOEXPERIMENT`, in the environment or set with `go env -w`, names the experiment; the tool adds `nojsonv2` to the experiments `go env GOEXPERIMENT` reports, so the others stay (`smallJSON` in `build.go`):

- macOS: `<name>.app`, signed with `sign.identity`, else ad hoc. iOS and tvOS: `<name>.app` and `<name>.ipa`, signed with `sign.profile`, else unsigned; tvOS's are iOS's (`appleOS` in `ios.go`) with its SDK, `GOOS=ios` still, its device family and an icon the Apple TV layers. watchOS: `<name>.app` alone, the Go executable built with the `nsgowatch` tag and the SwiftUI host (`watch/Host.swift`, `watchos.go`) compiled by swiftc into an object its external linker takes, ad hoc signed for the simulator and unsigned for devices; a watch-only app, arm64 alone, so watchOS 26 on Series 9, Ultra 2 and later. Android: `<name>.apk`, signed with `sign.keystore`, else the project's debug key.
- Windows and Linux: the executable with the resources beside it. The Windows executable links one resource object the tool writes into the main package's directory for the build (`writeWindowsResources` in `icon.go`, `winres.go`), as the linker takes `.rsrc` from one object alone: the icon, when the app has one, and a version resource, always, which Explorer's Details, Task Manager and the startup list read. Its fixed version is `version`'s four numbers, with `build_number` the fourth where it fits; `FileVersion` and `ProductVersion` are `version`; `InternalName` and `OriginalFilename` are `<name>.exe`; `CompanyName` is `windows.publisher`, else `windows.store.publisher_name`; `LegalCopyright` is `copyright`; and `ProductName` and `FileDescription` are the catalogs' `appName`, else `name`. Each language Windows has an ID for gets a version resource of its own, which the loader picks by the user's language; the source's is filed as the user's default language (`0x0400`), which it falls back to, as plain language neutral would win over the user's language and the lowest ID would win otherwise. The `.com` companion links the same object. An app's own `.syso` holding resources for the build's architecture replaces the tool's, with a warning.
- With `-embed`, for apps of their own to embed ([embedding](embedding.md)): iOS's `<module>.xcframework` (of dynamic frameworks with `-dynamic`) with `<name>Resources`, Android's `<name>.aar`, and no package for other targets.
- Web: `index.html`, `manifest.webmanifest`, `nsgo.json`, which names the rest for the loader, and every other file named by its content (`app.<10 hex>.wasm`, `nsgo.<10 hex>.js`, `page.<10 hex>.css`, `mount.<10 hex>.js`, `web.host`'s module as `host.<10 hex>.js`, a TSX app's bundle and chunks, the scripts its realm runs as `nsgo-runtime.<10 hex>.js` and each resource), so hosts cache them for good. The page runs the app with the loader, from files of its own and none inline, so a Content-Security-Policy needs no `'unsafe-eval'` ([embedding](embedding.md#on-the-web)). It never zooms, as a window does not: its viewport is not user-scalable, its elements pan but leave pinches and double taps to the views that zoom, and Safari's `gesturestart` is cancelled, as Safari ignores the viewport.
- Mini programs (`miniprogram_wechat`, `_qq`, `_alipay`, `_douyin`): a project for the platform's developer tool, its runtime from `miniprogram/common` and the platform's render layer, and the module brotli compressed in the subpackage `nsgo-app`, with `miniprogram.appid`'s entry for the platform (else the AppID the tool wrote, else WeChat's tourist one) and `miniprogram.custom_navigation`. It is built stripped, without the dev client, and left out of `all`, which says so, while `miniprogram` names the four; past 2 MB it is built again without inlining, then refused ([mini programs](miniprogram.md#the-package)). `-run` and `nsgo dev` open WeChat's with DevTools' command line, whose service port must be on, closing and auto-opening the project after each build so DevTools compiles the fresh files, and the others with their apps on macOS, once a session.

`resources/` ships at each package's resource root: beside the executable on Windows and Linux, beside the page on the web, in the bundle's `Contents/Resources` on macOS, at the bundle's root on iOS and in the APK's assets on Android, which with iOS leave out the paths `mobile.exclude_resources` lists. `imageload.ResourceRoot`, the web backend and Android's APK reader resolve `asset:` and font paths against it. App icons are drawn in Go; an Apple TV's is `icon.tvos`, Xcode's brand assets collection or a wide image, else the PNG over its own edges' color, as a two-layer image stack with top shelf images, since `actool` compiles no `.icon` for tvOS; an Apple Watch's is `icon.watchos`, its own `.icon` or square image, else `icon.apple`, which actool draws in circles; `actool` compiles Apple's `.icon` files, its output kept in the user cache by its version and the icon's content, and a Windows icon links from a `.syso` in the app's package directory, the only place Go links one from.

Native libraries come with the packages that hold them (`natives.go`): when the app's build links `base/terminal`'s library package, as `go list -deps` tells, libghostty-vt goes into a macOS app's `Contents/Frameworks` and an iOS app's `Frameworks/GhosttyVT.framework`, signed before the app so its signature seals them: ad hoc for macOS and the simulator, with the store's identity, or in Xcode's signing script for a device. `-embed` frameworks, Android and tvOS packages carry none yet ([roadmap](../roadmap.md#terminal)).

`build_number` sets `CFBundleVersion` and `versionCode`, else they follow `version`. `android.permissions` adds `uses-permission`s to the APK's manifest beyond the runtime's, a name without a dot under `android.permission.`, and a direct channel's APK asks for `REQUEST_INSTALL_PACKAGES` as well, for `updater`'s installs; `android.recording` declares the runtime's `RecordingService`, a foreground service of the microphone type, with `RECORD_AUDIO`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE` and `POST_NOTIFICATIONS`, without which its notification does not show from Android 13, in the APK's and the bundle's manifest, which an app recording with `microphone.RecordWAV` needs and Google Play asks an app to justify, so no other app declares it ([Android recording](android-recording.md)); `-embed` libraries leave both to the host's manifest. An app that reads `core.Env.Geometry`, as its executable and its sources both tell, declares the device's `androidx.window.extensions` library without requiring it, in its APK, bundle or AAR, and no other app does ([foldable displays](foldable.md#platforms)). Listing `SYSTEM_ALERT_WINDOW` declares the overlay's `specialUse` foreground service with `FOREGROUND_SERVICE` and `FOREGROUND_SERVICE_SPECIAL_USE`, in the APK's manifest and the `-embed` library's, and no other app declares them ([Android floating windows](android-floating-windows.md)). Listing `FOREGROUND_SERVICE_LOCATION` declares the runtime's `LocationService`, a foreground service of the location type that background location streams run in, in the APK's and the bundle's manifest, and no other app declares it; `-embed` libraries leave it to the host's manifest ([location and motion](location-motion.md#permissions-and-packaging)). `apple.info` adds scalar, array and dictionary entries to the Info.plist of macOS and iOS packages, such as the `NSMicrophoneUsageDescription` recording needs; a string entry whose key is a message of the app's catalogs is localized in each language's `InfoPlist.strings` ([languages](languages.md)). Device bundles for iOS, tvOS and watchOS add Xcode's SDK metadata and `UIRequiredDeviceCapabilities` for `arm64` to the app and extensions; simulator bundles omit these device-only entries, and an `apple.info` value wins over generated metadata. `apple.requires_full_screen` sets the iOS package's `UIRequiresFullScreen`, true unless it is false, which lets an iPad run the app in Split View, Slide Over and Stage Manager and declares all four orientations in `UISupportedInterfaceOrientations~ipad`, as App Store Connect requires of an iPad app that multitasks; `apple.orientations` lists them for a full-screen app instead, and must list all four for one that multitasks. `apple.info` may set neither key. `file_types` registers documents in macOS's `CFBundleDocumentTypes`, Windows's NSIS and MSIX packages, and Linux desktop entries with `MimeType` and `%F` (`filetypes.go`, `linuxfiletypes.go`): macOS exports app-owned IDs and imports others; NSIS records app-specific ProgIDs and extensions for guarded upgrade/uninstall cleanup; Linux uses the fixed `internal/mimeinfo` extension table or explicit `mime` references to system types, generating `application/x-<id>` and MIME-info XML for unknown owned extensions. Debian/Arch refresh caches after installation and removal; Flatpak installs the definition for export; AppImage bundles it for integration. Other targets leave the declarations out ([roadmap](../roadmap.md#application-and-windows)). `windows.command_line` adds a console-subsystem `<name>.com` beside the GUI `<name>.exe` (`windows_command.go`), forwarding arguments, standard streams and the exit code to it, so command lookup can run the app without changing its Explorer and Start menu behavior; the console's Ctrl+C and close reach the companion alone, which ends the app, as does the job it puts the app in when the companion is killed. Win+R, Task Manager's "Run new task" and Explorer's address bar look a bare name up through `Path` too and find the `.com` first, giving it a console of its own; with no other process on that console and its output not redirected, the companion starts the app untied to it and exits, so the console closes instead of staying open beside the app as a window whose close would end it. Store builds leave it out, since an MSIX installs where no command lookup finds it. `appearance` starts the app light or dark through `-X`, and sets `UIUserInterfaceStyle`, macOS's Aqua appearance, Android's activity theme and the page's `color-scheme`. `-run` starts the package of the first target this machine runs: the app, the iPhone's or Apple TV's, the simulator's, the Android device's, or the site served with a CDN's cache headers. `-device` picks the device as `nsgo dev`'s does; Xcode signs the iPhone's package again for `-team`, as in the dev loop, since devices install only development builds.

`android.loopback_cleartext` adds `android:networkSecurityConfig` to the APK's and App Bundle's application manifest. The `apk` package compiles the policy as binary XML for APKs and protobuf XML for bundles, with a resource table entry in each. The policy permits cleartext to the exact loopback host names `localhost`, `127.0.0.1` and `::1` and denies cleartext elsewhere. An AAR takes its host app's policy.

### Installers

Unless `build.installers` is false, `installer.go`, `dmg.go`, `nsis.go`, `linuxpkg.go` and `appimage.go` add what users install the desktop packages from, named `<slug>-<version>-<system>-<arch>` (`releaseName`) by the app's slug (`packageSlug`: its name in lowercase ASCII words, else its ID's last part), so a release page tells its files apart by system; MyGo's CLI makes them so (`mygo/cmd/mygo`) without the system's name. The Linux packages take it too, since dpkg and pacman read the name and version from inside. `release.go` moves each into `build.output`'s `releases` directory with a `<file>.sha256`. That directory holds everything to hand out, the one place to look: the installers, IPAs and APKs copied from their packages, the site zipped as `<slug>-<version>-web.zip` and the mini programs' projects in `miniprogram/<platform>/`, but no simulator's or watchOS's bundle. Machines building different targets add to it, so `.version` records its version, and a build of another empties it:

- macOS: `<slug>-<version>-macos-<arch>.dmg`. hdiutil images a folder holding the bundle, copied by `ditto --noclone`, a link to `/Applications`, the background picture in a hidden `.background` (`dmgbackground.go`: `macos.dmg_background`, joined with its `@2x` twin by `tiffutil`, else an arrow drawn in Go at both scales), a `.DS_Store` the tool writes (`dsstore.go`, MyGo's) placing the icons a quarter in from each side, each with its name centered from top to bottom (`dmgLabelDrop`, measured in Finder), and the hidden files stacked below the window at its left, so it scrolls no wider, which it sizes to the picture plus macOS 26's 32-point title bar, and `macos.dmg_icon` or the app's icon as `.VolumeIcon.icns`. Finder finds the picture through a Mac alias (`macalias.go`, as Python's `mac_alias` writes it for dmgbuild, checked against it byte for byte), whose node IDs and dates only the mounted image tells, so the layout is written again there over a placeholder of its size, and the volume's icon flagged; LZMA compresses it, through `diskutil image create from` where macOS 27 fails `hdiutil convert`. `sign.identity` signs it, and `notarize.go` notarizes it ([signing](#signing)).
- Windows: NSIS, as MyGo's CLI, whose makensis runs on macOS too. The script refuses compilers older than 3.06, whose `DeleteRegKey /ifempty` ignores values, so the document cleanup would delete other apps' Open With values and defaults with an extension's key. Every build writes `<name>.nsi` beside the executable, naming the files relative to itself, with `windows.installer_icon` and `windows.uninstaller_icon`, else the app's icon, as `<name>-setup.ico` and `<name>-uninstall.ico`, the executable's publisher and copyright as the setup's and its uninstall entry's, and compiles `<slug>-<version>-windows-<arch>-setup.exe` where makensis is on `PATH` or in NSIS's folder on Windows. When `windows.command_line` is true, the package also holds the console `<name>.com` companion, and the installer puts its folder on the user's `Path` under `HKCU\Environment`, announcing the change with `WM_SETTINGCHANGE`, which the uninstaller takes off again; PowerShell edits the value, unexpanded and whole, where NSIS's 1024-character strings would cut a long one. It installs for the user in `%LOCALAPPDATA%\Programs\<name>`, and again where the uninstall entry under `HKCU`, keyed by the bundle ID, says it is (`InstallDirRegKey`), which a silent install keeps as long as nothing passes `/D`: MyGo's `install.ps1` passed `/D` with the default folder, moving an app installed elsewhere. It quits the app running from that folder first, through PowerShell, asking unless silent, and its uninstaller deletes the files the build listed and their folders once empty, never `RMDir /r`, so a folder the user picked keeps what else it holds. It speaks the catalogs' languages the Modern UI translates, with words of its own for the desktop shortcut and the running app (`nsisWords`); `arm64` installers refuse other systems.
- Linux: a `.deb` and an Arch `.pkg.tar.gz`, archived in Go as no Mac has dpkg or makepkg, installing the directory in `/opt/<slug>`, `/usr/bin/<slug>`, a desktop entry whose `StartupWMClass` is the app ID, which the Linux backend gives the process as its program name before GTK opens the display, so X11's `WM_CLASS` and Wayland's app ID match it, and whose `Categories` are `linux.categories`, checked as `desktop-file-validate` checks them and required to hold a main category, and the icon in hicolor at 256 and 512 pixels. They depend on GTK 4 and recommend WebKitGTK 6, and append the app's `linux.depends` and `linux.recommends` entries to the Debian and Arch metadata, naming `linux.maintainer`, else the app's name. Beside them, an AppImage: AppImage's type 2 runtime, a static executable `fetch` downloads once by its pinned SHA-256 (`appImageRuntimes`), followed by a SquashFS 4.0 image `squashfs.go` writes, as no Mac has mksquashfs: zlib-compressed 128 KB data blocks with no fragments, 8 KB metadata blocks, inodes numbered children first, so a directory's listing knows its entries' inodes, and extended directory inodes for listings past 64 KB. Its AppDir is the Linux package with `AppRun`, a link to the executable, and `.DirIcon`.

When the build has a macOS, Windows or Linux target, the releases directory also holds `install.sh` and `install.ps1` (`install/`, NSH's install scripts made the app's), which download from `releases/download/<tag_prefix><version>/`, the version theirs unless `<SLUG>_VERSION` gives one, so the latest release's scripts install it, from `release.github`, else the GitHub repository the Git remote `origin` names, and check each file against its `.sha256`. The shell one copies a macOS app from the disk image, Apple silicon's even under Rosetta, or installs the Arch package with pacman, else the Debian one with apt-get or dpkg; the PowerShell one runs the installer with `/S` alone, and keeps to ASCII (`psQuote`), as `irm` decodes GitHub's untyped files as Latin-1. `<SLUG>_DOWNLOAD_URL` replaces the release's address, for mirrors and tests.

### Store packages

A `store` build (`-channel store`) makes each desktop and Android target's package for its store instead of its installers, and no install scripts:

- macOS (`macstore.go`): `<slug>-<version>-macos-<arch>.pkg`, the app in the App Sandbox with the network, the files the user picks, the microphone, camera, calendars and Bluetooth `apple.info` explains and `macos.entitlements`, `sign.macos_profile` embedded as `embedded.provisionprofile` with its application and team identifiers, signed with the profile's identity, and packaged by productbuild, signed with `sign.installer`, else the keychain's installer identity of the profile's team. Without a profile it is signed ad hoc and unsigned, which runs sandboxed but uploads nowhere. It is never notarized, and refuses widgets, whose timelines a sandboxed app cannot share yet. `internal/platform/macos` loads CoreFoundation with the executable (`sandbox.go`): its initializer has libsecinit enter the sandbox, which a Go executable loading AppKit alone never does, so AppKit's Launch Services check aborts it.
- Windows (`msix.go`): `<slug>-<version>-windows-<arch>.msix`, written as makeappx would: the package's files stored, its logos under `Assets`, `AppxManifest.xml` with `windows.store`'s identity, a full-trust app, its languages, `file_types` and the devices `windows.device_capabilities` declares, `AppxBlockMap.xml` hashing every file in 64 KB blocks past its local header, then `[Content_Types].xml`. It is unsigned, for the Store, which signs it; Windows installs no unsigned package with an executable, so testing registers its unpacked manifest with `Add-AppxPackage -Register` ([roadmap](../roadmap.md#installers)). Signing it is `AppxSignature.p7x`, which `sign.certificate` does not write yet ([roadmap](../roadmap.md#installers)).
- Linux (`flatpak.go`): `<slug>-<version>-linux-<arch>.tar.gz`, the package with its AppStream metadata, and once the targets are built `flatpak/<id>.yml`, a manifest on GNOME's runtime (`linux.flatpak_runtime`, 51 by default) that installs each architecture's archive from the release, or from beside it without a GitHub repository or feed, for Flathub or flatpak-builder to build. A `.flatpak` bundle is an OSTree commit, which no Mac writes.
- Android (`apk/bundle.go`): `<slug>-<version>-android-<arch>.aab`, the base module's manifest and resource table as aapt2's protocol buffers, from the same manifest and table the APK's binary XML encodes, `BundleConfig.pb` keeping native libraries compressed, which the runtime needs extracted, and a JAR signature with `sign.keystore` (`apk/jar.go`), Play's upload key. The manifest targets the API level Play requires, 36, which `android.target_sdk` replaces; a release build warns when it is below that level (`androidTargetWarning`).

### Steam depots

`steam.go` limits the Steam channel to desktop targets, including `macos_universal`. The tool writes the ordinary signed bundle or executable directory and skips installers, store archives and the releases directory. Native `dev` with `steam.app_id` writes `steam_appid.txt` into its build directory and launches the app there, which is where Steamworks reads the file. Steam release and development packages filter copies of that file out of app resources.

### Updates

`updates.go` builds each package for the channel `updates.channel` or `-channel` names, as [updates](updates.md#channels) describes; development builds never update. Only the direct channel adds anything to a package beyond `-X` flags giving `nsgo.Run` `updates.automatic`; every build, development ones too, gets the app's identity, version and build number in `core` (`core.App`).

- Each direct macOS, Windows, Linux and Android release writes `appcast-<target>.xml`: Sparkle's RSS format, with one item, this version's installer, signed with EdDSA by `NSGO_UPDATES_KEY`'s key, which must be `updates.key`'s secret one. `-release-notes`' Markdown becomes the item's `<description>`, HTML rendered by goldmark without raw HTML, which Sparkle and WinSparkle show and `internal/platform/updates` turns back into text for the updater's prompt.
- There is one feed per target, since machines build targets apart, so nothing filters by `sparkle:os` or architecture. The direct `macos_universal` target writes one universal DMG and `appcast-macos_universal.xml`; macOS and Windows get none without the secret key, as Sparkle and WinSparkle refuse unsigned updates; Linux and Android still get theirs, unsigned, which the app answers with the release's page rather than an install.
- The feed is `updates.feed`, else `release.github`'s `releases/latest/download/`. The keys are `nsgo keygen`'s, which is Sparkle's format too: `updates.key` holds the public key itself, and the secret one lives only where releases build.
- macOS packages carry Sparkle 2.10.1, unpacked by macOS's tar to keep its links and signatures, and signed inside out as Sparkle documents. Info.plist names the feed, key and schedule.
- Windows packages carry WinSparkle 0.9.4 beside the executable. The appcast runs the installer with `/S /RELAUNCH`, which starts the new version once installed.

Sparkle and WinSparkle are downloaded once into the user cache and checked against pinned SHA-256s, not committed as `classes.dex` is: they are other projects' builds, 16 and 27 MB of archives, that only a direct app needs, and WinSparkle builds with Visual C++ alone. Targets build at once, so one at a time downloads and unpacks them.

### Widgets

`widgets.go` adds a widget extension to the macOS and iOS packages of an app whose `nsgo.yaml` lists `widgets`, as package `widget` describes ([layers](layers.md#dependency-graph)). WidgetKit declares widgets in Swift alone, and its views are SwiftUI's, so neither purego nor the Go runtime can make one, and the extension runs none of the app's code: the app writes timelines, and a generic extension draws them.

- `widgets/Widgets.swift` decodes a kind's `timeline.json` and builds SwiftUI views of its nodes, with a policy of `.never`, as the app reloads it; it reads images with ImageIO at no more than 1024 pixels across, as the system bounds a widget's memory. `Kinds.swift`, written from `nsgo.yaml`, declares a `Widget` per kind in one `WidgetBundle`, which holds ten. The extension links with `-e _NSExtensionMain`, as Xcode links app extensions.
- `WidgetCenter`'s methods take `self` in a register purego does not set, so `widgets/Reload.swift` exports `nsgo_widgets_reload` with `@_cdecl`, in `libNSGoWidgetKit.dylib` on macOS and `NSGoWidgetKit.framework` on iOS, which the package loads from the bundle's frameworks with the first `Update`.
- Both compile with `xcrun swiftc` for the target, kept in the user cache by their sources, the target and the toolchain, as actool's icons are. The extension is `PlugIns/Widgets.appex`, `<id>.widgets`.
- Where timelines live, the Info.plists of the app and the extension say. On iOS, an app group's container (`NSGoAppGroup`, `apple.app_group` else `group.<id>`), which the simulator grants from ad hoc signatures' entitlements and devices from `sign.profile` and `sign.widgets_profile`. macOS opens a group's container only to apps a profile grants it, which no ad hoc signature has, so the macOS app writes `~/Library/Application Support/<id>/Widgets` (`NSGoWidgetsPath`), which the extension, in the App Sandbox as macOS runs widgets, reads through a read-only temporary exception, from the user's home rather than its container's (`getpwuid`).
- The extension is signed before the app, which is signed without `--deep`, so its entitlements stay its own. `nsgo dev` registers it with `pluginkit -a`, as it starts the app's binary rather than the bundle. For Xcode's device signing, the generated project gives it a target of its own, `<id>.widgets`, which copies the build's extension, is signed automatically and embedded in the app, both claiming the app group, which automatic signing registers; `-embed` packages carry none.
- `live_activities` gives the iOS app the extension too, `NSSupportsLiveActivities` and the app group. ActivityKit's `Activity` is generic over Swift types, so one `NSGoActivityAttributes` (`widgets/Activity.swift`, in both the extension and the library) holds a kind and an ID, and its content-state is the JSON package `widget` writes: the fields, which `widgets/ActivityViews.swift` lays out, and the views the app gave, drawn as timelines' are. Defaults drawn in Swift keep a state within ActivityKit's and APNs' 4 KB, and let a server push one without NSGo's views. `widgets/Activities.swift` exports the library's functions to start, update, end and list them and a callback for presses and push tokens; the library is weakly linked to ActivityKit and App Intents, younger than iOS 15.
- A button's `NSGoActionIntent` is a `LiveActivityIntent`, which iOS runs in the app's process: the library's copy, built with `NSGO_APP`, waits for Go's callback, which `OnAction` sets before `nsgo.Run` as no view runs in a background launch, and then for the updates the handler started. App Intents finds intents by the metadata Xcode extracts, so the tool compiles both with `-emit-const-values-path` and the toolchain's `SwiftConstantValues/AppIntents.json`, and runs `appintentsmetadataprocessor` as Xcode does, into `Metadata.appintents` of the extension and of the app; they match by the intent's name, whatever its module.

### App Clips

`appclip.go` nests an App Clip in the iOS package of an app whose `nsgo.yaml` has `app_clip`. The clip is an iOS app of its own, built by `buildIOSApp` from `clipProject`: the app's project under the clip's name, ID (`<id>.Clip`) and main package (`app_clip.main`, whose `resources/` it takes), without widgets or a clip. It goes to `AppClips/<name>.app`, its Info.plist holding `NSAppClip` and its `MinimumOSVersion` `app_clip.minimum` (16.0, as iOS 15 downloads clips of 10 MB alone).

- A device build larger than the system downloads, 15 MB or from iOS 17 100 MB, fails; the simulator's warns.
- `sign.clip_profile` signs a device build's clip before the app, as the widgets' profile does, its associated domains `appclips:` `app_clip.domains`; the app's profile must list the clip (`associated-appclip-app-identifiers`). The simulator refuses to launch an app whose ad hoc signature claims a `com.apple.developer` entitlement, so simulator builds claim none. Xcode's device signing leaves the clip out of the app with a warning ([roadmap](../roadmap.md#app-clips)).
- `nsgo dev -clip <url>` runs the clip alone, opened from the link: in the simulator it installs the build's clip and launches it with `_XCAppClipURL`, as Xcode does, and the iOS backend takes that as the opening link when no activity brings one, as `simctl` sends none. On an iPhone Xcode signs the clip as an App Clip product (`on-demand-install-capable`), with entitlements naming its parent through `$(AppIdentifierPrefix)` and its domains, and `devicectl` launches it with `_XCAppClipURL`; a personal team, which Apple lets sign no clip, is refused first, as Xcode's preferences mark it (`freeTeam`). It then prints the link as a QR code of half blocks, which the camera opens the clip from once the device's Local Experiences list the link.
- The backend reads a link from the scene's `NSUserActivityTypeBrowsingWeb` activities, as it connects and in `scene:continueUserActivity:`, into `Environment.OpenedURL`, and `NSAppClip` in the main bundle's Info.plist into `AppClip`.

### In-app purchases

`storekit.go` puts a library of `storekit/StoreKit.swift` among the frameworks of the macOS, iOS and tvOS packages of an app whose `nsgo.yaml` sets `apple.purchases`: StoreKit 2's products and transactions are Swift's alone, so the library exports `nsgo_storekit_start` and `nsgo_storekit_call` with `@_cdecl`, which `internal/platform/apple` loads through purego and calls with JSON ([services](services.md#in-app-purchases)). It is `NSGoStoreKit.framework` on iOS and tvOS and `libNSGoStoreKit.dylib` on macOS, compiled with `xcrun swiftc` for the target, macOS 12 at least, and kept in the user cache by its source, the target and the toolchain, as the widgets' are; it is signed as the bundle's other frameworks and libraries are. It claims no entitlement, as In-App Purchase needs none. Apps without the setting link none of it, App Clips never do, and watchOS leaves it out with a note.

## Signing

`sign.identity` signs macOS packages, libraries first: macOS keeps the permissions it grants an identity's app across builds, where each ad hoc signature counts as a new program. `nsgo dev` and `nsgo test` stay ad hoc, as macOS credits what a terminal starts to the terminal.

`sign.profile` signs the iOS package: `security cms` opens the profile, whose `application-identifier` must cover the bundle ID; a wildcard profile signs the app's own ID, which devices require. The profile goes in as `embedded.mobileprovision`, and `codesign` signs with `sign.identity`, else the keychain's identity for one of the profile's certificates. `-profile`, `-widgets-profile` and `-clip-profile` replace the app, widget extension and App Clip profiles from the command line.

`apple.sign_in_with_apple` claims `com.apple.developer.applesignin` with `Default` (`claimSignInWithApple`, `xcodeEntitlements`): in the entitlements Xcode's device signing registers, and in a device build's or a Mac App Store build's, whose profile must grant it, the build failing otherwise; a profile granting it claims it for no app that does not ask. macOS grants it only with a profile, so a direct macOS build leaves it out with a warning, and simulator builds, whose ad hoc signatures claim no developer entitlement, leave it out too ([services](services.md#sign-in-with-apple)).

`sign.notarize`, a notarytool keychain profile, or an API key in `NSGO_NOTARY_KEY`, `NSGO_NOTARY_KEY_ID` and `NSGO_NOTARY_ISSUER`, notarizes the macOS package of a release build (`notarize.go`), refused without a Developer ID `sign.identity` before anything builds. Every executable is then signed with the hardened runtime and a secure timestamp (`macSignArgs`), the app with the device entitlements `apple.info`'s usage descriptions ask for; the disk image, else the app zipped by `ditto`, goes to `notarytool submit --wait`, and the ticket is stapled to the image and the app. A rejection's error carries `notarytool log`.

`sign.keystore` signs release APKs (`apk/keystore.go`): PKCS#12, with PBES2 (PBKDF2 and AES or 3DES) as keytool and OpenSSL 3 write it or PKCS#12's SHA-1 schemes with 3DES and 40-bit RC2 as older tools do, or JKS, whose key protector is a SHA-1 stream of the password. `NSGO_KEYSTORE_PASSWORD` and `NSGO_KEY_PASSWORD` give the passwords, never `nsgo.yaml`; `sign.key_alias` picks a key. APKs sign with RSA keys only.

`sign.certificate`, a PKCS#12 that `apk.ReadKeystore` reads with `NSGO_CERTIFICATE_PASSWORD`, signs Windows packages with Authenticode in Go (`winsign.go`, `authenticode/`), so a Mac needs no Windows SDK: the executable, the command companion, the resources' PE images that carry no signature yet, and the installer. `authenticode/` appends a `WIN_CERTIFICATE` holding a PKCS #7 SignedData over the image's digest, as signtool and osslsigncode do: the digest covers the headers without the checksum and the certificate table's entry, every section's data in file order, and the bytes the sections leave out, whose last partial block pads to 8 bytes (NSIS's uninstallers need it), and it recomputes the PE checksum. An image signed before is signed again in place of that signature rather than twice. `sign.timestamp_url`, DigiCert's unless `none`, asks an RFC 3161 server for a token, which the signer carries as its unsigned attribute so the signature outlives the certificate. `sign.sign_command` signs each file with a tool of its own instead, `%1` standing for the path, for a certificate on a hardware token or in a cloud service. The installer's uninstaller is written by makensis, so signing it takes `!uninstfinalize`, which runs `nsgo sign-uninstaller` with the certificate in the environment, and needs NSIS 3.08; without it the uninstaller stays unsigned. `-certificate`, `-sign-command` and `-timestamp-url` replace the three from the command line.

## Signed packages

`publish.go` drives `tsx/pkg` ([signed packages](tsx.md#signed-packages)). Keys are base64 text, never files: `keygen` prints a pair, a 32-byte Ed25519 public key and the seed of its secret one, and writes nothing. Public keys are given as text, in flags, `nsgo.yaml` and apps' code; secret keys only in the environment, `NSGO_ROOT_KEY` for a root's and `NSGO_RELEASE_KEY` for a release key's, as `NSGO_UPDATES_KEY` gives updates' ([updates](#updates)), so none sits in a file beside the project, in shell history or in a process list. `certify` has the root certify the release key `-key` for `-apps` and `-days`, writing `-out`, `release.cert` by default, as JSON. `publish` compiles the app's TSX entry, the one its main package runs or `-entry`, else `App.tsx`, and signs it as the app of `nsgo.yaml`, its build `build_number` else Android's code of its version, with its `capabilities` (`capabilities.go`, read strictly and in snake case, as every command loading `nsgo.yaml` does), into `build.output`'s `<name>-<version>.nsgopkg`; given a package instead, it signs that again, to `-out`. It refuses to sign what devices would refuse. `verify` checks a package against the public keys `-root` lists and the revocation list files `-revocations` lists, or without roots against itself alone, and prints what it holds, its capabilities included, warning of a root whose list expired; `revoke` has a root sign list `-sequence` of release key IDs and packages, by SHA-256 or file, a root's lists counting up on their own and each holding all the root revokes, which expires in `-days` when given and otherwise never.

## Store listings

`listings.go`, `listings_appstore.go` and `listings_play.go` drive `nsgo publish -store appstore|play|all` (and `-dry-run`). Store metadata lives in `store/` (or `nsgo.yaml`'s `store.dir`, or `-listings`) as a strict, versioned (`version: 1`, unknown fields refused) top-level `listing.yaml` and per-locale `<locale>/listing.yaml` with optional `description.md`, `release_notes.md`, `promotional_text.md` and relative screenshot/preview files. Validation checks schema versions, locales (mapping canonical tags such as `zh-Hans` to `zh-Hans` on App Store Connect and `zh-CN` on Google Play), required fields, store character limits in Unicode runes, URL schemes and media files before reading credentials or making any HTTP request. App Store Connect uploads authenticate with ES256 JWTs signed from `NSGO_APP_STORE_KEY`/`KEY_ID`/`ISSUER` (falling back to `NSGO_NOTARY_*`); Google Play uploads exchange RS256 service-account JWTs from `NSGO_PLAY_SERVICE_ACCOUNT` for OAuth2 tokens and commit edits through Android Publisher API v3.
