# Application and windows

An app opens what it shows itself, as an Avalonia application does: windows, panels, tray icons and global shortcuts, on one engine whose windows share its signals. Read this before changing `nsgo.Run`, `nsgo.SetMainView`, `desktop`'s windows, tray icons, shortcuts or shutdown, or how the engine attaches surfaces. macOS opens the full set, Windows and Linux open them for `nsgo.Run(App)`, and Linux also handles global shortcuts; the [roadmap](../roadmap.md#application-and-windows) orders the remaining Windows and Linux work.

## Model

`nsgo.Run` takes a root view or the app's function. The function runs once, in the app's own scope, and decides what to open:

```go
func main() { nsgo.Run(App, nsgo.HideDock()) }

func App(app *core.Scope) {
	desktop.SetShutdownMode(app, desktop.ShutdownOnExplicit)
	panel := desktop.OpenPanel(app, desktop.PanelOptions{HideOnBlur: true}, Panel)
	desktop.NewTray(app, desktop.TrayOptions{View: TrayIcon, Panel: panel, Menu: trayMenu})
	launcher := desktop.OpenPanel(app, desktop.PanelOptions{Width: 480, Height: 64, HideOnBlur: true}, Launcher)
	desktop.RegisterHotKey(app, "ctrl+alt+space", launcher.Toggle)
}
```

| App | Opens |
| --- | --- |
| Desktop app | `nsgo.Run(Root)`: a main window, the app ending as it closes; others, such as settings, with `OpenWindow` |
| Tray app | A tray icon whose primary click shows a panel and secondary click a menu; an optional welcome window; `ShutdownOnExplicit` and `nsgo.HideDock` |
| Background app | Global shortcuts that show a panel, as Raycast's; an optional welcome window; `ShutdownOnExplicit` |
| Phone or web app | The view `nsgo.SetMainView` sets, or the root view; `desktop`'s functions do nothing |

`examples/tray` is a tray app with all of them.

## Crash reports

Standalone releases set the Go runtime's crash output before starting the platform. A file in `LogsDir()/crashes` starts with the platform, version and build of the crashed app, followed by the runtime's trace. The runtime also writes to standard error. Go controls the detail in its trace through `GOTRACEBACK`.

Foundation's uncaught exception handler records Objective-C names, reasons and stack symbols. The Android activity's default uncaught Java exception handler records the exception and its stack. Windows records the code and address of SEH exceptions that reach its top-level filter. Exceptions Go's Windows runtime handles already go to its crash output. Each native hook passes control to the platform's earlier handler if present.

`Scope.CrashReports()` lists pending reports oldest first and skips files held by a live Go process. Once an earlier file contains only its header, reading the list removes it. `CrashReport.Open()` streams the diagnostic body, and `Acknowledge()` removes the report after the app processes it. The app decides how to present or handle the report. Development builds and embedded iOS hosts keep their own process-wide handlers. Targets without a logs directory return an empty list.

## Surfaces

The engine runs one graph with a tree per surface (`core.Tree`). Where the platform opens windows (`core.RootOptions.Windows`, the main window's options), the first tree is the app's own surface: it shows no view, and the platform gives it no window, or a hidden one on Windows.

- `OpenWindow`, `OpenPanel` and a drawn tray icon make a tree under a scope adopted by the `cx` passed directly (rather than the running owner), so opening a window or panel with the app's scope from a button or menu handler keeps it open after that handler's scope goes, closing when `cx` goes or `Close` is called. Every scope under it knows its tree (`Scope.surf`), so services, key bindings and `desktop`'s window functions act on the window the code is in, and the app's own scope on the first tree.
- `WindowOptions.Parent` links a window to another open window in the same app. Its ID goes in `SurfaceConfig.Parent`, and closing the parent disposes the child without asking its closing handlers. On desktops the child stays above its parent and hides and comes back with it, keeping an explicit child hide until the app shows it again. Windows passes the parent HWND as the native owner, and Linux sets GTK transience and follows map/unmap and minimized-state notifications. Unlike NSH’s modal-window policies, close ownership remains in the shared core. On macOS the child also centers over its parent when `Frame` is unset. AppKit attaches the child while the parent enters and stays in full screen so they share its Space. In regular Spaces the child can move to a different display on its own.
- Each tree has its own `Env`: size, scale, safe area and title bar. What the app forces, its locale, appearance and host tokens, is one signal shared by every window's.
- On desktops, `Env.Displays` reports each display's whole and visible frame, scale and primary flag in the same coordinates as `desktop.SetWindowFrame`, so a saved frame can be placed on a chosen display.
- A panel takes the keyboard without activating the app where the platform can. With `PanelOptions.NoActivate` it never takes it, shown, focused or clicked, so the app the user types in keeps its focus and caret, as an input method's candidate window needs. `Window.ShowAt` shows a panel beside a rectangle in `Env.Displays`' coordinates, such as a caret's or the pointer's, on a `core.Placement` side, flipped to the opposite side when only that one fits and clamped into the visible frame of the display that holds it (`driver.PlaceWindow`); `Window.MoveTo` moves a panel that shows there without showing or focusing it, and both keep the placement for later shows until a tray icon shows the panel under itself. A platform that cannot place it leaves it hidden and reports `EventWindowPlacementFailed`, which `Window.OnPlacementError` hears.
- A panel with `PanelOptions.Transparent` draws nothing of its own, no background, frame or shadow, so its content draws its own corners and `BoxShadow`; the platform reports in `Env.WindowTransparent` (`desktop.Transparent`) whether it could, starting true until it reports. With `PanelOptions.FitContent` the core lays the panel's root out as an overlay sizes, up to `Width` and `Height`, filling that size only when the content is larger, and sends the size as `WindowFitSize` ahead of the commit's other window commands, so the first show comes at the content's size; the tree's size and `Env.Window` are that size, and a size the platform reports only has the core send it again when it differs. The platform keeps the panel's top edge, or places a panel that shows beside its `ShowAt` rectangle or tray icon again.
- Opening sends `ItemOpenSurface` to the app's surface. The platform makes the window and attaches it: `engine.Engine.Attach(id, platform)` returns the surface's `Engine`, which reports its size, environment and events as the first surface's does.
- The engine commits every attached tree after each wake-up, the first first, and asks the [frame's driving window](animation.md#frames) for display frames. A tree waits uncommitted until it is attached.
- A closed window's tree ends: the engine sends its platform one batch, `WindowDestroy`, and forgets it, or sends it to a platform that attaches after the close.
- Where the platform opens no windows (phones, the web, `nsgo.NewView`, the test hosts of targets, `nsgotest` headless except where a desktop environment has it open windows as `Run` would ([testing](testing.md)), and Windows and Linux apps run with a root view), the first tree is the one surface: `OpenWindow`, `OpenPanel` and, except on Windows and Linux, `NewTray` return nil, whose methods do nothing, and `core.AppRoot` shows the main view in it; Android opens one surface beside it, `mobile.OpenOverlay`'s window over other apps ([Android floating windows](android-floating-windows.md)), and an iPad app that declares multiple scenes one for each further scene the system connects, which shows the main view too ([iOS](#ios)). A platform that registers global shortcuts there, as Linux's own window does and `nsgotest` does, says so with `core.RootOptions.HotKeys`, and the shortcuts go to that surface.
- `ItemHotKeys` sends the app's whole set of global shortcuts whenever it changes, and the platform answers each shortcut's ID with `EventHotKeyState`: registered, taken by another registration, or unsupported. `desktop.RegisterHotKey`'s handle holds the answer in a signal, pending until it comes and again while a changed set registers anew; where no surface takes global shortcuts it is unsupported at once. `nsgotest` registers every shortcut but a second of one combination, and answers the combinations `nsgotest.HotKeyTaken` and `HotKeyUnsupported` name as they say.

## Lifecycle

- `SetShutdownMode`: `ShutdownOnLastWindowClose` (the default), `ShutdownOnMainWindowClose` or `ShutdownOnExplicit`, which keeps the app running when its windows close. Panels and tray views are not windows here.
- `OnQuit` handlers clean up as the app ends, however it does, with 200 ms for their work ([services](services.md#appearance-and-quitting)).
- An iOS app runs one engine for the life of its process, started as its first scene connects, and each of its scenes is a window of that engine; UIKit's disconnects and reconnects keep the scenes' trees, and only `applicationWillTerminate:` closes the engine ([iOS](#ios)).
- `desktop.OnQuitRequest` hears desktop Quit menu roles and `desktop.RequestQuit`, newest handler first. A handler can cancel with `q.Cancel()` or defer with `done := q.Defer()`, then answer with `done(true)` or `done(false)`. The app keeps one user quit request pending at a time. `Scope.Quit` and `Restart` remain immediate.
- A close the user asks for is `EventWindowClose`. The window's `OnClosing` handlers run newest first and may cancel it. On Windows and Linux, if the shutdown mode would end the app, it also asks `OnQuitRequest` while that window is still open. `Window.Close` and its owner going close it without asking.
- A session end runs `OnQuitRequest` with `q.Forced()` true, then bounded `OnQuit` cleanup, even while a user quit is pending. macOS distinguishes the termination reason in the quit Apple event. Windows allows `WM_QUERYENDSESSION` immediately and cleans up before returning from a confirmed `WM_ENDSESSION`. Linux acknowledges Query End on the XDG Inhibit portal immediately and cleans up on Ending, on desktops that provide those session states.
- `nsgo.SetMainView` sets the main view: it opens the main window at `nsgo.WindowSize` and makes it main, and a later call replaces the view in it. `nsgo.Run(Root)` is `SetMainView(Root)`.
- `OnReopen` hears a click on the Dock icon and a second launch (`EventReopen`); without a handler the main window shows and takes the focus, on Windows and Linux the app's one window, restored if minimized. Windows' named mutex and pipe and Linux's Unix socket, beside its lock in `$XDG_RUNTIME_DIR` (in a Flatpak, `$XDG_RUNTIME_DIR/app/$FLATPAK_ID`, which the app's instances share) or else in a private directory of the user's in the temporary one, hand a second launch to the running process before it creates a second engine, which dispatches `OnReopen` and its file arguments to `OnOpenFiles` and its links to `OnOpenLinks`; on Windows the second launch lets the running process take the foreground before it hands over.
- `nsgo.InstanceKey("profile")` scopes that Windows or Linux lock and handoff channel to the app ID plus key: launches with the same key still hand over, while a different key starts its own engine. An empty key keeps the default one instance per app ID; macOS and other targets ignore the option.
- `OnOpenFiles` hears files the system opens with the app (`EventOpenFiles`): on macOS `application:openURLs:` for the types `file_types` registers, on Windows and Linux the files named on the command line, and on iOS the file URLs in scene connection options or `scene:openURLContexts:`. iOS coordinates reads on a serial worker, balances each security scope and delivers app-owned temporary copies with their original names. Its path-only callback has no scope-release contract, so imports follow the document picker's copy model rather than retaining provider grants indefinitely; links remain `EventOpenLinks`. Launch files can arrive before the first handler; the core keeps them until one registers and posts them to it.
- `OnOpenLinks` hears links of the app's own URL schemes (`EventOpenLinks`). `url_schemes` registers them as the macOS package's `CFBundleURLTypes`, under `HKCU\Software\Classes\<scheme>` with `URL Protocol` in the NSIS installer, which records them with its uninstall entry to remove them, as a `windows.protocol` in MSIX, and as `x-scheme-handler/<scheme>` with `%U` in the Linux desktop entry. On macOS Launch Services hands their links to the running app, launching it first when needed, and `application:openURLs:` sends every URL that isn't a file's as a link. Windows and Linux start the app with the link, after `--` on Windows so a link that breaks out of its quotes reaches no flag, and there a launch that names a link takes no files, which such a link could otherwise name: `engine.LaunchLinks` takes every argument that is an absolute URL of a scheme longer than a drive letter and not `file`, whose URLs `LaunchFiles` takes as files, and the one-instance claim hands the running app `{"files": [...], "links": [...]}`. A launch with links alone brings its window to the front if it shows, as activating an app does on macOS, rather than dispatching `EventReopen`. The app filters links by scheme, so a development build, which registers none, takes those it is started with; a restart drops them, as they asked for something once. The core keeps the links that launched the app until a handler registers, as it keeps files. On iOS the app's `CFBundleURLTypes` register its schemes, and the scene delegate sends the URLs it opens. On Android each scheme adds a browsable `ACTION_VIEW` intent filter to the launcher activity, which uses `singleTask` to reuse the running app from another task. `onCreate` and `onNewIntent` deliver matching links, with arrivals before the first mount held by the native view.
- Packages register `file_types` on macOS, iOS, Windows (NSIS and MSIX) and Linux. iOS reuses the exported/imported type declarations and content-type matching, omitting macOS-only icon keys; App Clips and tvOS declare none. NSIS adds per-app ProgIDs and extension Open With values under `HKCU\Software\Classes`, retaining the user's defaults; upgrade and uninstall remove only entries whose commands still match the installation's records and notify the Shell. Linux desktop entries pass `%F`, name their MIME types, and deb/Arch install owned custom MIME definitions with cache hooks; Flatpak exports them, and AppImage carries them for desktop integration.
- `nsgo.HideDock` starts the app as an accessory app, before AppKit's loop runs, so its icon never shows in the Dock; `SetDockVisible` changes the activation policy later, as apps do while their settings show. macOS runs one instance of a bundle and reopens it.
- `desktop.SetDockMenu` sets the app icon's menu (`ItemDockMenu`), which the core keeps for the app rather than a surface, as the platform has one: the one any surface set last, until its owner goes. A chosen item comes back as `EventDockMenu`, by its ID (`Count`) to the surface that set it, or by its label (`Text`) to any surface for a Windows Jump List task, which the next run of the app numbers anew; a label that comes before the app set a menu, as the task that launched it, waits for the first one. Linux, phones and the web ignore it ([roadmap](../roadmap.md#application-and-windows)).
- `desktop.AddRecentFile` (`ItemRecentFile`) records a document the system offers again, which reaches `OnOpenFiles` when chosen, and `ClearRecentFiles` forgets the app's: `NSDocumentController` on macOS, `SHAddToRecentDocs` and `IApplicationDestinations` on Windows. Linux, phones and the web ignore them.
- `SetLaunchAtLogin` and `LaunchAtLogin` register and read `SMAppService.mainAppService` on macOS 13 and later. On macOS 11 and 12 they use a per-user `~/Library/LaunchAgents/<bundle id>.plist` with `RunAtLoad`; both paths require a bundled app. Windows and Linux write a login entry of their own (below). `desktop.LaunchedAtLogin` reports whether this run came from the login item, using the launch Apple event or the `--nsgo-launched-at-login` argument the other entries start the app with, before the app's first function runs; reopens leave the reason unchanged. Tests inject it with `nsgotest.Environment(core.Environment{LaunchedAtLogin: true})`.

`desktop.RequestRestart` asks the same quit request handlers and restarts only after approval, unlike the immediate `desktop.Restart`. Canceling it leaves the process's restart flag unchanged; a deferred decision sets that flag only when it approves.

## macOS

`Run` waits for `applicationDidFinishLaunching:` to capture the login launch reason, then starts the engine on a surface in no window (`own`), which applies the app-level items: it opens surfaces, adds tray icons, registers shortcuts, sets the activation policy and the login item.

- A window is an `NsgoWindow` centered at its content size. AppKit's close asks the delegate, which reports `EventWindowClose` and declines; `WindowDestroy` orders the window out and closes it once the batch returned.
- A panel is an `NsgoPanel`: an `NSPanel` that can become key without activating the app, titled for the system's rounded corners and shadow, with a transparent title bar and no controls, at the status level on every space. It shows beside the rectangle `ShowAt` gave it, else under its tray icon's button, clamped to the screen's visible frame, else in the upper middle of the screen with the mouse, as Spotlight. With `HideOnBlur` it hides as it resigns key and reports `EventWindowHidden`. With `NoActivate` it is an `NsgoStillPanel`, which never becomes key or main and orders front without `makeKeyAndOrderFront:`, its views taking the first click. A transparent one is borderless, not titled: clear, not opaque and without a shadow, its content view unclipped.
- A tray icon is an `NSStatusItem`: its button reports left and right clicks, a Control-click as secondary, with its window's screen bounds in the coordinates of `Env.Displays`. `Tray.ClickBounds` reads these in `OnClick` or `Menu` for `Window.ShowAt`; each click replaces them, including one with no bounds. A drawn surface reserves an empty image's width in the button so AppKit lays out `Title` beside it and sizes the item to both. The click that hides a panel by taking its focus does not show it again. Its menu is the status item's own, set for one `performClick:` and reported closed as a context menu.
- Alerts and open/save panels use their surface's window only while it is visible, not minimized and intersects a display. Otherwise they show independently, activating the app without restoring or moving the window. The surface cancels its dialogs as it closes; standalone alerts run one at a time from an `NSRunLoop` block so the main dispatch queue keeps mounting and responding.
- The Dock menu is the `NSMenu` the app delegate's `applicationDockMenu:` returns, built as the app sets it, since AppKit asks for it synchronously: its items, submenus, separators, check marks and disabled items as the application menu's, without roles or shortcuts, above the system's. Recent documents show there and in File › Open Recent for the types `file_types` declares.
- A drawn icon is a surface in the button: an embedded surface whose hit test lets clicks through to the button, the item as wide as the view.
- Global shortcuts are Carbon's `RegisterEventHotKey` on the application's event target, which needs no accessibility permission; a key names its ANSI virtual key code, and one without a code is unsupported. Carbon refuses a combination the app registered already, or another app registered exclusively, with `eventHotKeyExistsErr`, which is taken; it does not see other apps' ordinary registrations, so such a combination registers and the press goes to one of them.
- An alert asked from the app's own surface, which has no window to hold a sheet, runs app-modal.

## Linux

An app run with a function (`nsgo.Run(App)`, or a root view with automatic update checks) runs on a GTK window that never shows, as macOS's `own`, and its lifecycle is its windows': active while one has the focus, in the background while none shows. An app run with a root view shows it in the one window, where `NewTray` still works. `TestAppSurfacesShareStateAndPanelsFollowNativeFocus` verifies the hidden application surface, attached window and panel, real X11 keyboard input, shared state, hide-on-blur reporting and reopening after all windows close (2026-11-22).

- A window is a `GtkWindow` on the same main loop. Its `close-request` reports `EventWindowClose` and declines; `WindowDestroy` deletes its views, destroys it and drops its handle.
- Window constraints limit content in points. X11 augments GTK's `WM_NORMAL_HINTS` with maximums in physical pixels, adding the current client titlebar, menu and shadow extents, and reapplies them on mapping and allocation. A single-axis limit leaves the other unbounded, clearing limits removes the maximum hint, and full screen bypasses it. Restricted minimize/maximize buttons use a native `GtkHeaderBar` with the session's `gtk-decoration-layout` filtered, following later setting changes; it stays installed after restrictions clear to avoid remapping each toggle. Its actions preserve GTK's modal, transient, resizable and compositor capability checks (the capability API is optional on GTK before 4.20). NSH supplies the header approach; NSGo also adds X11 maximum hints. GTK's [public Wayland API](https://docs.gtk.org/gdk4-wayland/class.WaylandToplevel.html) exposes no `xdg_toplevel` handle and no nonfixed maximum-size setter, so that part remains a goal rather than reaching into its private ABI.
- A panel is a borderless window that takes the keyboard focus and with `HideOnBlur` hides as it loses it, reporting `EventWindowHidden`; GTK places it where the compositor does, not under its tray icon. On X11 `ShowAt` moves its X window once it shows, and a panel with `NoActivate` is an override-redirect window, as menus are, which no window manager decorates, lists or focuses, placed before it maps, at the upper middle of the primary display without `ShowAt`. A transparent one takes the window's background, border and shadow away with a CSS class where GDK's display is composited and RGBA, and keeps them elsewhere. A Wayland compositor places every toplevel and focuses a panel as it shows, so there `ShowAt` reports that it cannot place the panel; edge-docked panels on a layer-shell surface remain ([roadmap](../roadmap.md#application-and-windows)).
- A tray icon is a StatusNotifierItem on a session bus connection of its own, so that several have the protocol's `/StatusNotifierItem` path and a bus name each, closing which takes the icon away; a watcher, Plasma's or GNOME's AppIndicator extension's, shows it, and without one nothing does. It names the app's icon only without a PNG of its own, which hosts would otherwise show instead, and signals each change of its icon, title and tooltip.
- Its menu is a `com.canonical.dbusmenu` object at `/Menu`: the host's `AboutToShow` asks the app for the menu as a secondary click does and is answered once it comes, or after 250 ms with the one the icon has. Every entry has an ID of its own that later menus never reuse, and a click on one reports `EventMenu` and the menu closed. A drawn icon is not drawn yet.
- Global shortcuts are passive `XGrabKey` grabs on the X11 root window, made inside GDK's error trap so that a combination another client holds is taken rather than ending the app; GdkX11Display's `xevent` signal takes their presses, as GTK 4 has no display filters. A press matches on Shift, Control, Alt and Super alone, whatever its locks, buttons and layout group.
- On Wayland, and on X11 where no grab succeeds, they use the XDG `GlobalShortcuts` portal, where the compositor asks the user to bind them: only the IDs `BindShortcuts` returns in its `shortcuts` list register and dispatch activations, and the others are taken, as when the request is refused. A missing or wrongly typed list reports them unsupported, as when the portal has no session; a combination another X11 client grabbed stays taken there, and a second registration of one combination is taken without going to the portal. A session that binds nothing is closed. The portal knows an unsandboxed app by the ID it registers (`Registry.Register`), which must name its `.desktop` entry and comes before any other portal call on the connection; GTK calls the portal as it starts, so the shortcuts have a session bus connection of their own, whose calls run in order off the main thread.
- Both paths dispatch the same `EventHotKey`. A host's `NewView` takes none. Native acceptance covers a real XTest press while another X11 client has focus, including release on scope disposal, and GNOME 50.1's real Wayland portal grant and activation while another GTK application has focus (2026-11-22, [#1383](https://github.com/nsgo-dev/nsgo/issues/1383)).
- `SetLaunchAtLogin` writes an XDG autostart entry, `autostart/<app id>.desktop` under `$XDG_CONFIG_HOME` or `~/.config`, whose `Exec` starts the executable, or the AppImage it runs from, with the login marker, quoted and escaped as the Desktop Entry Specification reads it; the AppImage is used only when the executable is inside its `APPDIR`, so an app launched from an AppImage-packaged terminal does not register that terminal. An executable whose path holds `%` is refused, as GLib looks the program up before it expands the `%%` the specification asks for. `LaunchAtLogin` is true while that file is exactly the one this executable writes. A Flatpak or Snap app has a config directory of its own that no session reads, so there both log that they are unsupported and `LaunchAtLogin` is false ([roadmap](../roadmap.md#application-and-windows)).

## Windows

For `nsgo.Run(App)`, `Run` keeps its root window hidden as the app's own surface and attaches the surfaces the app opens on its message loop; `nsgo.Run(Root)` shows the main view in the root window and only adds tray icons.

- A window is a top-level window centered at its content size in its monitor's scale, with its material. Its close reports `EventWindowClose`, and `WindowDestroy` destroys it. Keys go to the key bindings and menu of the window they are sent to.
- A panel is a borderless popup tool window, so it has no taskbar button. It shows beside the rectangle `ShowAt` gave it in the work area of the monitor that holds it, else above or under its tray icon from `Shell_NotifyIconGetRect`, else in the upper middle of the monitor with the pointer, sized at that monitor's scale, and takes the focus, which activates the app; with `HideOnBlur` it hides as it loses it. The press on the icon that hides a panel by taking its focus does not show it again. With `NoActivate` it is `WS_EX_NOACTIVATE` and topmost, shows with `SW_SHOWNA` and answers `WM_MOUSEACTIVATE` with `MA_NOACTIVATE`, so neither showing nor a click takes the foreground. A transparent one draws through DirectComposition with alpha, as a window with a material does, clearing to nothing, with the system's rounded corners off; without DirectComposition it stays opaque.
- A tray icon is `Shell_NotifyIcon`'s at `NOTIFYICON_VERSION_4`: `NIN_SELECT` and `NIN_KEYSELECT` are primary clicks and `WM_CONTEXTMENU` secondary, its tooltip is the standard one, and the icons are added again when Explorer broadcasts `TaskbarCreated`. Its menu is owned by a hidden window, so it raises none of the app's. A drawn icon's borderless surface stays hidden and has no swap chain. Changes to its retained tree, animation frames and completed image loads coalesce a repaint on its message queue; the usual Direct2D painter renders with alpha at the notification area's small-icon size, then copies the bitmap into a private `HICON`. The latest icon stays cached while Explorer is absent; tooltip updates and `TaskbarCreated` retain it, and replacement and removal release it.
- Global shortcuts are `RegisterHotKey` on the hidden root window, with `MOD_NOREPEAT`; `WM_HOTKEY` reports the registered ID, and the whole set is replaced whenever it changes. A combination any window or thread on the desktop holds, the app's own included, fails with `ERROR_HOTKEY_ALREADY_REGISTERED` and is taken; a key without a virtual key code is unsupported.
- `SetDockMenu` writes the Jump List with `ICustomDestinationList` under the app's ID, which `Run` also gives the process (`SetCurrentProcessExplicitAppUserModelID`), so the list belongs to the taskbar button though the app started from its exe: each top-level enabled action is a task, an `IShellLink` titled by its label that starts the exe with `--nsgo-dock-menu=<label>`, beside the Recent category; submenus, separators and check marks are left out, and a menu without a task deletes the list. Windows keeps the list after the app ends; a task's launch goes to the running copy over the one-instance pipe, where it chooses the item rather than reopening the app. Recent documents show only for file types the app is registered for, which its installer does not register yet ([roadmap](../roadmap.md#application-and-windows)).
- An alert asked from the app's own surface shows the hidden root window as the alert's own window, without the app's menu bar, which closing cancels.
- `SetLaunchAtLogin` writes a value named by the app's ID under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` that starts the executable with the login marker, and clears the user's earlier switch-off of it under `Explorer\StartupApproved\Run`; turning it off deletes both. `LaunchAtLogin` is true while the value starts this executable and Task Manager's Startup apps has not turned it off. An MSIX app's writes to `HKCU` stay in its package, so there both log that they are unsupported and `LaunchAtLogin` is false ([roadmap](../roadmap.md#application-and-windows)).

## iOS

A scene is a window of the app's one engine, as a desktop window is (decided for #49). The engine starts as the first scene connects, and that scene shows its first tree. An app with `apple.multiple_scenes: true`, which writes `UIApplicationSupportsMultipleScenes`, can have more on an iPad, where the user opens more than one of its windows: each further scene the system connects shows a tree of its own that the engine opens as it connects (`EventOpenScene`, a `driver.SurfaceScene`), under the app's scope, so the scenes share the app's signals and storage, as windows do.

- Every scene shows the main view, the one `SetMainView` sets or else the root view the app runs, built anew in its tree, which has its own `Env`: the size, safe area, keyboard inset and traits read in that scene's window. The active scene applies the keyboard inset. When several are active, the backend sends an action up the responder chain to find the window receiving input. The status bar and the orientations a scene's root view controller answers UIKit with are its tree's, as are the keys pressed and the text selected in it.
- The system opens and closes scenes, as the user asks it: the app opens none and closes none itself, `OpenWindow` still returning nil, and its links, activities, notification presses, appearance and `Env.Lifecycle`, the application's state, stay the app's rather than a scene's. A scene the app asks for, and what a scene carries to say what it shows, are open ([open questions](../../ARCHITECTURE.md#open-questions)).
- UIKit may disconnect a scene while the process lives, as it releases one in the background, and connect it again as the user returns: `sceneDidDisconnect:` lets that scene's window and display link go and keeps its tree, surface view and controller, and the next `scene:willConnectToSession:options:` of its session shows that view in the new window, where it lays out at the window's size with the environment read there, rather than starting a second engine or tree over the first ([#1030](https://github.com/nsgo-dev/nsgo/issues/1030)). The other scenes run on meanwhile.
- The system discards a scene's session as the user closes that window (`application:didDiscardSceneSessions:`): a further scene's tree ends with it (`EventWindowEnded`), and the engine destroys it. The first tree is the app's own scope's and outlives its window: it waits windowless, and the next scene that connects shows it rather than a new tree.
- An app that declares no multiple scenes has its first tree alone: a scene that connects while that tree shows in another takes it over.
- The engine asks one surface for the display frames of all its trees; one whose scene is in the background, where its display link does not tick, hands the request to a scene in the foreground.

## Configuration

`nsgo.yaml` keeps what the package needs before any code runs: the name, the ID, the version and the launch screen's appearance. Windows are sized and limited in Go, `nsgo.WindowSize` and `nsgo.WindowConstraints` for the main window and `WindowOptions` for others; `nsgo.HideDock` and the shutdown mode are Go's too. A `window` in `nsgo.yaml` fails the tool, naming `nsgo.WindowSize`.

## Departures from NSH

| NSH | NSGo | Why |
| --- | --- | --- |
| `run_app` shows one `AppView` in one window; more windows are a host's, an engine each | One engine with a surface per window, panel and tray view, which the app opens as Avalonia's apps do | Go code is trusted and in one process, so windows share signals instead of crossing a host channel |
| `keep_alive_on_close`, macOS only | `SetShutdownMode` and a cancelable `OnClosing` | Tray and background apps outlive their windows |
| No tray, panels, global shortcuts, Dock policy or launch at login | `desktop` has them | Desktop apps need them |
| File types registered at runtime on Windows | NSIS owns registration and cleanup; Linux infers common MIME types and defines unknown owned extensions | Installers can remove dropped types on upgrade without changing user defaults; a build's declarations are independent of its host's MIME database |
| `nsh.json`'s window size | `nsgo.WindowSize`, `nsgo.WindowConstraints` and `WindowOptions` | An app opens windows of different sizes, or none |
| `transparent` apart from `frame`, `shadow` and `taskbar` on | `Transparent` drops the frame too; `NoShadow` and `SkipTaskbar` are off unless set | A see-through window inside the system's frame draws a box around nothing, and Go's zero values are the defaults ([services](services.md#desktop-windows)) |
