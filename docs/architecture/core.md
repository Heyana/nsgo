# Core

`core` turns Go components into one `MountBatch` per commit. Components run once; signals drive bindings, regions rebuild only what changed, and the commit lays the tree out and sends the differences. The mount protocol, the events and the values `core` shares with backends live in `internal/driver`; `core` aliases those its app API reaches in `shared.go`, and `TestPublicAPINamesNoInternalType` checks both the aliases and the explicit list of driver types allowed in a public API.

Read this before changing `core`, `internal/engine` or the mount protocol a backend implements; [text](text.md), [scrolling and lists](scrolling.md), [interaction](interaction.md) and [services](services.md) cover those parts of `core`.

## Reactive graph

The graph follows NSH's (Solid 1.9's scheduling): signals, memos, render effects for element bindings and user effects for the app, run in that order after each batch.

- Every computation and scope is an owner. Disposing an owner disposes what it created and runs its cleanups, last first, as `testing.T.Cleanup` does. A disposal is a batch, and a computation's disposal before it runs again is part of the run's: what cleanups write runs once it is over, so computations outside the owner run once against an intact tree and those inside it, already disposed, never run.
- Go has no goroutine-local state, so code finds its graph through `cx *Scope`. While the graph runs code, reactive primitives (`Effect`, `Memo`, `Cleanup`, `AfterFunc`, `Context`, `Child`, `Key.Provide`/`Use` and event registrations) belong to the innermost running owner, whichever `cx` the code captured, so closures inside an `Effect` clean up when it runs again; `Scope.Run` switches the running owner when calling those from another handler. Explicit-lifetime resources and surfaces (`OpenWindow`, `OpenPanel`, `NewTray`, `OpenOverlay`, `NewAudioPlayer`, `LoadSound`, `NewHolder` and `Post`) instead belong to `cx` itself, so passing the app's or a page's scope from a button's `OnPress` keeps them alive after the button's scope goes, while `Access` checks still hold both the running owner and `cx`. Handlers run under the owner their element was built in.
- The graph belongs to the engine goroutine and never locks. Other goroutines reach it with `Scope.Post`. Development builds (`nsgodev`) assert ownership; instrumented tests (`nsgocheck` headless, `nsgotest` on targets) do so for each graph created with `RootOptions.CheckCommits`, which an engine sets from `engine.Options.CheckCommits`. A signal write, a new computation, a batch, a run, a disposal or a commit from another goroutine panics with a `Scope.Post` diagnostic. The lookup parses `runtime.Stack`, which costs microseconds, so it runs only while the graph is idle: a call made inside a batch, a flush or a computation comes from code the graph is running on its own goroutine, unless another goroutine races with it, which is left to `-race`. Signal reads are not checked. Release builds compile these checks out; the WebAssembly runtime is single-threaded but may resume browser callbacks on a browser-managed goroutine, so development and test builds leave this goroutine-ID assertion out for the web engine; commit-consistency checks still run. `Scope.Context` is cancelled when the owner goes, so work started for a screen stops with it.
- A tree releases its prepared texts when its root scope is disposed, including when an embedded engine stops without a final commit. The backend releases the layouts and native views it owns after the engine stops.
- A reader and each source it read keep each other's index in their lists, so a computation that runs again unlinks in constant time however many read the same source: a table's thousand cells reading one signal.
- A write marks everything downstream for checking, through memos that will compute what they had. What follows a fast signal, such as a scroll offset, and rarely changes is set from it by an effect into a signal of its own, which reaches no one while it holds: `DataTable`'s windows.
- Timers go through the `Clock` interface. Tests inject a `ManualClock`. An `AfterFunc` timer is in its owner's set of pending timers from when it is armed until its call has run or it is stopped, so a timer re-armed under a long-lived scope keeps nothing there; disposing the owner, or its computation running again, stops what is in the set, a call the clock already posted included. The set has a lock of its own, as `stop` may be called on any goroutine.
- `NewResource` follows NSH's resource (Solid's `createResource`), as TSX's `resource` does: a value a fetcher loads on a goroutine of its own from a tracked source, with its value, error and state in signals. Only the latest load counts. Where NSH drops a superseded load's future, Go cancels its context, and the owner's disposal cancels the one running; results reach the graph through `Post`. A panic in a fetcher fails the load and goes to the nearest `Catch`.
- State beyond single values is NSGo's own, built on signals, as NSH has none: `From` (Solid's `from`) follows a source on another goroutine, coalescing what arrives before the graph takes it; `NewSelector` (Solid's `createSelector`) keeps a signal per key read and drops it when no reader is left; `Collection` holds items by key in signals of their own, as a Solid store holds an array, since Go has no proxies to track field reads; `Persisted` keeps versioned JSON in `Scope.Storage`; `History` records only its own writes, as an effect watching a signal cannot tell an undo's write from the app's within one batch.
- `Suspense` follows Solid's, as NSH has none: a resource's `Get` in a computation under its `Content` has it wait while the resource loads its first value, for as long as that computation's latest run read it. `Content` stays mounted, and its own views hide through `restyle` while a Suspense waits (`Tree.suspended`), so what they read keeps reading; a refetch, with a value already, does not suspend, where Solid's does outside a transition. TSX's `resource` has no Suspense yet.
- A panic in app code is recovered and sent to the nearest `Catch` above the owner it happened under. With no `Catch`, the host reports it and the app keeps running. An internal engine panic, including initial mounting, text preparation or committing, instead ends that engine: it reports a `PanicError` with its stack, stops accepting work and destroys every attached surface. `Scope.Abort`, used by the engine, stops computation scheduling before disposing resources, so cleanup writes cannot restart a damaged graph. An engine with `engine.Options.CheckCommits`, as test hosts start them, re-panics after fault cleanup so tests still fail.

## Elements and components

Host elements (`View`, `Text`, `Scroll`, `List`, `Image`, `Canvas`, `Overlay`, ...) are structs with exported fields whose zero values are defaults, as in `http.Server`. Apps take `Input`, `Screen`, `InputAccessoryView` and `Modal` through `base.Input`, `base.NavPage`, `mobile.InputAccessoryView` and `base.Dialog`, as NSH's apps do. [Hosted views](native-views.md), [images](images.md), [canvas](canvas.md) and [shaders](shaders.md) cover their elements.

- A field that can change has a twin, its name with `Func` added: `XFunc func() T` beside `X T` is `X` again whenever what it reads changes, bound by one render effect per part. A `Style`, classes and `Uniforms` take `XFunc`'s over `X`'s (merged, after, by name); any other `XFunc` replaces `X`, and an element or a component of `core`, `base`, `mobile` or `desktop` that sets both panics as it mounts. `TestFuncFieldsBindTheirValue` holds the names to it, and requires a twin for each part style that lives as long as its component, such as the list of rows' `ListStyle` of `base.List` and `base.Tree`, while those read once per presentation may stay fixed.
- A field with no static form takes only the function and keeps its name: `Disabled`, `Checked`, `Value`, `When`.
- Styles compose with `Style.Merge`, and text fields inherit down the tree as in CSS.
- State styles merge over the rest in NSH's order: `Checked`, `Indeterminate` and `Selected`, which the app sets, then `Hover`, `Focus` and `Active`, then `Disabled` over all; a `GroupStyle` follows its group's states first ([styles](styles.md)).
- The engine tracks `Hover`, `Focus` and `Active` from the events it asks the platform to report. Windows and Linux hit-test hovers themselves (`internal/platform/hover`).
- `PartStates` styles a view in states it does not report, as a control's part, NSH's `project_checked`.
- Props only one platform has sit in a field named after it, as NSH's `ios`, `android` and `desktop` objects: `View.IOS.BackdropMaterial`, `View.Android.Ripple`, `View.Desktop.WindowDrag`.
- What two platforms have stays top-level, so `InputAccessoryViewID` and `LiveRegion`, iOS's and Android's in NSH, are top-level because NSGo implements them on more.
- A `Ref`, usable at its zero value, names a mounted element for anchoring, focus, scrolling and its bounds.

A component is any type whose `Render(cx) Node` returns its nodes, like `http.Handler`. Its fields are its props. `Render` runs once under a scope of its own, so `Key.Provide` and cleanups stay inside it. `Func` turns a function into a component.

## Regions

`Show`, `Each`, `Dynamic` and `Catch` mount as regions. A region is a node with no native view, laid out as part of its parent's children, and owned by one render effect that rebuilds its span.

- A `Show`, `Dynamic` or `Catch` branch belongs to its region's render effect: the scheduler settles that effect before the branch's bindings, disposing a replaced branch before it can read the state that removed it. `Each` rows belong to the region's owner instead, so kept rows outlive the effect's runs.
- `Each` matches rows by key. A kept row gets its item and index through signals, and only the rows that moved are reinserted. `AfterEachRow` copies an `Each` to build a node after each row from the node the row built, in the row's scope, so it moves and goes with the row: `ui.FormSection` hangs its hairlines below the rows of an `Each` this way.
- An item of plain values (numbers, strings, arrays and structs of them) notifies its row only when it changes; one holding pointers, slices or interfaces notifies on every read, as what it points at may have changed.
- Go methods cannot take type parameters, so `Each` is a generic function rather than a method or struct.
- Region nodes are never laid out. Layout marks pass through them, so a change inside a branch or row still reaches the root.
- A `Holder` is NSH's render keys as a value: content built once, owned by the scope given to `NewHolder` rather than the running owner, and shown in the newest place mounted with `Place`.
- A held content moves to its place with its native views, keeping its state; with no place it stays built out of the tree, its overlays hidden. Focus, blur and scroll requests made while unplaced, or queued for content that leaves before commit, are dropped rather than replayed when placed again. Unsent scrolls also leave no predicted offset or pending count.

## Layers and navigation

`Overlay` and `Modal` stay in the shadow tree where they are built, for their owner, context, inherited text and lifetime. Their native views are hoisted into their host: the nearest modal around them, or the root view. Each is a layout root of its own at the host's size, placed after the main layout.

- An owner `Scope.Confine` confined, such as a TSX sandbox, shows within its frame, as a browser's cross-origin frame does: the nearest view around its views that it does not own (`confines`), which clips what it holds and so sends no overflow area, so its views neither draw nor take touches outside it however they are placed. Its overlays and fixed views go into that frame when it is nearer than a modal (`hostOf`), sized, placed and clipped there and laid out after the root's hosted views, the outer frames first (`placeFrames`); a frame keeps clear of the part of the safe area it covers. Its modals, which the platform presents over the window, mount only in the focus gate's window ([keyboard focus](interaction.md#keyboard-focus)), and once shown stay as any modal does.

- An overlay with an anchor goes beside it as NSH's `place` does: the side asked unless only the opposite side fits or has more room, aligned along it, then clamped into the safe area. `OnPosition` reports the side, the frame and the room on that side, again when they change. A `HoldToRoom` overlay picks its side at its natural height and is then held to the room there (`hoistNode.held`, a max height its layout takes, kept below one of its own), laid out again at its natural height only while that hold still limits it; a menu's items scroll past it.
- A modal provides the insets its content keeps clear of; a screen does too, without the top when it has a header. `Insets` reads them.
- `Overlay.Topmost` keeps an overlay above the overlays and modals its host shows, later ones too: hoisting and a holder's rehosting insert others below the host's Topmost overlays (`addHosted`), which keep the order they came in. DevTools' overlay and the layout audit's ruler are such overlays.
- `EventBack` (Escape, the back button) goes to the root view's last Topmost overlay that listens for cancel, else the topmost overlay that listens for cancel in the topmost modal or the root view, then in the frames shown there, else the topmost modal's `OnRequestClose`, else the `Scope.OnBackPress` handlers newest first, those whose owner shows nothing the user can see left out as `OnKey`'s are ([keys](services.md#keys-and-the-status-bar)), else the innermost stack that can pop. A confined owner's overlays, handlers and stacks listen only while the focus is within it (`Scope.Confine`); a modal it showed hears back wherever the focus is, as the user expects of what covers the window, and back deletes its view after `OnRequestClose` whether or not its owner removes it, so it cannot keep the window covered.
- A back gesture that begins (Android's predictive back, iOS's swipe) sends `EventBackStarted`; the core answers `ItemBackPreview` with the screen a back would pop and shows the one below. `EventBackCancelled` hides it again.
- `ItemHistory` counts the backs the app can take: screens above each stack's first and modals shown. The web keeps that many browser history entries when the app is the whole page, so the browser's back goes back in the app.
- `Scope.AppURL`, `SetAppURL` and `OnAppURLChange` keep one tracked address per application. A web surface initializes it before mounting; `ItemHistory.Address` accompanies the committed navigation depth, while browser traversals use `EventOpenLinks` with a `PageAddressChange`. The web mirrors entry indices separately from depths, coalesces explicit pushes with navigation, waits for its own asynchronous pops, restores refused backs, and leaves entries preceding this player. Native links update the same value; confined scopes cannot reach it. This follows NSH's `app_url` and `set_app_url` with scoped Go notifications instead of its queued async iterator. [Application addresses](../public/en/addresses.md) describes the app contract.
- `OnBackPress` stays in `core`, where NSH's apps take it from `nsh/mobile`, because it also hears Escape and the browser's back.
- A popped screen reports `OnDismiss` and stays hidden until the app removes it; the last screen never pops.
- Where the environment has `HeaderHeight` (iOS, Android), screens get NSH's system header: the core pads the content below the bar and the status bar, sends `ItemScreen`, and lays `HeaderLeft`, `HeaderRight` and `HeaderTitle` out as roots the platform puts in the bar. `HeaderLeft` and `HeaderRight` take their content's size; `HeaderTitle` fills the room between the bar's ends (`ScreenConfig.TitleFills`) when its views grow or take a percentage width, and takes its content's size bounded by that room otherwise.
- `Screen.IOS.HeaderRightSystemItem` with a `HeaderRight` asks iOS for UIKit's own bar button in its place, as NSH's `headerRightSystemItem`. iOS reports its press on `HeaderRight`'s first view that takes presses.
- `Screen.IOS.HeaderRightSymbols` asks iOS for UIKit's own bar buttons by SF Symbol in `HeaderRight`'s place, each on glass of its own through a zero-width space between them; a press reaches the view of `HeaderRight` at its place among those that take presses, and none returned takes the item away.
- `Header` is then mounted as a root of its own that the native header leaves unused (`ScreenConfig.Header`), as NSH makes it; elsewhere it is the screen's first child.
- iOS gives each screen a `UINavigationBar` of its own with a back item, Android a `Toolbar`; their back buttons and iOS's leading-edge swipe send `EventBack` with the screen's ID.
- iOS slides the screens and their bars as `UINavigationController` pushes and pops: 0.35 s on the keyboard's curve, the screen below moving 30% of the width under a dimming view.
- `Screen.Animation` fades the screen instead or shows it at once: a push takes the pushed screen's, a pop the popped one's.
- `HeaderClass` gives the system header its colors as classes (`bg-*`, `text-*`, `tint-*`) under `HeaderStyle`. `HeaderTitleStyle` and `HeaderLargeTitleStyle`, with their `Func` forms, independently override family, size, weight and slant on iOS and Android; zero fields preserve native defaults. NSH supplies header colors alone: NSGo adds title typography so an app need not replace a native title just to style its font.
- A hidden screen has no layout, so iOS keeps the layout the screen a batch hides or pops last showed: it skips the frames of no size inside it, and keeps a popped screen's views until its slide ends. The slide moves the screens themselves, as the swipe back does; a snapshot cost a push 5–13 ms of the main thread in the simulator, waiting on the render server.
- Each platform measures its bar with what it holds and reports its height and the room left for `HeaderTitle` (`EventScreenHeader`), which replace the core's estimates; the insets a screen reports (`EventScreenInsets`) replace those the core derives.
- A transparent header and a large title lay the content under them: each vertical scroll view whose top they cover gets that part as `ScrollConfig.HeaderInset`, added to its top content inset.
- iOS collapses a large title into the bar once its scroll view scrolled half the title's row under it, and brings it back above that, as UIKit's navigation controller does; the bar has no background until it collapses, then the system's blur.
- Android gives a large title a Material 3 large top app bar (`Header.java`, `HeaderLayout.java`): a 64 dp `Toolbar` pinned below the status bar for the back arrow, actions and 22 sp collapsed title, with a band of at least 88 dp below it holding a 28 sp headline (152 dp total by default). The band grows for a larger title font, shrinks linearly and crossfades into the toolbar title as the screen's top vertical scroll view scrolls under it.
- Android keeps the expanded `Title` when `HeaderTitle` replaces its compact title; the custom view fades into the toolbar as the headline fades away. `Android.HeaderRightWithLargeTitle` puts the end view beside the expanded headline, reserving text space and tracking its center until the control reaches the pinned toolbar, in either layout direction. It keeps the same native holder and input handlers through the collapse.
- `mobile.TabBar` is the system's tab bar, a native component iOS (`UITabBar`) and Android (a Material 3 navigation bar drawn by the runtime's `TabBar.java`) register themselves; elsewhere it shows nothing. `ui.TabShell` floats iOS's over its sections, which read `ui.TabBarInset` to keep what they show clear of it; under any other bar it provides its sections insets without the bottom (`core.ProvideInsets`), which the bar keeps clear of itself, giving it back while the keyboard hides the bar. `ui.SidebarShell` likewise pads its panes' bodies by the side insets at the window's edges, the sidebar's left, the content's right and, while the sidebar is closed, left, and provides what they hold insets without the sides, so a `ui.NavHeader`, which adds the side insets to its padding, or a page that pads itself is not padded twice inside it.
- iOS presents a modal with `ModalPageSheet` or `ModalFormSheet` as a sheet view controller, which reports its size (`EventModalSize`) and its swipes (`EventRequestClose`, "swipe"); a swiped sheet stays hidden until the app removes it.
- `EventModalShown` and `EventModalDismissed` (`Modal.OnShown`, `OnDismissed`) are each backend's reports that a modal finished presenting or going away, so `base.Dialog`'s `OnOpen` and `OnClose` follow the platform directly; `core` holds a deleted modal's ID and `OnDismissed` callback until `EventModalDismissed` arrives.
- `IOS.SupportedOrientations` takes precedence over the app's [scoped orientation request](services.md#interface-orientation) in the controllers' `supportedInterfaceOrientations`. On Android a modal over the surface starts below the status bar unless `Android.StatusBarTranslucent`.
- `EventPressOutside` reports presses outside an overlay, ignoring those on its anchor or on overlays above it, in its host and after each modal around it in that modal's host, so the root view's Topmost overlays count above every modal; an overlay above whose `PointerEvents` is `None` lets every press through, and one of `BoxNone` those its views do not take, so a tooltip or DevTools' overlay keeps no popover open.
- A view's `Tooltip` is a hint overlay above it that the core shows after half a second of hover on desktops, and hides when a finger or pointer goes down on the view, and shows at once while the focus the keyboard moved is on the view or inside it (`updateFocusHint`); `Overlay.PointerEvents` keeps it from taking the pointer.
- A `mobile.InputAccessoryView` is a layout root as wide as the surface and as tall as its content, which no view holds: its views are sent before the tree's, and an input's `InputConfig.Accessory` names it.
- iOS makes it the field's `inputAccessoryView`; Android shows it above the keyboard while the field has focus; other platforms leave it unmounted.

## Commit

`Tree.Commit` runs up to eight rounds. Its batch holds a copy of the items; `Tree.CommitShared` hands a platform that applies the batch within `Mount` the tree's own, until the next commit (`engine.SharedMounter`: the web, where copying a busy table's half megabyte a commit fed Go's collector on the page's thread). `OnLayout` handlers' changes go into the same batch, and so does the layout audit's drawing of every view's box while it shows: a round that moved, resized, hid, showed or removed a view, restyled what layout reads of one, such as its padding, or followed a scroll draws it again after the `OnLayout` handlers (`bumpAudit`). A commit costs what changed, not what the tree is: each change marks its node, `mark` for its parts and `markResolve` for its styles or content, and the walks below reach the marked nodes only, through the views they are emitted in (`dirtyKids`) and their shadow parents (`resolveKids`). What every node reads (the environment, the layout direction, the font scale, an accessory's ID) marks them all, except a report that changes only the window's frame, maximized state, lifecycle, title bar, thermal state or low-power mode, which reaches only what reads them through `Env`, so a window drag costs nothing per view (`environmentNeedsFullRound`).

1. **Resolve.** Inherit text styles into the marked nodes, and into every node under one whose inherited fields changed; prepare text whose content or style changed.
2. **Layout.** CSS block, flexbox and grid from `internal/layout` over each view's native children; overlays and modals are layout roots of their own. Results stay cached until a node changes, and frames are rounded to the environment's device pixels as Taffy rounds to whole ones, an overlay's or fixed view's origin too: a pointer's position holds fractions, and a box off the pixel grid draws its border and fill apart. Texts round up to a pixel, so at Android's 2.625 a text of 56 pixels is not laid out 58 tall. A new pixel ratio lays everything out again.
3. **Emit.** Compare each marked view's parts with what was sent: view style, props, events, text, input, scroll; layout marks the views it moved. Then sync children against the sibling order last sent, reinserting only the views outside the longest run already in order.

`Tree.Remount`, used by the Android backend after detach, makes the next commit recreate native views from the existing graph. It resets sent snapshots, refreshes drawings and component props, rebinds animation values and restores logical focus, scroll and zoom. The backend retains its process services and animation graph and discards the old native tree before that batch. `engine.Engine.Remount` orders the backend's reset callback immediately before mounting the complete batch; repeated requests before a commit share the reconstruction ([Android lifetime](android-lifecycle.md)).

Layout is incremental, as NSH's layout tree:

- A change stops at a relayout boundary (`layout.Boundary`): an in-flow flex item of fixed points both ways that does not shrink, has an auto basis and is not aligned by its baseline, or an absolute view of fixed points both ways placed by an inset on each axis. A size its containing block stretches is none: laid out on its own it would keep the block's last size.
- A boundary is laid out again on its own with what its parent gave it last, and its parent only when its size, baselines or overflow changed (`layout.Relayout`); the overflow of a view that clips both ways never reaches its parent.
- The deepest boundaries go first: an outer one laid out from its caches would leave an inner one's subtree as it was and clear its mark.
- A restyled view is no boundary, and overlays and modals always mark the root's layout, which places them.
- A text whose content changed lays nothing out when it measures as before for every input layout asked of it since its cache was cleared (`layout.MeasuresAsBefore`), or when only its colors changed.
- Texts with attachments always lay out. A restyle lays a view out only when the layout style it maps to changed.
- Sizes and offsets are counted in whole pixels before they become points (`span`), each edge snapped to a 64th of a pixel first, so the same pixels give the same `float32` wherever a scroll puts them and a frame that stays on its pixels is not sent again, as NSH's `#617`.
- Rounding goes only under a node laid out again since its children were rounded, or carried from another place than whole pixels away from the last: a box scrolled by whole pixels rounds itself, not its subtree (`roundLayout`), unless its subtree reaches past 2^14 pixels, where `float32` sums are too coarse for whole pixels to move every edge by whole pixels (#809). Frames are taken again only under a view whose children were rounded since (`syncFrames`), as NSH's `#637`: a positioned view is the containing block of what is absolute in it, so all of its subtree is rounded through it, and the frames under a static one are always taken, since its absolute views are placed by its ancestors.

Tests keep the marks honest: with `RootOptions.CheckCommits`, which `nsgotest` and the core's tests enable for their own graphs, each commit is followed by one that lays every node out anew and compares every node, and panics on what the first missed. An engine passes this setting to every surface it opens; a performance measurement disables only its own engine's checks.

`layout.go` maps styles with React Native's defaults, as NSH does:

- Column direction, no shrinking and no automatic minimum sizes.
- `flex-start` content alignment outside grids.
- Left and right swapped where the subtree lays out right to left.

## Animation

Style `Transition`s, animated values and layout animations run on the platform, with no engine work per frame and nothing for the engine's garbage collector to pause; [animation](animation.md) covers them. `Scope.RequestAnimationFrame` waits for the display's frames, and `Scope.Animate` steps app values on them for what a platform cannot animate itself; every step commits.

## Storage and directories

`Scope.Storage` follows NSH's `nsh/storage`: strings by key with a 5 MB quota, held in memory by a `Store` and loaded once from its `core.StorageBackend`. Hosts pass a backend to `core.NewStore`; its `Write` takes owned `core.StorageChange` values and `core.StorageOp` constants. The engine adapts those changes to the platforms' private driver contract, keeping persistence messages out of the host API.

`Scope.Store` returns the graph's `Store` so code that owns more than one root can pass the same store through `RootOptions.Storage`. The roots then share entries, change notifications, quota and the platform's persistence. It is the whole store, beneath any partition `ProvideStorage` gives an owner.

- Engines given the same `Store` share its entries and quota. Each graph keeps a signal per key it read and one for the key set; its own changes bump them at once, and other graphs' changes arrive through `Post`.
- The store hands each change to the backend under its lock, so every graph and the backend see one order.
- Native targets keep `storage.json` in the data directory: `engine.OpenFileStorage` returns one store per file in the process and rewrites the file on a goroutine of its own.
- A file that does not parse is set aside as `storage.json.corrupt`, and one that cannot be read leaves changes in memory. Platforms call `engine.SyncStorage` as the process ends.
- An iOS app with `app_clip` and explicit `apple.app_group` uses `Library/Application Support/NSGo` in that group’s container for its data and storage, shared with its clip; logs follow the data and each bundle keeps its own cache. `NSGoStorageAppGroup` opts the two bundles in without moving widget-only apps’ storage. A host’s explicit data directory still wins, and an inaccessible configured group stops startup rather than forking storage. Enabling the setting does not migrate existing sandbox data.
- The web keeps entries in `localStorage` under `nsgo:<app id>:`.
- `Scope.ProvideStorage(name, quota)` gives a subtree a partition: its keys are stored under a prefix starting with a zero byte, which the app's own `Storage` neither lists nor clears, and hold at most `quota` bytes besides the app's quota. A partition's `Clear`, and the app's while partitions hold entries, remove key by key.
- `storage.json` is plain, so secrets go to `Scope.Secrets`, the platform's secure store ([services](services.md#secrets)).
- By default, `Scope.DataDir`, `Scope.CacheDir` and `Scope.LogsDir` are named by the app's ID, which the tool passes from `nsgo.yaml`: `engine.AppDirs` on Apple platforms, Windows and Linux, the files and cache directories the runtime passes on Android, and none on the web. Logs go where each platform's tools look: `~/Library/Logs/<id>` on macOS, `%LOCALAPPDATA%\<id>\Logs` on Windows, which is inside the cache directory, and `$XDG_STATE_HOME/<id>` on Linux; iOS, watchOS and Android, which have no such place, keep them in `logs` in the data directory. A host's data directory (`nsgo.DataDir`, `dataDirectory`, `setStorageDirectory`) moves logs with the data, and tests keep all three in a temporary directory. The engine makes them as it starts; NSGo writes no logs there itself.

## Access

`Scope.ProvideAccess` holds a subtree to a `core.Access`, NSH's `nsh_core::access`, for code a host did not write ([sandbox](tsx.md#sandbox)); one below another is held to both. Core asks it where it makes requests, so nothing is checked until an app provides one (`runtime.restricted`): images, videos, menu item icons, custom cursors, canvas and shader images at commit (canonicalizing `http(s)` URLs under `AccessNetwork`, symlink-resolving regular local files under `AccessFS` `read` into canonical `file:///` URLs, and attaching a per-source redirect/local-file validator for `imageload`), a web view's source and the hosts its platform lets it navigate to (`WebConfig.Restricted`, `Hosts`), with the `about:`, `blob:` and `data:` pages a page makes when the Access implements `AccessWebSchemes` (`WebConfig.Schemes`; one without it allows all three, and the app's own sources, `Source` and what `Ref.Load` loads, are not held to them), and `Ref.SendInput`, by the node's owner; and the services, by the running owner, the one whose render, effect, handler or `Run` is running, or outside one the scope the service is called on. `Scope.CheckAccess` answers code that makes requests of its own, on the graph's goroutine; background work posts its check to the requesting scope with `Scope.Post`, as TSX's fetch redirects do, and stops waiting if the request is cancelled.

- Services ask one gate, `Scope.gate`, for a kind of request, and its table (`services` in `access.go`) maps each kind to the capability it needs: `OpenURL`, status bars, notifications, biometrics, secrets, permissions, speaking, host calls and `ImageSize`. A kind missing from the table is refused to held code. The clipboard, the pickers and speech are entries that pass, as only TSX's runtime checks them ([TSX](tsx.md#where-this-departs-from-nsh)).
- `gate_test.go` lists every exported `Scope` method as gated, with its kind, or exempt, with why, and fails on a method missing from the list or one that does not reach the gate as listed.
- A host's handlers and its URL handler run outside the owner that called them, so trusted Go code is held to the scope it calls a service on, the app's own for the app's scope, whether it answers at once or later through `Post`.

## Mount protocol

The protocol is defined in `mount.go` and `events.go`. Backends apply items in order on the main thread, in one hop per batch. Android's Java runtime numbers the kinds in `Protocol.java`; `TestJavaProtocolMatchesTheDriver` checks every `ITEM_*` and `EVENT_*` declaration against the driver by name and number, including Java's hover names and the shared video event numbers. Driver kinds Android does not implement need no Java declaration; changes to Java's runtime are rebuilt into `classes.dex` by CI after merge.

- IDs are dense and reused after the round drops a retired node's commands and emits `ItemDelete` for its created view, possibly later in the same batch; nodes discarded before creation wait for that round too, so their commands cannot reach a replacement. NSH's IDs instead grow monotonically.
- Backends create a view in `driver.DefaultViewStyle`, with no props and an empty event mask, so a new view's `ItemViewStyle`, `ItemViewProps` and `ItemEvents` come only when they differ, as NSH's do: they were 2,646 of the 18,252 items opening the gallery's DataTable. A view's first style shows at once; one that changes from the default in a later batch transitions. Android's runtime takes the default style and props as Go encodes them from a surface's first batch, and starts each view it creates in them.
- `ItemInsert` places a view before a sibling, not at an index, so views a platform adds itself cannot shift positions.
- A view that changes parents, or comes back after `ItemRemove`, is inserted after the round's other inserts, once its new parent is in place.
- Backends move such a view in one step, so scroll offsets and iframes' pages stay: the web with `moveBefore`, parking removed views in a hidden element.
- Each round's deletes come last.
- Commands whose targets are deleted or have no view in unplaced Holder content are dropped, with or without view pacing. Focus and scroll commands also require a place showing the content; other commands may reach retained native views while unplaced. Commands for placed content make their waiting views before delivery. Commands, such as `Ref.Seek`'s `ItemVideoSeek`, follow the round's view items. A video's seeks go ahead of its `ItemVideo` in the update that changes its config and keeps its source, so a video at its end leaves it before an unpause in the same update plays it, where AVPlayer would reach the end again and stop; they stay after an `ItemVideo` that opens a source, which they apply to.
- A text field counts the user's edits. `ItemInputValue` carries the edit count the engine had seen, and the field ignores a value older than its last edit.
- Platforms report only the events in a view's mask, and never wait for the engine. The engine queue is unbounded, merges scroll events per view and keeps only the last resize.

## Where Go departs from NSH

The departures of Go's API shape as a whole are in [NSGo and NSH](nsh.md#gos-api-shape).

| NSH (Rust) | NSGo | Why |
| --- | --- | --- |
| `MountItem` enum | One struct with a `Kind` and pointers to large parts | No allocation per item kind; easy to encode across a pipe |
| `accessibilityActions` as a list in the props | `ViewProps.Actions` points at the element's list, never changed | `ViewProps` stays comparable, so the core diffs it with `!=` |
| Per-platform image loading and caching | One Go loader, `internal/platform/imageload`, over each system's HTTP client | Written once; platforms only download, decode and draw |
