# Long-running Android recording

This is the design for issue [#38](https://github.com/nsgo-dev/nsgo/issues/38). `microphone.RecordWAV` implements it; the remaining Android protocol, fake `AudioRecord` and device checks are listed under [Verification](#verification) ([roadmap](../roadmap.md)). Where it follows one of its [decisions](#decisions), confirmed by the user on 2026-11-15, the decision's number marks it. Android long recording is a runtime service, not a view feature: `AudioRecord`, a foreground service, app-owned storage and level callbacks must share one owner and one lifecycle.

The process/view split in [#12](https://github.com/nsgo-dev/nsgo/issues/12) is a prerequisite. An `NsgoView` detaching must not stop a recording, and an activity recreation must not create a second reader for the same microphone.

## API boundary

The existing `microphone` package remains the portable entry point. `RecordWAV(name, RecordOptions)` opens a recording with an explicit format, 16-bit PCM WAV at the rate and channels asked for, and destination, a file name in the app's recordings directory, and returns a `*Recording` with `Stop`, which waits for the file to be complete, `Ended`, `File`, `Err` and `Interrupted`; `RecordOptions.Level` takes its levels. The handle owns no view and belongs to the process, as the microphone does, not to an engine. `Supported`, `Allowed` and `Authorize` answer for the app's `RECORD_AUDIO` and recording service, and `Earlier` returns the terminal records of earlier runs.

On Android the app's Go code is an executable the runtime starts (`NsgoView` with `ProcessBuilder`), with no audio API of its own, so `microphone` reaches the runtime the way `widget`'s Live Activities do: through a channel in `internal/driver` outside any surface, which the Android backend connects and whose messages wait until it does (`driver.SendRecording`, `ConnectRecordings`, `HearRecordings` and `ReportRecording`, after `driver.SendLiveUpdate` and `ConnectLiveUpdates`, carried as JSON in the backend's `msgRecording` and `msgRecordingReport` as Live Updates are in `msgLiveUpdate`). So `layering_test.go` lets `microphone` import `internal/driver`, which stays portable, and `microphone` still builds on every target. The backend hands the runtime's reports to `microphone` on the goroutine that serves the app's views, which `microphone` never holds up: it updates the recording and wakes the goroutine that delivers its levels.

The first API records to an app-owned file rather than streaming unbounded PCM through the Go/Java pipe, so `microphone.Capture` stays unsupported on Android (decision 1). The backend reports the actual format and rejects a format it cannot write. Raw PCM and a bounded frame-stream API are separate APIs, if any follow, because they change memory, bridge and back-pressure guarantees.

Level callbacks carry peak and RMS values over a configurable interval, at least ten a second by default so a waveform can be drawn. They are metering data, not a second audio stream, and describe frames already written to the file. They run on a goroutine of `microphone`'s, never on an engine's, as `Capture`'s samples run on a thread of the system's on macOS and iOS; an app that updates its views from one hops with `Scope.Post`. A level the callback has not taken yet is replaced by the next, so a slow callback never holds up the recording.

## Android runtime

The Java runtime owns `AudioRecord`, its reader thread, the file writer and the foreground service, all in the app's process. Go sends start, stop and level-interval commands over the channel above; Java sends state, levels, file completion and stable errors. The reader never calls Go synchronously and never waits for Go while holding an `AudioRecord` buffer. One recording runs per app at a time: the service refuses a second start, from this process or another view's, as busy. A recording belongs to the `NsgoEngine` whose process started it (`RecordingService.java`). An active recording keeps that engine and its view running off screen if the standalone Activity is destroyed. The next Activity reuses the kept view. A sender thread writes reports to the engine's pipe, keeping only the latest level Go has not taken. When the recording's reports have been sent, its view reevaluates whether the engine is still needed. The service returns `START_NOT_STICKY`, so a killed process's service does not come back.

`RECORD_AUDIO` is asked for when a recording starts, through the visible activity as the runtime asks for `CAMERA`; an `-embed` host passes its `onRequestPermissionsResult` on as it does today ([embedding](embedding.md)). A refusal is `ErrDenied`, and a later start after the user grants it records without restarting the app. A start with no visible activity fails with `ErrUnavailable` instead of asking, since Android shows its permission dialog only over an activity, as does a start in an app whose manifest declares no recording service. A start waits for the user's answer however long it takes; a process that ends meanwhile leaves nothing to start.

The foreground-service rules span the whole supported range, API 28 to the target (the runtime's manifest has `minSdkVersion` 28 and `targetSdkVersion` 36):

- From Android 9 (API 28), an app capturing with no foreground UI and no foreground service receives silence, and a foreground service needs the `FOREGROUND_SERVICE` permission.
- From Android 11 (API 30), an app targeting it must declare the `microphone` foreground-service type to use the microphone in a foreground service, and a foreground service started while the app is in the background cannot use the microphone at all.
- From Android 14 (API 34), every foreground service declares its type, the app also declares `FOREGROUND_SERVICE_MICROPHONE`, `RECORD_AUDIO` must be granted before the service starts, and Google Play asks the app to declare the type in Play Console.

So the service starts only while an activity of the app is visible and after `RECORD_AUDIO` is granted, on every API level, not only on Android 14. The service shows the required ongoing notification. From Android 13 (API 33) that notification is not shown unless the app holds `POST_NOTIFICATIONS`, which controls its visibility, not whether the service runs or the microphone permission is granted: an app without it records with no notification in the shade. So `android.recording` declares `POST_NOTIFICATIONS` too, and from API 33 the start asks for it in the same prompt as `RECORD_AUDIO`, or alone where `RECORD_AUDIO` is granted, once, as `Notifications.java` asks for it; a refusal still records, without a visible notification.

Two processes can die. If the Go process ends while the app's process lives, the service finishes and closes the current file itself and reports the terminal record when Go connects again. If the app's process is killed (low memory, force stop, an OEM's swipe from recents), the service and the Go child die with it and no code runs, so the file on disk must already be usable: that is what the format below guarantees. A recording never resumes silently with a new file. No service restarts a stopped process to deliver `Ended`: the app can inspect the durable file, and the next start of the channel reports the terminal record (decision 4). The terminal records of abandoned recordings and of repaired files are kept in `.earlier` in the recordings directory (`RecordingJournal.java`), written whole through a temporary file, until `Earlier` returns them and `microphone` tells the runtime it took them, so a record survives the processes it was reported to: every Go process that connects hears those its directory keeps, and a record whose file the app deleted is dropped.

## Files and formats

Recordings live in `recordings` under the app's data directory, the one an embedding host gives `NsgoView.setStorageDirectory`, the app's files directory otherwise, so a host supplies the storage root, and its cleanup policy is its own: the runtime deletes no recording. A recording is written sequentially under the temporary name `.<name>.part` and renamed to its name when it ends; a name that is taken refuses the start with `fs.ErrExist`, so nothing is replaced. `File.Path` is the file's path, which `microphone` and `core` read without copying the audio through the bridge.

The first format is 16-bit PCM WAV, as #38 asks, written by the Java reader itself. WAV is chosen over AAC in MPEG-4 because a killed recording stays playable: the writer rewrites the header's sizes about once a second and at stop, the writer holds no buffer of its own past one `AudioRecord` read, so what it wrote before a kill is in the system's page cache rather than the process's, and the next start repairs the header of a temporary file from its length and reports it as a partial recording with its duration. An MPEG-4 file `MediaMuxer` writes has no index until it stops (its `moov` box is written then), so a killed one is unplayable from its first second. The backend exposes the sample rate, channel count and duration actually written, reporting the rate the device gave rather than the one asked for. RIFF's 32-bit sizes cap a WAV at 4 GiB, about 12 hours of 16-bit mono at 48 kHz; the size limit and a free-space error, once less than 8 MiB is left, are explicit terminal states before that (`ErrFull`, `ErrNoSpace`), and the service never deletes an app's prior recording to make room.

## Permissions, interruption and privacy

The tool's `nsgo.yaml` key `android.recording: true` adds the runtime's recording service to the APK's and the bundle's manifest as a `<service>` with `android:foregroundServiceType="microphone"`, and the `RECORD_AUDIO`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE` and `POST_NOTIFICATIONS` permissions. `android.permissions` cannot express this, as it adds only `<uses-permission>`s ([tool](tool.md)), so both encoders encode `foregroundServiceType` under the framework's attribute ID. An app without the key declares no recording service, since Play asks the app to declare and describe every foreground-service type its manifest has. An `-embed` library leaves them to the host, as it leaves permissions: the host's manifest declares the runtime's service with that type and the four permissions.

The API reports denied, unavailable, busy, interrupted, stopped and completed separately: `ErrDenied`, `ErrUnavailable` and `ErrBusy` from `RecordWAV`, `ErrInterrupted` from `Err` once `Ended` closed, a nil `Err` after `Stop`, and `ErrAbandoned` and `ErrPartial` for `Earlier`'s records. Interruptions are detected from the capture, not from missing frames, as an interrupted capture usually keeps delivering frames:

- From Android 10 (API 29), a voice call (`MODE_IN_CALL` or `MODE_IN_COMMUNICATION`) or a higher-priority capture leaves the recording running but silenced. The runtime registers `AudioRecord.registerAudioRecordingCallback` before `startRecording`, as Android requires, and reports interrupted while `AudioRecordingConfiguration.isClientSilenced()` is true.
- Before Android 10, `startRecording` fails while another app captures, which is reported as busy.
- A revoked permission or an `AudioRecord` read error ends the recording.

Whether an interruption pauses the file, inserts nothing and goes on, or ends the recording is an explicit option, which ends it by default (decision 3); the handle never claims to record while the capture is silenced. The recorder requests no audio focus and listens for none: focus arbitrates output, `AudioRecord` needs none, and requesting it would pause the app's own playback, so a recording and the app's playback, or another app's, run together as #38 asks.

The recording indicator and system privacy controls remain Android's. NSGo does not upload, transcribe or inspect the recording. Level values are not written into the audio file. Logs contain IDs and error codes only, never microphone data or file contents.

## Verification

The implementation is complete only when these checks exist:

- headless `microphone` tests cover format validation, state transitions, owner cleanup, level cadence and terminal errors;
- Android protocol tests cover start/stop, busy, writer failure, partial-file reporting and repair, a dead Go process and level back-pressure without an Android device;
- runtime tests use a fake `AudioRecord` to cover permission, buffer starvation, a silenced capture reported through the recording callback, rotation and the rename at stop; and
- device tests on an Android 9 or 10 device, one of Android 11 to 13 and one of Android 14 or later run a 30-minute recording across an activity recreation and a screen-off period, verify the foreground notification and file duration, play a sound while recording and record while playing with neither interrupted, report a phone call as an interruption, keep a playable WAV after the app's process is killed, and confirm that stopping leaves no open descriptor.

So far `microphone`'s headless tests (`recorder_test.go`) cover format validation, state transitions, level cadence and back-pressure and terminal errors, as Go hears them over the channel, and `internal/driver`'s and the Android backend's tests the channel and its message types. `RecordingJournal`, which uses `java.*` alone, runs on the JVM under the Android backend's tests (`TestRecordingJournal`), which keep a repaired record across processes until it is taken. The rest of the Java runtime has no harness yet, so neither the protocol tests of `RecordingService` (start and stop, busy, writer failure, repair, a dead Go process and its sender's level back-pressure) nor the runtime tests with a fake `AudioRecord` exist.

On a Pixel 3 XL running Android 12 (API 31), a 15-second recording survived `Activity.recreate()` and a six-second screen-off period with the microphone foreground service active. The runtime delivered 150 level callbacks and wrote a valid mono WAV at the reported 44.1 kHz. The 30-minute run, the other Android versions and the full playback checks remain open. Android's `audio.Player` support is tracked in [#1097](https://github.com/nsgo-dev/nsgo/issues/1097).

`nsgotest` records what an app records, as #38 asks, through a fake that connects to the channel in `internal/driver` as the runtime does. The channel is one per process while `nsgotest` runs many apps in one, so one app at a time uses the fake (decision 5).

## Decisions

The user confirmed on 2026-11-15 the answers the body proposes:

1. The first public recording API is file-only; `microphone.Capture` exposes no bounded PCM frames on Android and stays unsupported there.
2. Only formats that stay playable when a recording is killed are offered: WAV, with no encoded format such as AAC in MPEG-4 that a killed recording loses.
3. An interruption is an explicit option, pausing and resuming or ending the recording. The body proposes no default, so the implementation takes the conservative one: it ends the recording, its file finished and the end reported as interrupted, as an interruption ends a capture on iOS.
4. No background service restarts a stopped process to deliver completion; the durable file and the terminal record the next start of the channel reports are enough.
5. Recording stays in `microphone` behind the channel in `internal/driver`, with callbacks on a goroutine of `microphone`'s rather than an engine's, and `nsgotest` records one app at a time. Level metering is a recorder option and callback type of the file API, not part of `microphone.Stream`.
