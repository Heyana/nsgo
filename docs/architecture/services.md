# Services

Services are what the platform does for the app outside its views: alerts, the clipboard, opening links, the photo picker, taking a photo, file and folder picks and saves, opening and sharing the app's files, installing packages on Android, speech recognition, speaking text, biometrics, secrets, disk space, Sign in with Apple, in-app purchases, sign-in sessions, notifications and the badge, the system's permissions, keeping the computer awake, haptics, the app's lifecycle, the appearance, keyboard shortcuts, the status bar, the desktop window and quitting. Read this before changing one, in `core` or in a backend; [application and windows](application.md) covers the windows, tray icons and global shortcuts an app opens. A service goes to the platform of the window the code asking is in.

Audio playback is the `audio` package, whose engine part `core` carries as a service through the batch ([audio playback](audio.md)). macOS, iOS, Windows, Linux and the web play it so far; elsewhere an app plays sound only through a `Video`.

Remote push is designed separately in [Remote push](remote-push.md); it is not implemented by the local notification service described below.

Location and motion are scoped fixes and bounded streams on Apple and Android, under the system's [permissions](#permissions); [location and motion](location-motion.md) defines caching, units, lifecycle, background declarations and unavailable targets.

## Packaged Apple apps’ logs

`internal/backend` installs `internal/platform/applelog` before it parses launch flags. The default Go logger, and default `slog` handler through it, write to Apple’s unified log under the running main bundle’s identifier and category `nsgo`, including when Finder, the Dock or the Home screen supplies no useful stderr. An unbundled process uses its executable’s name. An app’s custom log writer or `slog` handler remains its own.

The helper loads libSystem, Foundation and CoreFoundation through purego, with no C or Swift shim. `_os_log_impl` needs a formatter registered in a loaded image’s `__oslogstring` section; Go’s string literals lack that metadata and produce UUID compose failures. The helper finds a canonical one-string formatter in Foundation’s loaded Mach-O sections and encodes a public string argument with Clang’s OSLog buffer layout. If the libraries or formatter are unavailable, installation leaves stderr alone. Messages are public: apps must keep secrets out of their diagnostics.

The standard Go logger has no severity or target metadata, so every record uses the stored default log type and keeps its original prefixes, rather than guessing severity from its text as a substitute for NSH’s structured logger. Records escape NUL, repair invalid UTF-8 for the native string, and split at line or UTF-8 boundaries within 960 bytes. A terminal, file or pipe also receives the original bytes; Xcode’s unified-log console suppresses duplicate stderr unless `OS_ACTIVITY_MODE=disable`, while development builds always keep stderr. iOS, tvOS and watchOS share this installation with macOS; other targets keep their existing logging paths.

On 2026-11-22, a packaged macOS app opened through Launch Services and a signed iPhone XR app launched without console capture both stored readable warning and error text, Unicode, literal formatting tokens, escaped NUL and a pre-`main` launch-flag diagnostic under their bundle ID. The iPhone fixture queried only its own process’s `OSLogStore`. tvOS, watchOS and Intel macOS were vetted but not run. `internal/testhost/testdata/applelogs` keeps the fixture and reproduction steps; `applelog` tests buffer splitting, stderr policy, setup failure and live macOS decoding.

## Requests and answers

A service is a command item in the batch. One that answers, such as a clipboard read, an opened URL or a pick, carries a number in `Count` and comes back as an event with it.

- `Tree.request` keeps the callback under the owner that asked, and the root runs it when that owner is gone, so a closed menu still hears its answer.
- Platforms answer on any goroutine through `Engine.Dispatch`; slow work, such as encoding a photo, runs off the main thread first.
- `nsgotest` answers from its model: `App.Clipboard`, `ClipboardImage` and `ClipboardFiles`, `OpenURL`, `PickImages`, `TakePhoto` (recording `Photos`), `ScanCode` (recording `Scans`), `PickFiles`, `PickDirectories`, `SaveFile`, `OpenFile`, `RevealFile`, `TrashFile`, `CanInstallPackages`, `OverlayPermission`, `AuthAnswer` (recording `AuthSessions`) and `WebCookies`, the web views' store, whose writes `SetWebCookies` may refuse and whose clearings `WebsiteDataClears` counts, and it records the shares, the packages installed, the install and overlay settings opened, the overlay over other apps (`App.Overlay`, [Android floating windows](android-floating-windows.md)), the appearance, quits and the context menu shown. Under `nsgo test -target`, `PickImages`, `TakePhoto` and `ScanCode` answers go through the test host in place of system pickers, cameras and scanners, and reach the app's engine as the platform's answers would. A speech session it runs hears what `HearSpeech` says and ends with `EndSpeech`; an utterance it speaks joins `Spoken` and speaks until `FinishSpeaking` ends it or the app stops it, and `App.Voices` answers `Scope.Voices`. `MicrophoneInput` gives the app a fake recorder for `microphone.RecordWAV`, which writes what `Microphone.Emit` sends into real WAV files and lists them in `Recordings`; it connects to the channel Android's runtime does, one per process, so one app at a time takes it ([Android recording](android-recording.md)).

## Clipboard

`SetClipboard` and `SetClipboardImage` write; `ReadClipboard`, `ReadClipboardImage` and `ReadClipboardFiles` read; `HasClipboardText` and `HasClipboardImage` read only what the clipboard holds, so iOS and Android show no paste notice for them.

- `ReadClipboardItems`, `WriteClipboardItems` and `ClipboardChangeCount` share the clipboard service's mount and reply path. Reads and writes cap the sum of representation bytes at 48 MiB and report `CodeQuotaExceeded`. The write copies caller data, validates it and prepares the native items before clearing the clipboard.
- macOS reads `NSPasteboard.pasteboardItems` and checks `changeCount` before and after materializing their types. It replaces the contents through `writeObjects:` with new `NSPasteboardItem` objects.
- Windows enumerates formats with the clipboard open, copies global-memory payloads and keeps the standard or registered name. The clipboard is one ordered format list, including `CF_HDROP`, rich text and registered byte formats. GDI handles, owner-display formats and private numeric IDs are skipped. Writes combine distinct formats under one `OpenClipboard` and reject duplicates before clearing. A presence-only format gets a zero byte because Win32 rejects a discarded zero-length allocation. The count comes from `GetClipboardSequenceNumber`.
- Other backends report representation access as unavailable. `nsgotest` models these commands in its own clipboard. Its representation writes, plain text writes and image writes all advance the same count.

- An image is read as a PNG and its size in pixels. One whose PNG is over 48 MB fails with `CodeQuotaExceeded`, as NSH's, and one the platform cannot read or convert fails with why (`driver.ReadClipboardImage`), so `readImage` rejects both and resolves null only for none. One beside copied files is their icon, not the user's image, and reads as none.
- Files are the `file:` URLs a file manager copied. Android and iOS rarely hold any, and the web has no access to them.

| Target | Writes an image as | Reads an image from |
| --- | --- | --- |
| macOS | PNG and TIFF | PNG, TIFF, JPEG, HEIC or GIF, converted by ImageIO |
| iOS | PNG | The same types, else `UIPasteboard.image` |
| Windows | `PNG` and a DIB over white | `PNG`, else the DIB through `x/image/bmp` |
| Linux | A `GdkTexture` | A texture, saved as PNG |
| Android | A PNG `FileProvider` serves | An image URI, decoded and encoded as PNG |
| Web | The PNG browsers take | `image/png`, with the page's permission: a refused read fails |

Android's clipboard holds images only as content URIs, which the runtime's `FileProvider` serves ([sharing files](#opening-and-sharing-files)). NSH writes no images on Android.

## Opening URLs

`OpenURL` refuses what `CheckURL` refuses, as NSH's `check_url` does: a URL without a scheme, over 16 KiB, with spaces, a web address without a host, and `javascript:`, `data:`, `blob:`, `file:`, `about:` and `asset:`. An embedding host's handler (`Host.HandleOpenURL`, [embedding](embedding.md#the-host-channel)) takes a URL before the platform.

| Target | Opens with | Answers false when |
| --- | --- | --- |
| macOS | `NSWorkspace openURL:` | No app handles it |
| iOS | `UIApplication openURL:options:completionHandler:` | The completion says so |
| Android | `Intent.ACTION_VIEW` | No activity handles it |
| Windows | `ShellExecuteExW` without UI, after the scheme is found under `HKEY_CLASSES_ROOT` | The scheme is unregistered |
| Linux | `GtkUriLauncher`, through the desktop portal | Launching fails |
| Web | A new tab for web pages, a followed link for other schemes | A popup blocker keeps the tab from opening |

Windows checks the registry first because the shell asks the user for an app for an unknown scheme, even without UI.

## Photo picker

`PickImages` resolves `PickOptions` into a `PickRequest`, as NSH's `PickImagesOptions`: one image, or up to `Limit` of at most 100.

- `PickRequest.Encoding` decides each image: kept as it is, or decoded upright, scaled to `MaxDimension` and encoded as PNG (a PNG scaled) or JPEG.
- By default HEIC and other formats browsers do not show become JPEG; `PickCurrent` keeps them. A quality encodes JPEGs again.
- `FinishPick` trims to the limit, sniffs missing types and names files after their type (`IMG_0042.HEIC` as JPEG is `IMG_0042.jpg`).

| Target | Picker | Prepared by |
| --- | --- | --- |
| iOS | `PHPickerViewController`, ordered, no permission | ImageIO |
| macOS | An `NSOpenPanel`, a sheet while its owner is visible, otherwise standalone | ImageIO |
| Android | The Photo Picker from API 33 (30 with its extension), else the documents UI | `ImageDecoder` in `Services.java` |
| Windows | `GetOpenFileNameW`, from a message of its own | `internal/platform/picked` |
| Linux | `GtkFileDialog` | `internal/platform/picked` |
| Web | `<input type=file>`, which needs the press's user activation | The browser's codecs, through `createImageBitmap` and a canvas (`web/picked.go`) |

`picked` decodes in Go, which reads no HEIC, so those pickers offer only the formats it reads unless `PickCurrent`. It turns JPEGs upright by their EXIF orientation and scales with Catmull-Rom. The web does the same with the browser's codecs, so pages link no Go image codec.

## Taking a photo

`TakePhoto` shows the system's camera for one photo, which NSH has not: a `PickRequest` of one whose JPEG is always encoded again, upright and at the quality asked for (0.9 by default), scaled to `MaxDimension`, and answered by `EventPick` as a pick is. `done` gets nil for a cancel and an error for a failure, such as a refused permission. `Env.CanTakePhoto` says the platform shows a camera; elsewhere `TakePhoto` fails with `ErrNoCamera` without asking it.

| Target | Camera | Permission |
| --- | --- | --- |
| macOS | The scanner's sheet (`scan.go`) with a shutter, the sheet's default button, which an `AVCapturePhotoOutput` (`apple.NewPhotoCapture`) on the default video device answers, enabled once the session runs; prepared with `apple.PreparePicked`, which turns it upright; `Env.CanTakePhoto` is `Env.CanScanCode`'s `apple.ScanCamera` | `AVCaptureDevice`'s, asked once through `privacy`, as the scanner's; the Info.plist declares `NSCameraUsageDescription`, without which a photo fails |
| Windows | The scanner's Direct2D card over `MediaCapture`'s BGRA8 frames with a shutter, the default button for Return and Space, that takes the frame shown, which `picked.Photo` encodes; `Env.CanTakePhoto` is `Env.CanScanCode`'s camera check | The capability consent store's `webcam`, as the scanner's |
| Linux | The scanner's modal GTK 4 window over the desktop portal's `Camera` and GStreamer `pipewiresrc` with a shutter, enabled at the first frame, that takes the frame shown, which `picked.Photo` encodes; `Env.CanTakePhoto` is `Env.CanScanCode`'s `IsCameraPresent` probe, and TakePhoto fails with `ErrNoCamera` (`driver.NoCamera`) where GStreamer lacks `pipewiresrc` | The portal's `AccessCamera`, as the scanner's |
| iOS | `UIImagePickerController`, where `isSourceTypeAvailable` says the device has a camera, which the simulator has not | `AVCaptureDevice`'s, asked once; the Info.plist declares `NSCameraUsageDescription` (`nsgo.yaml`'s `apple.info`), without which a photo fails, since the system would end the app as it asks |
| Android | `ACTION_IMAGE_CAPTURE`, where the device has `FEATURE_CAMERA_ANY`; the camera app writes into a file of the cache's `nsgo-camera`, the only files `FileProvider` opens for writing, which Java prepares and deletes | None, unless the manifest asks for `CAMERA`, which the camera app then needs granted: Java asks for it first (`permissionResult`) |
| Web | `<input type=file capture=environment>` on touch screens (`pointer: coarse`), which mobile browsers open as the camera; prepared with the browser's codecs | The browser's |

Windows and Linux take the frame the preview shows, at the camera's preview resolution, rather than a still from a separate photo pipeline.

## Scanning a code

`ScanCode` shows the camera and answers with the first code it reads of the kinds `ScanOptions.Kinds` asks for (a QR code alone by default), as `ItemScanCode` with a `ScanRequest`, answered by `EventPick` carrying a `*ScannedCode` (its kind and text), none when the user closes the scanner, and `Text` for a failure. It shares the picker's gate and the camera's permission. `Env.CanScanCode` says the platform shows a scanner; elsewhere `ScanCode` fails with `ErrNoScanner` without asking it. A code's binary data is not given, only its text.

| Target | Scanner | Permission |

## Bundled assets

NSH serves bundled assets through `fetch`. NSGo's `Scope.ReadAsset` resolves an `asset:` URL inside the app's `resources/` directory and gives Go apps the bytes through a scope callback. The platform reads on a worker goroutine and the callback runs on the engine while its owner is active. Missing files report `ErrAssetNotFound`. A host without a reader reports `ErrAssetsUnavailable`.

Apple reads from bundle resources and Windows and Linux read beside the executable. Android's runtime opens the asset with `AssetManager` and sends 64 KiB chunks from a worker. The web fetches the packaged resource name from the app's asset manifest. HarmonyOS fetches from the page's packaged `resources/` directory. Headless tests use the project's resource directory.

## Files

`PickFiles` and `SaveFile` move files of any type in and out of the app. As in NSH, the system dialog lets the user choose a path. NSGo's save request also carries the file source, which the backend writes after the user chooses. `PickFilesOptions.Types` offers media types (`application/pdf`), families (`image/*`) and extensions (`.zip`). A picker that filters only by one kind gets the other through `driver`'s table of common types and offers every file when a type has no counterpart.

Both pickers take hints a platform without the setting ignores, each empty for the system's own: `Title` says what the picker is for, `Button` labels the button that picks and `Start` is the folder it opens in, ignored where no such folder exists, as the table says per target. `PickFilesOptions.TypesName` names `Types` in the type menu of Windows and Linux, which otherwise read the English "Files", and Windows "All files" where every file is offered. Android's `EXTRA_INITIAL_URI` and the web's `startIn` take a document URI or a handle rather than a path, so neither has a `Start`. `nsgotest` records the hints with each pick (`App.FilePicks`, `App.DirectoryPicks`). The desktops' folder pickers let the user make a new folder: macOS's through `setCanCreateDirectories:`, Windows' and GTK's on their own.

- A picked `File` is on disk: the user's own on desktops, a copy in the app's storage on iOS and Android (`Temporary`) that the app deletes. The web has no disk, so `File.Open` reads the file's `Blob` a slice at a time. `FinishFiles` fills names, sizes, modification times and types.
- `SaveFile` copies the file at `SaveOptions.Path`, or `Data` where it names none. `SaveOptions.Start` opens the desktop and iOS save dialogs in an existing absolute folder. With no usable folder the system chooses where to start. `nsgotest` records the absolute path in `App.Saves`. Desktops write through a temporary file beside the destination (`SaveRequest.SaveTo`) and report the chosen path to the app. iOS and Android stage bytes or a renamed source in a directory that is removed once the dialog answers (`SaveRequest.Stage`).
- With `SaveOptions.Preflight` or `Accept`, the desktop backend sends `EventSavePreflight` with the destination. `Tree.answerSavePreflight` runs the check under the requesting owner and returns `ItemSavePreflightAnswer`. Windows intercepts `IFileDialogEvents::OnFileOk` and checks off the UI thread. AppKit's `panel:validateURL:error:` waits for its decision on the main thread, so the macOS backend delivers the answer when the engine hands it the batch. Linux checks from the in-process GTK chooser's response handler when the portal is unavailable or disabled. These dialogs display the refusal and check each retry. If the user cancels after a refusal, the save reports the refused path and original error. The Linux desktop portal reports a path after the chooser closes, so a refusal there completes the save. A five-second deadline refuses a destination whose check has not answered. On Android the preflight variant uses `ACTION_OPEN_DOCUMENT_TREE` so selecting the folder creates no file. Java asks the engine about the tree URI with the proposed name in its query, calls `DocumentsContract.createDocument` after approval, and verifies the provider's returned name before copying. iOS's export picker copies the document before it reports the destination, so it reports an error for a preflight request, as HarmonyOS does. The web keeps its ordinary save flow. The `nsgotest` model checks what `App.SaveFile` chooses before it writes.
- `PickScreenColor` lets the user pick a color anywhere on the screen where `Env.CanPickScreenColor` says so: `NSColorSampler` on macOS, a transparent topmost virtual-screen capture overlay with `GetDC(0)` and `GetPixel` on Windows, the XDG Desktop Portal `org.freedesktop.portal.Screenshot.PickColor` interface (version 2 or later) on Linux, and the browser's `EyeDropper` on the web.
- `PickDirectories` picks folders apart from files, so a caller that wants files gets no folders to filter out. A `Directory` is an `fs.FS` of the user's folder: on desktops and iOS it reads the folder on disk at `Path`, which iOS keeps in its security scope while the app runs; Android and the web have no path, so it reads through `Directory.FS`, waiting for the platform, and the app reads it off the engine's goroutine. `driver.FolderFS` makes that `FS` of a platform's listings and reads, finding a name through the listings it remembers and listing a folder afresh whenever it is read.
- `done` tells a cancel from a failure: no files or folders, or `saved == false`, with a nil error, against the error the platform reported.

| --- | --- | --- | --- |
| macOS | An `NSOpenPanel`, a sheet of a visible owner or standalone, with `UTType`s; `Title` is its `message`, `Button` its `prompt`, `Start` its `directoryURL` | An `NSOpenPanel` for directories with the same presentation and hints | An `NSSavePanel` with the same presentation, the name's extension and `Start` as its `directoryURL` |

| Windows | `IFileOpenDialog`, filtering by extension; `SetTitle`, `SetOkButtonLabel`, `SetFolder` and a named filter | `IFileOpenDialog` with `FOS_PICKFOLDERS`, the same hints applying; Windows 11's Home, not on disk, opens the profile | `IFileSaveDialog`, with `SetFolder` for `Start` and an overwrite prompt |

## Background downloads

`core.Scope.Download` hands GET requests and their destination to the platform transfer host on a process channel. Each task has a stable ID. Progress notifications cross the pipe as snapshots, with callbacks posted to the scope's graph goroutine. The platform owns the transfer after an initiating scope goes away. Apple runners configure this host for standalone apps; embedded Apple views do not configure it.

The APK and App Bundle declare the private `BackgroundDownloadService` with `dataSync` and the foreground-service permissions when `android.background_downloads` is set. An Android embedding host declares the same service and permissions in its own manifest. The service owns the requests, progress notification, partial files and terminal journal independently of `NsgoView` and `NsgoEngine`. Each task writes beside its destination and publishes with an atomic rename. A paused transfer keeps its partial file and uses `Range` with `If-Range` when it has a server validator. The service keeps request credentials in memory and journals only the task's path, byte counts and state. It reconciles interrupted files and reports journaled results to the next engine until the app acknowledges them.

An optional exact leaf certificate pin supplies trust for one HTTPS request. The HTTPS connection still checks the hostname and the certificate's validity. iOS uses background URLSessions, grouping system-trusted requests and each exact certificate pin in separate sessions so an authenticated connection cannot cross trust policies. It reconnects their stable identifiers at launch before scene creation. Its delegate moves finished files into app-owned staging and publishes them atomically, retaining the staged original until the result journal is durable. UIKit's background-session completion runs after delegate events and pending publications finish. macOS uses the same host with an in-process URLSession. The private Apple journal retains request metadata and native resume data for paused transfers, with file protection after first unlock on iOS; terminal records discard request credentials. Windows and Linux transfer hosts remain in the [roadmap](../roadmap.md#finish-the-existing-platforms).

## Opening and sharing files

`OpenFile` opens a file the app has in the app the system associates with its type. `RevealFile` opens the system file manager with a file or folder selected, and `TrashFile` moves it to the user's recoverable Trash or Recycle Bin; it never deletes permanently and returns `ErrNoTrash` when the volume has no trash or its trash would not keep the item. `Share` shows the system's share sheet for files, text or both. Each `SharedFile` is a path on disk (or, for `Share`, in-memory `Data` bytes such as on the web), with the name the other app sees and its type, which the file's name and extension say by default. Disk files go by path or content URI, so their size costs the bridge nothing.

Android's standalone manifest declares `SEND` and `SEND_MULTIPLE` for `android.share_types`. The launcher reuses its running task and resolves the incoming MIME type against those filters. It reads text from the intent and streams content URIs with read grants to the same cache directory as documents picked. Transfers run in arrival order off the UI thread. Each share travels as one `EventShared` with the item's text or local path and metadata. The view queues events until mounting, and the core keeps their batches until the app registers `mobile.OnShared`.

`desktop.QuickLook` shows macOS's `QLPreviewPanel` on regular files, starting at an index, and answers nothing back: the panel keeps its own place and closes itself. The app delegate takes control of the panel as the responder chain asks (`acceptsPreviewPanelControl:`) and gives it the files of the last request as `NSURL`s; a request while it shows changes its files, as the Finder's selection does. `Env.CanQuickLook` is false in a view a host embeds, whose app delegate is the host's, and on targets without a preview backend.

Windows resolves the file type's registered `IPreviewHandler` through `AssocQueryStringW` and activates it out of process. It supplies a native owned window and `IPreviewHandlerFrame` site; stream initialization is preferred to item or file initialization. The site advertises host accelerators and posts the handler's forwarded keys back to the window, so an RPC never unloads its own handler from inside the callback. Space/Escape closes, arrows select files, and replacing a file or closing the owner unloads and detaches the handler. Formats without a registered handler cannot render; availability describes the facility, not each file.

Linux discovers a running or activatable `org.gnome.NautilusPreviewer` without starting it during environment reads. A coalesced worker introspects the service and supports the legacy X11 `sub` and Sushi 2 `ssb`/`ssbs` ShowFile contracts. File URLs preserve escaped and non-ASCII paths. Sushi owns the window. Its ParentHandle/Visible signals attribute arrow selection and owner-close to the requesting X11 window; successful ShowFile fills missing initial values because Sushi 50 advertises property getters that fail. A service replacement clears that attribution. Legacy services and Wayland's currently unexported parent handle only show a file; ownership and selection stay unavailable there. KDE-specific services remain a [roadmap](../roadmap.md#from-nsgos-issues) goal. NSH has no Windows or Linux preview backend to port, so these follow the native host and Sushi contracts directly.

- `core` checks each file is a regular file before asking the platform, and fails a share of neither files nor text. `OpenFile` also takes a folder on macOS, Windows and Linux, whose openers hand it to the file manager; phones have no file manager an app can open a folder of its own in, so `core` fails it there. `RevealFile` and `TrashFile` take a file or a folder, which `core` checks exists; the targets without a file manager answer `NoFileRevealer`.
- `OpenFile` tells a type no app opens (`opened == false`, no error) from a failure. `Share` answers once the sheet shows, which says nothing of what the app chosen did with the files.
- Where a platform hands files on by path and shows their own names, a file whose `Name` differs is linked under it in a directory of the temporary one (`SharedFile.Stage`), which a later share removes after `ShareStageAge`. Desktops open a file itself, under its own name.
- `ShareOptions.Anchor` is the element a sheet shown as a popover points at, on macOS and iPads; it points at the root's center without one.

## Installing packages

`mobile.InstallPackage` hands an APK in the app's storage to Android's package installer, as `OpenFile` hands a file on: `ACTION_VIEW` of a `FileProvider` URI typed `application/vnd.android.package-archive`. The installer asks the user to confirm, and sends them to the setting first where they have not let the app install packages, so the answer says only that it started. `CanInstallPackages` is `canRequestPackageInstalls`, and `OpenInstallSettings` opens `ACTION_MANAGE_UNKNOWN_APP_SOURCES` for the app. Elsewhere `core` answers at once, without asking the platform.

The installer refuses an app whose manifest does not ask for `REQUEST_INSTALL_PACKAGES`, which stores review, so the runtime asks for nothing: an app lists it in `nsgo.yaml`'s `android.permissions` ([tool](tool.md)), which the tool adds itself to a build on the direct updates channel ([updates](updates.md)), an embedding host in its own manifest, and `InstallPackage` fails with that advice without it.

## Local service discovery

`Scope.AdvertiseService` and `Scope.BrowseServices` send `ItemDiscovery` on the calling surface. Both operations belong to the current scope, use an ID for subsequent `EventDiscovery` reports, and release the native operation when stopped or disposed. `AccessServiceDiscovery` gates advertising and browsing by DNS-SD service type. The headless model serves synthetic browse results from `nsgotest.LocalServices`.

NSH has no local service discovery API. On macOS and iOS, the system's DNS-SD library registers services in `local.`, browses on every interface and resolves the endpoint and TXT records of each matching instance. Resolvers are cancelled if their instance disappears. A matching endpoint seen on multiple interfaces is reported once and removed when its last record goes away. Each surface owns its operations, and callbacks and reference release run on Apple's main dispatch queue. Apps declare `NSLocalNetworkUsageDescription` and `NSBonjourServices` in `nsgo.yaml` through `apple.info`.

On Linux, GTK's GDBus calls Avahi asynchronously on the system bus. The backend prepares each browser and subscribes to its signals before starting it, so cached services reach the app. Results from interfaces and address families are grouped by endpoint. Discovery reports an asynchronous error when Avahi is unavailable.

On Windows, the backend loads the system's DNS-SD API from `dnsapi.dll`. It registers a service in `local`, browses PTR results on all interfaces and resolves each instance once. A goodbye record cancels its pending resolve or removes its reported endpoint. Native callbacks copy their results for the window thread and free the native records. Each window cancels its queries and deregisters its advertisements when it closes. DNSAPI takes NUL-terminated Unicode TXT keys and values, so Windows advertisements accept UTF-8 text values without NUL.

On Android, `NsdManager` registers and browses services, and resolves each instance to an IP address. The primary view and its overlays share a controller on the UI thread, and commands and results carry the surface and operation IDs. Resolutions queue because older Android allows one at a time. If an instance is lost while resolving, the runtime discards its result and cancels the request where Android allows it. Cached endpoints are removed when their last matching instance leaves. The runtime holds a Wi-Fi multicast lock during active discovery and advertising on Android releases that require one. The environment advertises support after the Java runtime gains the discovery command.

A Pixel 3 XL on Android 12 found a Mac's Bonjour advertisement, read its binary TXT, connected to the advertised TCP endpoint, and reported removal when the Mac stopped advertising (2026-11-22).

## Speech

`StartSpeech` recognizes what the user says, NSH's `Speech.start`: one session per engine, which a new one and its scope's end abort. It reports the whole transcript so far, before it is final with `Interim`, and ends once with the last one and a `SpeechError` named as the Web Speech API's (`not-allowed`, `no-speech`, `audio-capture`, `network`, `language-not-supported`, `unavailable`, `failed`). `Stop` has the recognizer finish what it heard; `Abort` ends it at once. A `Lang` of "" is the app's locale.

- macOS and iOS (`apple/speech.go`) feed the Speech framework's recognizer from `AVAudioEngine`'s input, asking for speech recognition and the microphone once each. The app's Info.plist declares `NSMicrophoneUsageDescription` and `NSSpeechRecognitionUsageDescription` (`nsgo.yaml`'s `apple.info`): without them a session ends `not-allowed`, since the system would end the app as it asks. iOS holds the audio session in the record category while it listens.
- Android (`Speech.java`, `android/speech.go`) recognizes through `android.speech.SpeechRecognizer` (falling back to the on-device recognizer from API 31 when available). The runtime's manifest and AAR query `android.speech.RecognitionService` so API 30 and later discover the service (`Env.CanRecognizeSpeech`); the app lists `RECORD_AUDIO` in `nsgo.yaml`'s `android.permissions`, which `Speech.java` asks the activity for before listening and without which a session ends `not-allowed`.
- Windows (`windows/speech.go`, `windows/speech_state.go`) recognizes through WinRT's `Windows.Media.SpeechRecognition.SpeechRecognizer` and its `ContinuousRecognitionSession`, reporting live interim transcripts from `HypothesisGenerated` when `Interim` is set, matching `Lang` against `SupportedTopicLanguages` (or `Windows.Globalization.Language`), and finalizing on `StopAsync` or cancelling on `CancelAsync`. `Env.CanRecognizeSpeech` reports whether the WinRT class is registered.
- Web (`web/speech.go`) uses the browser's `SpeechRecognition` (or `webkitSpeechRecognition`) when present, setting `Env.CanRecognizeSpeech` from its presence and cleanly ending `unavailable` when absent.
- Elsewhere (Linux, tvOS, watchOS, mini programs) `Env.CanRecognizeSpeech` is false and a session ends `unavailable` without asking the platform.

## Speaking

`Speak` speaks text aloud in a `Voice`: a BCP 47 `Lang`, the app's locale when empty, the `ID` of one of `Voices`' voices, the platform's default for the language when empty, and a `Rate` and `Pitch` from 0.5 to 2, 1 being the voice's own, 0 standing for 1. One utterance speaks per engine, as one session listens: a new one stops the one speaking, and so do `StopSpeaking` and the end of the scope that spoke it. `done` runs once, in a later turn, finished, stopped, or failed with a `SpeakError` named as the Web Speech API's `SpeechSynthesisErrorEvent` errors (`not-allowed`, `language-unavailable`, `voice-unavailable`, `text-too-long`, `audio-busy`, `synthesis-unavailable`, `synthesis-failed`). Core ends a stopped utterance itself as it sends `SpeakStop`, so the platform's own report of it, and of one a new utterance cut, finds no one; blank text finishes without asking the platform. `Voices` answers with the voices installed that speak a language and the tags under it, or every one, sorted by language and name. `Env.CanSpeak` says the platform speaks; elsewhere an utterance fails `synthesis-unavailable` and `Voices` answers none without asking it. Code whose `Access` does not grant `AccessTextToSpeech`, TSX's `textToSpeech` capability, fails `not-allowed` and hears no voices. One item, `ItemSpeak`, carries the three commands, and `EventSpeak` reports an utterance's end or answers the voices.

## Sign-in sessions

`AuthSession` signs the user in with an OAuth provider in the system's authentication session, as RFC 8252 asks of native apps, never in a web view, which Google refuses. The app keeps the protocol: it makes the PKCE verifier and the state, builds the authorization URL for the redirect the session gives it, and checks the callback's `state` and trades its `code` itself; NSGo only opens the URL and catches the redirect. `done` hears the callback URL, or an `AuthError`: `AuthCancelled` when the user closes the session or the app calls the returned `cancel`, `AuthTimeout` once `AuthSessionOptions.Timeout` passes, `AuthUnavailable` where the platform cannot catch the redirect asked for or the owner's `Access` does not grant `AccessAuthSession`, and `AuthFailed` wrapping what failed. Like other answers it outlives the owner that asked, running under the root then.

The session takes two steps through one item, `ItemAuthSession` (`driver.AuthRequest`), each answered by `EventAuthSession` (`driver.AuthEvent`): `AuthStart` has the platform prepare the redirect and report it, as a loopback redirect's port is known only once the platform listens; `core` then calls the app's `url` with it and sends `AuthOpen` with the URL, refusing one that is no web address, and the platform ends the session once. `AuthCancel` ends it without an answer, which `core` gives itself.

The redirect follows `AuthSessionOptions`: `Scheme` is the app's own scheme, the redirect `scheme:/path`, or `https` with `Host` for `https://host/path`; without one, desktops serve `http://127.0.0.1:port/path` and the web the page's origin. Desktop loopback redirects escape the decoded path and resolve dot segments before reporting it; the web serializes its redirect with the browser's URL parser, so both match the address navigation returns.

The core claims a browser session's callback URI only when the platform's `AuthRedirect` marks `OpenLinks`. A matching private scheme and normalized path complete that session with the original callback, including its query and fragment; unrelated and late links remain ordinary `OnOpenLinks` deliveries. Reusing a browser callback URI cancels its previous waiter, while different URIs can wait in different surfaces. Disposing a region leaves its session alive, but disposing the entire surface releases its callback claim and timer. Native sessions that report `AuthEnded` keep that completion path.

`Ephemeral` holds on macOS, iOS and watchOS. Android requests ephemeral Custom Tabs where the browser supports them; a browser may ignore the request, so it does not promise cookie isolation there. The loopback server reads the browser's request with `net` alone: a backend's handling of every item links into every app, and no app links Go's HTTP stack unless it asks for it ([layers](layers.md#what-an-app-links)). `nsgotest` catches a scheme as Apple's session does and serves other redirects on `nsgotest.AuthLoopback`; `AuthAnswer` answers each session with a callback or an error, and without one the session waits for `cancel` or its timeout.

The watch host retains each native session until completion, ignores late callbacks after cancellation, and copies its callback URL or error through the UTF-8 bridge to `EventAuthSession`. NSGo's existing watchOS 26 build minimum still applies; it is not lowered to the system API's introduction. On watchOS 27's simulator (2026-11-22), a local synthetic provider completed an S256 request, code/state callback, verifier exchange and app cancellation; physical-watch sign-in, associated-domain HTTPS and user dismissal of the system session remain unverified.

Android uses the existing two-phase request: `AuthStart` validates a live Activity and that its manifest claims the callback, then reports the canonical private redirect; `AuthOpen` launches a browser intent with the Custom Tabs session extra. The callback must match the normalized destination URI, including its authority and escaped path, before query/fragment data reaches the app unchanged. A matching callback is consumed before ordinary open-link events. Activity lifecycle callbacks observe a browser return and defer cancellation one main-loop turn so a link delivered before `onResume` wins. Replacing a session cancels the prior waiter, and release unregisters its Activity callbacks. Explicit cancellation attempts to bring the same Activity back without recreating it; a browser in a separate task may remain behind it. Embedded hosts forward their accepted links with `NsgoView.openLink`. Unlike NSH's core-level URL-scheme completion, NSGo's runtime emits `EventAuthSession` directly, keeping unrelated open-link listeners out of a live authentication callback. Mount items carry no length, so Go sends `ItemAuthSession` only to a runtime whose environment sets the fourth capability byte's `capAuthSession` (`Protocol.CAP_AUTH_SESSION`); for an older runtime it answers the session `AuthUnavailable` itself, as before.

## In-app purchases

NSGo's own, as NSH has none ([#353](https://github.com/nsgo-dev/nsgo/issues/353)). `Products` looks up products by ID, answering those the store sells with its own title, description and `DisplayPrice`, formatted for the user's storefront, which apps show as it is and never replace with a price of their own, and a subscription's group, period and offers. `Purchase` buys one through the store's sheet, with an `AccountToken` UUID that ties it to the app's user (StoreKit's `appAccountToken`), a quantity and a signed promotional offer, and answers once: the `Transaction`, whose `Signed` is the store's JWS for the app's server to verify, or a `PurchaseError`: `PurchaseCancelled` and `PurchasePending` (Ask to Buy, or a purchase the user completes outside the app) apart from `PurchaseFailed`, which wraps the store's words. `OnPurchaseUpdate` hears the transactions the store makes or changes outside a `Purchase` call, renewals, approved and refunded purchases, those made on other devices and, as the app starts, those it has not finished, the ones that came before any handler kept for the first, as `OnNotificationPress` keeps its press. `FinishTransaction` finishes one by ID once the app delivered it, `PurchaseNotFound` when none unfinished has it; `CurrentEntitlements` answers the latest transaction of each product the user owns now; `SyncPurchases` is the Restore Purchases button's `AppStore.sync()`. Code whose `Access` does not grant `AccessPurchases` gets `AccessDenied` and hears no updates, and TSX's `Purchases` module needs the `purchases` capability.

`ManageSubscriptions` opens the iOS StoreKit sheet or the App Store subscriptions page on macOS and tvOS. `RequestRefund` begins Apple's refund flow for a transaction and answers success or cancellation. They share `ItemPurchase` and `EventPurchase` with the existing purchase commands; `core` checks that a refund has a transaction ID before asking. StoreKit presents the macOS refund sheet from a view controller, which NSGo's windows lack, so the library anchors it with a transient controller whose empty view sits in the window's content view while the request runs; iOS passes the surface's active `UIWindowScene`.

All six share one item, `ItemPurchase` (`driver.PurchaseRequest`), answered by `EventPurchase` with a `driver.PurchaseAnswer`; updates come as `EventPurchaseUpdate`, which the root's tree hands to the handlers. `core` checks the account token and an offer's nonce are UUIDs and answers no IDs without asking.

The opt-in native regression in `internal/platform/apple/testdata/purchases` uses an owned iOS simulator and StoreKit Testing, with `apple.purchases` enabled in its fixture. It checks local prices, verified Xcode transaction updates, concurrent finishes and finished entitlements. Set `NSGO_STOREKIT_NATIVE_TEST=1`, `NSGO_STOREKIT_TEST_FRAMEWORKS` to Xcode’s simulator `Developer/Library/Frameworks`, and `DYLD_FRAMEWORK_PATH` to that directory plus its sibling `PrivateFrameworks`, through `nsgo test -env`, then run the fixture with `-target ios_simulator -device <owned UUID>`. It creates local transactions through `SKTestSession`; it does not verify a payment sheet, a sandbox account or an App Store Server API signature.

## Secrets

`Scope.Secrets` returns the app's secure store, which NSH has not: strings by account under a service, as MyGo's `App.Secrets` and keytar keep them. Unlike the other services it is synchronous, as `Storage` is, and no item of the batch: the platform gives the engine a `driver.SecretStore` (`engine.Options.Secrets`, `RootOptions.Secrets`) whose calls run on the goroutine that makes them, so an app calls them off the engine's, as a keychain may wait for the user. `core.Secrets` is a value: its `Service`, the app's ID by default, else its executable's name, `AccessGroup` and `Accessible` name and protect the items, so an app reads what an earlier build or another framework wrote by naming them as it did. A target without a store, or a store finding none (`driver.ErrNoSecretStore`), answers `ErrSecretsUnavailable`; nothing falls back to `storage.json`.

- `Secrets` asks the gate for `AccessSecrets` as it is called, and the value it returns fails every call with `AccessDenied` when refused. `ProvideSecrets(name)` gives a subtree a partition, the service `<service>#<name>`, out of which it cannot name another service or access group; TSX's `Sandbox.Storage` names both partitions, so a package's `Secrets` module, under the `secrets` capability, keeps its own.
- `nsgotest` and every target's test host keep secrets in a `driver.MemorySecrets` (`App.Secrets`, `testhost.Options.Secrets`): `engine.Options.UseTest` replaces the platform's store, so no test reaches the machine's keychain.

## Notifications and the badge

`NotificationPermission` answers whether the app may show notifications without asking, `RequestNotificationPermission` asks with the system's prompt the first time, as NSH's `Notifications`: not asked (`"default"`), granted, denied, or unavailable where the platform or build shows none. `ShowNotification` shows one, replacing one of its ID, also while the app is in front, and answers whether the system took it; `CloseNotification` removes one, and `CloseNotifications` all those `ShowNotification` showed, carried by the same item with an empty ID; `OnNotificationPress` hears a press, the one that started the app kept for the first handler. `SetBadge` sets the count on the app's icon. Code its `Access` does not grant `AccessNotifications` gets unavailable and nothing shown.

A `Notification` with an `At` later than the wall time is scheduled: natively where the platform offers a schedule (whether the app's process runs or not on macOS, iOS, watchOS, Android and Windows) or kept in memory while the app or page runs on Linux and the web (`driver.NotificationScheduler`), and showing another of its ID or closing it while it waits moves or cancels it. `Repeat` shows it daily or weekly at `At`'s time of day, its clock reading in `At`'s location kept in the device's time zone, from the next such time after now; core sends that first time as the driver's `At`. Scheduling, which NSH does not have, is NSGo's own for [#356](https://github.com/nsgo-dev/nsgo/issues/356). Where the backend reports `Environment.ScheduledNotifications` false (such as tvOS, mini programs, or browsers without `Notification`), core answers a scheduled one false without sending it, and `Env.CanScheduleNotifications` tells the app.

On 2026-11-22, the Android pending-intent regression failed for `Aa` and `BB` before the URI fix and passed afterward on an API 35 emulator and a physical Pixel 3 XL on API 31. The owned API 35 emulator restored the one-minute and moved schedules after a reboot, showed both without Go running, omitted the cancelled ID, and cold-started the fixture with `move1356` on a press. An app that shows in its window what its notifications told clears them as it comes to the front:

```go
cx.Effect(func() {
	if cx.Env().Lifecycle() == core.LifecycleActive {
		cx.CloseNotifications()
		cx.SetBadge(0)
	}
})
```

`nsgotest` keeps the notifications shown, the badge and the permission (`NotificationPermission`, `NotificationAnswer`), and `PressNotification` presses one. Where its environment says `ScheduledNotifications`, `PendingNotifications` keeps the scheduled ones, each `At` its next time, which `Advance` and `FastForward` show as the clock's wall time reaches it.

## Permissions

`PermissionStatus` answers whether the app has one of the system's permissions without asking, `RequestPermission` asks with the system's prompt where it has one and has not asked yet, `OpenPermissionSettings` opens the page of the system's settings that gives it, and `desktop.GuidePermission` opens that page and waits for the user to give it, after MyGo's PermissionFlow, itself after [PermissionFlow](https://github.com/jaywcjlove/PermissionFlow) (`NOTICE`). A `Permission` is a key, from `accessibility` to `media-library` in the order of macOS's Privacy & Security (including `contacts`, `photos`, and `automation`, with `PermissionAutomationOf(bundleID)` producing `automation:<bundleID>` for a target app), then the sensors' `location`, `background-location` and `motion`, and `notifications` (`core.Permissions`). Core asks the [location and motion](location-motion.md#api-and-ownership) service for the sensors' permissions and the [notification](#notifications-and-the-badge) service for `PermissionNotifications`, held to each service's own capability, rather than sending `ItemPermission`, except to open their settings or guide. Its status is `prompt` (not asked), `granted`, `limited` (partial access, such as selected photos or contacts, which `Allowed` counts with granted), `denied`, `unknown` (kept but not told), `not-gated` (nothing keeps it from the app, which `Allowed` counts with granted) or `unavailable`: the platform has no such thing, the key names none, or the owner's `Access` does not grant `AccessPermissions` for it, or the owning service's capability for sensors and notifications. Face ID and Touch ID are not permissions but [biometrics](#biometrics), which answer for themselves. One item, `ItemPermission`, carries the five commands, checking, asking, opening the settings, guiding and ending a guide; `EventPermission` answers each but the last.

- Asking on Apple platforms needs the permission's usage description in the Info.plist the system reads (`nsgo.yaml`'s `apple.info`), on macOS the responsible process's: without it the request answers unavailable and logs the key, since the system would end the app as it asks. `internal/platform/privacy` holds the checks and the prompts (loading optional frameworks lazily through `purego.Dlopen` so minimal apps link none of them), which the `microphone` package's `Allowed` and `Authorize`, speech, iOS's camera and biometrics' Face ID check share. On macOS, `hardenedEntitlements` in `cmd/nsgo/sign.go` also claims `com.apple.security.personal-information.addressbook`, `com.apple.security.personal-information.photos-library` and `com.apple.security.automation.apple-events` when `apple.info` declares `NSContactsUsageDescription`, `NSPhotoLibraryUsageDescription` or `NSAppleEventsUsageDescription`.
- macOS charges what a program started from another app does to that app, so under `nsgo dev` the terminal is asked and listed, and a grant to an ad hoc signed build lapses with the next build's signature. Screen Recording tells a grant only once the app starts again. `AEDeterminePermissionToAutomateTarget` checks and asks for a running target app by bundle ID (`automation:<bundleID>`); asking runs off the main thread because Apple's call blocks while the prompt is open, and a non-running target answers unknown (`procNotFound`).

macOS's guide is a borderless panel that never takes the focus (`macos/permissionguide.go`). A goroutine follows System Settings 30 times a second through `CGWindowListCopyWindowInfo`, which needs no permission: the panel sits under its window, lined up with the pane, and hides while another app is in front. For the panes whose list takes an app dragged into it — Accessibility, Screen Recording, Input Monitoring, Full Disk Access, App Management, Developer Tools, Bluetooth and Media & Apple Music — it says "Drag MyApp to the list above to allow Accessibility." in `desktop/locales`' words, naming the pane as System Settings does (Device Control and Data Access from macOS 27), and holds the app's icon and name for the user to drag; the pointer stays the arrow. The app is its bundle, else its executable, never the terminal that started it; `GuideOptions.App` names another, which code under an `Access` cannot. The guide ends, answering once, as the app has the permission (granted or limited, checked every 250 ms), the user closes the panel or System Settings, System Settings does not open within 10 seconds, `stop` is called, its owner goes or another guide starts; one whose window closes ends unanswered.

It departs from MyGo where Go apps differ: answers come to callbacks on the engine instead of blocking calls, the guide waits so no `Wait` is needed, `not-gated` stands for MyGo's `ErrUnsupported` beside `Allowed`, and the statuses take the web's names.

`nsgotest` keeps each status (`Permissions`) and what a request makes of one not asked (`PermissionAnswers`), both made by `Start`, keeping `Permissions[PermissionNotifications]` and `NotificationPermission` in sync, the settings opened (`PermissionSettings`) and the guide showing (`Guide`), which `GrantPermission` and `CloseGuide` end.

## Thermal state and low-power mode

`Env.ThermalState` and `Env.LowPowerMode` read separate signals from the platform's environment. A change reaches its readers without resolving the whole tree. `nsgotest` pins both on headless and native targets.

- Apple reads the two `NSProcessInfo` properties and follows Foundation's thermal and power state notifications on the main thread.
- Android reads `PowerManager` from the view. Battery Saver broadcasts and API 29's thermal status listener refresh its environment. Android's light and moderate thermal levels map to fair, severe to serious, and critical through shutdown to critical.
- Windows reads the battery saver flag from `GetSystemPowerStatus` and follows `GUID_POWER_SAVING_STATUS` notifications on each engine's window.
- Linux follows the D-Bus `ActiveProfile` of power-profiles-daemon, using the legacy endpoint where needed. Power saver reports on, and balanced and performance report off.

Unreported states are unknown, including thermal pressure on Windows and Linux and both reads on the web, HarmonyOS and mini programs.

## Keeping the system awake

`KeepAwake` takes a hold until the returned `release` function runs or its scope is disposed, and releasing twice is harmless. `KeepAwakeOptions.Display` keeps the display on as well; a computer-only hold keeps the computer from idle sleep and lets the display sleep. Windows, Linux and iOS count every surface's holds together and give holds of one kind one power request, inhibitor or setting, given the reason of the hold that made it where the platform takes one; macOS gives each surface's holds of one kind one IOKit assertion. A backend ends a surface's holds as the surface closes, since its tree's last releases never reach the platform. As the app quits, Linux ends every hold and waits up to two seconds for the releases to reach the session bus, since the process exits before its queue would send them, and elsewhere the system ends the rest. `nsgotest.App.Awake` lists the holds the app keeps, each with its ID, `AwakeHolds` every one it took and `AwakeReleases` the IDs it released, without changing the test machine's power state.

| --- | --- | --- |
| macOS | IOKit `IOPMAssertionCreateWithName(PreventUserIdleDisplaySleep)` | IOKit `PreventUserIdleSystemSleep` |
| Windows | A `PowerCreateRequest` power request with the hold's reason, which `powercfg /requests` lists, set to `PowerRequestDisplayRequired` and `PowerRequestSystemRequired` | `PowerRequestSystemRequired`; `PowerRequestExecutionRequired` keeps a packaged app's process from suspending rather than the computer awake |
| Linux | `org.freedesktop.ScreenSaver.Inhibit` on the session bus | For an app outside Flatpak and Snap on GNOME, `org.gnome.SessionManager.Inhibit` with its Suspend flag, since GNOME's portal backend passes on the empty ID the portal knows such an app by, which the session manager refuses while the portal answers that the hold was taken; otherwise the desktop portal's `Inhibit` with its Suspend flag, and without the portal the ScreenSaver inhibitor, which keeps the display on too |

| Mini programs | No-op | No-op |

GNOME's inhibitors refuse an empty app ID and an empty reason, so on Linux a hold names an app built without `nsgo.yaml`'s id, as `go build` and `go run` make it, by its name, else its executable's, and gives that ID as the reason when the app gives none. A playing `Video` keeps the display on only on iOS, where `AVPlayer`'s `preventsDisplaySleepDuringVideoPlayback` is on by default; on macOS that default is off, and the other targets' players ask for nothing, so an app that plays video, or draws its own frames, takes a display hold while it plays.

## Task progress

`SetTaskProgress` puts a task's state and fraction on the app icon, where the platform has a surface, and clears it with `TaskProgressNone`. Values are clamped to 0..1; where one indicator shows several surfaces' progress, as the Dock tile, the launcher entry and the progress Windows shows from surfaces without a button, the latest call wins: each call is numbered (`driver.TaskProgress.Call`) and the platform ignores one older than what it shows, as the app's tree commits before the others whatever the order of the calls. Repeating what the same window, panel or tray view sent last sends no update, unless another surface changed the progress since. It does not require notification access.

## Haptics

`mobile.PlayHaptic`, NSH's `Haptics`, plays a selection, an impact of five weights or a task's outcome: UIKit's feedback generators on iOS, and on Android the view's nearest `HapticFeedbackConstants`, `CONFIRM`, `REJECT` and `SEGMENT_TICK` where its API has them, as the user's touch feedback setting allows. The core sends nothing elsewhere.

`mobile.PlayHapticPattern` sends a sequence of relative events to the platform while the surface is in the foreground and `Env.CanPlayHapticPattern` is true. Core Haptics takes their intensity, sharpness and duration. The Android and web backends turn the sequence into intervals and take the strongest intensity during overlaps. Android supplies amplitudes to `VibrationEffect` where its vibrator supports them and uses on/off timings elsewhere. Android browsers with `navigator.vibrate` take the on/off timings.

The Android runtime and embedding manifest declare `VIBRATE`, a normal permission. An empty pattern cancels playback, and a new one replaces it. The core sends a cancellation when the surface moves to the background or loses support. Native backends stop their own pattern on backgrounding, and the page also stops it when hidden. Each backend keeps the current pattern's owner so closing a surface whose playback was replaced leaves the replacement playing. `nsgotest.App.HapticPatterns` records requests and cancellations.

## The app's lifecycle

`Env.Lifecycle`, NSH's `lifecycle()`, says whether the app is in use: `active`, `inactive` (shown without the focus) or `background` (none of it shows). Each backend reports it with the environment, as it changes. On desktops it is the window's: a scope in a window's content reads that window's, so a minimized or covered window turns background while the others stay as they are, and a scope of an embedded view reads its host window's. The app's own scope, which `nsgo.Run(App)` runs in no window, reads them all together: background only while none of the app's windows shows.

`Env.Minimized`, `desktop.Minimized` for apps, says the window is minimized. It is not `Window.Visible`, which follows only the app's own `Show` and `Hide`: a window the user minimizes, or an app hidden with Cmd+H, stays visible there.

| --- | --- | --- | --- |
| macOS | The app is hidden, or the window is not visible, miniaturized, or its `occlusionState` says none of it shows (covered, the screen locked) | The app is active | The window `isMiniaturized` |
| iOS | `applicationState` is background | It is active: not under a call, the app switcher or Control Center | Never |
| Android | `NsgoView`'s window is not visible | The window has the focus | Never |
| Windows | The window, or an embedded view's subclassed `GA_ROOT` window, is minimized or hidden | The app is active (`WM_ACTIVATEAPP`), or an embedded view's `GA_ROOT` window is active (`WM_ACTIVATE`/`WM_ACTIVATEAPP`) | The window, or an embedded view's `GA_ROOT` window, `IsIconic` / `WM_SIZE` |
| Linux | The surface is unmapped, or its toplevel minimized or suspended | One of the app's windows `is-active` | Its toplevel is `GDK_TOPLEVEL_STATE_MINIMIZED`, which X11 reports and Wayland's xdg-shell has no state for |
| Web | The document is hidden | The document has the focus | Never |

`core.App`, NSH's `appInfo()` and TSX's too, is the app's ID, name, version and build number as `nsgo.yaml` gives them, which the tool builds into `core` with `-X`, and whether it is a development build: any but `nsgo build`'s. It is the binary's, not an engine's, so every view a host embeds reads the host build's.

## Interface orientation

`Scope.RequestOrientation` keeps the newest live request on the app's root surface. Disposal restores the next request. A commit sends `ItemOrientation` with the resulting mask, zero to restore the app's default, and `nsgotest.App.Orientation` records it without rotating headless views.

iOS's controllers use the request after the topmost modal's `IOS.SupportedOrientations`. From iOS 16, the scene requests geometry in that mask and restores its pre-request orientation on release when the normal policy permits it. Android's launcher activity applies the mask through `setRequestedOrientation` and restores its previous setting. Android accepts single directions, both directions of one axis and the full set. For other sets, it locks to an allowed direction. These commands target the standalone application's interface.

The web applies `ItemOrientation` through `screen.orientation.lock`. A `ToggleFullScreen` request calls the browser in the press's commit and applies the current orientation mask after entering full screen. The browser accepts one direction, either axis or all directions. For other sets, NSGo chooses an allowed direction, preferring the one already shown. Releasing the last request or leaving full screen unlocks the screen. Missing APIs and rejected requests are logged with the operation that failed.

## Network state

`Env.Network` shares one connectivity signal across the engine's surfaces. `Scope.OnNetworkChange` follows the signal without an initial event or duplicate values. Test environments can replace it. Targets without a source report online and unmetered.

Apple, Windows, Linux and web providers implement the optional `NetworkWatcher` method interface. The first network read installs the activation hook, so ordinary environment updates leave unused watcher code unreachable to the linker.

Apple reads the default path with Network.framework. Windows reads Network List Manager's connectivity and cost, wakes on interface changes, and rechecks validation and cost while observed. Linux follows GIO's default-route availability and metered properties. The web follows `navigator.onLine` and the browser's online and offline events. These observers start on the app's first read and stop when its graph ends. Android carries its validated route and metered state in the environment through its existing default network callback, which also sends DNS settings. No backend probes the app's servers.

## The device

`Env.DeviceName` is the name the user gave the device, as the system's settings show it, and `Env.DeviceModel` its hardware model, so an app that pairs devices can tell two of a kind apart. Each is empty where the platform does not give it, and `nsgotest.Environment` sets both, also under `nsgo test -target`. The name is read with the rest of the environment, so a rename reaches the app at its next refresh; the model is read once.

| Target | `DeviceName` | `DeviceModel` |
| --- | --- | --- |
| macOS | `SCDynamicStoreCopyComputerName`, Sharing's computer name; not `NSHost`, whose `currentHost` resolves the machine's addresses and can block for seconds | `hw.model`, such as `Mac15,7` |
| iOS | `UIDevice.name`, empty when it is only the generic model, as iOS 16 and later answer apps without the user-assigned device name entitlement | `hw.machine`, such as `iPhone15,2`, or a simulator's `SIMULATOR_MODEL_IDENTIFIER` |
| Android | `Settings.Global.DEVICE_NAME` | `Build.MANUFACTURER` and `Build.MODEL`, such as `Google Pixel 8`, the maker left out when the model starts with it |
| Windows | The physical DNS host name, Settings' device name | The firmware's `SystemProductName` |
| Linux | `/etc/machine-info`'s `PRETTY_HOSTNAME`, else the host name | DMI's `product_name`, else the device tree's `model` |
| watchOS | Empty; attributing the user-assigned name remains open | `hw.machine`, such as `Watch8,3`, or the simulator's `SIMULATOR_MODEL_IDENTIFIER` |
| HarmonyOS | Empty | `deviceInfo.marketName`, else `productModel` |
| Mini programs | Empty | The platform's brand and model from `getDeviceInfo`, else `getSystemInfoSync`, with an existing brand prefix kept once |
| Web | Empty | Empty |

watchOS 9 and later return a generic device name without Apple's user-assigned device name entitlement. It can differ from `WKInterfaceDevice.model`, so comparing those strings cannot attribute the name; NSGo keeps it empty until that attribution is implemented. The identity fixture passed on an unentitled physical iPhone XR (iOS 18.7.11, `iPhone11,8`) and in the watchOS 27 simulator (`Watch8,3`); entitled Apple names and physical HarmonyOS and mini program readings remain unverified ([roadmap](../roadmap.md#from-nsgos-issues)).

On Windows and Linux, a firmware placeholder such as `To Be Filled By O.E.M.` or `System Product Name` leaves the model empty. Mapping Apple's identifiers to marketing names, such as `iPhone15,2` to iPhone 14 Pro, would need a table kept current with every release, so the identifier stays as the platform gives it.

## Displays and locale settings

`Env.Displays` lists the platform's `DisplayInfo` values. `Env.Display` follows the window's current display and the information it reports. `Frame` is the whole display and `VisibleFrame` the area left for windows where the system reports it. Desktop frames use the same top-left, y-down coordinates as `desktop.SetWindowFrame`. `Scale` is device pixels per point and `Main` marks the primary display. On Windows a display's top left is its pixel offset from the primary display divided by the smallest display scale, and points within a display are its own scale's, so displays with different scales never overlap. The list changes when the platform reports a display arrangement change. Linux reads an X11 work area change at the next environment update. An embedded view reads the display of its host window.

`RefreshRate` is in Hz and `MaxRefreshRate` is the highest rate the platform reports. Zero means unavailable. On the web `RefreshRateEstimated` marks the median rate rounded to the nearest Hz from a short `requestAnimationFrame` sample. The browser reports only its current screen, and focus, visibility and screen or window changes restart measurement. `nsgotest.Environment` can set `Displays` and `DisplayID` together to pin both reads.

| Target | Display source | Locale settings source |
| --- | --- | --- |
| macOS | `NSScreen`, `NSWindow.screen` and `CGDisplayModeGetRefreshRate`. AppKit's panel limit supplies the rate when the current mode is variable | `NSLocale` and its calendar and date format preferences |
| Windows | `EnumDisplayMonitors`, `MonitorFromWindow`, per-monitor DPI and `EnumDisplaySettingsW`. Supported modes at the active resolution and color depth give the maximum | `GetLocaleInfoEx` for first weekday, hour cycle and measurement |
| Linux | GDK's monitor model and active refresh rate in millihertz. Surface monitor notifications follow moves. X11 supplies work areas | the session's locale categories and GTK settings |
| iOS and tvOS | `UIScreen` and the window's screen. UIKit reports the panel's maximum frame rate | platform locale settings |
| Android | The native view's `Display`, its active rate and the highest supported mode rate at the same resolution. The activity follows display changes | format locale's Unicode extensions (`fw`, `mu`, `ms`), `Calendar`, `LocaleData` and `DateFormat.is24HourFormat` |
| Web | The browser's `screen` and measured animation frame callbacks | browser locale settings |

`desktop.Monitors` reads `Env.Displays`. `desktop.CursorPoint` sends `ItemCursorPoint` to the desktop backend and receives one `EventCursorPoint` with the location in the same coordinates as the displays. macOS converts AppKit's `NSEvent.mouseLocation` from its primary screen's lower left. Windows converts `GetCursorPos` using the monitor under the pointer. Linux divides X11 root pixels by GDK's X11 scale. Wayland exposes surface-local positions, so the query reports unavailable, including in an app running under Xwayland. Hosts can withhold `core.AccessCursorPoint` from restricted scopes.

`LocaleSettings` reports `FirstDayOfWeek`, `HourCycle`, `MeasurementSystem` and `TemperatureUnit` independently of `Env.Locale`, so a localized app can follow the user's calendar, clock, measurement and temperature choices. A zero field means the platform did not report that choice.

## The application in front

`desktop.FrontmostApp`, NSGo's own as NSH has none ([#570](https://github.com/nsgo-dev/nsgo/issues/570)), is the application in front on the desktop, the app itself included: its ID, its name, its process ID and whether its frontmost window is in full screen, so a desktop pet, an input method or a time tracker follows what the user works in. Each backend reports it with the environment, every window the same value, as it changes, and `CanReadFrontmostApp` beside it says the backend follows it. `Scope.FrontmostApp` and `Scope.CanReadFrontmostApp` read them from signals `Env` keeps unexported, so code whose `Access` refuses `AccessFrontmostApp` reads them zero and false and never tracks them, as they say what else the user runs; asking `CanReadFrontmostApp` logs no refusal. `FrontmostApp` is zero wherever `CanReadFrontmostApp` is false, a test's environment included.

| Target | The app in front | Follows it by | `FullScreen` |
| --- | --- | --- | --- |
| macOS | `NSWorkspace.frontmostApplication`: its bundle identifier, else executable path, and `localizedName` | Workspace activation/Space notifications and KVO of `NSApplication.currentSystemPresentationOptions`, including changes that create no Space | AppKit's `NSApplicationPresentationFullScreen`; geometry cannot distinguish a zoomed window under auto-hidden system UI |
| Windows | A packaged process's AUMID and AppsFolder display name, else its executable path/description. `ApplicationFrameWindow` resolves its packaged child, preferring CoreWindow; a suspended/inaccessible client keeps the frame's AUMID with unknown PID | `SetWinEventHook`: foreground changes and location changes of the foreground frame owner, which can differ from the UWP client PID | The window covers its monitor and is neither `IsZoomed` with a caption or sizing frame, as a maximized one keeps, nor the desktop's own |
| Linux on X11 | The root window's `_NET_ACTIVE_WINDOW`: `_GTK_APPLICATION_ID`, else `WM_CLASS`'s class, and `_NET_WM_PID` | `PropertyNotify` on the root window and on the window in front, through `GdkX11Display`'s `xevent` | `_NET_WM_STATE_FULLSCREEN` |
| Wayland with wlr foreign-toplevel management v2+ | Compositor application ID; desktop-entry display name, else that ID. The protocol exposes no PID | A private libwayland queue on GTK's display, drained every 50 ms; handle `done` events commit complete states | The compositor's fullscreen state, independently of maximized |
| Other Wayland compositors, phones, the web and mini programs | None; `CanReadFrontmostApp` is false | | |

A Windows process that refuses `PROCESS_QUERY_LIMITED_INFORMATION` may have unknown path/name; an unresolved UWP frame never claims its host PID as the app's. The foreground frame is re-read even while the host PID stays the same, and its move hook stays on the frame owner. macOS follows AppKit's declared presentation state instead of assuming any display-sized window is fullscreen; legacy players that never declare that state remain an acceptance gap. Other Wayland integrations, including GNOME Shell extensions and KWin scripting, remain goals; NSGo installs or enables none ([roadmap](../roadmap.md#application-and-windows)).

The isolated Sway native test plays a real video and verifies application IDs/names, focus transfers, fullscreen entry/exit and closing a second window. Sway ignored its maximize request, so this is not maximized-window evidence. `TestFrontmostFollowsSystemPresentationKVO` emits real Foundation KVO to verify the deferred observer/cache path without changing system presentation settings; it is not fullscreen-player acceptance. An isolated Openbox/Xvfb test verifies actual video playback, application identity/PID and maximized/fullscreen/restore transitions. Windows tests check native window-property metadata and the unpackaged fallback. An opt-in packaged fixture resolved a fresh Calculator CoreWindow's real AUMID, localized name and PID; an actual frame-hosted client remains unchecked. The window-state player fixture passes actual Media Foundation playback and maximized/fullscreen/restore checks through the native reader. The separate tracked fixture still requires foreground access: the disconnected native session returned no foreground HWND, so a visible owned window and its direct native identity do not prove public signal delivery.

## Appearance and quitting

`SetAppearance` forces light or dark, and `nsgo.Appearance` starts the app in it. The core keeps the system's appearance beside the forced one and reports the one shown as `Env.Dark`, so platforms may report either. A subtree forces its own with `SetSubtreeAppearance` ([themes](themes.md#scope)).

| Target | Native chrome that follows |
| --- | --- |
| macOS | `NSApp.appearance`: title bar, menus, alerts and hosted controls |
| iOS | The window's `overrideUserInterfaceStyle` |
| Android | System bar icons, alerts, the activity's theme, system headers and web views (forced dark from Android 10) |
| Windows | DWM's dark title bar and uxtheme's menu mode (ordinals 135 and 136); alerts are drawn in the appearance shown |
| Linux | `gtk-interface-color-scheme` from GTK 4.20, `gtk-application-prefer-dark-theme` before |
| Web | The page's `color-scheme` |

`Quit` ends the app. On desktops `nsgo.Run` returns once the engine stopped and storage was written, as NSH's `run_app`: macOS cancels `applicationShouldTerminate:` and stops AppKit's loop, posting an event to wake it. Android finishes its task; iOS apps never quit themselves. `mobile.ExitApp`, NSH's `BackHandler.exitApp`, does what Android's back does when nothing in the app takes it (`ItemBackUnhandled`): the task's root goes to the background, another activity finishes.

Desktop Quit roles and `desktop.RequestQuit` send `EventQuitRequest`. The core sends `ItemQuitResponse` once its handlers pass, cancel or answer a deferred request, and an approval ends the app as `Quit` does. On macOS the Dock also asks through `applicationShouldTerminate:`. AppKit's `NSTerminateLater` waits in a nested modal loop and exits the process when answered yes, so NSGo runs the app's teardown itself. Windows and Linux also ask when closing a window would end the app. A later user request waits for a pending answer. A panic in a handler after deferring cancels the unanswered request.

When macOS sends a quit Apple event for logout, restart or shutdown, the delegate recognizes its `keyAEQuitReason` and suspends the Apple event reply. It stops the run loop even while a user request is pending. The engine reports `Forced()` to the quit handlers and runs `OnQuit` as it closes. After the storage flush, `Run` resumes the Apple event with a successful reply and returns to the caller.

`desktop.Restart`, NSH's `Application.restart()`, quits as `Quit` does with `ItemQuit`'s `On` set, and `nsgo.Run`, once the app has ended, starts the program again with the arguments it started with, its launch flags among them. The two never run side by side: on macOS and Linux a shell waits up to 10 seconds for the old process to exit, then starts the new one, a macOS bundle through `open -n` as the user opens it, and an AppImage through its outer image path so the runtime mounts it again; on Windows the new process waits for the one `NSGO_RESTART_AFTER` names before `Run` starts. A release process started by a restart carries `NSGO_RESTART_GUARD`, so an app that restarts again within 10 seconds of its restart, as one restarting itself at launch does, logs one refusal instead of looping, while a restart the user asks for later still runs. Under `nsgo dev`, which ends with the app it started, it only quits.

When the app ends by itself, and which of its windows a close keeps, is its shutdown mode's and its windows' `OnClosing` ([application and windows](application.md#lifecycle)).

`OnQuit` handlers clean up as the app ends, as NSH's `Application.on("quit")` and GPUI's `on_app_quit`: `Engine.Close` runs them on the engine goroutine, oldest first, with one context that ends `QuitTimeout` (200 ms) after they start, before the graph is disposed, and waits for them no longer than that and 100 ms. They run however the engine closes: `Quit`, the shutdown mode, AppKit's terminate, the window closing on Windows and Linux, the Java runtime ending on Android, iOS's `applicationWillTerminate:` and a host removing an embedded view. The web and watchOS have no such moment, as the system may end either unheard: `Engine.Hide` runs the handlers as a page hides (`pagehide`) or a watchOS app goes to the background, keeps them and the graph in case the app shows again, as a page from the back-forward cache does, and a page hidden for good closes the engine.

## Desktop windows

Package `desktop` is NSH's `nsh/desktop`: native controls, an app-drawn title bar, and the menus below. Its functions call the `Scope` methods of the same names, the core's part.

- `SetTitleBar` hides the system title bar and gives the app's bar its height, in which the platform centers its controls. `TitleBar` then reports the area they keep, and views with `Desktop.WindowDrag` drag the window.
- macOS centers the traffic lights in the bar, 16 points from the left; Windows draws NSGo's compact rounded caption buttons by default, or full-height 46-point Windows 11 buttons when `WindowControls.Style` is `WindowControlsSystem`; Linux reports the bar's height and the app draws its buttons.
- `SetWindowControls` hides those controls for the app's own, or moves the traffic lights, as Electron's `trafficLightPosition` does: the close button's top left from the window's, zero X or Y keeping the default.
- macOS 27's AppKit puts the traffic lights back whenever it lays the title bar out, without a notification, so NSGo's `NSWindow` subclass places them after each `layoutIfNeeded`. Hiding and showing them makes AppKit place them again once the app's position goes, as Electron's `window_buttons_proxy.mm` notes.
- `Maximized` reports a maximized or zoomed window, so an app-drawn maximize button can show restore, and `FullScreen` one in full screen.
- `SetFullScreen` asks for a state instead of toggling and takes an optional `Env.Displays` ID on macOS, Windows and Linux. AppKit enters its native Space after positioning the window on the requested display and restores its original frame on exit. Windows keeps the original placement and style and covers the monitor with a borderless window. GTK asks its compositor through `gtk_window_fullscreen_on_monitor` and tracks `GtkWindow:fullscreened`. The web uses the browser's display and `fullscreenchange` reports its state, including a user exit. Entry needs a user gesture on the web.
- `Minimized` reports a minimized window, so an app can stop work while its content is hidden and resume it when the user restores the window. It is always false on phones and the web.
- The platform decides a window drag on the main thread from the mounted props: the nearest view setting `WindowDrag` decides, and a nearer pressable, input or gesture view keeps the press.
- A double click on a drag view does what the system's title bar does. macOS follows `AppleActionOnDoubleClick`, and on Windows the view is caption to the hit test (`HTCAPTION`), so the system does it. Linux follows GTK's `gtk-titlebar-double-click` (GNOME's `action-double-click-titlebar`) as GTK's `GtkWindowHandle` does, `menu` showing the window manager's menu for the press, and like it moves the window only once a press is dragged past GTK's threshold, as a move started at the press takes the pointer on Wayland and the second press would not count. A transparent window, a panel and a view a host embeds drag on Linux as for one click, as a transparent window does on macOS.
- `nsgo.WindowMaterial` starts the window with a material behind the app's views and `SetWindowMaterial` changes it: an `NSVisualEffectView` on macOS, Mica, Acrylic or Mica Alt on Windows 11 22H2 and later. `ShowsMaterial` reports whether one shows; elsewhere the window stays opaque.
- Windows shows a material only in a window started with one: its content needs DirectComposition and `WS_EX_NOREDIRECTIONBITMAP`, which holds from the window's creation. Such a window changes its backdrop, or turns it off, any time.
- `WindowOptions.Transparent`, `nsgo.WindowTransparent` and `SetWindowTransparent` leave a window without a background or frame, so what is behind it shows wherever the app draws nothing, as a desktop pet does; `NoShadow` (`SetWindowShadow`) drops the system's shadow and `SkipTaskbar` (`SetSkipTaskbar`) the taskbar button. A panel opened `PanelOptions.Transparent` is cleared the same way on each platform, without a shadow, its content drawing its own corners and shadow ([application](application.md)).
- macOS makes a transparent window a borderless `NsgoWindow`, which may become key, with `setOpaque:NO` and a clear background; its shadow, which `setHasShadow:` keeps, AppKit casts from what the window draws and recomputes after each batch (`invalidateShadow`), and Cmd+W and `CloseWindow` ask the app, as `performClose:` only beeps without a close button. Off the taskbar it is out of the Window menu and Cmd+`, the Dock being the app's activation policy.
- Windows makes it a `WS_POPUP` drawn through DirectComposition, as a material's window is, with DWM's non-client rendering off and square corners, so it has no shadow; only a window opened transparent changes later, clearing to white while framed. A window with the system's title bar keeps its frame and its shadow under `NoShadow`: DWM casts that shadow with the frame's non-client rendering, which has no switch of its own, and turning it off would leave the classic frame `DefWindowProc` draws. A window with a hidden title bar, which draws its own chrome, is shadowless under `NoShadow` (`SetWindowShadow(false)`): DWM's non-client rendering is off and `WM_NCCALCSIZE` gives it no non-client area, so nothing classic is drawn, and `WM_NCHITTEST` answers its side and bottom resize edges in the client area as it already does the top one. Off the taskbar it is a `WS_EX_TOOLWINDOW`, which Alt+Tab leaves out too, its button added or deleted with `ITaskbarList` as that changes.
- Linux undecorates a transparent GTK window and takes its theme's `background` class, so GTK's RGBA visual or Wayland surface shows through, with a style of NSGo's clearing what GTK would draw and the surface omitting its usual opaque root fill. `NoShadow` and `SetWindowShadow(false)` clear only the shadow GTK draws around its own (client-side) decorations; a window the window manager decorates keeps the manager's frame and shadow, as NoShadow never swaps that frame for GTK's title bar. Off the taskbar it sets `gdk_x11_surface_set_skip_taskbar_hint` on X11; Wayland has no such hint.
- `Env.CanMakeWindowsTransparent` and `Env.CanSkipTaskbar` (`desktop.CanMakeWindowsTransparent`, `desktop.CanSkipTaskbar`) say in a window's scope whether these take effect, rather than a log line. Transparency does on macOS, on Windows in a window opened transparent where `DCompositionCreateDevice2` succeeds, and on Linux where `gdk_display_is_composited` and `gdk_display_is_rgba` hold, which the backend rereads as the display's `composited` property changes, as an X11 compositing manager starts or stops. Skipping the taskbar does on Windows, on X11 and on macOS, whose per-window part is the Window menu and Cmd+`, `SetDockVisible` being the Dock's. It is false on Wayland. Both are false on phones and the web, and for a surface with no window of its own: an embedded view, the app's own hidden surface, a panel and a tray icon.
- `Env.WindowTransparent` (`desktop.Transparent`) is the state where `CanMakeWindowsTransparent` is the capability: whether the scope's window or panel draws nothing of its own now. The core starts it at what the surface opened with, and each backend reports it from the field its windows and panels share: true for a window opened transparent or made so by `SetWindowTransparent` and for a transparent panel, false once a window is framed again, and false where the platform could not clear the surface: on Windows without DirectComposition and on Linux while the display does not composite, which the backend rereads as the display's `composited` property changes.
- `SetWindowFrame` moves and sizes the window in points from the main screen's top left, keeping the top edge without a move.
- macOS converts the frame to its bottom-left one and animates it; Windows takes the window's pixels; Linux sets GTK's default size and positions the window on X11 through `_NET_MOVERESIZE_WINDOW` with explicit northwest gravity where supported, else `XMoveWindow`, in the whole scale GTK uses for X11. `Env.CanPlaceWindows` is true there for a surface with a window of its own, as on macOS and Windows and for an Android overlay; it stays false for an ordinary Wayland toplevel.
- `Frame` reports the frame `SetWindowFrame` takes, through the environment, so an app reads it as an `Env` signal. Windows keeps the last one through a minimize, which parks the window off-screen. Linux reports `gtk_window_get_default_size`, the size GTK keeps apart from maximizing, and on X11 the actual visual corner read through `XTranslateCoordinates`, accounting for window-manager decorations and GTK's invisible shadows; native configure events refresh it after an app or the user moves the window. A position requested while hidden is applied again once the window maps, without resetting later user placement on every map.
- `nsgo.WindowFrame` and `WindowOptions.Frame` open a window at such a frame rather than moving it after it shows, so an app restores one without a flash. `WindowFrame.OnScreen` keeps a window whose top edge no screen shows from opening out of reach: it centers on the main screen on macOS, and on the nearest monitor on Windows.
- `SetWindowConstraints`, `WindowOptions.Constraints` and `nsgo.WindowConstraints` limit a window's content size, which it moves into, and say whether it resizes, minimizes and maximizes, the app's own `MinimizeWindow`, `ToggleMaximize` and `SetWindowFrame` sizes included. `NoResize` implies `NoMaximize`, but `SetWindowFrame` still sizes the window.
- macOS sets `contentMinSize`, `contentMaxSize` and the style mask, disables the zoom button and declines `windowShouldZoom:toFrame:`; AppKit limits only the user's resizes, so `SetWindowFrame` clamps. `NoMaximize` also sets `FullScreenNone`, the same button going full screen there. `isZoomed` reports a window at its maximum, so it cannot tell a maximized one.
- Windows answers `WM_GETMINMAXINFO`, without limits in full screen, and clears `WS_THICKFRAME`, `WS_MINIMIZEBOX` and `WS_MAXIMIZEBOX`; the caption buttons it draws dim and take no presses.
- Linux sets the content minimum with GTK's size request and fixes `NoResize`, or matching minimums and maximums, with `gtk_window_set_resizable`. X11 adds nonfixed maximums to `WM_NORMAL_HINTS`, preserving GTK's minimum and resize hints and accounting for client decorations and scale. `NoMinimize` and `NoMaximize` filter a native `GtkHeaderBar`'s session layout and disable its window actions; clearing them restores the allowed buttons. Nonfixed maximums on Wayland remain unsupported ([application](application.md#linux), [roadmap](../roadmap.md#application-and-windows)).
- `SetWindowLevel` floats a window (`NSFloatingWindowLevel`, `HWND_TOPMOST`, `_NET_WM_STATE_ABOVE`) or sinks it to the desktop's icons on macOS, on every space, to the bottom of the z-order on Windows, or below other windows with `_NET_WM_STATE_BELOW` on X11. GTK 4 has no keep-above, so on X11 the backend sends EWMH's `_NET_WM_STATE` client message for the window's X window, and again each time its `GdkSurface` maps, as a window manager forgets the state of a withdrawn window and GDK rewrites the property as it maps one. Wayland has no protocol for stacking a toplevel, and an override-redirect panel has no window manager to ask, so `Env.CanSetWindowLevel` is false there, as for an embedded view. On every platform both are false for a surface with no window of its own: an embedded view, the app's own hidden surface an `nsgo.Run(App)` function runs on, and a tray icon's. `OrderFront` restores, raises and activates.
- `SetWindowWorkspaces` and `WindowOptions.Workspaces` show a window on every workspace, after NSH's `Workspaces::All`. macOS gives it `canJoinAllSpaces`, `fullScreenAuxiliary` and `ignoresCycle`, so it follows the user across Spaces, shows over other apps' full screen spaces and stays out of Cmd-`; one collection behavior is computed from the level, the workspaces and `NoMaximize` together, so a later `SetWindowLevel` keeps it on every Space, and an auxiliary window drops `FullScreenNone`. The desktop's level takes `stationary` instead of `fullScreenAuxiliary`, as NSH's does, so a window there stays behind other apps' full screen spaces. Panels start on every space. `Env.CanSetWindowWorkspaces` is true on macOS for a surface with a window of its own, and on X11 where `gdk_x11_screen_supports_net_wm_hint` finds `_NET_WM_DESKTOP` in the window manager's `_NET_SUPPORTED`, the same check GDK makes before it sends the request, read as the surface's environment is; it is false on Windows, Wayland, phones and the web, and for an embedded view, the app's own hidden surface, a tray icon and an unmanaged X11 panel. Linux asks an X11 window manager for `_NET_WM_DESKTOP` `0xFFFFFFFF` through `gdk_x11_surface_move_to_desktop` from the `GtkWindow`'s own `map` signal, which runs after `XMapWindow`, each time the window maps, as GDK clears it there, and asks for the current desktop by number to go back, since `gdk_x11_surface_move_to_current_desktop` does nothing for a window GDK knows is on every desktop; Wayland has no protocol, and Windows no public API, `IVirtualDesktopManager` only moving a window to another desktop, so both leave the window where it is ([roadmap](../roadmap.md#application-and-windows)).
- `SetWindowPointerEvents`, `WindowOptions.PointerEvents` and `PanelOptions.PointerEvents` let the pointer through a window to the windows below it, of any app (`WindowSetPointerEvents`, `SurfaceConfig.PointerEvents`): `WindowPointerNone` everywhere, and `WindowPointerPainted` wherever no view under the pointer is `driver.Painted`, that is draws a background, a border, a gradient, a backdrop or content of its own, hears the pointer or drags the window. The window's own background, its material and the title bar the system draws do not count. Core holds both to `AccessOverlay`, as NSH's `windows` capability's `overlay` holds `pointerEvents: "none"`, sending `WindowPointerAuto` to code without it.
- `Image.HitTestAlpha` lets an image in a painted macOS or Windows window take the pointer by its bitmap alpha. The normal hit test skips the image on a miss, so a view underneath can still take the pointer ([images](images.md#painted-window-hit-tests)).
- macOS sets `ignoresMouseEvents`. A painted window gets no moves while it ignores them, so a timer on the main run loop's common modes hit-tests the views under `mouseLocationOutsideOfEventStream` every 1/60 s once the pointer moved, a batch came or an animation ticks, by the hit test window drags use (`rawHit`), the innermost view and the views it is in; a held button keeps what the window does, so a drag goes on to its end.
- Windows makes the window layered at full opacity, as a layered window draws nothing without one, while it lets the pointer through anywhere, and clears it again with `WindowPointerAuto`, as NSH does; it toggles `WS_EX_TRANSPARENT`, which passes the pointer to the windows of every process where `HTTRANSPARENT` passes it only to the thread's own; a painted window does so from a 16 ms `SetTimer`, `GetCursorPos` and the views' hit test, a button held from `GetAsyncKeyState` keeping it.
- Linux sets the surface's input region, on X11 and Wayland alike: an empty one, or the union of the painted views' bounds within what scroll views and clipping views show, by their pointer events, so a transparent view over a painted one does not take the pointer from it. GTK sets its own region as it allocates the window, for its client-side shadows, so the window sets its own again in the next frame's snapshot; giving the pointer back, it clears the region and queues a resize for GTK to set its own.

## Menus

`SetApplicationMenu` and `PopupMenu` send menus as data, handlers replaced by IDs that come back in `EventMenu`. Role items are the platform's own, except that a non-editing role with an `OnSelect` only reports its ID, on macOS through `nsgoMenuChosen:` rather than the role's action, so Quit or Minimize with one runs the app's handler without quitting or minimizing, and an editing role with an `OnSelect` (Undo, Redo, Cut, Copy, Paste, Paste and Match Style, Delete, Select All) reports its ID when nothing edits: a focused field or web view takes the role first, and the text selection Copy (with something selected) and Select All, so the app's Select All can select its own items, as Finder's does. macOS decides in the item's own action (`nsgoMenuRoleChosen:`) rather than by the responder chain's target alone, since every window answers `undo:` and the surface answers `copy:` and `selectAll:` with no selection; validation uses the same key window, main window or menu owner's window as dispatch, enables the app's fallback when no editor takes the role, and otherwise follows the editor's undo history and selection. The backends say roles, and macOS's default menu, in the language the app shows, which `ItemDirection` carries, from the catalogs of `desktop/locales`: an item without a label of its own, as the bar is rebuilt when the language changes. macOS's full screen item takes its own action, since AppKit's titles it in the language of the bundle. An app says its menus' titles and items itself, setting the menu again from an `Effect` as the language changes. The last surviving surface's menu returns when the owner that set the menu goes; the default menu returns when none remains. macOS's default menu follows AppKit's template: an app menu of About, Check for Updates… while Sparkle runs (its controller is the item's target, made again once Sparkle starts), Hide, Hide Others, Show All and Quit, then Edit and a Window menu registered as AppKit's `windowsMenu`; it has no Services menu, since AppKit moves its one Services menu into each bar an app sets. It takes no key an app may bind: Hide and Hide Others have no key equivalents and the Window menu no Minimize, which AppKit gives ⌘M, since the bar takes a key before the window's `keyDown:` matches the app's bindings. An item's `When` resolves to `MenuEntry.NotInText`, as a key binding's does: Windows and Linux leave such a shortcut to a focused input in their key path, and macOS disables the item while a key press looks for its key equivalent with a field focused in the window the key went to, whichever window set the menu (`validateMenuItem:`), so AppKit hands the key to the field. A field editor has no binding of its own for an editing role's key, such as ⌘Z, ⇧⌘Z, ⌘X, ⌘C, ⌘V, ⌘A and ⌥⇧⌘V, and takes it only from the menu, so an item with one of those keys stays enabled and its action sends the role's (`undo:`, `redo:`, `cut:`, `copy:`, `paste:`, `selectAll:`, `pasteAsPlainText:`) to that window's focused field or web view in its place: an app's own Undo item leaves ⌘Z to undo the field's typing, and runs when chosen with the pointer or with the key elsewhere.

- macOS sends each item role's action down the responder chain, so `MenuPasteAndMatchStyle` (`pasteAsPlainText:`, which NSGo's fields answer as a paste), `MenuDelete`, `MenuStartSpeaking`, `MenuStopSpeaking` and `MenuBringAllToFront` reach the focused field or AppKit. Windows and Linux leave out the roles only macOS has (About, Hide, Hide Others, Show All, Services and Bring All to Front), and run the editing roles in the focused input, and else in the focused web view as the editor command its shortcut runs, which Windows sends through CDP and Linux through WebKit, and else Copy and Select All on the text selection, as its keys do; where they speak (`Env.CanSpeak`), Start Speaking reads the focused field's selection, or its whole text without one and nothing of a password field, through the synthesizer `Speak` uses, in a voice for the app's language, which Windows replaces with its default voice where it has none, as an utterance of the platform's own that stops the app's and reports to no engine, and Stop Speaking stops it; a focused web view's is read by a script, `menuspeech.WebSelection`, which reads the page's focused text control as a field is read, and else the document's selection, following focus into frames of the page's origin, and comes back as the script's value, `ExecuteScript`'s answer on Windows and `webkit_web_view_evaluate_javascript`'s on Linux, not as a message the page posts, so the page's own messages reach the app as before; it is said only if no Speech item was chosen since and the view has neither closed nor started another navigation. Where nothing speaks both are left out. Paste and Match Style pastes in an input as Paste does and in a page as plain text, and has a shortcut on macOS alone, and Delete removes the selection only. A submenu left with none of its items is left out, and so is a separator at either end of a group.
- `MenuServices`, `MenuWindowMenu` and `MenuHelpMenu` mark the item that holds a submenu, even with no items, at any depth. After building or syncing the bar, macOS gives the first of each to AppKit from the bar it shows, which syncing keeps, so Services, the window list and the help search field come whatever the menus are titled; the holder's tag carries the role, and a holder of another role replaces it rather than syncing. AppKit keeps the first Services menu it is given and ignores nil for the Services and Window menus, so a later bar's Services holder takes that menu over with its own items, and only the Help menu is taken back when no holder marks it. Windows and Linux show the Window and Help holders as ordinary submenus and leave them out with no items.
- `MenuItem.Icon` (`MenuIcon`) attaches an icon from encoded image bytes (`Data`), an `ImageSource` (`Source`, local/asset/data URI, bytes or `Pixels`) or a parsed `*SVG` (`SVG`), with `Template` (and monochrome `SVG`s by default) following light/dark appearance and highlight tinting: macOS builds a cached 16×16 pt `NSImage` (1× and 2× representations for SVGs) with `setTemplate:` and attaches it via `setImage:` (explicitly visible from macOS 27) on application, Dock, popup and tray menu items and syncs it in place; Windows creates DPI-scaled 32-bit premultiplied BGRA `HBITMAP`s (`CreateDIBSection`) attached via `SetMenuItemInfoW` (`MIIM_BITMAP`) and frees them when menus rebuild or close; Linux encodes PNG bytes into a `GBytesIcon` via `g_menu_item_set_icon` and makes its generated `GtkImage` visible beside the label using public widget/image APIs, retaining GTK’s native menu rows, actions, check/radio indicators, focus and accessibility. This departs from NSH’s GTK icon attribute alone, which GTK hides beside text; menu trees and their submenus are built before the image walk and rebuilt together. Tray menus carry `icon-data` for `com.canonical.dbusmenu`.
- `MenuItem.Radio` is a checkable item drawn as one of a group of choices, whose `Checked` the app keeps: Linux makes its action string-stated with a string parameter and the item's target the state it has while checked, which GTK draws as a radio, and tray menus give dbusmenu `toggle-type` `radio`; Windows adds `MFT_RADIOCHECK`, a bullet; macOS keeps the check mark AppKit shows for a choice.
- Setting the application menu again updates the shown menu bar in place on every desktop backend: macOS syncs its `NSMenu` items in place, Windows diffs its `HMENU` tree with `SetMenuItemInfoW`/`InsertMenuItemW`/`DeleteMenu` (calling `DrawMenuBar` only when top-level items change) while preserving submenu handles, and Linux mutates its existing `GMenu` models and `GSimpleAction` states/enabled flags in place without recreating the `GtkPopoverMenuBar` or `GSimpleActionGroup`.
- `SetMenuBar(MenuBarAutoHide)` hides the bar Windows and Linux draw until Alt is pressed and released alone, which is kept from Windows' menu mode. Alt with a mnemonic or F10 shows it for the menu they open; a press in the window or a closed menu hides it. A window with `TitleBarHidden` has no bar, in either mode. Windows and Linux open the application menu as a popup from its top leading corner instead, its first item selected as in a bar's menu, on Alt alone and F10; Alt with a top-level item's first letter or digit opens that item's menu or chooses it. Mnemonics follow the keyboard layout's character (`WM_SYSCHAR` on Windows and GDK's Unicode keyval on Linux), including non-Latin labels; other Alt chords, such as Alt+F4 and Alt+Space, stay with the system, and Shift+F10 stays the context menu's. A key the focused view or a binding consumes while Alt is held still ends the Alt-alone gesture. Linux uses a nested `GtkPopoverMenu` and leaves its navigation and dismissal keys to GTK, restoring the previous still-attached widget's focus on choosing or closing it, before dispatching an editing role.
- `PopupMenu` shows one context menu at a time at a point in the root's points, and answers `EventMenuClosed`. Its items stay choosable until another menu replaces it, since GTK may activate an item after the popover closed.
- macOS tracks it with `popUpMenuPositioningItem:` from the main queue, which keeps applying batches; Windows with `TrackPopupMenuEx` from a message of its own, ended by `EndMenu`; Linux with a `GtkPopoverMenu` on the surface.

## Keys and the status bar

Shortcuts are scoped to their owner: the platform matches key presses against the table synchronously and reports only matches.

- An input method composing text keeps its keys on macOS and the web, so arrows still choose its candidates.
- `Scope.SelectInputSource` selects an enabled keyboard input source by the platform's ID, and `RestoreInputSource` goes back unless the user chose another since; `core.Input`'s `InputSource`, which `base.Command` passes to its search field, selects one each time the field takes the focus and restores it as the field loses it, unless `KeepInputSource`; phones and the web ignore both, and `nsgotest` records them in `App.InputSource`.
- macOS selects through Text Input Sources (`com.apple.keylayout.ABC`), which need no field's input context, so restoring works after the field is gone. Windows activates a keyboard layout for the process by its KLID (`00000409`), unloading again one the user has not enabled. Linux asks the input method framework over D-Bus, off the main thread: Fcitx 5's input methods of the current group (`keyboard-us`), else IBus's engines (`xkb:us::eng`) on the bus its daemon names.
- Each `KeyBinding` says whether it fires while a text input or web view has the focus, which focused controls it yields its key to (`Yields`), and on a held key's auto-repeats; `driver.FindKey` decides for every Go backend and `nsgotest`, Android's Java the same way, from what the focused view uses (`driver.FocusKeyUse`, by its kind, role and presses).
- The platform's match decides which binding runs: every in-app binding has an `ID` the core never gives another, `FindKey` returns the one that fires and `EventKey` reports it, and the core runs that binding (`Tree.pressKey`), not the newest of its key, so a newer `KeyAuto` or `KeyNotEditing` binding of the key cannot run in place of a `KeyAlways` one the platform matched in a focused field. A press matched to a binding since removed, or one that no longer takes part, runs nothing, and a held key repeats as the matched binding's `Repeat` says.
- By default (`KeyAuto`) a binding leaves the focused view the keys it uses: an input those of `EditsText`, a pressable view unmodified Return and Space, a slider or spin button the arrows, Page Up, Page Down, Home and End, and a tab bar, radio group, list, menu or tree and their items the same keys; it fires once while held. A focused view's `OnKeyDown` hears the key before the keymap and may consume it, and its `OnKeyUp` hears it come up; `KeysDown` and `KeyHeld` read the keys held, for a frame loop ([keyboard focus](interaction.md#keyboard-focus)). `OnKeyWith` asks for `KeyAlways`, which fires wherever the focus is, `KeyNotEditing`, which leaves an input every key but takes its key from any other focused view, as a control's own bindings while it has the focus do (a select's Return while its trigger keeps the focus), and `Repeat`.
- Bindings and `OnBackPress` handlers take part only while the user can see what their owner shows: the views of the nearest owner at or above it that has any, as a binding's owner often has none (a `Show` that binds while a control has the focus). None of them shows in a `Holder`'s content no place shows, under a `DisplayNone` view (a stack's screen below the top, a waiting `Suspense`'s content) or in a dismissed modal. While a modal shows, the bindings of an owner with views outside the topmost modal rest too, as the page under a dialog does, so Escape reaches the dialog's `OnRequestClose`; what shows only the modal, its content, a `Holder` placed in it and a Topmost overlay keep theirs, and `KeyOptions.OverModals` keeps an app-wide shortcut's. They come back as the views show again, without binding them again. The core decides it (`keyPlaces`) for the keymap it sends, which every platform and `nsgotest` match by, and checks it again as a press arrives; placing or unplacing a holder, a modal mounted, dismissed or deleted and a view's `Display` changing send the keymap again.
- Desktops match the keymap before the application menu, so a binding takes its key from a menu item with the same shortcut. `KeyOptions.YieldsToMenu` leaves it to the menu instead: the core keeps such a binding out of the keymap, and runs it for no press, while an enabled item of the application menu the window shows takes its key where the focus is on macOS, Windows and Linux, the platforms that show the menu: the window's own on Windows and Linux, and on macOS, whose one menu bar shows the menu a surface set last, that menu (`runtime.menuBar`), the app's own surface's while its windows set none, a role's own shortcut included and "mod" read as the platform's Command or Control; while an input or web view has the focus, an item marked `NotInText` takes nothing and keeps its shortcut from the items after it on every desktop, as macOS disables it during the key press and Windows and Linux keep the first item of each shortcut, and Linux offers the menu no key pressed without Control, Alt or a logo key (`driver.MenuShortcut`). Menu and focus changes send the keymap again. `nsgo dev`'s reload key binds so, leaving Command or Control+R to an app's own Run or Reload item.
- A binding is its surface's: the platform matches a press against the keymap of the window, panel or tray view the focus is in. `KeyOptions.AllSurfaces` binds a key in every surface of the app instead, for an app-wide shortcut such as `nsgo dev`'s reload key: the core adds a binding of it to the tree it is bound in as `OnKey` does, and to each other surface's tree, those opened later included (`newTree`), before that tree's own bindings, so a window's own binding of the key wins there whenever it was made, and resting while a modal shows in that tree unless `OverModals` keeps it (`keyBinding.home`). As its owner shows no views there, such a copy follows whether the owner shows in the surface it was bound in, a modal covering it there aside: it rests in every surface while the owner is hidden there, under a `DisplayNone` view, in a `Holder`'s content no place shows or in a dismissed modal, so a component's app-wide shortcut does not run while the user cannot see it, and a binding of the app's root, which shows no views, fires everywhere. As the owner comes to show there or stops showing, the other surfaces send their keymaps again (`Tree.followHome`), one the platform committed first in the next pass. It drops them all as the owner goes.
- A focused page has the keys in the web view's own windows. On Windows the bindings and the menu's shortcuts still take theirs first, through WebView2's `AcceleratorKeyPressed`, which comes before the page for the keys WebView2 counts as accelerators: those pressed with Control or Alt and those that type no character, such as the arrows and the function keys. A key one of them takes reaches neither the page nor WebView2's own accelerators (Control+R's reload); the rest go to the page as before, and plain letters never reach the keymap there. Checked on Windows 11 by the system's own key events into a focused page (2026-11-18).
- `Scope.Confine` holds the bindings and `OnBackPress` handlers made under an owner to the focus: they fire, and the table holds them, only while the keyboard focus is on a view the owner owns, and a press they leave goes on to the others. TSX confines each sandbox.
- GTK flags no repeats, so Linux counts a key pressed again before its release; UIKit reports a held key once, so iOS repeats a binding on a timer.
- iOS and Android match a hardware keyboard too. `KeyLabel` names a binding as the platform shows it (⇧⌘L, Ctrl+Shift+L), `Environment.AppleKeyboard` telling the web on Apple platforms.
- NSGo extends NSH's iOS keymap with localized `KeyOptions.Title` and `Group` functions. The current winning titled bindings become `UIKeyCommand`s in the surface responder chain, and the application delegate builds their named groups as `UIMenu`s on iPadOS 26 and later. The main menu rebuilds when the active commands or their labels change. UIKit actions check the binding ID and the current keymap before sending `EventKey`. Hardware presses that UIKit leaves to the responder chain follow the ordinary keymap.
- iOS offers a software Return to the same keymap before `UITextField` submits or blurs, or `UITextView` inserts a newline or submits. Android does the same for an input method's editor action or committed Return. `KeyAlways` takes it while an input has focus; automatic and `KeyNotEditing` bindings leave it to `SubmitBehavior`. Each software action matches once, starts no hardware repeat timer and leaves input modality alone. On iOS, marked text keeps Return for composition. iOS matches a physical Return at the editor before UIKit handles it, preserving its modifiers and preventing the delegate from matching an unhandled physical press again as software input. This extends NSH's hardware-only iOS keymap (#414, #1351).
- An alert's `Sheet` presents its actions as an action sheet, and `Cancelable` lets Escape, back and a press outside close it with -1 ([components](components.md#popups)). On macOS, alerts and open/save panels attach as sheets only while their owner is visible, not minimized, and intersects a display; otherwise they activate the app and show independently. Standalone alerts serialize on the main run loop, whose block permits the main dispatch queue to apply batches and answer or cancel them during `runModal`; a dispatch-queue block would hold that serial queue until the alert closed. Closing a surface cancels its native dialogs, including queued alerts.
- System-bar settings layer as in NSH's `status_bar.rs`. `SetStatusBar` patches the window default, with each shown screen or modal over it. The latest wins field by field. A TSX app's default is `nsgo.yaml`'s `status_bar` (`foreground`, `hidden`, `immersive`). NSGo extends the same layer with `Immersive`, which leaves `Hidden` intact for when immersion ends. Android hides the system bars with `WindowInsetsController`, using transient reveal by swipe, or immersive-sticky flags on API 28 and 29. iOS hides the status bar and asks UIKit to auto-hide the home indicator on the root and presented controllers. HarmonyOS hides the status and navigation bars with `setWindowSystemBarEnable` and the navigation indicator with `setSpecificSystemBarEnabled`, in a window laid out full screen from launch, and reports the display cutout on every side as an inset. Outside immersive mode the bars' avoid areas, including their side areas in landscape, are insets too; while it is on, bars an edge swipe reveals lie over the content, so the safe area keeps only the cutout and does not move with each reveal. A failed bar request is made again only for the next batch that carries the status bar. Each backend continues to report its native safe-area insets.

## Where NSGo departs from NSH

| NSH | NSGo | Why |
| --- | --- | --- |
| `setFrame`'s `x` and `y` are the bottom left on macOS, with `anchorTop` | The top left from the main screen everywhere | One coordinate system; the top edge stays without an option |
| A bar height picks an `NSToolbar` style, and AppKit places the traffic lights | NSGo places them in the app's bar, where `SetWindowControls` says | Any bar height and position, as Electron allows |
| No window material | `nsgo.WindowMaterial` and `SetWindowMaterial`, after Electron's `vibrancy` | Desktop apps show the system's materials behind sidebars |
| `pointerEvents` is `auto` or `none` | `WindowPointerPainted` too | A desktop pet takes presses on itself and lets the ones around it through, which a window-wide switch cannot do, as the window that lets the pointer through never hears it come back |
| No window limits; a size only in `nsh.json` | `WindowConstraints`, after Electron's `minWidth` and `minimizable`, in content points | Settings and palette windows keep their size and buttons out of the user's hands |
| `openUrl` throws for a refused URL | `OpenURL` answers false; `CheckURL` says why | A callback has no exception to throw |
| No images written on Android | `FileProvider` serves them | The clipboard holds images only as content URIs |
| Picked images become `File`s whose bytes stay native | `PickedFile` holds the bytes | Go apps hold bytes directly |
| No camera | `TakePhoto` through the system's camera UI | Apps take a photo without a camera view of their own |
| No secure store; apps keep tokens in `Storage` | `Secrets` through the platform's keychain, credentials or keystore | `storage.json` is a plain file any program of the user's reads |

## Browser document metadata

`web.Head` and TSX's `nsgo/web` `Head` render no node. The core binds their title and description to the current owner and merges visible owners in mount order, field by field; hiding or removing a page restores the earlier values, and removing all heads restores the document's originals. Static empty fields inherit, while an accessor returning empty clears a field. `ItemPageHead` carries the result to a surface that reports `CanSetPageHead`; a web app keeps this capability when imitating another OS, while embedded, native and confined owners cannot change their host's metadata. The browser writes strings as text and attributes, preserves an original description element and keeps `SetTitle` as the underlying title while a head overrides it. This follows NSH's `nsh/web` metadata ownership and adds visibility gating for retained hidden pages. [Publishing](../public/en/web.md) covers document semantics and the existing CDN loader, verified from a built app on two HTTP origins.
