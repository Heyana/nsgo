# Embedding

NSGo apps run inside apps of their own: Go desktop programs make views with `nsgo.NewView`, and iOS, tvOS and Android apps link the framework and library `nsgo build -embed` makes. NSH's design is in `nsh/docs/dev/embedding.md`. Read this before changing views, the host channel, `-embed` packages or the iOS, tvOS and Android faces.

An app linking `base/terminal` also receives a runtime-only `GhosttyVT.xcframework` beside its app XCFramework, with the same device, simulator and (on iOS) Catalyst architectures. Hosts embed and sign the companion for static and dynamic apps; the terminal discovers its framework in flat iOS and tvOS bundles and versioned Catalyst host bundles. An arm64 AAR includes `jni/arm64-v8a/libghostty-vt.so` beside `libnsgo.so` once #1452 supplies its Android prebuild; its loader and device acceptance belong to that issue.

## Views

A view is one surface and one engine; `nsgo.Run` runs one engine with its loop, whose windows are surfaces of it ([application and windows](application.md)). A host makes as many as it likes, in one window or several, so backends keep a surface's state on the surface. What is the process's by nature stays process-wide: the standalone app's runner, window and controller, registries keyed by native object (views, widgets, menu targets), observers that report to every live surface, fonts, the image cache and file storage per data directory.

| Target | `Handle` / class | The engine starts | It stops |
| --- | --- | --- | --- |
| macOS | An `NSView` | In `viewDidMoveToWindow` | `View.Close` |
| Linux | A `GtkWidget`, its floating reference sunk | At GTK's first allocation | `View.Close` |
| Windows | A child window of `nsgo.Parent` | At its first `WM_SIZE` | `View.Close`, or the parent's destruction |
| iOS / tvOS | `NSGoView`, a `UIView` | In `didMoveToWindow` | As it is deallocated, or `stop` |
| Android | `NsgoView`, a `FrameLayout`, starting a process of the app | At its first size | `stop`, or the process's end |

The engine waits for its place so that the host's settings made before are in the app's first frame: `engine.HostSettings` keeps them until it starts. Once the engine stops, the backend destroys the native components still showing, since a stopped app deletes nothing: Android's runtime calls `NsgoComponent.destroy` as the process ends, and the Go process closes its own components when the pipe closes. A repeated `View.Close` does nothing on every desktop backend. On macOS the `NSView` is the host's until `View.Close` releases it: an engine that ends on a fault only stops the surface and takes the view out of its superview, and `Handle` returns 0 once the view is released. On Linux `View.Close` also takes the surface out of the process-wide registries and observers and releases its tree, text contexts and native references, leaving the widget in its parent for the host to remove.

Linux checks GDK's default display after `gtk_init_check` in both standalone startup and `NewView`: GTK's initialization flag may stay true after opening its display failed. Repeated attempts with no display return their usual no-display error. An embedding host may later supply a valid GDK display and create a view; NSGo does not cache the earlier failure. Native subprocess tests cover repeated and mixed startup paths and a host-supplied X11 display.

The host owns the window around a view:

- Title, window commands, the menu bar and quitting are ignored. Dialogs and pickers belong to the top-level window.
- A forced appearance shows in the view: an `NSView`'s appearance, `overrideUserInterfaceStyle`, Windows' drawn fields, and on Linux, where GTK's settings are the process's, a CSS provider scoped to the view's widget name that draws its fields, scroll bars and menus in it.
- A view takes the keyboard while the focus is in it, which a press gives it, and keymaps fire only then. On Windows the host's loop translates keys before NSGo sees them, so a shortcut drops the character that follows. Embedded views receive `OnKeyDown` and keymap bindings for both ordinary and system key messages, including F10 and Alt chords, while an unhandled Alt+F4 or Alt+Space remains the host window's command.
- On Windows an embedded view subclasses its ancestor root window (`GA_ROOT`) through `comctl32.dll` (`SetWindowSubclass`, `RemoveWindowSubclass` and `DefSubclassProc`), ref-counted per root HWND so sibling views share one subclass, to follow the root window's minimize, restore, show/hide and activation in `Env.Lifecycle` and `Env.Minimized`; it tracks reparenting on `WM_WINDOWPOSCHANGED` and cleans up the subclass on both the view's `WM_DESTROY` and the root window's `WM_NCDESTROY`.
- macOS fields get NSGo's field editor from their cell (`fieldEditorForView:`) rather than from the window's delegate, which is the host's.
- A macOS embedded view passes mouse wheel, trackpad gesture and momentum `scrollWheel:` events up its `nextResponder` chain whenever no inner scroll view or `OnWheel` handler can scroll that way, deferring rubber-banding to an enclosing scrollable host (`NSScrollView` or custom responder), locking each gesture and its momentum to whichever side started scrolling, and replaying a held zero-delta `phaseBegan` event ahead of the first passed delta so an enclosing `NSScrollView` enters its tracking loop in order.

On the web each app is a Go program of its own, and a page shows several. `nsgo build -target web` writes `nsgo.json` beside the app, naming its WebAssembly, `wasm_exec.js`, resources, host module, the scripts its realm runs and `nsgo.js`, the loader (`cmd/nsgo/web/nsgo.js`), relative to itself. The loader's `mount(element, url, options)` runs the app in the element, or the whole page for null, with `NSGO_MOUNT` (a CSS selector of the element), `NSGO_BASE`, `NSGO_RESOURCES`, `NSGO_HOST` and `NSGO_REALM` (the page's global of the frame its realm runs in) in its environment; the app's own page mounts it so too. An app in an element of a page, or in a frame, leaves the browser's history and title to the page. A same-origin frame whose iframe element has `data-nsgo-history` follows the page's history as if it were the page, so the browser's back goes back in the app, as the website's gallery previews do; a cross-origin frame cannot opt in.

## The host channel

`core.Host` is the view's one object for the host's side, in Go for desktop hosts and behind the iOS and Android faces. The app side is `Scope.HasHost`, `HostParams`, `OnHostEvent`, `CallHost` and `PostHost`, which TSX's `host` reaches.

- Parameters are read as the app starts and fixed for its life; later requests are events.
- `Send` never waits. While no app runs the channel keeps events for the next one; a stopping app leaves what it had not taken there.
- An app keeps the events of a name nobody hears until its first listener, which hears them once the turn that added it ends. Each keeps `HostInbox` (256), dropping the oldest.
- A call runs the handler of its name on the app's goroutine at once, which answers once, from any goroutine; posts reach it with nothing to answer.
- A call fails without a handler, after `HostCallTimeout` (30 seconds; `CallHostTimeout` with 0 waits for good), when the handler panics, or past 1024 waiting.
- `HandleOpenURL` sees the URLs `Scope.OpenURL` opens, once they pass `CheckURL`, before the platform: the host answers once, and false hands the URL to the platform.
- Values cross as JSON, encoded and decoded again even in Go, so a Go host sees what Swift and Java see: maps, slices, strings, `float64`, booleans and nil.

`HandleDefault` answers every name without a handler of its own, for a host that looks names up itself, as a page does. `Scope.ProvideHost` gives a subtree a channel of its own in place of the app's, none for nil, which a Go app answers itself: `tsx.View` gives a package so its `Sandbox.Host`. `nsgotest.Host` runs an app with a channel, so a test plays the host.

### On the web

The page is the host: `mount`'s `params` are the parameters, and its `host` object answers. `call(name, args)` returns the result or a promise of it, a throw or rejection failing the call with its message; posts go to `post(name, args)`, else to `call` with the answer dropped; `openURL(url)`, when present, returns or resolves with whether it took the URL. `player.hostEvent(name, payload)` sends an event, throwing at once for a payload that is not JSON.

Without a `host` option the loader imports `nsgo.json`'s host module, which `nsgo.yaml`'s `web.host` names inside the app's directory and the build copies, named by its content in a release. When the module exports `createHost(player)`, the loader waits for its result and requires a `call` function on it. A module can supply the loading callback alone. The module imports other code by absolute URL, since it is copied alone. `nsgo dev` serves it and builds again when it changes.

The loader counts decoded chunks in the response stream it passes to WebAssembly. `nsgo.json` carries the raw module's byte count, including for compressed responses whose `Content-Length` counts encoded bytes. An unencoded response can supply the length when the config omits it. A native `progress` element shows while the app starts. An embedding page's `onProgress` option or the host module's export can replace it, and the loader sends `null` to that callback when startup ends. Providing a compiled `module` skips downloading and reporting.

The loader keeps a bridge per app in the global `NSGO_HOST` names (`internal/platform/web/host.go`): the parameters, `call` and `openURL` with an ID that Go answers through `reply` and `opened`, and the events sent before the app ran, which Go takes as it starts, so its first listeners hear them. Values cross as JSON text.

## Settings

`engine.HostEnvironment` (a locale, a text size, light or dark) stands in for the platform's values: the engine applies it over each environment the platform reports, before a test's pin. The layout direction stays the system's, and an appearance the app forces still wins. Android writes the three into the environment its runtime reports instead.

A page runs as another OS with `--nsgo-os` (`?nsgo-os=ios`), as the website's gallery previews each platform in a frame: `web.Options.OS` has the web's environment report that OS with `driver.Environment.Simulated` set, its idiom a phone for iOS and Android and a desktop otherwise, and `core.Env.Simulated` reads it. What only chooses a look follows the OS. A check for a native part, which the web has not, asks for the host instead: in the core `Env.host` and `hostUntracked`, the web's while simulated, for the system header, `TabBar`, `SystemSwitch`, the application menu's keys, popup menus, haptics, overlays, opening files and the Android installer; outside it `Simulated` itself, for `mobile.IsAvailable`, `desktop.IsAvailable`, `ui`'s system header and the chat composer's glass rim. A new check of that kind does the same. Keys are the visitor's keyboard's, so `AppleKeys` follows the browser's `AppleKeyboard` alone. Other platforms ignore the flag and log so.

The host's theme overrides are `core.Tokens`: CSS colors by role name, `Values` in both appearances and `Dark` over them, which go over every theme's palette ([themes](themes.md#hosts)). `OnError` hears each failure `RootOptions.Report` does, and `DataDir` moves the app's data, storage and logs. An internal panic on the engine goroutine also reaches `OnError` as `core.PanicError`, with its original value and stack. That engine stops and destroys its attached surfaces; other engines keep running. Pending waits finish, later posts are dropped and a later attachment is destroyed immediately. The host creates a new view to restart the app. Fault cleanup runs without scheduling more computations; a cleanup or error listener that panics is logged without stopping the remaining surfaces from being destroyed. A test engine, started with `engine.Options.CheckCommits`, re-panics after this cleanup.

## iOS and tvOS

`nsgo build -embed -target ios` builds a static library per platform with the `nsgoembed` tag and `-buildmode=c-archive` (devices; the simulator and Mac Catalyst, each arm64 and x86_64 joined with `lipo`), and makes `<module>.xcframework` of them, the module named after the app. `nsgo build -embed -target tvos` (or `tvos_simulator`) does the same for Apple TV devices (`appletvos`, arm64) and the tvOS simulator (`appletvsimulator`, arm64 and x86_64 joined with `lipo`), with a tvOS 17.0 minimum. `-dynamic` links each into a dynamic framework instead, with `CFBundleSupportedPlatforms` (`iPhoneOS`/`iPhoneSimulator`/`MacOSX` or `AppleTVOS`/`AppleTVSimulator`) and `MinimumOSVersion`, exporting only `NSGoStart`, since iOS and tvOS have no Go `c-shared`. A static library starts Go's runtime on a thread of its own, and only a function cgo exports waits for it, so the tool overlays one file on the app's main package: `NSGoStart`, the one C function, which runs the app's `main` on a goroutine until its `Run`, then loads UIKit's classes and registers NSGo's. Packages keep no cgo files; the overlay is generated.

`NSGo.h` declares `NSGoView` and `NSGoComponentContext` with `objc_runtime_visible`: Go registers them at run time, so they have no symbols, and Swift looks them up by name. The status-bar, home-indicator and screen-edge gesture properties are guarded with `#if !TARGET_OS_TV` so the header compiles cleanly against both iOS and tvOS SDKs. The header only declares; its module map autolinks UIKit, Security and libresolv, which Go's runtime needs. The app's resources go beside the framework as `<name>Resources`, which the host copies into its bundle.

- `NSGoView` is registered on `UIView` with the surface's methods, not as a subclass of NSGo's surface class: `apple.Super` finds the superclass from the nearest of NSGo's classes, so one may not inherit another's. On tvOS it also implements `preferredFocusEnvironments` so modal and capture-overlay focus updates route within the embedded view.
- Foundation's JSON objects cross through `NSJSONSerialization`; the host's blocks are called through their function pointer (`apple.CallBlock`), since purego invokes only blocks it made, and copied while kept.
- The display link holds its view, so a view leaving its window lets the link go. It asks for the screen's top rate, which an iPhone grants only when the host's `Info.plist` sets `CADisableMinimumFrameDurationOnPhone`.
- purego returns no floats from methods, so the text size is a setter, `setFontScale:`.
- Catalyst is GOOS=darwin built with the `ios` tag, as gomobile builds it, so the iOS backend serves it. AppKit's threads drop the signal stack Go's preemption signal needs, so its slices link with `asyncpreemptoff=1`.

## Android

`nsgo build -embed -target android_arm64` (or `android_x64`) writes `<name>.aar`: the Java runtime as `classes.jar`, which `runtime/build.sh` builds beside `classes.dex`, the app's executable as `jni/<abi>/libnsgo.so`, its resources as assets and a library manifest asking for extracted native libraries and naming the clipboard's provider after the host's `applicationId`.

Each `NsgoView` runs a process of the app, its own or that of the `NsgoEngine` the host gives it, started as the view first gets a size, so views are apart by nature. The parameters go in `NSGO_HOST_PARAMS`, the data directory in `NSGO_DATA_DIR` and the cache in `NSGO_CACHE_DIR`, which Go also makes `TMPDIR`, as Android gives an app's process none, and the device's time zone in `TZ`, which Go loads into `time.Local`, as Go on Android reads no zone of its own; the engine sends the zone again as `msgTimeZone` whenever `ACTION_TIMEZONE_CHANGED` arrives, so times read after a change are in the new zone without a restart. Tokens, events, the host's handled names, replies and the URL handler's answers cross as `msgHost`; calls, posts, URLs and failures come back as `msgHostCall`, queued in Java until the process starts. A component name Go does not know goes to Java as `host:<name>`, which the view's registered `NsgoComponent.Factory` makes; its events carry one JSON value. A host package holds one app, since the runtime starts `libnsgo.so`. The host's activity passes its `onActivityResult` to each view's `activityResult`, which the photo and file pickers, the camera and the save dialog answer through, and its `onRequestPermissionsResult` to `permissionResult`, which `Scope.RequestPermission` (`Permissions.java`), a photo where the host's manifest asks for `CAMERA`, and a recording for `RECORD_AUDIO` and, from Android 13, `POST_NOTIFICATIONS` wait on. A host whose app records declares `dev.oneo.nsgo.RecordingService` with `android:foregroundServiceType="microphone"` and the `RECORD_AUDIO`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE` and `POST_NOTIFICATIONS` permissions in its own manifest, as `android.recording` does for an APK; recordings go under `recordings` in the directory `setStorageDirectory` gives, the app's files directory by default, and the runtime deletes none ([Android recording](android-recording.md)).

A host keeps an `NsgoEngine` in its `Application` or a foreground service so that the app runs on without an Activity; `attachToEngine` shows it in a view, which starts the engine's process with the view's flags, parameters and storage, and `destroy` ends it. Until the surface protocol in [Android engine and view lifetime](android-lifecycle.md) lands, an engine serves the one view that first attached to it and refuses others. Detach releases its native children and rejects queued view deltas while text replies and process commands continue. Reattaching the same view rebuilds it from its live Go graph, preserving signals, input, focus and scroll state; native web pages and players restart from their app configuration. The engine still holds the first view, and so its Activity, until the process ends; a new Activity's view cannot replace it yet. An engine starts once: after `destroy` or a crash, `isAlive` is false, `attachToEngine` refuses it and the host makes a new engine and view. A host-owned view detaches itself as it leaves its window, unless the host enabled `setBackgroundVideoPlaybackEnabled`, which keeps the tree mounted so `core.Video` plays on ([Android engine and view lifetime](android-lifecycle.md)).

## Departures from NSH

| NSH | NSGo | Why |
| --- | --- | --- |
| A runtime library loads apps' bundles (`AppView.load`) | The framework, library or Go program is the app; a view runs the one app built with it | Go apps are native code, compiled with the engine |
| A Swift module and a C ABI | A header declaring classes Go registers, and one cgo export | NSGo writes no C or Swift; purego reaches the runtime |
| A dropped `HostReply` rejects the call | An unanswered call fails at its timeout | Go has no destructors |
| One engine thread per Android view, over JNI | A process per view, over pipes | Android runs NSGo apps as processes |
| Native modules, `EngineContext`, limits, cache options, dev server sessions | Not ported | Go hosts call the app's Go directly and give each view its values |
| A web page's host has only `call`; `nsh test` runs the host module | The page's host also takes posts and URLs; tests play the host with `nsgotest.Host` | NSGo's channel has posts and the URL handler, and Go tests run without a JS engine |

Capabilities stay an [open question](../../ARCHITECTURE.md#open-questions): the host's handlers are its own code, which any app it embeds may call.
